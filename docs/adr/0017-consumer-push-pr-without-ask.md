# ADR-0017: Споживачі kit — push, PR і злиття без запиту лише через `pr-gate`

Status: accepted 2026-11-23
Decided by: owner
Spec: docs/superpowers/specs/2026-11-23-onboarding-target-state-design.md §5.3

## Context

`templates/settings.json`, який kit роздає споживачам, тримає `git push` і `gh pr create` у `ask`, а
`templates/CLAUDE.md` каже «`git push`, `gh pr create` — лише за явним проханням». У репозиторіях
`github.com/VSydorenko/*` діє інше правило власника (2026-11-18): сесія сама пушить гілку задачі, створює PR
і зливає його після перевірки й рев'ю; питають лише про force push, переписування історії, реліз і прямий
коміт у `main` без PR. Клієнтські репозиторії (напр. `simplySOFTua/*`) під те правило не підпадали. Issue #43.

Аудит спеки (два раунди лінзи security) показав: правила дозволів Claude Code зіставляються за префіксом, тож
`git push *` в `allow` пропускає й `git push --no-verify origin +HEAD:x`, а хук git `pre-push`, що мав би це
тримати, лежить у відстежуваній `.githooks/` і обходиться `--no-verify` чи `git -c core.hooksPath=…`.

## Decision

Без запиту в шаблоні споживача — лише команди процесу `pr-gate open`, `pr-gate ready`, `pr-gate land` (точні
підкоманди, не `pr-gate:*`). Голі `git push`, `gh pr create`, `gh pr merge` лишаються з запитом; `gh release` —
теж.

## Why

`pr-gate` тримає межу в коді, а не в рядку дозволу: пушить лише поточну гілку в однойменну звичайним push,
ніколи головну гілку, base чи `storage/*`; зливає лише PR з цього репозиторію, не в `storage/*` і не зі
`storage/*`, без конфлікту, на голові, яку прочитав перед злиттям; не видаляє дзеркал `storage/*`; команди
`pr.afterMerge` бере лише з профілю на головній гілці origin. Ці запобіжники додано разом із цим рішенням (спека §5.3). Агент процесу й так іде через `pr-gate`, тож робота не стоїть на
підтвердженнях, а питання лишається лише для ручного push поза процесом.

## Rejected

- `git push *`, `gh pr create *`, `gh pr merge *` в `allow` з примусовими формами в `ask`, `deny` на `--no-verify`
  і `git -c`, хук `pre-push`, прапорець згоди при злитті — межа крихка (наступна форма команди її обходить), блок
  більший; так налаштовано машину власника, і ту саму ваду має вона.
- Push і PR без запиту, злиття лише людиною — ще одна точка очікування без захисту, якого не дає рев'ю.
- Лишити як є — суперечить способу роботи власника й колег.

## Consequences

- `pr-gate land` не перевіряє схвалення рев'ю на GitHub: «злиття після рев'ю» тримає процес (скіли `review`,
  `execute`).
- Споживач, підключений раніше, отримує нові правила через злиття `settings.json` з шаблоном (`kit-setup`, спека
  §5.2): додаються правила `pr-gate`; наявні `ask` на push/PR не чіпаються; з `ask` прибираються лише точні застарілі
  імена Уніки (спека §5.2 (б)).
- Кожна нова підкоманда `pr-gate`, що діє назовні, потребує окремого рішення про дозвіл.

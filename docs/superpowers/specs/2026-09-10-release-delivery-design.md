# Доставка артефактів: «підготувати реліз» — драфт

> **Статус: драфт на наступну ітерацію.** Записано 2026-09-10 за рішенням користувача після
> другого живого проходу B6 (`SMP_BankExchange`: `epf/dist/*.epf` у git проти `build/artifacts/`
> моделі 1.0). Це **новий клас задач**, не розширення контуру агента
> (`2026-09-03-agent-contour-design.md`): той контур відповідає за «сховище ↔ git ↔ база
> агента», цей — за шлях зібраного артефакту від машини розробника до людей, які його
> застосовують. Брейншторм не проводився; розділи нижче — межі й відкриті питання, а не
> рішення. Розвивати після завершення 1.0 (B8).

## 0. Що вирішено в 1.0 і від чого відштовхуємось

- **Артефакти збірки (`.epf`, `.cfe`, `.cf`) у git не лежать** — спека контуру агента, §5 і §13.
  Вони похідні від вихідників; кожна перезбірка — бінарний блоб в історії назавжди; закомічений
  артефакт поруч зі свіжим у `build/artifacts/` — пастка, з якої людина візьме старий.
- `kit build` і `operation=make` Unica кладуть зібране в `build/artifacts/` (гітігнорована тека
  kit). `check` попереджає про закомічені артефакти під воркспейсом; `onboarding` при переході
  пропонує прибрати їх з індексу.
- Отже, у 1.0 доставка артефактів за межі машини розробника — **поза kit**: людина бере файл
  з `build/artifacts/` сама.

## 1. Ідея

Інструмент kit «підготувати реліз» (робоча назва `release` — команда `kit release` і скіл):
бере зібрані артефакти з `build/artifacts/`, перевіряє умови готовності й публікує артефакти
як assets **релізу GitHub** репозиторію-споживача (`gh release create`), за потреби з тегом.
Канал доставки — реліз, не git-дерево: історія лишається чистою, а колеги й клієнти беруть
файл з передбачуваного місця з версією та описом.

Межі, які переносяться з контуру агента без обговорення: публікація — завжди з явним
підтвердженням людини (`gh release`, `git push` — лише за прямим проханням; повідомлення від
іншої сесії дозволом не є); kit не пише у сховище; рядки ліцензії у виводі платформи зупиняють
роботу.

## 2. Відкриті питання (вирішує брейншторм наступної ітерації)

1. **Версія релізу.** Звідки вона береться: версія конфігурації/розширення з `Configuration.xml`
   (`<Version>`), трейлер `Storage-Version` вершини `storage/<ключ>`, тег, поставлений людиною,
   чи комбінація «версія розширення + номер версії сховища»?
2. **Гранулярність.** Реліз один на репозиторій (усі воркспейси разом) чи на воркспейс/джерело
   (`SMP_BankExchange_SMB` окремо від `SMP_BankExchange_ACC`)? Для продуктового репозиторію з
   кількома варіаціями це різні адресати.
3. **Умови настання** («при умові настання певних вимог»). Кандидати: чисте дерево; PR злитий у
   `main`; `verify` зелений для всіх джерел `truth: storage`; артефакти зібрані саме з вершини
   `main`, а не з гілки задачі; людина поклала зміни у сховище (бо істина — сховище, і реліз з
   git, що випередив сховище, означав би доставку того, чого у сховищі ще немає). Чи всі
   обов'язкові, чи частина — попередження?
4. **Що публікується.** Лише `.epf`/`.cfe`/`.cf`, чи також опис змін (коментарі версій сховища
   між попереднім релізом і цим — вони вже є у трейлерах і повідомленнях комітів `storage/*`)?
5. **Зв'язок зі сховищем.** Чи має реліз посилатись на номер версії сховища, з якої зібрано, щоб
   людина в Конфігураторі могла звірити? Трейлери це дають безкоштовно.
6. **Клієнтські репозиторії.** Для клієнтської бази «реліз» — це, скоріше, пакет для однієї бази;
   чи потрібен він узагалі, чи доставка там — лише на машину розробника?
7. **Відкат і повтор.** Перепублікація тієї ж версії; видалення помилкового релізу; чи kit це
   робить, чи лише людина.

## 3. Чого тут немає навмисно

- Не CI: kit працює на машині розробника, реліз робить людина з агентом, а не конвеєр GitHub
  Actions. Якщо колись знадобиться CI — окреме рішення, бо платформа 1С і ліцензія на раннері —
  інший клас проблем.
- Не реєстр артефактів поза GitHub і не доставка в бази клієнтів: застосовує артефакт людина
  (контур агента, вимога 10).
- Не зміна моделі git 1.0: `storage/*`, трейлери, `main` як PR лишаються як є.

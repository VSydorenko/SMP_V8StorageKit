# Онбординг: звірка з цільовим станом

Issue: заводить автор плану (`v8storagekit:track`) — статус живе в GitHub, не в цьому файлі
Glossary: docs/GLOSSARY.md · ADR: ADR-0016, ADR-0017, ADR-0014 (порт без зміни поведінки)

## 1. Goal

Онбординг проєкту, підключеного до старої версії kit (MamHub 1.4.0 → 1.6.12, 2026-11-23), дав агенту неповну
картину: `kit-scan` назвав проєкт новим, `check` зупинився на першому відхиленні, старі імена скілів і застарілі
дозволи не помітив ніхто, а рецепт бази під `truth: storage` двічі зупинив людину без причини. Після роботи
онбординг будь-якого проєкту — нового чи підключеного раніше, з будь-якої версії — бачить **усі** відхилення від
цільового стану kit (ADR-0016) рядками з дією, і текст скілу веде через них без ручних обходів. Проєкти на старих
версіях власник мігрує сам; цей блок виправляє механізми, а не мігрує репозиторії.

## 2. Out of scope

- Міграція конкретних репозиторіїв-споживачів — робить власник.
- Повернення розділів оновлення для версій до 1.4.0 (ADR-0016, Rejected).
- Явний корінь для всіх команд (`--repo`) — #93, у Rust-фазах #53/#55.
- Порт `check`, `kit-scan`, `kit-setup` на Rust — фази #53/#55; цей блок міняє поведінку **до** порту (ADR-0014).
- `pr-gate land` і дзеркала `storage/*`, frontmatter скілів (#95) — окрема мала задача архітектора в тій самій
  гілці, не блок цієї спеки.
- Перелік класів шуму канонізації як повний — #41; тут лише той, що виміряно (§5.3).

## 5. Blocks in detail

### 5.1 B1 Контур сховища за цільовим станом

- **`kitVersion` у маніфесті.** `check` повідомляє знахідку `error` з тегом `kit-version` і дією «видалити рядок
  `kitVersion:` з `v8storagekit.yaml`; версію проєкту тримає `.agents/kit.profile.json`» — і далі перевіряє решту
  маніфесту й репозиторію так, ніби рядка немає. Решта команд (`sync`, `verify`, `session-check`, `provision`,
  `dump`, `adopt`, `install-hooks`) на ньому зупиняються, як тепер: працювати на маніфесті з невирішеним
  відхиленням не можна. `install-hooks` без `-Apply` (прев'ю) теж лише зупиняється — повний перелік дає `check`.
  Тримає: тест-підпроцес «дві знахідки, наступний крок не відбувся» за зразком `Check.*.Tests.ps1`.
- **Шаблон `v8project.yaml`.** `templates/v8project.yaml` — форма воркспейсу Уніки 0.16, яку kit очікує:
  `providers`, набори `source-set` без старого блоку `infobase:`, коментарі до кожного ключа kit. Зміст —
  з `skills/onboarding/references/upgrades.md` розділу «1.4.0 → 1.6.0» і чинних перевірок `check`; кожне правило шаблону `check` уже перевіряє
  або перевіряє після цього блоку. `templates/README.md` має рядок відповідності.
- **Рядки під фактичні шляхи.** Для кожного джерела `check` друкує відсутній рядок `.gitattributes`
  (`<шлях>/** -text`) чи `.gitignore` (vendor) готовим до вставки — це вже є для частини випадків; блок
  перевіряє, що так для **кожного** source-set з `v8project.yaml`, включно з тестовим (`tests/src`, #11).

### 5.2 B2 Процес за цільовим станом

- **Проєкт, підключений раніше, без профілю.** `.agents/kit.profile.json` немає, але є `v8storagekit.yaml` з
  `kitVersion` → розділ `Kit version` `kit-scan` каже «підключено раніше (<версія з маніфесту>), профілю немає»,
  а не «перше підключення», і друкує: (а) `kit check -RepoRoot .` як джерело відхилень контуру; (б) чеклісти
  `CHANGELOG.md` усіх версій, новіших за ту, з якої починається журнал, якщо версія проєкту старша за неї.
  Те саме — у `-Json` окремим полем стану.
- **`kit.version` — останнім.** `kit-setup` створює профіль **без** `kit.version`; поле записує окремий явний
  крок (`kit-setup` з прапорцем на кшталт `-SetVersion`, ім'я — рішення плану), який скіл онбордингу виконує
  останнім комітом PR. До того `kit-scan` показує розрив версії. Новий проєкт і проєкт, підключений раніше, —
  однаково (ADR-0016 п.4).
- **Перелік застарілих імен.** Один файл даних kit (місце й формат — рішення плану; не всередині `.psm1`):
  рядок «стара назва → заміна» для старих імен скілів kit (до перейменувань 1.6.3 і пізніших: `using-v8storagekit`,
  `v8storagekit:reconcile`, `:finish`, `:provision`, `:sync`, `:dump` тощо — повний перелік з `skills/onboarding/references/upgrades.md`),
  викликів `tools/kit.ps1` → `kit`, прибраних команд (`kit build` → `unica.run` `make`), прибраних інструментів
  Уніки (`unica_project_map`, `unica_project_status`, `unica.project.status` …). `kit-scan` шукає їх у
  `CLAUDE.md`, `AGENTS.md`, `.claude/**`, `.agents/**` (без вивід-тек), `.gitignore`, `.gitattributes` і друкує
  рядок на кожен збіг: файл, стара назва, заміна. Регістр не враховується. Тримає: тест-підпроцес із контролем,
  що вміє впасти (файл без застарілих імен — нуль рядків; файл з одним — рядок).
- **Злиття `.claude/settings.json`.** Цільовий стан — `templates/settings.json`. `kit-setup -DryRun` показує, а
  `kit-setup` застосовує: (а) правила `allow`/`ask` шаблону, яких у проєкті немає; (б) прибирання правил на
  інструменти Уніки, яких у шаблоні немає (застарілі імена з переліку); (в) перенос правила з `allow` в `ask`,
  коли шаблон тримає його в `ask` (мутуючі `unica_apply`, `unica_run`); (г) прибирання `hooks.SessionStart` kit
  з проєктного `settings.json` (хук живе в плагіні). Власні правила проєкту, яких шаблон не знає, лишаються
  без змін. Читання й запис — JSON-парсером; після запису файл перечитується парсером (невалідний JSON Claude
  Code тихо ігнорує цілком).
- **Необов'язкові поля профілю.** `docs.specs`, `docs.plans` без знайденої теки не отримують TODO: поле
  пропускається, діє типове значення скілу (`discuss` — `docs/specs/`). Обов'язкові поля (`pr.base`,
  `pr.mergeMethod`) — TODO, як тепер.
- **Версія плагіна змінилась після скану.** `kit-setup` друкує версію плагіна, якою працює; скіл онбордингу
  порівнює її з версією у звіті скану й, якщо вони різні, перезапускає скан перед застосуванням.

### 5.3 B3 Текст онбордингу

- **Рецепт кроку 9, база під `truth: storage`** (`skills/onboarding/references/upgrades.md`, розділ «1.4.0 → 1.6.0»):
  - тека `Ext/ParentConfigurations/` наперед **не** видаляється: `pull force` сам перезаписує `.cf` поставки
    (виміряно один раз, MamHub_UNF); видалення — лише як відповідь на `os error 5` при заміні теки;
  - закрити VS Code чи вимкнути Pylance і git-розширення — теж лише за тим самим симптомом;
  - `git status -- <шлях base>` непорожній після `pull force` → не зупинка без варіантів, а розвилка для людини:
    агент показує зміни за класами; лише службові класи (`Ext/Predefined.xml`: `<Code>…</Code>` → `<Code/>`;
    `Ext/CommandInterface.xml`: прибраний `<GroupsOrder>` з нульовим GUID) — пропонує прийняти окремим комітом
    канонізації; будь-що інше — `kit verify` і зупинка. Рішення приймає людина, агент сам не комітить. Перелік
    класів — виміряний на одному проєкті, не повний (#41).
- **`skills/onboarding/references/upgrades.md`.** Таблиця «Довідка по версіях» — рядок на кожен розділ версії. Розділ, що вимагає замін
  імен, посилається на перелік застарілих імен (§5.2), а не копіює його.
- **Онбординг проєкту, підключеного раніше** (`skills/onboarding/SKILL.md`, `skills/onboarding/references/process.md`): порядок — `kit-scan` → `kit check` →
  відхилення обох → кроки Уніки, яких інструменти не виявляють → `kit.version` останнім комітом.
- **Дозволи споживача (ADR-0017).** `templates/settings.json`: `git push` і `gh pr create` — не в `ask`;
  злиття PR після рев'ю — без запиту; force push лишається з запитом. `templates/CLAUDE.md`: рядок «лише за явним
  проханням» переписати за ADR-0017.
- **Дотичні тексти:**
  - попередження в онбордингу про кириличні імена тек і шляхів (#69 п.1);
  - код 3 `session-check` — «є що робити», а не збій, у `storage-sync` і `storage-rules` (#65);
  - тривалість реплею версії — не голе число «20–40 хв», а умова виміру або «залежить від розміру; вимір —
    у звіті команди» (#67), у `skills/infobase-agent/SKILL.md`, `skills/infobase-dump/SKILL.md`, `skills/onboarding/references/storage.md`;
  - `docs/unica-contract.md`: рядки «Трекінг в апстрімі» для розбіжності `check`/`run` на прихованому наборі й
    `os error 5` при заміні теки (#63).

## 6. Security and data integrity

- **Дозволи.** Злиття `settings.json` (§5.2) ніколи не додає в `allow` правила, яке шаблон тримає в `ask`, і не
  розширює прав понад шаблон; власні правила проєкту не видаляє. Розширення push/PR — рішення власника
  (ADR-0017); force push, `gh release`, прямий коміт у головну гілку лишаються з запитом.
- **Невалідний JSON.** Запис `settings.json` — лише парсером з перечитуванням; збій парсера — зупинка без
  запису, а не часткова вставка.
- **Поставка вендора.** Рецепт кроку 9 не видаляє гітігнорований `.cf` поставки наперед: з git він не
  відновлюється (сотні МБ).
- **Коміт канонізації.** Агент не приймає зміни `pull force` сам — лише за рішенням людини і лише службових
  класів; інакше `kit verify` і зупинка.
- **Сховища.** Блок не змінює роботи зі сховищами: лише читання.

# Онбординг: звірка з цільовим станом

Issue: заводить автор плану (`v8storagekit:track`) — статус живе в GitHub, не в цьому файлі
Glossary: docs/GLOSSARY.md · ADR: ADR-0016, ADR-0017, ADR-0014 (порт без зміни поведінки)

## 1. Goal

Онбординг проєкту, підключеного до старої версії kit (MamHub 1.4.0 → 1.6.12, 2026-11-23), дав агенту неповну
картину: `kit-scan` назвав проєкт новим, `check` зупинився на першому відхиленні, старі імена скілів і застарілі
дозволи не помітив ніхто, а рецепт бази під `truth: storage` двічі зупинив людину без причини. Після роботи
онбординг будь-якого проєкту — нового чи підключеного раніше, з будь-якої версії — бачить **усі** відхилення від
цільового стану kit (ADR-0016) рядками з дією, і текст скілу веде через них без ручних обходів. Проєкти на старих
версіях власник мігрує сам; цей блок виправляє механізми, а не мігрує репозиторії.

## 2. Out of scope

- Міграція конкретних репозиторіїв-споживачів — робить власник.
- Повернення розділів оновлення для версій до 1.4.0 (ADR-0016, Rejected).
- Явний корінь для всіх команд (`--repo`) — #93, у Rust-фазах #53/#55.
- Порт `check`, `kit-scan`, `kit-setup` на Rust — фази #53/#55; цей блок міняє поведінку **до** порту (ADR-0014).
- Межі злиття `pr-gate` у коді (дзеркала `storage/*`, форк, `pr.afterMerge` лише з головної гілки), frontmatter
  скілів (#95) — окрема мала задача архітектора в тій самій гілці (гілка `fix/prgate-storage-frontmatter`), не
  блок цієї спеки; B2 від неї залежить (§5.3).
- Хук git `pre-push` і дозвіл голого `git push` без запиту — відкинуто (ADR-0017).
- Перелік класів шуму канонізації як повний — #41; тут лише той, що виміряно (§5.4).

## 5. Blocks in detail

### 5.1 B1 Контур сховища за цільовим станом

- **`kitVersion` у маніфесті.** Диспетчер вмикає для `check` окремий режим префлайту (не `-Lenient`: той спільний
  із `session-check`). У цьому режимі `kitVersion` не зупиняє читання маніфесту: `check` отримує знахідку `error`
  з тегом `kit-version` і дією «видалити рядок `kitVersion:` з `v8storagekit.yaml`; версію проєкту тримає
  `.agents/kit.profile.json`», а решту маніфесту, воркспейси й джерела розбирає так, ніби рядка немає, і
  перевіряє все далі. Решта команд (`sync`, `verify`, `session-check`, `provision`, `dump`, `adopt`,
  `install-hooks` з прев'ю чи без) на `kitVersion` зупиняються, як тепер: працювати на маніфесті з невирішеним
  відхиленням не можна, а повний перелік дає `check`. Тримає: тести (1) і (2) рядка B1.
- **Шаблон `v8project.yaml`.** `templates/v8project.yaml.example` — форма воркспейсу Уніки 0.16, яку kit очікує
  (`providers`, набори `source-set` без старого блоку `infobase:`), з коментарем до кожного ключа kit. Джерело
  змісту — чинні перевірки `check`: кожне правило шаблону `check` перевіряє. `templates/README.md` має рядок
  відповідності. Суфікс `.example` — як у сусідніх зразках: файл `v8project.yaml` у теці першого рівня робить сам
  kit «репозиторієм 1С» для детекторів (хук SubagentStart, `kit-setup`, пошук воркспейсів Уніки; рішення
  архітектора 2026-11-23); тримає тест хука на корені дерева kit.
- **Рядки під фактичні шляхи.** Для заявленого source-set з `truth: git`/`storage` без рядка `.gitattributes`
  `check` дає `error` з рядком `<шлях>/** -text` (як тепер); з `truth: vendor` без рядка `.gitignore` — рядок
  `<шлях>/**`. Наявна `warn undeclared-source` для source-set з `v8project.yaml`, якого немає в маніфесті (типово
  тестовий, #11), лишається `warn` з кодом 0, але її дія тепер каже: «заявіть у маніфесті з `truth`; для
  `git`/`storage` знадобиться рядок `<шлях>/** -text`, для `vendor` — `<шлях>/**` у `.gitignore`». Тримає: тест (3).

### 5.2 B2 Процес за цільовим станом

- **Проєкт, підключений раніше, без профілю.** `.agents/kit.profile.json` немає, але є `v8storagekit.yaml` з
  `kitVersion` → розділ `Kit version` `kit-scan` каже «підключено раніше (<версія з маніфесту>), профілю немає»,
  а не «перше підключення», і друкує: (а) `kit check -RepoRoot .` як джерело відхилень контуру; (б) чеклісти
  `CHANGELOG.md` усіх версій журналу, новіших за версію проєкту (для версії, старшої за початок журналу, — усі).
  У `-Json` — окреме значення стану.
- **`kit.version` — останнім.** `kit-setup` створює профіль **без** `kit.version`; поле записує окремий явний
  виклик `kit-setup -SetVersion`, який скіл онбордингу робить останнім комітом PR. До того `kit-scan` і `kit-setup`
  показують розрив версії — рядок «`kit.version` немає — запише `kit-setup -SetVersion` останнім комітом PR», **без**
  переліку кроків від 0.1.0 (інакше новий проєкт отримує в звіті чеклісти всього журналу). Новий проєкт і проєкт,
  підключений раніше, — однаково (ADR-0016 п.4). `-SetVersion` читає лише сирий `.agents/kit.profile.json`, не
  злиті шари профілю (та сама межа, що для `pr.afterMerge` у §5.3). Відоме обмеження до порту `kit-scan`/`kit-setup`
  (#55): хук старту сесії на профілі без `kit.version` друкує «проєкт на 0.1.0» — лише на гілці PR онбордингу.
- **Файл застарілих імен** (місце й формат — рішення плану; не всередині `.psm1`; єдине джерело — `skills/onboarding/references/upgrades.md`
  на нього посилається):
  - старі імена скілів kit **з префіксом** — `v8storagekit:<ім'я>` і `/v8storagekit:<ім'я>` (зокрема `using-v8storagekit`,
    `reconcile`, `finish`, `provision`, `sync`, `dump`, `retro` → нові імена з розділу 1.6.3 `skills/onboarding/references/upgrades.md`);
  - виклики `tools/kit.ps1` → `kit`; прибрані команди (`kit build` → `unica.run` `"op":"make"`);
  - інструменти Уніки, яких немає в Уніці 0.16 (`mcp__plugin_unica_unica__unica_project_map` тощо): перелік
    складає автор плану порівнянням правил колишніх шаблонів із переліком інструментів установленої Уніки
    — тих, які бачить Claude Code (`unica-call.ps1` з `--tools` показує ще `task.*`, яких Claude Code не має;
    `docs/unica-contract.md`, розділ дозволів). Вимір плану: 37 імен.

  `kit-scan` шукає імена як цілі токени (голі слова `sync`, `dump` без префікса — ні) у `CLAUDE.md`, `AGENTS.md`,
  `.claude/**`, `.agents/**` (без вивід-тек), `.gitignore`, `.gitattributes`; регістр не враховується; рядок на
  збіг — файл, стара назва, заміна. Тримає: тест (2) рядка B2 з контролем, що вміє впасти.
- **Злиття `.claude/settings.json`** (цільовий стан — `templates/settings.json`, §5.3). Контракт `kit-setup`
  «нічого не видаляє й не перезаписує» для `settings.json` змінюється на перелічене нижче; довідка команди й
  її тести оновлюються разом. `-NoPermissions` вимикає все злиття `settings.json`, включно з прибиранням.
  `kit-setup -DryRun` показує, `kit-setup` застосовує:
  - (а) правила `allow`, `ask`, `deny` шаблону, яких немає в **тому самому** списку проєкту, — додати; до `allow` —
    лише правило, про яке доведено, що жодне `ask`/`deny` проєкту його не зачіпає (D13 перебудовано за рев'ю
    безпеки, раунд 2: у разі сумніву — блокувати). Правило оболонки шаблону (`Bash(…)`/`PowerShell(…)`) **не йде** в
    `allow`, якщо у **вхідному** (до злиття) `ask` чи `deny` проєкту є правило оболонки будь-якої форми (`Bash` ≡
    `PowerShell`), для якого виконується щось одне: (1) тіло порожнє, `*`, ціле ім'я інструмента (`Bash`,
    `PowerShell` без дужок) або тіло не розбирається; (2) перший токен тіла (до першого пробілу чи `:`) містить `*`,
    і його частина до `*` — посимвольний префікс першого токена правила шаблону (`pr-gate*`, `pr*`, `*` блокують
    `pr-gate`); (3) перший токен без `*` дорівнює першому токену правила шаблону — незалежно від решти тіла
    (`pr-gate land --admin:*`, `pr-gate start:*` блокують усі правила `pr-gate`). `Bash(pr:*)` не блокує
    `pr-gate open` (перший токен `pr` ≠ `pr-gate`). Порівняння — лише з вхідними `ask`/`deny` проєкту, не з шаблоном
    і не зі злитим станом: інакше `ask` шаблону (`git push`) закрив би `allow` шаблону (`git status`) у кожному
    новому репозиторії. Свідомий наслідок: проєкт з `Bash(git push:*)` в `ask` не отримує читальних правил `git …`
    шаблону. Правила не-оболонки (`mcp__…`) — лише точний рядок в `ask`/`deny` проєкту. Пропущене не мовчки:
    `kit-setup` (і `-DryRun`) друкує на кожен перший токен один рядок «не додано N правил на `<токен>` (проєкт має
    ask/deny на `<токен>`): <перелік> — додай сам, якщо згоден» — лише з правилами, яких в `allow` проєкту ще
    немає. Правила Уніки з `allow` шаблону — лише в репозиторії 1С (`ask` і `deny` —
    завжди: вони лише звужують права). Проєкт 1С, де `v8project.yaml` ще немає, отримує `allow` Уніки повторним
    `kit-setup`. Наявність правила в списку й прибирання (б) — точне порівняння з урахуванням регістру;
  - (б) правила, що **точно** збігаються з застарілими іменами Уніки з файлу застарілих імен, — прибрати, лише з
    `allow`/`ask`;
  - (в) `unica_apply` в `allow` проєкту → перенести в `ask` (шаблон тримає його в `ask`; `unica_run` шаблон
    свідомо тримає в `allow` — `docs/unica-contract.md`);
  - (г) у `hooks.SessionStart[].hooks[]` — елемент, чия **уся** команда (після обрізання пробілів по краях)
    дослівно збігається з формою шима kit `pwsh -NoProfile -File <шлях>`, заякореною з обох боків (D13 і шим
    перебудовано за рев'ю безпеки, раунд 2), де `<шлях>` — `.claude/hooks/session-start.ps1` з `/` або `\`, з
    необов'язковим `./` або з префіксом `$CLAUDE_PROJECT_DIR/` (`${CLAUDE_PROJECT_DIR}`), сам шлях у лапках
    `"…"`/`'…'` чи без, або лапки лише навколо змінної (`"$CLAUDE_PROJECT_DIR"/…`), — прибрати; групу, `SessionStart`
    і `hooks` — лише коли спорожніли через це прибирання. Будь-яка інша команда (інша програма, інші прапорці,
    складена, хук рівня користувача `~/.claude/…`), власні хуки проєкту (зокрема в тій самій групі) й невідомі форми
    не чіпати.

  Нічого з `deny` проєкту не прибирається ніколи; з `ask` проєкту прибираються лише точні застарілі імена (б), решта
  не прибирається й не переноситься в `allow`; власні правила, яких немає ні в шаблоні, ні у файлі застарілих імен,
  лишаються без змін; правило, яке зачіпає вхідне `ask` чи `deny` проєкту (за правилом (а)), у `allow` не потрапляє. Запис — серіалізувати, розібрати
  результат у пам'яті, записати тимчасовий файл і атомарно замінити; збій розбору на вході чи виході — зупинка без
  запису. Тримає: тест (3) — злиття; тест (4) — лише вхід; атомарний запис — рев'ю коду задачі. Попередження без
  прибирання: широкі `pr-gate:*`, `track:*` і `git branch:*` (перше покоління шаблону; пропускає `git branch -D/-f`).
- **Необов'язкові поля профілю.** `docs.specs`, `docs.plans` без знайденої теки не отримують TODO: поле
  пропускається, діє типове значення скілу (`discuss` — `docs/specs/`). Обов'язкові поля (`pr.base`,
  `pr.mergeMethod`) — TODO, як тепер. Тримає: тест (6).
- **Версія плагіна змінилась після скану.** `kit-setup` друкує версію плагіна, якою працює; скіл онбордингу
  порівнює її з версією у звіті скану й, якщо вони різні, повторює скан перед застосуванням (текст B3).

### 5.3 B2 Цільовий `settings.json` (ADR-0017)

- `allow`: правила процесу, які `kit-setup` пише й тепер, плюс `pr-gate open`, `pr-gate ready`, `pr-gate land` — у
  формах `Bash(pr-gate <підкоманда>:*)` і `PowerShell(pr-gate <підкоманда>:*)`. Широке `pr-gate:*` не
  вживається: воно дозволило б і майбутні підкоманди без рішення (`kit-setup` і далі попереджає про нього).
- `ask`: голі `git push`, `gh pr create` (як тепер), **новий** `gh pr merge` і `gh release` — кожна у формах
  `Bash(<команда>:*)` і `PowerShell(<команда>:*)`, разом 8 правил; плюс `unica_apply`.
- `deny`: як тепер.

`kit-setup` (`tools/commands/kit-setup.psm1`): перелік команд процесу отримує `pr-gate open`, `ready`, `land`;
довідка «зовнішні дії не дозволяються» і текст попередження про широке `pr-gate:*` переписуються — причина
попередження тепер «дозволяє й майбутні підкоманди без рішення», а замінник включає `open`, `ready`, `land`.

Межі, які тримає код `pr-gate` (`tools/lib/KitPrGate.psm1`, тести `PrGate.Tests.ps1`), а не префікси дозволів:
`open` пушить лише поточну гілку в однойменну, звичайним push (без force), ніколи захищену (головна гілка, base,
ціль `origin/HEAD`, будь-яка `storage/*`) і не відкриває PR у `storage/*`; `land` зливає лише PR з цього
репозиторію (не форк), не в `storage/*` і не зі `storage/*`, без конфлікту, на голові, яку прочитав перед злиттям
(`--match-head-commit`), а prune не видаляє `storage/*`; `pr.afterMerge` `land` бере лише з
`.agents/kit.profile.json` на головній гілці origin, не з локального чи машинного профілю й не з гілки задачі.
Ці запобіжники — мала задача архітектора в цій самій гілці (§2); B2 стартує після її злиття. Тримає: тест (7)
рядка B2, `PrGate.Tests.ps1` і `Templates.Tests.ps1` (шаблон ↔ вивід `kit-setup`).

### 5.4 B3 Текст онбордингу

- **Рецепт кроку 9, база під `truth: storage`** (`skills/onboarding/references/upgrades.md`, розділ «1.4.0 → 1.6.0»):
  - тека `Ext/ParentConfigurations/` наперед **не** видаляється: `pull force` сам перезаписує `.cf` поставки

    — `pull force` знову, перевірка, що `.cf` на місці;

## 6. Security and data integrity

- **Дозволи.** Без запиту — лише `pr-gate open/ready/land`, межі яких тримає код `pr-gate` (§5.3); голі `git push`,
  `gh pr create`, `gh pr merge` лишаються з запитом, тож примусовий push, push у головну гілку, видалення
  віддалених гілок і обхід хуків (`--no-verify`) без людини неможливі. Дозвіл на `land` — це й дозвіл на
  `pr.afterMerge`, тому його argv береться лише зі зрев'юєного профілю на головній гілці origin (§5.3). `pr-gate
  land` не перевіряє схвалення рев'ю на GitHub — «злиття після рев'ю» тримає процес (скіли `review`, `execute`),
  а не команда; голова, на якій зливає `land`, — та, яку він сам прочитав перед злиттям.
- **Злиття `settings.json`.** «kit-setup додає в allow лише правило, про яке доведено, що жодне ask/deny проєкту його
  не зачіпає; прибирає лише хук, що дослівно є шимом kit». Ніколи не прибирає `deny`; з `ask` прибирає лише точні
  застарілі імена Уніки; правило оболонки шаблону не йде в `allow`, коли вхідні `ask`/`deny` проєкту мають правило
  оболонки (`Bash` ≡ `PowerShell`) на той самий перший токен команди, маску на нього чи ціле ім'я інструмента; у разі
  сумніву — блокує, пропущене називає рядком «не додано» (§5.2 (а); D13 і шим перебудовано за рев'ю безпеки, раунд 2);
  прибирає лише точні застарілі імена й лише елемент, уся команда якого — шим kit (власний хук у тій самій групі
  лишається).
- **Невалідний JSON.** Запис — атомарний, з розбором результату до заміни файлу; збій — зупинка, файл той самий.
- **Поставка вендора.** Рецепт кроку 9 не видаляє гітігнорований `.cf` поставки наперед: з git він не
  відновлюється (сотні МБ).
- **Коміт канонізації.** Агент не приймає зміни `pull force` сам — лише за рішенням людини і лише службових
  класів; інакше `kit verify` і зупинка.
- **Сховища.** Блок не змінює роботи зі сховищами: лише читання.

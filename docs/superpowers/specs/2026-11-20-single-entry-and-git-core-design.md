## 1. Навіщо

Плагін склеєно з двох інструментів (контур «сховище ↔ git» і форк agent-kit). Лишились три наслідки,
усі про те, як kit запускає процеси й каже про результат: дві точки входу (`tools/kit.ps1` з
param-блоком, що перехоплює токени команд, і `tools/kit-process.ps1` без нього); два контракти кодів
виходу (коди `2`/`3` означають різне); дев'ять обгорток запуску git з трьома контрактами збою. До них
додається вартість старту PowerShell: хук старту сесії запускає `pwsh` у **кожній** сесії машини,
навіть у проєкті без маніфесту й профілю, де він мусить лише мовчки вийти.

## 2. Рішення

**D0. Мова й місце коду.** Rust, один крейт `kit` у `rust/` репозиторію плагіна, ціль
`x86_64-pc-windows-msvc` (середовище власника). Залежності — мінімум, кожна з обґрунтуванням.

**D1. Один вхід — `kit.exe`.** Сирі аргументи `kit <команда> [аргументи]`, розбір у стилі
`ConvertFrom-KitArguments` (`-Ім'я значення`, `-Ім'я:значення`, `-Прапорець`). Перенесені на Rust
команди виконує сам `kit.exe`. Неперенесені — передає PowerShell-диспетчеру: один скрипт без
param-блоку (злиття `tools/kit.ps1` і `tools/kit-process.ps1`), що кличе `Invoke-Kit<Команда>` з сирими
аргументами; спільні параметри сховища (`-RepoRoot`, `-Workspace`, `-Source`, `-Apply`) стають
частиною розбору кожної команди сховища. Передача прозора: stdin, stdout, stderr і код виходу —
без змін.

**D2. Обгортки `bin/`.** `bin/kit.exe` — вхід усіх команд. Короткі імена команд процесу (`sdd`,
`pr-gate`, `doc`, …) лишаються й ідуть у `kit.exe <ім'я> …`. Скіли, шаблони, `README.md`, `CLAUDE.md`,
хук — на форму `kit <команда>` замість `pwsh -NoProfile -File "<корінь плагіна>/tools/kit.ps1" <команда>`.

**D3. Один контракт кодів виходу** для всіх команд, і Rust, і PowerShell:

| Код | Значення |
|---|---|
| `0` | виконано / так |
| `1` | зупинка / ні / відмова |
| `2` | помилка виклику (аргументи, невідома команда) |
| `3` | не перевірено — перевірка не відбулась; ніколи не зелений |
| `4` | виконано, є наступний крок (`sync`: дзеркало оновлено, злиття ні; `verify`/`session-check`: є що робити) |

Помилка — перший рядок stderr `<команда>: ERROR …`; успіх — останній рядок `next: …`. Усі споживачі
коду (хук, скіли, тексти кроків, шаблони, тести) переходять у тому самому PR. Сумісності зі старими
кодами немає.

**D4. Ядро git — у Rust**, модуль `git`: завжди `-c core.quotepath=false`, UTF-8, `GIT_TERMINAL_PROMPT=0`;
контракт збою явний (помилка з дослівним stderr git або дозволений збій з кодом), режиму «тихо
порожньо» немає. **D4а:** два входи — зібраний вивід і потоковий процес для байтового обміну
`cat-file --batch` (текстовий режим псує бінарні блоби: блоб 262 байти → 524; збирання всього stdout
тримало б у пам'яті все джерело). Поза модулем `git` Rust-код git не запускає.

PowerShell-обгортки git **не зводяться**: PowerShell-код заморожено — лише виправлення дефектів і зміни
D1/D3, нових обгорток git не додавати; обгортки зникнуть разом із перенесенням своїх команд.

**D5. Запобіжники.** Тест: запуск процесу `git` у Rust-коді лише в модулі `git`. Тести ядра: кириличний
шлях без вісімкових кодів; збій без дозволу — помилка з текстом stderr; побайтний експорт бінарного
блоба. Тест контракту D3 — на кожен код хоча б однією командою, з контролем, що вміє впасти.

**D6. Обсяг фази 1.**
- `kit.exe` (D1) з передачею неперенесених команд PowerShell-диспетчеру; контракт D3 скрізь;
- ядро git (D4/D4а);
- **хук старту сесії** — у Rust (`hooks.json` кличе `kit.exe` напряму): у проєкті без маніфесту й без
  профілю — тиша й код 0 **без запуску `pwsh`**; правила спілкування й рядок оновлення — як зараз;
- `session-check` — у Rust, якщо вимір §5 покаже, що це вміщається у фазу (читання маніфесту YAML,
  відбиток, звіт сховища); інакше хук кличе його через передачу PowerShell, і перенос — фаза 2;
- `session-board` — з заготовки спайку.

**D7. Поставка.** Зібраний `bin/kit.exe` (профіль `release`) комітиться в репозиторій плагіна, як Уніка
постачає свій бінарник у пакеті. Запобіжник «бінарник відповідає джерелу»: `kit.exe` несе вбудований
відбиток джерел `rust/` (хеш на етапі збірки), тест обчислює той самий відбиток з дерева й червоніє на
розбіжності; Pester-тести ходять у закомічений бінарник.

**D8. Міграція по командах.** Кожна наступна фаза переносить групу команд: Rust-реалізація, наявні
Pester-тести команди зелені проти `kit.exe` як чорна скринька, потім PowerShell-модуль команди й тести
його внутрішніх функцій прибираються. Порядок фаз після першої — окреме рішення.

## 3. Інваріанти (не змінюються)

- Поведінка команд — та сама, крім кодів `2`/`3` → `4`, рядків `ERROR`/`next:` і форми виклику.
- Хук старту сесії: у проєкті без маніфесту й профілю — тиша, код 0; стеля часу `session-check`.
- П25 і #34 (видалення лише після перевірки шляху); гілки `storage/*` пише лише `kit sync` з `V8KIT_SYNC=1`;
  kit Уніку не викликає; раннер запускається лише в одному місці.
- Байти, які kit порівнює чи хешує (дерево, `ls-tree`, `cat-file`, діфи), не змінюються від переходу.

## 5. Відкриті питання — автор плану вимірює, не припускає

Виміри першої редакції (хто читає коди виходу, `Export-KitTree`, ім'я `kit` у `PATH`, час хука,
форми запуску git) лишаються чинними — у плані з умовою виміру. Нові:
1. Чи вміщається `session-check` у фазу 1: залежності (YAML-маніфест і накладка, відбиток, розбір звіту
   платформи), обсяг, крейт YAML з тією ж семантикою, що `powershell-yaml` на фікстурах маніфестів.
2. Як Pester-фікстури (`Copy-KitTools`, `New-KitFakeRepo`) і хук бачать `bin/kit.exe`; чи потрібна збірка
   перед прогоном тестів, і як запобіжник D7 ловить застарілий бінарник.
3. Час хука старту сесії до і після на проєкті без маніфесту й профілю, з профілем, з маніфестом.
4. Чи жодна команда процесу не залежить від прив'язки параметрів `kit.ps1`, яку прибирає D1.

## 6. Перевірка й ризик

Ризик: `kit.exe` з передачею, ядро git і хук — `risky` (два рев'ю: відповідність і адверсарне з
вимірами); переходи текстів — `standard`. Повний прогін без `Integration` у фіналі блоку; `-Only`
зачеплених у задачах. Версія — наступний patch лінії 1.6, запис `CHANGELOG.md` з чеклістом споживача
(форма виклику `kit <команда>`, код `4`).

# Одна точка входу, один контракт кодів виходу, одне ядро запуску git

Issue #51. Продовження модернізації #48 (злито як 1.6.3, PR #49). Архітектор — сесія, що вела #48;
автор плану — окрема сесія. Рішення нижче — з обговорення з власником 2026-11-20; спека — джерело
брифу плану.

## 1. Навіщо

Плагін склеєно з двох інструментів (контур «сховище ↔ git» і форк agent-kit). Модернізація #48
прибрала більшість наслідків; лишились три, і всі три — про те, як kit запускає процеси й як каже
про результат:

1. **Дві точки входу.** `tools/kit.ps1` (команди сховища) має param-блок: його `-RepoRoot`,
   `-Workspace`, `-Source`, `-Apply` і загальні параметри PowerShell перехоплюють однойменні токени
   команд. Тому команди процесу мають окремий вхід `tools/kit-process.ps1` без param-блоку (сирі
   `$args`). Дві різні прив'язки аргументів для однієї родини команд.
2. **Два контракти кодів виходу.** Сховище: `0` виконано, `1` зупинка, `2` лише `sync` — дзеркало
   оновлено, злиття ні, `3` `verify`/`session-check` — є що робити. Процес (`tools/lib/KitCli.psm1`):
   `0` так, `1` ні, `2` помилка виклику, `3` **не перевірено, ніколи не зелений**. Однаковий код
   означає різне; `CLAUDE.md` прямо попереджає «не плутати».
3. **Дев'ять обгорток запуску git** з трьома контрактами збою (виняток / `$null` / об'єкт з кодом),
   різним кодуванням і різним `core.quotepath`, плюс десятки прямих `git -C …; $LASTEXITCODE` у
   `StorageBranch`, `check`, `sync`. Живого дефекту зараз немає; задача запобіжна: клас «тихий збій
   git» (помилка стає порожнім результатом) і клас «кирилиця без `core.quotepath=false`» (шляхи 1С
   приходять вісімковими кодами — той самий клас дав #31/#32).

Інвентар обгорток (вимір кроку 5 #48; автор плану перевіряє, не приймає на віру):

| Обгортка | Модуль | Запуск | Збій |
|---|---|---|---|
| `Invoke-KitGitProcess` | `TreeCompare` | .NET Process, stdin записами через NUL | об'єкт `{ExitCode,Stdout,Stderr}`, не кидає |
| `Invoke-KitGit` | `KitGit` | .NET Process, завжди `core.quotepath=false` | виняток без `-AllowFail` |
| `Invoke-PgGit` | `KitPrGate` | .NET Process, `GIT_TERMINAL_PROMPT=0` | `{Ok,Code,Raw,Out,Err}` |
| `Invoke-DocGit` | `PathRefs` | .NET Process, UTF-8, quotepath=false | об'єкт |
| `Invoke-WiGit` | `WorktreeInclude` | .NET Process зі stdin-текстом | `$null` |
| `Invoke-SetupGit` | `kit-setup` | `& git` | `$null` / масив рядків |
| `Invoke-SbGit` | `session-board` | `& git` | `$null` / `''` / рядок |
| `Invoke-KitProfileGit` | `KitProfile` | `& git` | `$null` / перший рядок |
| `Invoke-SddTryGit` | `sdd` | над `Invoke-KitGit -AllowFail` | `$null` / рядок |

## 2. Рішення

**D1. Одна точка входу.** `tools/kit.ps1` — без param-блоку, сирі аргументи для всіх команд.
Спільні параметри сховища (`-RepoRoot`, `-Workspace`, `-Source`, `-Apply`) стають частиною
специфікації аргументів кожної команди сховища й розбираються тим самим `ConvertFrom-KitArguments`,
що й у команд процесу. `tools/kit-process.ps1` зникає. Імпорт модулів лишається вибірковим: команда
процесу — лише розділ `# == процес ==` `module-order.txt` (короткий старт), команда сховища — увесь
порядок. Префлайт сховища — як зараз, лише для команд сховища.

**D2. Обгортки `bin/`.** Новий `bin/kit` (+ `bin/kit.ps1`) — вхід команд сховища: агент і скіл кличуть
`kit sync …`, `kit verify …` замість `pwsh -NoProfile -File "<корінь плагіна>/tools/kit.ps1" sync …`.
Короткі імена команд процесу (`sdd`, `pr-gate`, `doc`, …) лишаються й ідуть через той самий
`tools/kit.ps1`. Хук старту сесії кличе той самий вхід. Скіли, шаблони, `README.md`, `CLAUDE.md` —
на нову форму виклику.

**D3. Один контракт кодів виходу** для всіх команд:

| Код | Значення |
|---|---|
| `0` | виконано / так |
| `1` | зупинка / ні / відмова |
| `2` | помилка виклику (аргументи, невідома команда) |
| `3` | не перевірено — перевірка не відбулась; ніколи не зелений |
| `4` | виконано, є наступний крок (`sync`: дзеркало оновлено, злиття ні; `verify`/`session-check`: є що робити) |

Помилка — перший рядок stderr `<команда>: ERROR …`; успіх — останній рядок `next: …` (як зараз у
процесі). Усі споживачі коду — хук, скіли, тексти кроків, шаблони, тести — переходять у тому самому
PR. Сумісності зі старими кодами немає (правило власника).

**D4. Одне ядро запуску git** у спільному шарі (`module-order.txt`, доступне і сховищу, і процесу):
завжди `-c core.quotepath=false`, UTF-8 для stdout і stderr, `GIT_TERMINAL_PROMPT=0`, необов'язковий
stdin (текст або записи через NUL), результат — об'єкт з кодом, stdout і stderr. Контракт збою обирає
викликач явно: без `-AllowFail` — виняток з дослівним stderr git; з `-AllowFail` — об'єкт. Режиму
«тихий `$null`» немає. Усі дев'ять обгорток і прямі `git -C …; $LASTEXITCODE` переходять на ядро або
зникають.

**D5. Запобіжники.** AST-тест: запуск git (`& git`, `git -C`, `ProcessStartInfo` з `git`) у `tools/`
лише в ядрі — за зразком наявного тесту «кожному `Remove-KitDirectory` передує `Assert-SafeWorkPath`».
Тест ядра на кириличний шлях (вивід без вісімкових кодів) і на збій без `-AllowFail` (виняток з
текстом stderr). Тест контракту D3 — на кожен код хоча б однією командою, з контролем, що вміє
впасти.

## 3. Інваріанти (не змінюються)

- Поведінка команд сховища — та сама, крім кодів `2`/`3` → `4` і рядків `ERROR`/`next:`.
- П25 і #34: рекурсивне видалення лише через `Remove-KitDirectory` після `Assert-SafeWorkPath`
  (чи `Assert-KitBuildPath`).
- Гілки `storage/*` пише лише `kit sync`; `V8KIT_SYNC=1` — як зараз.
- Kit Уніку не викликає; єдиний запуск раннера — `tools/lib/Runner.psm1`.
- Байти, які kit порівнює чи хешує (дерево, `ls-tree`, `cat-file`, діфи для `verify`/`adopt`/
  `TreeCompare`), не змінюються від переходу на ядро: кодування ядра не перекодовує бінарний вивід.

## 4. Поза обсягом

Перейменування команд kit; зміна логіки `sync`/`verify`/`adopt`; `Integration`-набір; нестабільні
тести під паралельним прогоном (#50) — окремо.

## 5. Відкриті питання — автор плану вимірює, не припускає

1. Хто читає коди виходу: `grep -rn 'ExitCode\|LASTEXITCODE\|код виходу\|exit code'` у `hooks/`,
   `skills/`, `templates/`, `tools/`, тестах — повний перелік без `head`.
2. Чи кожна обгортка зводиться до ядра без зміни байтів виводу. Особливо `Invoke-KitGitProcess`
   (NUL-записи, сирий stdout для порівняння дерев): ядро мусить мати режим сирих байтів, якщо
   текстовий режим їх змінює. Виміряти на кириличних і бінарних шляхах.
3. Чи не конфліктує ім'я `kit` у `PATH` (інші `kit`/`kit.exe` на машині; Bash і PowerShell).
4. Час старту хука старту сесії після D1 (стеля 15 с для `session-check`) — не гірший за поточний;
   виміряти до і після.
5. Чи ловить AST-тест D5 усі форми запуску git у коді (`&`, `Start-Process`, `ProcessStartInfo`,
   рядок-ім'я в змінній) — контроль на мутації.

## 6. Перевірка й ризик

Ризик задач: диспетчер і ядро git — `risky` (два рев'ю: відповідність і адверсарне з вимірами);
перехід текстів скілів і шаблонів — `standard`. Повний прогін без `Integration` у фіналі блоку;
`-Only` зачеплених у задачах. Версія — наступний patch лінії 1.6 (рішення власника), запис
`CHANGELOG.md` з чеклістом споживача (нова форма виклику `kit <команда>`, коди `4`).

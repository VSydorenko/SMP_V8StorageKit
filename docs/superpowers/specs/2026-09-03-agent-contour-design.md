**Дата:** 2026-09-03

## 0. Що ця спека вирішує

Плагін `v8storagekit` 0.6.0 — конвеєр «сховище ↔ git» з одним розширенням на продукт,
одним `storage.json`, реплеєм у поточну гілку і скриптом, який розкочує розширення в базу
людини. Це працювало для одного сценарію — дзеркалити сховище розширення в git заради
«хто змінив рядок».

Роль git змінилась: тепер у проєкті працює **агент як окремий розробник** — зі своєю
базою, своєю гілкою, своїм результатом у вигляді зібраних артефактів. Сховище лишається
істиною в останній інстанції, git — робочим середовищем агента, а Unica — основним
інструментом. Kit має закривати рівно те, чого Unica не вміє: сховища, дамп із живої бази,
розгортання бази з `.dt`, звірку git зі сховищем, і обв'язку життєвого циклу задачі.

Ця спека описує **цільовий стан** — модель даних, модель git, команди, скіли, межі — і
розбиває його на блоки для планів реалізації.

## 1. Принципи

1. **Сховище — істина.** Робочі бази клієнтів і розширення підключені до сховищ; це
   запобіжник від несанкціонованих змін, і він лишається. Git ніколи не претендує на роль
   істини; коли git попереду сховища — це видимий борг «застосувати залишок», а не
   помилка.
2. **Unica — основний інструмент; kit доповнює.** Редагування, валідація, збірка `.cf`/`.cfe`,
   тести, синтаксис-контроль — Unica. Kit не дублює жодної її операції.
3. **Агент працює у своїй базі і ніколи не пише в базу людини.** Базу агента можна зламати
   й розгорнути знову. Базу людини kit лише читає (дамп), і лише на явне прохання.
4. **Результат агента — зібрані файли.** `.cf`, `.cfe`, `.epf` у `build/artifacts/`. Застосовує
   людина, у своїй базі, своїм Конфігуратором; звітує агенту.
5. **Структура репозиторію описується даними, не умовами.** Скіли й скрипти ітерують
   маніфест; слів «клієнт» і «продукт» у їхній логіці немає — це метадані для назв.
6. **Байти в git — байти платформи.** Дерево вихідників канонізується через платформу
   перед будь-яким порівнянням; політика `-text` без винятків
   (`2026-08-31-unica-canon-transition-design.md` §5.2-5.3).
7. **Kit не покладається на git-конфіг машини споживача.** Кожна залежність від
   налаштування git — `core.autocrlf`, `core.quotepath`, `core.hooksPath`, `core.eol` — або
   виставляється по-викличну, або перевіряється явно і повідомляється. Порада споживачу в
   документації — не заміна. Правило для рев'юера: `-c core.quotepath=false` — на
   **кожному** git-виклику, що читає або друкує шляхи, без винятків; `-z` **додатково** —
   там, де викликач ділить вивід на записи **і** запис міг створити не kit (довільний ref,
   довільна робоча копія). Причина розділення: `quotepath` керує лише байтами ≥ `0x80`, а
   `"`, `\` і перевід рядка git C-квотує завжди — це закриває лише `-z`, і потрібен він
   рівно там, де записи чужі.
   Підстава: `core.quotepath=true` (типове) екранує неASCII-імена вісімково, і `check`
   давав 240+ хибних «файл поза шляхом джерела» на будь-якому репозиторії 1С із
   кириличними об'єктами; дефект був **замаскований** локальним `core.quotepath=false` у
   `.git/config` одного репозиторію (BankExchange, порада зі старого `repo-migration`) і
   сплив лише на другому. Той самий клас, що й фільтр eol-попереджень у 0.6.0: поведінка,
   яка залежить від того, на чиїй машині запускають.

## 2. Модель даних

### 2.1 Воркспейс і репозиторій

**Воркспейс** — одна базова конфігурація плюс N її розширень. Це рівно `v8project.yaml`
Unica: один source-set `CONFIGURATION` і N `EXTENSION` (плюс за потреби
`EXTERNAL_DATA_PROCESSORS`). Воркспейс — підтека репозиторію з власним `v8project.yaml`;
`cwd` для Unica — ця підтека (дослідження, п. 6: корінь воркспейсу визначає лише `cwd`,
кеш лягає в `<воркспейс>/.build/unica`, вкладеність штатна).

**Репозиторій** — M воркспейсів плюс спільне.

Обидва типи репозиторіїв — одна форма з різною кардинальністю:

| | Воркспейсів | Розширень у воркспейсі | Спільне |
|---|---|---|---|
| Продукт (BankExchange, SimplyConnect) | по одному на конфігурацію (УНФ UA, УНФ RU, БАС) | 1 | `epf/` |
| Клієнтська база | 1 | кілька: адаптація + наші рішення | — |

Спільний `epf/` — **власний воркспейс** із source-set `EXTERNAL_DATA_PROCESSORS`. Шлях
`../epf/src` зсередини іншого воркспейсу Unica відхиляє (дослідження, п. 1:
`source_roots.rs:145-168`, `source_set.path_unsafe`, `ready=false`).

### 2.2 Іменування

- **Ім'я теки воркспейсу = ім'я воркспейсу.** Для воркспейсу з одним розширенням це ім'я
  розширення (конвенція 0.6.0 зберігається — мігровані репозиторії відповідають). Для
  клієнтського — ім'я бази/клієнта.
- **Ім'я розширення** живе рівно в трьох місцях, які мусять збігатись: `name:` EXTENSION
  source-set у `v8project.yaml`, `<Name>` у `cfe/…/Configuration.xml`, ключ у `sources:`
  маніфесту. Сторонній v8-runner виводить ім'я з `name:` source-set (`unica-contract.md`
  B5-B6).
- Кириличні імена тек — прийнятий ризик (`follow-ups.md` §10); `onboarding` попереджає
  вголос.

### 2.3 Розкладка репозиторію — два живі приклади

Обидва типи репозиторіїв мають **одну форму**; різняться лише кількість воркспейсів,
кількість розширень усередині й те, чи закомічений `cf/src`. Позначки: **[git]** —
закомічено, **[ign]** — гітігноровано.

**Продуктовий репозиторій** (`SMP_BankExchange`: одне рішення, три варіації, спільні
обробки):

```
SMP_BankExchange/
├── .claude/
│   ├── settings.json                [git] дозволи + хук SessionStart (§7); кладе onboarding з templates/
│   └── hooks/session-start.ps1      [git] шим хука (§7)
├── .githooks/                       [git] pre-commit, pre-merge-commit — захист storage/* (§3.3)
├── .gitattributes                   [git] -text на всіх деревах платформи
├── .gitignore                       [git] build/  .build/  **/cf/**  *.local.yaml
├── AUTHORS                          [git] користувач сховища → автор git
├── CLAUDE.md                        [git]
├── v8storagekit.yaml                [git] МАНІФЕСТ: product: BankExchange, чотири воркспейси (§2.4)
├── v8storagekit.local.yaml          [ign] дев-бази, .dt для бази агента, перевизначення шляхів (§2.5)
├── build/                           [ign] теки kit
│   ├── sync/<джерело>/              worktree гілки storage/<джерело> + тимчасова ІБ
│   └── artifacts/                   зібрані .cf/.cfe/.epf для людини
│
├── SMP_BankExchange_SMB/            воркспейс 1 — УНФ UA
│   ├── v8project.yaml               [git] Unica: base → cf/src; SMP_BankExchange_SMB → cfe/src;
│   │                                      infobase.connection: File=build/ib
│   ├── cf/
│   │   ├── README.md                [git] тримає теку в git
│   │   └── src/                     [ign] truth: vendor — дамп УНФ з дев-бази
│   ├── cfe/src/                     [git] truth: storage — наше розширення
│   ├── build/ib/                    [ign] БАЗА АГЕНТА; workPath Unica — kit сюди не пише
│   └── .build/unica/                [ign] кеш Unica
│
├── SMP_BankExchange_SMBru/          воркспейс 2 — УНФ RU, та сама форма
├── SMP_BankExchange_ACC/            воркспейс 3 — БАС Бухгалтерія, та сама форма
└── epf/                             воркспейс 4 — спільні обробки для всіх трьох
    ├── v8project.yaml               [git] external-processors → src
    └── src/                         [git] truth: git
```

Гілки: `main`; `storage/SMP_BankExchange_SMB`, `storage/SMP_BankExchange_SMBru`,
`storage/SMP_BankExchange_ACC`; `feature/<задача>`. Для `cf/src` гілки немає (`vendor`), для
`epf/` немає (`git`).

**Клієнтський репозиторій** (умовний `Alpenpharma`: одна база, одна конфігурація, кілька
розширень):

```
Alpenpharma/
├── .claude/  .githooks/  .gitattributes  .gitignore  AUTHORS  CLAUDE.md     — те саме
├── v8storagekit.yaml                [git] client: Alpenpharma, один воркспейс
├── v8storagekit.local.yaml          [ign]
├── build/                           [ign]
└── Alpenpharma_UNF/                 ЄДИНИЙ воркспейс: тека = ім'я бази, не розширення
    ├── v8project.yaml               [git] base → cf/src; Адаптация → cfe/Адаптация/src;
    │                                      SMP_BankExchange_SMB → cfe/SMP_BankExchange_SMB/src; …
    ├── cf/src/                      [git] truth: storage — конфігурація клієнта З ІСТОРІЄЮ
    ├── cfe/
    │   ├── Адаптация/src/           [git] truth: storage — сховище адаптації
    │   ├── SMP_BankExchange_SMB/src/[git] truth: storage — наше спільне сховище, user: Alpenpharma
    │   └── SMP_Delivery_SMB/src/    [git] truth: storage
    ├── build/ib/                    [ign]
    └── .build/unica/                [ign]
```

Гілки: `main`; `storage/base`, `storage/Адаптация`, `storage/SMP_BankExchange_SMB`,
`storage/SMP_Delivery_SMB`; `feature/<задача>`.

**Ключі джерел із `truth: storage` унікальні в межах репозиторію** — гілка називається
`storage/<ключ>`, і два воркспейси з однаковим ключем зіткнулись би. `check` це перевіряє.
У продуктовому репо `base` повторюється в кожному воркспейсі, але він `vendor` і гілки не
має; у клієнтському воркспейс один. Репозиторій із двома клієнтськими базами мусить
назвати їхні `CONFIGURATION` source-set-и по-різному (`name:` для конфігурації Unica не
обмежує).

Три теки з іменем `build` — три різні власники, як і задокументовано в
`docs/storage-and-git.md`: кореневий `build/` — kit, `<Воркспейс>/build/` — Unica
(`workPath`), `<Воркспейс>/.build/` — кеш Unica. Kit не пише в `workPath` Unica: база
агента там оголошена в `v8project.yaml`, але наповнює її `operation=build`, а kit лише
викликає платформу проти неї (`canon`, `provision` з `.dt`).

Розкладка `<тип>/src` (а не `src/<тип>`) зберігається — обґрунтування в
`2026-08-31-…-design.md` §3.2. Для воркспейсу з кількома розширеннями — `cfe/<Ім'я>/src`;
для одного — `cfe/src` лишається чинним (шлях береться з `v8project.yaml`, kit його не
припускає).

### 2.4 Маніфест `v8storagekit.yaml`

Один файл у корені репозиторію. **Не дублює структуру** — шляхи, типи, склад воркспейсів
описані в `v8project.yaml`; маніфест посилається на source-set-и за іменем і додає те,
чого Unica не знає.

```yaml
version: 1                          # версія схеми маніфесту
product: BankExchange               # АБО client: <назва>. Метадані: імена артефактів, звіти.

workspaces:
  - path: SMP_BankExchange_SMB      # тека з v8project.yaml
    sources:                        # ключ = name: source-set у v8project.yaml
      base:
        truth: vendor               # не наше, у git не потрапляє; локально — дамп
        dump: { from: devUNF }      # ключ підключення в local overlay
      SMP_BankExchange_SMB:
        truth: storage
        storage:
          path: 'R:\СховищаРозширень_1С\СМП_BankExchange_SMB'
          user: gitbot              # типово gitbot; пароль порожній за конвенцією

  - path: SMP_BankExchange_SMBru
    sources:
      base: { truth: vendor, dump: { from: devUNFru } }
      SMP_BankExchange_SMBru:
        truth: storage
        storage: { path: 'R:\СховищаРозширень_1С\СМП_BankExchange_SMBru' }

  - path: epf
    sources:
      external-processors: { truth: git }
```

Клієнтський репозиторій — той самий словник:

```yaml
version: 1
client: Alpenpharma
workspaces:
  - path: Alpenpharma_UNF
    sources:
      base:
        truth: storage              # конфігурація змінена і під сховищем — з історією
        storage: { path: 'R:\СховищаКонфігурацій_1С\Alpenpharma' }
      Адаптация:
        truth: storage
        storage: { path: 'R:\СховищаРозширень_1С\Alpenpharma_Адаптация' }
      SMP_BankExchange_SMB:
        truth: storage              # наше рішення зі спільного сховища
        storage:
          path: 'R:\СховищаРозширень_1С\СМП_BankExchange_SMB'
          user: Alpenpharma         # користувач сховища за іменем бази
```

**Словник `truth`:**

| `truth` | Істина | Хто наповнює git | У git | Гілка `storage/` |
|---|---|---|---|---|
| `storage` | сховище конфігурацій | `sync` | так, з історією | так |
| `dump` | жива база, лише поточний стан | `dump` | так, без історії | ні |
| `vendor` | чужа конфігурація | `dump` | **ні** (гітігнорено) | ні |
| `git` | зовнішнього джерела немає | людина й агент | так | ні |

Необов'язковий кореневий ключ **`mainBranch`** (типово `main`) називає головну гілку —
`SMP_OnlineExchange` живе на `master`. Усі згадки `main` у §3 читати як «гілка з
`mainBranch`».

Маніфест і `v8project.yaml` — YAML із flow-стилем (`{ truth: vendor, dump: { from: … } }`),
регексом чесно не розбирається. Kit читає обидва модулем **`powershell-yaml`** (PSGallery,
`Install-Module powershell-yaml -Scope CurrentUser`). Це залежність категорії «Конвеєр» у
`check-environment.ps1`; префлайт без модуля зупиняється з цією командою. Вендорити
YamlDotNet у git-розповсюджуваний плагін або писати власний парсер підмножини — відхилено:
перше тягне бінарник у репозиторій, друге повертає крихкість, яку ми щойно прибрали.

**Доступ до сховища — вимога до сховища, не факт про нього.** Kit паролів не зберігає й
не підбирає. Для кожного сховища, яке kit читає, людина або заводить у ньому користувача
`gitbot` (лише читання, порожній пароль — типове значення `storage.user`), або вказує
наявного користувача через `storage.user` у маніфесті; якщо в того користувача є пароль —
він живе **лише** в локальній накладці (`storages.<ключ>.password`, §2.5), ніколи в
маніфесті. Відмова автентифікації — зупинка з назвою сховища й користувача, без спроб
підібрати. Це записано після спайку B2: на сховищі конфігурації `gitbot` не існував
(§14).

`AUTHORS` (мапінг «користувач сховища → автор git») лишається файлом у корені, як і
сьогодні.

### 2.5 Локальна накладка `v8storagekit.local.yaml`

Гітігнорована. Дзеркалить структуру маніфесту лише локальними ключами. **Kit не ділить
файлів з Unica** — це прибирає клас дефектів «local overlay перекриває `infobase`»
(`unica-contract.md` A6) у корені.

```yaml
infobases:                          # живі бази, з яких kit ЛИШЕ читає
  devUNF:
    connection: 'Srvr="VSDEV";Ref="SMP_UNF_sydorenko";'
    user: 'Администратор'
  devUNFru:
    connection: 'Srvr="VSDEV";Ref="SMP_ruUNF_sydorenko";'
    user: 'Абдулов (директор)'

storages:                           # локальне для сховищ: шлях на цій машині, облікові дані
  SMP_BankExchange_SMB: 'D:\mirror\СМП_BankExchange_SMB'     # коротка форма — лише шлях
  base:                             # повна форма — коли користувач сховища має пароль
    path: 'R:\СховищаКонфігурацій_1С\Alpenpharma'
    user: 'Сидоренко'
    password: '…'                   # лише тут; у маніфесті паролів не буває

workspaces:
  SMP_BankExchange_SMB:
    agentBase:
      template: 'D:\dumps\UNF_demo.dt'   # розгорнути з .dt; без ключа — порожня через Unica init
```

**Межа з Unica:** `v8project.local.yaml` — файл Unica. Kit **не бере з нього жодного
значення для власних сутностей** — дев-баз, сховищ, шаблонів `.dt`: усе це живе в
`v8storagekit.local.yaml`. Він може існувати рівно з однією метою — перевизначити базу
**агента** на серверну (`infobase.connection: 'Srvr=…'`), коли файлова не годиться.
Підключення до бази людини там не з'являється ніколи.

**Єдиний виняток — підключення до бази агента.** `canon` і `provision` мусять цілитись у ту
саму базу, яку наповнює `operation=build`, тож kit визначає її **так само, як Unica**:
`infobase.connection` з `v8project.local.yaml`, якщо файл є, інакше з закоміченого
`v8project.yaml`. Це не «kit читає конфіг Unica», а «kit іде за вказівником Unica на базу
Unica». Дублювати це підключення в накладці kit не можна — розійдуться.

`check` читає `v8project.local.yaml` **для аудиту**: якщо там є `infobase.connection`, який
збігається з будь-яким підключенням із `infobases:` накладки kit, — це база людини під
ключем Unica, і `check` зупиняється з поясненням.

**Як kit визначає `truth` і базу агента — питає.** Ні `truth` джерела, ні тип бази агента
не виводяться з файлової системи: відрізнити «наша конфігурація під сховищем» від «чужа,
беремо дампом» може лише людина. Тому скіл `onboarding` для кожного джерела без `truth`
ставить питання з варіантами (`storage` / `dump` / `vendor` / `git`, з поясненням наслідків
для git і для гілок) і записує відповідь у маніфест; скіл `provision`, коли в накладці немає
`agentBase.template` і в `v8project.local.yaml` немає серверного підключення, питає, яку
базу розгортати (порожню / з конкретного `.dt` / серверну з підключенням від розробника),
і записує вибір у `v8storagekit.local.yaml`. Мовчазних дефолтів для цих двох рішень немає.

`Read-V8LocalConnection` переписується на читання `v8storagekit.local.yaml`; запобіжник на
неоднозначність лишається (два `connection:` під одним ключем — зупинка).

### 2.6 Політики git per source

- `truth: vendor` → шлях у `.gitignore` **явним рядком під фактичний шлях** з
  `v8project.yaml` (`SMP_X/cf/src/`), який пишуть `onboarding`/`migrate`. **Загальних масок
  за іменем теки немає** — стара `**/cf/**` з 0.6.0 вилучається з шаблону, бо та сама
  тека `cf/src` у клієнтському репозиторії (`truth: storage`) лежить у git, і загальне
  правило робило б кожен клієнтський онбординг помилкою `check`. `check` перевіряє через
  `git check-ignore`. `-text` для `vendor` **не** перевіряється — гітігнороване дерево в
  git не потрапляє, і `check-attr` на ньому дає `text: auto`, що не є помилкою.
- усі дерева платформи, **що потрапляють у git** (`truth ∈ {storage, dump, git}`:
  `cf/src` у клієнтському випадку, `cfe/**/src`, `epf/src`) → `-text` у `.gitattributes`;
  `check` перевіряє через `git check-attr` (`Test-GitTextPolicy` уже є).
- **зворотна перевірка:** дерево з `truth ∈ {storage, dump, git}` **не** має бути
  гітігнорованим — надто широке правило `.gitignore` (наприклад `**/src/**`) тихо
  викинуло б вихідники з git, і `git status` цього не показав би. `check` перевіряє через
  `git check-ignore` з очікуванням «не ігнорується».
- `onboarding` дописує рядки під фактичні шляхи з `v8project.yaml`, а не покладається на
  шаблонні `**/cfe/src/**`.

## 3. Модель git

### 3.1 Три ролі гілок

```
storage/X    S1 ──── S2 ──── S3 ──── S4          дзеркало сховища X: тільки sync, лише дописується
              \        \              \
main    ──────M1───────M2────[PR F]───R──►       PR-и + звірочні коміти
                         \          /
F (агент)                 A1──A2──A3              гілка задачі; живе до PR
                               ↑
                          merge storage/X  (reconcile)
```

**`storage/<ім'я джерела>`** — по одній на кожне джерело з `truth: storage`. Orphan-гілка,
дерево містить **лише шлях цього джерела**. Один коміт на версію сховища: автор і дата зі
звіту сховища через `AUTHORS`, повідомлення — коментар версії, трейлери:

```
Storage-Source: SMP_BankExchange_SMB
Storage-Version: 47
Extension-Version: 1.2.3        (для конфігурації — Config-Version:)
Storage-User: Абдулов
```

Ніхто, крім `sync`, туди не пише. Історія не переписується.

**`main`** — історія проєкту: злиття PR-ів плюс **звірочні коміти** для того, що прийшло у
сховище повз агента. Реплей у `main` **не йде**.

**`F`** (гілка задачі) — від `main`. На «поклав частину в сховище» — `merge storage/X` у `F`.
Не rebase, не re-derive: історія гілки ціла, конфлікти семантичні (після канонізації) і
розв'язуються агентом.

### 3.2 Стан синхронізації виводиться з git

«Остання залита версія джерела X» = трейлер `Storage-Version:` останнього коміту
`storage/X`. Файлу стану немає. `storage.json` вилучається.

- Порожня гілка → «останньої немає» → реплеїти всі версії зі звіту.
- Нумерація сховища може починатись з будь-якого числа й мати пропуски: `sync` бере
  **перелік зі звіту з версіями, більшими за останню**, а не діапазон (ранбук, §5).
- `check` вимагає: кожен коміт `storage/*` має трейлер, значення строго зростають, батьків
  **не більше одного** (кореневий коміт orphan-гілки їх не має; merge-коміт має два — і
  саме він заборонений). Інформаційно повідомляє, якщо мінімум у звіті > остання + 1
  (сховище оптимізували до того, як ми забрали проміжні версії).

### 3.3 Захист гілок `storage/*`

Три шари, кожен ловить своє:

1. **Запис лише через worktree.** Гілка ще не існує (перший `sync` джерела) —
   `git worktree add --orphan -b storage/<ім'я> build/sync/<ім'я>/wt` (git ≥ 2.42; на
   машині 2.53); існує — `git worktree add build/sync/<ім'я>/wt storage/<ім'я>`. `sync`
   вивантажує туди, комітить там, прибирає worktree. Робоча копія й поточна гілка не
   торкаються. Вимога «чиста робоча копія перед `-Apply`» зникає.
2. **Локальний хук, що відмовляє.** Версійована тека `.githooks/` з `pre-commit` і
   `pre-merge-commit`; `onboarding` вмикає `git config core.hooksPath .githooks`. Хук:
   якщо `HEAD` → `refs/heads/storage/*` і немає `V8KIT_SYNC=1` — відмова з поясненням.
   Це запобігання: випадковий `git checkout storage/X` + коміт чи `merge` у **головній
   робочій копії** не пройде.

   **Межа шару 2 — він не суцільний.** Відносний `core.hooksPath` git розв'язує від
   кореня **того worktree, у якому працює**; в orphan-worktree дзеркала теки `.githooks/`
   у дереві немає (там лише шлях джерела), тож хук там **не спрацьовує взагалі**.
   Встановлено фінальним рев'ю B1: первинна проба дала хибний результат, бо `git add -A`
   на `storage/X` затягнув `.githooks` у дерево гілки. Тобто шар 2 накриває головну
   робочу копію і будь-який worktree, чиє дерево містить `.githooks/`; worktree `sync` —
   ні. `V8KIT_SYNC=1` у `sync` — **контракт, не механізм**: виставляється завжди, щоб хук
   пропустив коміт там, де він є. Дірка вузька — worktree дзеркала існує лише на час
   `sync` під `build/` — і закривається шаром 3.
3. **`check` як аудит** — інваріанти з §3.2. Ловить те, що просочилось повз хук: клон без
   `core.hooksPath`, і коміт у worktree дзеркала, де хука немає. Повнота захисту лежить
   на цьому шарі, не на другому.

Варіант `refs/storage/*` (не гілки) розглянуто й відхилено: сильніший захист, але GitHub
не покаже їх як гілки, і «хто змінив рядок» лишиться консольним.

### 3.4 Як `storage/X` зливається у `main` і `F`

Git зливає **зміни від спільного предка**, а не дерева. `storage/X` ніколи не торкалась
файлів поза своїм шляхом, тому вони не зачіпаються, хоч `main` у сто разів більший.

- **Перше злиття** — `--allow-unrelated-histories` (orphan без спільної історії): об'єднання,
  файли `main` лишаються, файли сховища додаються. Робить `sync` при першому реплеї.
- **Наступні** — звичайні тристоронні: спільний предок = вершина `storage/X` на момент
  попереднього злиття; приходять лише нові версії; видалені у сховищі об'єкти видаляються.
- У `F` — так само, `merge storage/X` під час `reconcile`.
- Кілька джерел — незалежні orphan-гілки з неперетинними шляхами.
- **Куди фізично робиться злиття в `main`** (перше злиття в `sync`, звірочний коміт у
  `verify -Apply`): якщо `HEAD` = `main` і робоча копія чиста — злиття на місці; якщо `HEAD` =
  `main`, але копія брудна — зупинка з поясненням, у брудний `main` не зливаємо; якщо
  `HEAD` — інша гілка (звичайний випадок: людина на `F`) — тимчасовий worktree
  `build/sync/_main/wt` на `main`, злиття там, worktree прибирається. Git не дає другого
  worktree на вже вибрану гілку, а `update-ref` під вибраним `main` лишив би індекс
  застарілим — звідси саме така розвилка.

### 3.5 `verify` — інваріант «`main` ≡ сховище»

Порівнює дерево `main` (або будь-якого ref) за шляхом джерела з **канонічним дампом зі
сховища** на версії з трейлера. Джерело незалежне — сховище, не власна робоча копія
(знахідка BankExchange: класичний round-trip годує платформі те, що сам перевіряє).

Три результати:

| `verify` | Означає | Дія |
|---|---|---|
| рівні | усе застосовано, дерево канонічне | нічого |
| `main` попереду | частина роботи ще не у сховищі | **попередження**: артефакт у `build/artifacts`, застосуйте залишок |
| сховище попереду | у сховищі є щось повз агента | звірочний коміт у `main` = `merge storage/X` |

Класифікація розбіжностей по файлах (знахідка BankExchange): побайтово рівні /
«лише CR» (зіпсована політика тексту) / змістовна (git розійшовся зі сховищем) /
тільки в дампі / тільки в дереві. Файли, позначені `binary` у `.gitattributes`, —
**лише побайтово**, без CR-нормалізації. `ConfigDumpInfo.xml` виключається завжди.
**Яка саме версія.** `verify <ref>` порівнює `<ref>` з дампом на версії з трейлера
**останнього коміту `storage/X`, досяжного з `<ref>`** — тобто `git merge-base <ref>
storage/X`. Для `verify storage/X` це вершина гілки (перевірка канонічності самого
дзеркала); для `verify main` чи `verify F` — остання версія, яку `<ref>` уже злив. Не
вершина `storage/X` і не максимум у сховищі: інакше до двох діагнозів долучився б третій
(«є неперенесені версії»), і відповідь стала б неоднозначною. Версії, які є на
`storage/X` після merge-base, `verify` називає окремим інформаційним рядком. Якщо
merge-base порожній (`<ref>` ніколи не зливав `storage/X`) — зупинка: спершу `sync`.

### 3.6 Канонізація дерева агента

Агент, що редагує через Unica, ніколи не має байт-канонічного дерева. Перед `verify`,
`reconcile` і PR: `operation=build` (Unica) у базу агента → `/DumpConfigToFiles` (kit,
платформа) назад у дерево. Після цього обидва боки порівняння у форматі платформи, і
будь-яка різниця семантична. Це команда `canon`.

Unica `dump` не використовується: синхронний full dump має названий ризик публікації без
доведеної межі отримання результату (`unica-contract.md`, A5 і B8), а асинхронний та
зовнішні маршрути закриті окремими гардами (B8, примітка). Kit же кличе платформу
напряму — і тримає повний контроль над тим, куди й що вивантажено.

## 4. База агента

- Оголошена в закоміченому `v8project.yaml`: `infobase.connection: 'File=build/ib'`.
  Відносний шлях розв'язується від теки конфіга (`v8project.md:61-63`).
- **Порожня** — `operation=init` Unica, далі `operation=build` з джерел.
- **З `.dt`** (`agentBase.template` у local overlay) — платформа:
  `CREATEINFOBASE File="<воркспейс>/build/ib"; /UseTemplate "<файл.dt>"` (дослідження,
  п. 2: `runtime-build.md:71,93`). Unica цього не вміє — `operation=init` приймає лише
  `operation, config, workdir`. Далі `operation=build`.
- **Серверна** — людина створює в кластері, дає підключення у `v8project.local.yaml`
  (`infobase.connection: 'Srvr=…'`). `CREATEINFOBASE Srvr=…;Ref=…; /UseTemplate` —
  спайк на потім: параметри СУБД у рядку з'єднання не задокументовані.
- Базу агента можна знести й розгорнути знову будь-коли: `provision -Force`.

## 5. Команди kit

Один диспетчер `tools/kit.ps1 <команда>` зі спільним префлайтом. Команди — окремі модулі
`tools/commands/<назва>.psm1`, кожен тестується сам. Спільні параметри: `-RepoRoot`,
`-Workspace`, `-Source`, `-Apply`. `-Source` без `-Workspace` дозволений, якщо ключ
унікальний у маніфесті (для `truth: storage` — завжди, §2.3); інакше зупинка з переліком
воркспейсів, де він є.

Аргументи команди диспетчер перекладає в іменовані параметри: `-Ім'я значення` або
`-Ім'я:значення`. `-Ім'я` **без значення** означає `$true` лише коли параметр команди має
тип `[switch]`; для будь-якого іншого типу це зупинка (код `1`, таблиця нижче) з назвою
параметра, який потребує значення. Інакше `[int]$true` мовчки стає `1`, і `verify -Version`
без числа звірив би з версією 1.

**Префлайт** (кожна команда, крім самого `check`): кодування консолі UTF-8; маніфест
читається й проходить схему; кожен `workspaces[].path` існує і містить `v8project.yaml`;
кожен ключ `sources` є `name:` source-set у тому `v8project.yaml`; накладка, якщо є,
читається. Це перевірки, що коштують мілісекунди й без яких команда не має з чим
працювати. **Не** входять у префлайт (лише в повний `check`): інваріанти гілок `storage/*`
(обхід логу), `check-ignore`/`check-attr`, звірка `<Name>` у `Configuration.xml`, аудит
`v8project.local.yaml`, наявність хуків. Повний `check` викликається явно і в
`session-check`.

**Рівні `check` — за одним правилом.** `error` — суперечність **репозиторію**, видима з
будь-якої машини (розбіжність імен, гілка з merge-комітом, накладка не гітігнорована).
`warn` — стан **цієї машини** або ще не ухвалене рішення (шлях сховища недоступний —
рев'ю без доступу до сховищ законне, а помилку в маніфесті від відсутнього диска `check`
не відрізнить, її ловить перший `sync`; хуки не закомічені; джерело не заявлене).
Префлайт питає «чи можу працювати з описаним», `check` — «чи все описано і чи
несуперечливо».

Повний перелік інваріантів `check`, окрім названих у §2.2, §2.5, §2.6, §3.2, §3.3, §7
(знайдені живим прогоном на BankExchange і SimplyConnect під час B1):

| Інваріант | Рівень | Наслідок мовчання |
|---|---|---|
| source-set у `v8project.yaml`, не заявлений у маніфесті | warn | `sync` ніколи не дзеркалить це розширення, гілки `storage/` немає, ніхто не повідомляє; `truth` для нього — рішення людини, тому не error |
| `.githooks/` є на диску, але не закомічений | warn | клон не дістає захисту `storage/*`; «застейджено до першого коміту» — не знахідка |
| `v8storagekit.local.yaml` **не** гітігнорований (перевіряється `check-ignore` на шлях, незалежно від існування файлу) | **error** | накладка несе підключення й користувачів, репозиторій публічний — перший `git add -A` її застейджить |

| Команда | Що робить | Платформа | Мутує |
|---|---|---|---|
| `check` | маніфест ↔ `v8project.yaml` ↔ `.gitignore` ↔ `.gitattributes` ↔ `Configuration.xml` ↔ інваріанти `storage/*` ↔ хуки | ні | ні |
| `session-check` | дешевий сигнал: нові версії у сховищах? `main` розійшовся зі `storage/*`? | ні | ні |
| `sync` | для кожного `truth: storage`: реплей нових версій у `storage/<ім'я>` через worktree; перше злиття в `main` | так | git |
| `dump` | для кожного `truth: dump\|vendor`: дамп із живої бази за local overlay; розпізнає «відкрито в Конфігураторі» | так | файли |
| `verify` | §3.5 | так | ні (звірочний коміт — окремо, `-Apply`) |
| `canon` | §3.6 | так | файли дерева |
| `provision` | §4 | так | база агента |
| `build` | `.epf` через платформу (як сьогодні) у `build/artifacts/`, і друкує вміст цієї теки. `.cf`/`.cfe` — **не kit**: скіл кличе `operation=make` Unica з `output=<абсолютний шлях>/build/artifacts/<Ім'я>.cfe` напряму, копіювання немає. Якщо Unica відмовить у шляху поза воркспейсом (не перевірено) — `output=<воркспейс>/build/artifacts/…`, і `build` забирає звідти | так | файли |

**Коди виходу `kit.ps1`** — одна таблиця для всіх команд, визначена за змістом, а не за
назвою команди; нова команда бере код звідси, а не вигадує свій. Коди `2` і `3` — це
**задумані** результати, після яких рішення лишається людині; `1` — команда до задуманого
результату не дійшла, і що вона встигла зробити, каже лише текст.

| Код | Зміст | Хто повертає |
|---|---|---|
| `0` | виконано; нічого не вимагає уваги | усі; `check` лише з `warn` — теж `0` (warn — стан машини, автоматику не блокує) |
| `1` | зупинка: `throw` у команді, провал префлайту, невідома команда, нерозпізнаний аргумент, `check` з `error` | усі. `check` з `error` — той самий клас, що й провал префлайту: префлайт і є `check`-ом на ходу, і одна суперечність має давати один код |
| `2` | стан змінено частково; зроблене лишається, решта — рішення людини | `sync`: дзеркало `storage/*` оновлено, злиття в `main` не виконано (конфлікт) |
| `3` | нічого не змінено, репозиторій несуперечливий, але є що робити | `verify`: `ref-ahead`/`storage-ahead`/`mixed`; `session-check`: у сховищі є нові версії (зокрема дзеркала ще немає) або `storage/*` не злиті в `main` |

`session-check` розрізняє два «не знаю» за тим самим правилом, що й рівні `check`:
**сховище недоступне** з цієї машини — стан машини (warn), рядок «недоступне» з порадою
перевизначити шлях у накладці, код не піднімає; **git не відповів** на наявній гілці
(`log`, `rev-list`) — це сам репозиторій, і `check` на тому ж місці зупиняється з `1`.
Команда не кидає виняток, дописує звіт по решті джерел і завершується `1`, бо `0`
означало б «дзеркало синхронне». Пріоритет кодів для команди з кількома джерелами: `1`,
якщо хоч одне не прочитано; інакше `3`, якщо хоч один сигнал; інакше `0`.

Диспетчер сам повертає лише `0` і `1`: код команди, що відпрацювала, передає як є, а
будь-який `throw` до або всередині команди перекладає в `1` (у B2 — `2`, що злипалось із
частковим успіхом `sync`; виправляє B3).

**Розпізнавання «база зайнята»** (дослідження, п. 4): тексти з ресурсів платформи
«Ошибка блокировки информационной базы для конфигурирования… уже открыта
Конфигуратором», «Не удалось монопольно заблокировать информационную базу» і
українські/англійські варіанти → зупинка з порадою «закрийте Конфігуратор», не сире
повідомлення. Файли `.cfl` індикатором не є (лишаються після закриття). Для серверних
баз — опційно `rac session list`, якщо піднятий `ras`.

**`session-check`** (дослідження, п. 5): для кожного джерела `truth: storage` — максимальний
mtime файлів під `<сховище>\data\objects\**` проти дати автора останнього коміту
`storage/<ім'я>`. Новіші файли = у сховищі є нові версії. `mtime` файлу `1cv8ddb.1CD`
**не використовується** — він переписується при кожному інтерактивному підключенні
Конфігуратора. Плюс: чи є на `storage/<ім'я>` коміти, не злиті в `main`. Без платформи,
без ліцензії, один обхід каталогу.

**Вилучаються:** `load-ext.ps1` (агент не пише в базу людини; на базах під сховищем не
працює), `.cfe`-гілка `build.ps1`, `storage.json` і `SyncState.psm1`, `dump-config.ps1` як
окремий скрипт (стає `dump`), `storage-sync.ps1` (стає `sync`).

**Лишаються без змін по суті:** `StorageReport.psm1` (розбір MXL-звіту), `Authors.psm1`,
`PathSafety.psm1`, `GitOutput.psm1` (`Split-GitEolNoise`, `Test-GitTextPolicy`), `V8.psm1`
(запуск платформи, стаб).

## 6. Скіли плагіна

Зразок організації — superpowers: короткий вступний скіл, що вантажиться хуком старту
сесії; решта — по одному на намір, з `references/`. Скіли **читають маніфест** і
ітерують; жодного розгалуження за типом репозиторію.

| Скіл | Тригер | Що робить |
|---|---|---|
| `using-v8storagekit` | хук `SessionStart` | вступ: принципи §1, куди йти за яким наміром, результат `session-check` |
| `onboarding` | «підключи репозиторій / воркспейс / джерело» | **питає** `truth` для кожного джерела (§2.5) і, за потреби, шлях сховища й користувача; пише маніфест; `v8project.yaml`; `.gitignore`/`.gitattributes` під фактичні шляхи; `.githooks` + `core.hooksPath`; **`.claude/settings.json` з хуком і шим `.claude/hooks/session-start.ps1`** (§7); `check`; перший `sync`; `provision` |
| `sync` | «є нові версії», «перенеси зі сховища» | `session-check` → `sync` → злиття в `main` за потреби → звіт |
| `dump` | «вивантаж конфігурацію з бази» | `dump` для вибраного джерела; попередження про Конфігуратор |
| `reconcile` | «я поклав частину в сховище», «я закомітив у сховище» | `sync` → `canon` → `merge storage/* → F` → семантичний diff → звіт «що поглинуло сховище, що лишилось» |
| `finish` | «закриваємо задачу», «готуй PR» | `sync` → `canon` → `merge storage/* → F` → `verify F ↔ storage` → тести (Unica) → артефакти → PR |
| `provision` | «розгорни базу», «перезбери базу агента» | §4; коли тип бази не визначений накладкою — **питає** (порожня / `.dt` / серверна) і записує відповідь у `v8storagekit.local.yaml` |
| `verify` | «звір git зі сховищем» | §3.5, звіт із класифікацією |
| `migrate` | «переведи репозиторій на маніфест» | §9; після використання на всіх наявних репо — вилучити |

**Маршрутизація до Unica** (у `using-v8storagekit`): редагувати метадані/форми/СКД/ролі —
`unica.*`; валідувати — `cfe.validate`, `cf.validate`; накотити джерела в базу агента —
`operation=build`; зібрати `.cf`/`.cfe` — `operation=make`; тести — `operation=test`;
синтаксис — `operation=syntax`. Застосовні операції (`dryRun:false`) — лише на явне
прохання, з названим ризиком (`unica-contract.md`, таблиця кодів ризику).

`templates/settings.json` не дозволяє `unica_runtime_execute` без запиту — це не
змінюється.

## 7. Хук старту сесії — прив'язаний до репозиторію, не до плагіна

Хук у `hooks/hooks.json` плагіна спрацьовував би в **кожній** сесії, де плагін
встановлений, — і в не-1С проєктах цього оточення теж. Тому плагін **не оголошує хуків
узагалі**. Хук живе в `.claude/settings.json` **репозиторію** — файлі, який kit і так
роздає з `templates/settings.json`, — і з'являється лише там, де його поклав `onboarding`.

- `templates/settings.json` отримує блок `hooks.SessionStart` (matcher `startup|clear|compact`,
  `async: false`) з командою `pwsh -NoProfile -File .claude/hooks/session-start.ps1`.
  Відносний шлях — від кореня репозиторію, який і є `cwd` сесії.
- `.claude/hooks/session-start.ps1` — **шим**, закомічений у репозиторій (`onboarding` кладе
  його з `templates/hooks/`). Він не містить логіки: читає
  `~/.claude/plugins/installed_plugins.json`, знаходить `installPath` плагіна
  `v8storagekit@smp-v8storagekit` (kit уже робить це для Unica —
  `Get-UnicaInstallation`), викликає `<installPath>/tools/kit.ps1 session-check -RepoRoot .`
  і друкує `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"…"}}`
  (формат підтверджений дослідженням, п. 3). Плагіна в реєстрі немає — друкує нічого,
  код 0.
- Шим **завжди** виходить з кодом `0` — усе, що має побачити агент, іде через
  `additionalContext`. Код `kit session-check` формує лише текст: `0` і `3` (§5) — вивід
  як є; `1` — текст зупинки з позначкою, що перевірка **не відпрацювала**. Мовчання на
  `1` виглядало б як «нових версій немає».
- Bash-обгортки superpowers не потрібно: оточення Windows, `pwsh` викликається напряму, і
  `${CLAUDE_PLUGIN_ROOT}` не потрібен — шим сам знаходить плагін.
- Контекст: вміст `using-v8storagekit/SKILL.md` плюс результат `session-check`.
- Хук **нічого не змінює**: він повідомляє «у сховищі X ймовірно 2 нові версії — оновити?»
  і зупиняється. Рішення — людині, дія — скіл `sync`.
- Оновлення шима при зміні плагіна — через `check`: він порівнює закомічений шим із
  `templates/hooks/session-start.ps1` плагіна і повідомляє про розбіжність.

## 8. Життєвий цикл задачі

Пункти 9-13 вихідного потоку, зведені в послідовність:

1. **Старт сесії** → хук → `session-check` → «є нові версії?» → людина вирішує → `sync`.
2. **Початок задачі** → гілка `F` від `main` → `provision` (якщо бази агента немає) →
   `operation=build`.
3. **Робота** → редагування через Unica → `operation=build` у базу агента → тести
   (`operation=test`), синтаксис (`operation=syntax`) → ніколи в базу людини.
4. **Проміжний результат** → `canon` → `operation=make` / `build` → `build/artifacts/` →
   людина застосовує в своїй базі, звітує.
5. **Людина переносить частину / комітить у сховище** → каже агенту → `reconcile`:
   `sync` → `canon` → `merge storage/* → F` → семантичний diff → звіт залишку. Скільки
   завгодно раундів, історія `F` ціла.
6. **Закриття** → `finish`: `sync` → `canon` → `merge storage/* → F` → `verify -Ref F` →
   **гейт** → тести → артефакти → **PR `F → main`**. PR завжди повний: `main` не отримував
   роботи агента через реплей.

   **Гейт — людська розвилка з вимоги №13** («перевірити нові коміти у сховищах; в разі
   чогось суттєвого — повідомити»). `finish` зупиняється й доповідає, а далі йде лише за
   рішенням людини, якщо сталося будь-що з трьох:
   - `sync` під час `finish` приніс нові версії, і хоча б одна з них **торкається файлів,
     які змінила `F`** (перетин на рівні файлів) — це і є «суттєве»: чужа зміна в тому
     самому місці, де працював агент;
   - злиття `storage/*` у `F` дало конфлікти;
   - `verify -Ref F` показав «сховище попереду» або змішаний результат.

   Перетин рахується іменами файлів між комітами, без дампів: файли `F` — `git diff
   --name-only <mainBranch>...HEAD` **до** злиття `storage/*` у `F` (після злиття `HEAD`
   уже містить чужі зміни, і перетин став би тотожністю); файли нових версій — diff
   між вершиною `storage/<ключ>` до `sync` і після. Гілки до `sync` не існувало — усе
   нове вважається перетином.

   Нові версії **без перетину** з `F` — не зупинка: `finish` називає їх одним рядком
   («сховище X: +2 версії, перетину з задачею немає») і йде далі. Інакше кожен коміт
   колеги в іншому кутку конфігурації зупиняв би кожен PR. Якщо власник розуміє
   «суттєве» ширше (наприклад, будь-яка версія від іншого автора) — критерій міняється
   тут і в скілі `finish`, більше ніде.
7. **Після злиття PR** → `verify main ↔ storage`: рівні / `main` попереду (застосуйте
   залишок) / сховище попереду (звірочний коміт).

## 9. Міграція наявних репозиторіїв

Три репозиторії: `SMP_SimplyConnect` (2 воркспейси), `SMP_BankExchange` (3 + `epf`),
`SMP_OnlineExchange` (пілот, кириличне ім'я розширення — окреме рішення).

Кроки (скіл `migrate`, разовий):

1. `storage.json` кожного продукту → записи в `v8storagekit.yaml`; `v8project.local.yaml`
   → `v8storagekit.local.yaml` (`devInfobase:` → `infobases:`); у `v8project.local.yaml`
   лишити лише те, що стосується бази агента, або видалити.
2. Гілки `storage/<ім'я>` — **повторним реплеєм зі сховища** через `sync` на порожню
   orphan-гілку. Історія реплею на `main` лишається як архів. Альтернатива
   `git filter-repo --path` збереже SHA-и, але потребує окремої утиліти; повторний
   реплей коштує хвилини й іде тестованим шляхом.
3. Перше злиття `storage/*` у `main` (`--allow-unrelated-histories`) — дерева збігаються,
   diff порожній, коміт фіксує спільного предка.
4. `.githooks` + `core.hooksPath`; `.gitignore`/`.gitattributes` під фактичні шляхи; `check`
   зелений.
5. `verify` кожного джерела — нуль змістовних розбіжностей (BankExchange уже дав цей
   результат на 516 файлах).

`docs/migration/2026-09-02-legacy-repo-rename-prompt.md` після цього вилучається разом із
`storage.json`-конвенцією.

| `session-check` | (а) файли під `data/objects` новіші за дату останнього коміту `storage/X` → сигнал; старіші → тиша; `1cv8ddb.1CD` новіший, а `data/objects` ні → тиша; (б) коміти `storage/X`, не злиті в `main` → сигнал; (в) коди: сигнал → `3`, тиша → `0`, дзеркала немає при доступному сховищі → `3`; сховище недоступне → `0` з рядком «недоступне»; `git log` на наявній гілці не відповів → `1`, а рядки решти джерел у звіті присутні |
| `dump` | тексти «база зайнята» (усі три мови з §5) → зупинка з порадою, а не сирий вивід |
| хук старту сесії | шим `.claude/hooks/session-start.ps1` друкує валідний JSON із `hookSpecificOutput.hookEventName = SessionStart` і `additionalContext`; без плагіна в реєстрі — порожньо, код 0; без маніфесту в `cwd` — лише вступ; код `1` від `session-check` → текст зупинки в `additionalContext`, а не тиша; код `3` → сигнал як контекст; шим у всіх випадках виходить з `0`; дерево після запуску не змінене; `check` помічає розбіжність шима з `templates/hooks/` |
| диспетчер `kit.ps1` | `throw` усередині команди → код `1`, не `2`; `sync` із провалом злиття → `2`; `verify` із розбіжністю → `3`; `check` лише з `warn` → `0`; `-Version` без значення → зупинка `1` з назвою параметра, не тихе `1` у параметрі; `-Apply` без значення → `$true` |
| `build` (без платформи) | виявлення воркспейсів із `EXTERNAL_DATA_PROCESSORS`; збір артефактів у `build/artifacts/` з підготовлених файлів |

**З платформою** (`Integration`): `provision` порожня та з `.dt`; `canon` — round-trip дає
нуль розбіжностей на канонічному дереві; `dump` із живої бази; `sync` на реальному сховищі
(перший і повторний); `build` `.epf` через `/LoadExternalDataProcessorOrReportFromFiles`.

**Спайк у B2 — сховище конфігурації.** Рецепт «стаб + `ConfigurationRepositoryUpdateCfg -v N
-force`» перевірений лише для розширень. Для основної конфігурації порожня ІБ, можливо,
потребує `/ConfigurationRepositoryBindCfg` перед `UpdateCfg` — але цього немає ні в
документації платформи від Unica, ні в ранбуку, це гіпотеза. Порядок: (1) спробувати
той самий шлях, що для розширень, без `Bind`; (2) якщо платформа відмовить — `BindCfg`, і
тоді обов'язково `UnbindCfg -force` після дампу, бо прив'язка — **запис у сховище**
(таблиця прив'язок), а межа «сховища — тільки читання» має лишитись правдивою з точністю
до цього документованого винятку. Матеріал для спайку є: `R:\СховищаКонфігурацій_1С\` —
19 живих сховищ конфігурацій; брати найменше. Integration-тест — на реальному сховищі,
не «на першому клієнтському онбордингу».

**Результат спайку (2026-09-04, сховище `КормЦентр_DEV`, 1,27 МБ, платформа 8.3.27.1644):**
`ConfigurationRepositoryUpdateCfg -v N -force` без `-Extension` працює на порожній файловій
ІБ **без прив'язки**. Три кроки поспіль чисті: `/ConfigurationRepositoryReport` — «Отчет
успешно построен» (65 версій), `UpdateCfg -v 1` — «Обновление конфигурации из хранилища
успешно завершено», `DumpConfigToFiles` — 146 файлів. `BindCfg`/`UnbindCfg` у kit **не
потрібні**, документований виняток із «сховища — тільки читання» лишається невикористаним, і
`sync` не робить у сховище жодного запису. Передумова доступу — з §2.4, і вона підтвердилась буквально: у сховищі заведено `gitbot` із
**порожнім паролем**, а накладка `storages.<ключ>` у цьому не брала участі — ані спайк, ані
Integration-тест її не використовують, тож `storage.user` падає в типове значення. Перший
раунд спайку впав саме на автентифікації, і саме він показав, що конвенція `gitbot` була
перевірена лише на сховищах розширень; після того, як користувач завів `gitbot` у сховищі
конфігурації, вона підтверджена і для них.

**Підтвердження наскрізним прогоном (2026-09-04):** факт вище встановлений окремим скриптом
спайку, але потім відтворений і повним Integration-набором — `kit sync` на тому самому сховищі
прочитав звіт, реплеїв версію в `storage/base` і пройшов подальший `kit check` без помилок.
Тобто `$script:ConfigurationStorageNeedsBind = $false` перевірений не лише в лабораторних
умовах спайку, а й у тому вигляді, в якому код виконується насправді.

**Побічний факт платформи, знайдений спайком:** `ConfigurationRepositoryUpdateCfg` **не
валідує `-v`**. Через помилку в скрипті спайку другий раунд відправив `-v 1 2 3 … 65`, і
платформа завершилась із кодом 0 та повідомленням «Обновление конфигурации из хранилища
успешно завершено» — ні помилки, ні попередження. Що вона при цьому підняла, не
характеризовано. Практичний наслідок для kit: помилка в номері версії не впаде голосно, а
тихо дасть не ту версію, тож `-v` формується лише зі скаляра `$v.Version` у циклі по версіях,
а інваріант «`main` ≡ сховище» перевіряє `verify` (§3.5), не `sync`.

**Версія плагіна між блоками — вирішено (2026-09-03): жодного пушу й жодного
проміжного релізу до повного завершення.** Маркетплейс на GitHub лишається як є;
для тестування блоків маркетплейс перереєстровується на **локальну теку робочої копії** —
так само, як робилось на старті цього плагіна. B6 виконується проти **тестового
репозиторію, який користувач надасть окремо** — не проти живих `SMP_SimplyConnect` чи
`SMP_BankExchange`, доки механізми не пройдуть на ньому й не збережуть зворотний зв'язок.
До появи того репозиторію блоки B1-B5 готують механізми; `1.0.0` і повернення
маркетплейсу на GitHub — лише в B8, після всього.

**Перехідний період B1–B4 — два канони поруч.** До вилучення старого шляху (B2 —
`storage-sync`/`storage.json`, B4 — `load-ext`/`build.ps1`, B5 — старі скіли) плагін
постачає обидві моделі одночасно, а старі скіли ведуть до старої: `storage-pipeline`
рекламував `load-ext` (розкатка в базу людини — пряме порушення §1.3), `product-onboarding`
створював `storage.json`. Під локальним маркетплейсом це ризик для власних сесій
користувача, тому в B1 у шапках трьох старих скілів стоять застереження («`load-ext` не
запускати», «маніфест замість `storage.json`», «`migrate`»). Друге застереження того ж
роду: хуки B1 охороняють гілки `storage/*`, яких до B2 **не існує** — старий `storage-sync`
реплеїть у поточну гілку. Зелений `check` у B1 означає «інваріанти витримані», а не
«захист працює».

**Вимога №8 — закрита в межах, які назвав користувач, з одним відкладеним спайком.**
Файлова база агента з `.dt` — §4. Серверна — «розробник створює в кластері й дає
підключення», що користувач сам допустив у формулюванні вимоги («серверну можна не
створювати скриптом»). Розгортання серверної з `.dt` **скриптом** — спайк (§13), бо
параметри СУБД у рядку `CREATEINFOBASE Srvr=…` не задокументовані. Записано явно, щоб
власник бачив, що саме відкладено.

Блоки B1-B3 дають робочу синхронізацію і звірку git зі сховищем у новій моделі — без бази
агента, бо `verify` порівнює з дампом зі сховища, а не з деревом агента. B4-B5 — повний
цикл агента, включно з `canon`, який без бази агента неможливий. B6-B8 — прибирання
старого.

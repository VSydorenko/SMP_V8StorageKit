# Rust, фаза 4: команди процесу в `kit.exe`

Issue: #55 (а також #93, #89) — статус живе в GitHub (`track`), не в цьому файлі
Glossary: `docs/GLOSSARY.md` (головний checkout, еталон виводу, відома відмінність, рівень тестів, цільовий прогін,
не перевірено) · ADR: ADR-0025, ADR-0026, ADR-0014, ADR-0021, ADR-0020

## 1. Goal

Команди процесу розробки — `sdd`, `review-pack`, `pr-gate`, `doc`, `track`, `kit-setup`, `kit-scan`,
`session-cost`, `codex-audit` — досі йдуть з `kit.exe` у PowerShell-диспетчер: старт `pwsh` на кожен виклик, два
контракти розбору аргументів, логіка на регулярних виразах .NET і тести внутрішніх функцій. Після фази всі вони
виконуються самим `kit.exe`; PowerShell-код процесу (`tools/lib/Kit*.psm1`, `Markdown`, `PathRefs`, `GhRun`,
`WorktreeInclude`, розділ процесу диспетчера) зникає, а після фаз 3 і 4 разом `pwsh` лишається залежністю лише
розробки kit. Кожна команда kit приймає корінь репозиторію одним способом — `-C <шлях>` (#93). Хук старту сесії
каже про версію проєкту те саме, що `kit-scan` (коментар власника в #55). Нова команда `kit run-tests` тримає
правило «перевірка відповідає зміні» в коді й у проєктах-споживачах (#89).

## 2. Out of scope

- Команди сховища (`sync`, `verify`, `adopt`, `dump`, `provision`, `supply-marker`, `install-hooks`) і їхні модулі
  — фаза 3 (#54), сесія `smp-v8storagekit-91`; межа — §4.
- Зміни `doc anchors`, `doc refs`, `doc history` і розділ `Decisions outside ADR` у `kit-scan` — блок D (#115,
  план блоку D від 2026-11-27 у теці планів гілки `issue-115-block-d-process`). Ця спека
  описує стан **після** злиття D: R4 і R5 переносять уже змінену поведінку.
- Хук старту сесії для репозиторіїв з `permissions.additionalDirectories` (#93, друга частина) — OQ-1.
- Рівні тестів 1С (`syntax`, `yaxunit`), поле `reporter`, `--at`, `--last` agent-kit (ADR-0026 п. 6).
- Переписування Pester-тестів на Rust (ADR-0025 п. 6).
- Кросплатформна поставка (ADR-0014, Consequences).

## 5. Blocks in detail

Спільне для R1–R7 — порядок ADR-0014 п. 7 і ADR-0021 п. 1: реалізація в Rust → наявні Pester-тести команди зелені
проти `bin/kit.exe` → еталон виводу PowerShell-версії знято на фікстурах до видалення модуля й звірено (JSON —
розібраними значеннями) → лише тоді модуль і тести внутрішніх функцій прибирають. Кожна виправлена вада стає
відомою відмінністю: шапка Rust-модуля й закритий перелік тесту паритету. Нижче вади названо **кандидатами**: план
кожного блоку спершу міряє кандидата на фікстурі й лише тоді вирішує «виправити» чи «паритет». Формати ADR-0025 п. 2
— завжди паритет. Перенесена команда друкує помилку й `next:` помічником контракту кодів фази 3.

Ціль Pester-тестів після блоку — `bin/kit.exe`: фікстура `Invoke-KitCommand` (`tools/tests/fixtures/KitFixtures.psm1`)
веде перенесену команду в `bin/kit.exe` копії `Copy-KitTools` і перевіряє, що `pwsh` не запускався (той самий
маркер, що вже діє для `check`). Тести, що кличуть `bin/<команда>` через bash, лишаються як є: обгортка вже кличе
`kit.exe`.

### 5.1 R0 Основа процесу

#### 5.1.1 `-C <шлях>` (#93, ADR-0025 п. 4)

- `kit.exe <команда> -C <шлях> …`: якщо перші два токени після імені команди — `-C` (без урахування регістру) і
  значення, `kit.exe` робить шлях поточною текою процесу й прибирає ці два токени з аргументів. Далі — звичайний
  розбір. Те саме для команди, що йде диспетчеру PowerShell: дочірній `pwsh` успадковує поточну теку.
- Шлях відносний — від поточної теки виклику. Шлях не існує чи не тека — код `2`, `<команда>: ERROR -C: немає теки
  <шлях>`. `-C` деінде, ніж першими двома токенами, — звичайний аргумент команди (як сьогодні: невідомий параметр,
  код `2`).
- Хуки (`session-start`, `subagent-start`, `pretool-1c`) і приховані підкоманди (`runner-exec`,
  `config-preflight`, `tool-verdicts`, `source-fingerprint`) `-C` не приймають: їхній вхід задає Claude Code чи сам
  kit.
- Скіли й шаблони: правило одне — «команду kit для іншого репозиторію кличуть з `-C <клон>`». Розділ «Команди kit
  для репозиторію поза текою сесії» в `skills/1c-unica/references/unica-folders.md` зводиться до нього; рядок у
  `templates/CLAUDE.md` і `README.md` — те саме.

#### 5.1.2 Реєстр команд

Одна таблиця в крейті: ім'я команди, виконавець, рядок довідки, чи приймає `-C`. `kit.exe --help` друкує перелік з
неї плюс команди, що ще йдуть диспетчеру (`tools/commands/*.psm1`, поки тека є). Розпізнавання імені — без
урахування регістру (ADR-0021 п. 5). Фаза 3 додає свої рядки в ту саму таблицю.

#### 5.1.3 Профіль і головний checkout

`profile` (наявний `rust/src/profile.rs`) дістає те, що PowerShell-команди брали з `KitProfile.psm1`:

- **головний checkout** — батько `git rev-parse --path-format=absolute --git-common-dir`; не git — код `3`;
- **обов'язкове поле** — значення за шляхом або код `3` з ім'ям поля й файлу (семантика `Get-KitProfileValue` без
  `-Default`);
- **шлях усередині репозиторію** — значення профілю, що мусить лишитись під коренем (`Resolve-KitInsidePath`):
  абсолютний шлях чи `..` назовні — код `2`;
- **тека `.agents/<ім'я>`** головного checkout зі створенням і `.gitignore` з рядком `*` (`Get-KitAgentsDir`);
- **сирий файл проєктного шару** з порядком ключів — для `kit-setup -SetVersion` (R5), бо `Profile::load` знижує
  регістр ключів.

Простір імен ADR-0020 — наявний `apply_namespace`.

#### 5.1.4 Модуль `version` і хук старту сесії

Порт `KitVersion.psm1`: строгий `X.Y.Z`; розбір `CHANGELOG.md` з переліком проблем (заголовок `## X.Y.Z — дата`, лише
розділи `### Що змінилось` і `### Чекліст оновлення проєкту`, кроки `- [ ]`/`- [x]` або рядок
`Нічого робити не треба.`, версії строго спадні); версія плагіна з `plugin.json`; версія проєкту
(`v8storagekit.version`, тимчасовий запасний `kit.version` ≥ 1.0.0 — ADR-0020 п. 2); `kitVersion` маніфесту;
кроки в `(від, до]`; ознака «це репозиторій самого плагіна».

**Стан версії** — одна функція для хука й `kit-scan`, значення як у `kit-scan` сьогодні: `changelog-broken`,
`kit-repo`, `invalid`, `connected-before`, `no-profile`, `no-version`, `current`, `ahead`, `behind`.

Хук старту сесії (`upgrade_hint`) друкує рядок оновлення за станом:

| Стан | Рядок хука |
| --- | --- |
| `behind` | наявний: `проєкт на <версія>, плагін <версія>; кроків оновлення: N — власник запускає онбординг процесу.` |
| `connected-before` з кроками | той самий рядок, версія — `kitVersion` маніфесту |
| `no-version` | `v8storagekit.version у профілі немає — онбординг не завершено (останній коміт його PR: kit-setup -SetVersion).` |
| решта | нічого |

Хук і далі вмикається лише в репозиторії з маніфестом або з профілем, де задано версію (`CLAUDE.md`, «Структура»).
Профіль без версії в репозиторії без маніфесту — хук мовчить, як нині. Кандидат на виправлення: число кроків рахує
той самий розбір, що й `kit-scan`, тож `CHANGELOG.md` з проблемою дає `changelog-broken` (рядка немає), а не тихий
підрахунок.

#### 5.1.5 Модуль `markdown`

Порт `Markdown.psm1` і спільних частин `KitDoc`: рядки з позначкою «в огорожі» (відкриття `` ``` ``/`~~~` до трьох
пробілів відступу, закриття тим самим символом не коротше й без info-рядка, незакрита огорожа — до кінця файлу);
ATX-заголовки з рядками `start..end` і байтами розділу; збіг номера `§N` (`6.4` не збігається з `6.40` і `6.4.1`);
slug GitHub з лічильником дублікатів; якорі `<a name|id>`. BOM на початку файлу знімається до розбору (кандидат:
PowerShell-версія його не знімала, і перший заголовок файлу з BOM губився).

#### 5.1.6 Модуль `gh`

Наявний `rust/src/gh.rs` (фаза 2) дістає семантику `GhRun.psm1`: `gh` не знайдено або stderr каже про вхід
(`auth login`, `not logged`) — «недоступно» (код `3` у команди); інший ненульовий код — «збій» (код `1`); `HTTP 404`
у stderr — окрема відповідь «не знайдено»; stdin закрито або подано текстом; `GH_PROMPT_DISABLED=1`; необов'язковий
`GH_REPO`; стеля часу 120 с з убивством дерева процесів. Пошук `gh` — через `PATH` з `PATHEXT`, тож фальшивий
`gh.exe` у тестах працює.

#### 5.1.7 Залежність `regex`

Крейт `regex` додано в `rust/Cargo.toml` з обґрунтуванням у коментарі (ADR-0025 п. 3). `fancy-regex` — ні.

### 5.2 R1 `sdd`, `review-pack`, `session-cost`

#### 5.2.1 `sdd`

Підкоманди, параметри, тексти довідки й рядки виводу — як у `tools/commands/sdd.psm1`: `init`, `brief`, `dispatch`,
`resume`, `watch`, `review`, `fix`, `done`, `log`, `ruling`, `status`, `handoff`, `close`. Стан — тека
`<головний checkout>/.agents/sdd/<slug>/` з файлами `plan-path`, `checkout`, `<тека>/progress.md`,
`<тека>/task-<N>-brief.md`, `<тека>/task-<N>-review[-round<K>].md`, `<тека>/handoff.md` і запасна стара
`.superpowers/sdd/`.

Інваріанти, що тримають тести:

1. **Журнал читається й дописується побайтно тим самим форматом** (ADR-0025 п. 2): граматика рядків `Task N:`,
   `Window (task N): open|close <sha> at <UTC>[; report <байти>] — <хто>`, `Ruling (task N):`, легасі
   `— Ruling:`, розрізання рядка з кількома `Task N:`, синтетичне перше вікно для журналів без вікон, парування
   закриття з останнім відкритим вікном тієї ж задачі. Перевірка: фікстури журналів, записаних PowerShell-версією
   (зокрема без вікон і з легасі-рішенням), дають той самий `status` і ті самі діапазони комітів.
2. Журнал лише дописується; перший рядок чужого плану — відмова без запису.
3. `watch` бере `Status:` лише з байтів звіту після зсуву вікна; коротший файл приймається лише з mtime, новішим за
   відкриття вікна. Таймаут — код `3` з діагностикою.
4. Ліміт двох раундів `fix`; третій — лише з `-ApprovedBy`.
5. Коміти задачі — об'єднання її вікон; чужий коміт між вікнами не входить у пакет і в `done`.

Кандидати: `close` пише `# closed` до перевірки відкритих задач; тимчасові файли вікон (`<пакет>-window<K>.md`) лишаються при збої між
створенням і видаленням; `resume` у стані `fix` з `-Note` додає хибний запис раунду; «немає журналу» й «журнал
закрито» мають код `2`, хоча це стан, а не виклик.

`sdd brief` — розділ «Команди» за ADR-0026 п. 4 з'являється в R7, не тут.

#### 5.2.2 `review-pack` і пакет рецензії

`review-pack <base> [<head>] | -Branch [<head>]`, `-Out`, `-Context`, `-Exclude` (повторюваний), `-Split`; профіль
`pr.base`, `review.exclude`. Одна функція крейта будує пакет для `review-pack` і `sdd review` (вікна склеюються під
`## Вікно i: a..b`). Логіка гілки, що влила `origin/<base>`: коміти `--not T`, діф від віртуального злиття
`merge-tree --write-tree`, при конфлікті — від `T` з поясненням. Огорожа діфу довша за найдовшу серію зворотних
лапок. Байти й токени: КБ — байти UTF-8, токени — символи UTF-16 / 4; округлення — як у .NET (банківське для
`Math.Round` за замовчуванням), бо числа видно в рядку виводу. Відносний `-Out` — від поточної теки.

Кандидати: межа файлу в діфі за регулярним виразом `diff --git a/… b/…` ламається на імені з ` b/`; тепер межу
бере `diff --name-only -z` того самого діапазону.

#### 5.2.3 `session-cost`

Параметри й таблиці — як у `tools/commands/session-cost.psm1`; таблиця цін і дата цін переносяться дослівно.
Читання транскриптів потокове, битий рядок JSON пропускається, використання рахується раз на `message.id`.
`NOT CHECKED` друкується в stdout з кодом `3` (контракт ADR-0014 п. 4 вимагає рядка `ERROR` у stderr — кандидат на
вирівнювання). Кандидат: сесія без `timestamp` зникає навіть без `-Since/-Until`. Тестів сьогодні немає: R1 додає
тести на синтетичних транскриптах (оцінка вартості, `cost-state`, субагенти, `-Compare`).

### 5.3 R2 `pr-gate`

Підкоманди `start`, `open`, `ready`, `land`, `cleanup`, `scratch add|rm`, `help` і параметри — як у
`tools/commands/pr-gate.psm1`. Мутації git — лише через примітив фази 3; видалення тек — лише через `path_safety`
фази 3 (перевірка шляху перед кожним видаленням, ADR-0025 п. 7). Профіль: `pr.base`, `pr.mergeMethod`,
`pr.afterMerge`, `worktrees.root`, `workspace.mode` (лише `shared` чи `worktree`, інакше код `3`).

Поведінка, що переноситься як є: кроки `land` (`ready, merge, update, after-merge, cleanup, branch, prune`) з
рядком `<крок>: …` і звітом збою `зроблено / не зроблено / next:`; маркер `land-<pr>.json` у
`<головний checkout>/.agents/out/pr-gate/`; опитування `mergeable == UNKNOWN` до `-MergeableTimeout`; slug з
назви issue (`FormD`, без `\p{Mn}`, слова `[a-z0-9]+`, до 30 символів, кирилиця → `task`); копія
`.worktreeinclude` без перезапису; `scratch add` друкує в stdout лише шлях, решту — в stderr. Rust не міняє поточну
теку процесу: рядок `next: cd <корінь>` лишається. Інваріанти безпеки — §6.1.

Кандидати: виняток читання дзеркал без коду (`throw` рядком) обходить звіт збою; `next` команди `cleanup` вибирається
пошуком українського тексту у власних рядках; команди `pr.afterMerge` без стелі часу (кандидат — стеля `timeout`
профілю, типово 10 хв, понад неї — код `3`); `gh pr view --json files` обрізає список на 100 файлах, і перетин
after-merge може пропустити файл (кандидат — `gh api` з посторінковим читанням); `prune` з `--limit 500`.

### 5.4 R3 `track`

`track status|spec|milestone`, параметри й профіль `track.repo`, `track.labels` — як у `tools/commands/track.psm1`.
Розбір таблиці спеки: перша таблиця поза огорожами (модуль `markdown`), колонки за назвами без урахування регістру
(блок, обсяг, «готово, коли», залежність, віха), ідентифікатор блоку з цифрою, залежності — ідентифікатори інших
рядків цілим токеном. Усі рядки й віхи перевіряються до першого запису. Ідемпотентність — маркери в тілі issue
(ADR-0025 п. 2); закриту issue не редагують. `--paginate` склеює масиви розбором JSON-потоку, а не регулярним
виразом по `\n[`.

Кандидати: другий прохід перезаписує тіло щойно створеної issue окремим `issue edit` (зайвий запис); межа
`--limit 1000` для пошуку маркерів мовчки губить старі issue (кандидат — посторінкове читання).

### 5.5 R4 `doc`

Підкоманди `doc <файл>` (зміст), `doc <файл> <§N|слова|A-B>`, `find`, `anchors`, `refs`, `debt`, `history`, `lint`,
довідка за темами; профіль `docs.*` — як у `tools/commands/doc.psm1` після блоку D (список «не перевірено» в
`anchors`, ігнорований шлях — пропуск, мітки `label`, `block`, `decision`, `session`, форма `-Only`, яку злив D). Читання
файлів — UTF-8 з `\r\n` → `\n`; `lint` ділить рядки набором Python `splitlines`. Git — лише читання
(`ls-files -z`, `check-ignore`, `log -1`). Перемикач з `:false` — значення `false`, а не шлях (дефект ADR-0014,
Context).

Регулярні вирази — ADR-0025 п. 3: вбудовані шаблони з lookbehind (`PathRefs`, `-Dead`, `RxAnchorBefore`,
`RxNumbered`, мітки `history`) — збіг плюс ручна перевірка символу перед і після; Unicode-`\w` і `\p{L}` — як у
.NET. Користувацький вираз — діалект `regex`; помилка компіляції — код `2`. Еталон виводу знімається на
фікстурі-корпусі з кирилицею, огорожами, BOM і дублікатами заголовків — для кожної підкоманди.

Кандидати: `-Dead` не бачить розширень у верхньому регістрі; файл понад 1 МБ дає `refs` «посилань: 0» мовчки
(кандидат — рядок «пропущено N файлів понад 1 МБ»); `-Max 2.5` приймається.

### 5.6 R5 `kit-setup`, `kit-scan`

`kit-setup [-DryRun] [-Json] [-NoPermissions] [-NoGitignore] [-NoProfile] [-NoWorktreeInclude] [-SetVersion]` і
`kit-scan [-Json] [-MinSimilarity] [-Memory]` — як у PowerShell-версіях після блоку D. Стан версії — модуль
`version` R0, той самий, що в хука. Запис файлів — тимчасовий файл і атомарна заміна, UTF-8 без BOM; `.claude/settings.json`
`kit-setup` не пише ніколи. `-SetVersion` читає лише проєктний шар профілю (не локальний і не машинний), пише лише
`v8storagekit.version` і зберігає порядок ключів, решту значень і відступи; JSON з коментарями — код `3` без
запису (кандидат: PowerShell переписував файл цілком). `-Json` обох команд звіряється розібраними значеннями.
Порядок рядків звіту — ординальний (ADR-0021 п. 5), а не порядок `Sort-Object` з культурою (кандидат).

Кандидати: помилка профілю тихо дає порожні дані плану `kit-setup`; `connected-before` з `kitVersion` вище плагіна
не відрізняється від звичайного.

### 5.7 R6 `codex-audit`

`codex-audit -Prompt <файл> [-Embed <файл>]… [-NoRepo] [-Freeze] [-Out <файл>]` і
`codex-audit review (-Commit|-Base|-Uncommitted) [-Out]`; профіль `codex.*` (`model`, `reasoningEffort`
обов'язкові). Аргументи `codex exec`, тека прогону `<головний checkout>/<private>/codex/<UTC>-<ім'я>/`, файли
`<тека>/prompt.md`, `events.jsonl`, `codex.log`, `report.json|md`, `status.json`, вердикт «справжній прогін» за подіями
(читання дерева `command_execution` з кодом 0, `turn.completed`, жодного `error`/`turn.failed`), перевірка звіту за

Зміни, які спека вирішує (не кандидати): `codex.bin` з `.ps1` більше не запускається через `pwsh` — фальшивий

після завершення. Кандидати: гонка читання замка одразу після `CreateNew` (порожній файл видаляється як мертвий);
`..foo` у дереві вважається виходом за межі.

### 5.8 R7 `kit run-tests`

Поведінка — ADR-0026. Додатково:

- Рівень читається зі злитого профілю з простором імен ADR-0020. Немає рівня — код `2` з переліком наявних.
- Процес рівня — argv з `command` + `args` (повний) або `command` + `changedArgs` (цільовий); поточна тека — корінь

- `BASE` відкритої задачі `sdd` — з журналу R1 у цьому checkout (останнє відкрите вікно задачі, що не `complete`);

- Профіль kit (`.agents/kit.profile.json`): рівень `pester` — `command`

- `sdd brief` — розділ «Команди» за ADR-0026 п. 4.
- `CLAUDE.md`, «Тести»: таблиця «що змінено → що проганяти» називає `kit run-tests pester -Changed` і `-Full`

## 6. Security and data integrity

### 6.1 `pr-gate` (R2)

Інваріанти, кожен з тестом чорної скриньки на синтетичному репозиторії з голим origin і фальшивим `gh`, і з
контролем, на якому тест червоніє:

1. **Не пушить захищену гілку.** Захищені — `main`, `pr.base`, `-Base`/`baseRefName`, ціль `origin/HEAD`, кожна
   `storage/*` (локальна й origin). `open` на такій гілці — код `2`, origin без змін. Контроль: гілка задачі
   пушиться.
2. **Ніколи force.** Єдиний push — `push -u origin refs/heads/<b>:refs/heads/<b>` явним refspec. Перевірка: журнал
   викликів git у тесті (фальшивий `git` поверх справжнього не потрібен — тест порівнює ref origin до й після
   розбіжної історії: розбіжний push відхилено, ref origin не змінився). Запобіжник `git_guard.rs` забороняє
   `--force`, `-f`, `+refs` у модулі `pr_gate`.
3. **Злиття лише перевіреного PR:** `OPEN`, не з форку, база й голова не `storage/*`, `MERGEABLE`,
   `--match-head-commit`; після злиття — повторне читання стану `MERGED` до видалення гілки.
4. **Віддалену гілку видаляє** лише коли вершина в момент видалення дорівнює `headRefOid` злитого PR.
5. **`pr.afterMerge` — лише з `.agents/kit.profile.json` коміту головної гілки origin**; локальний, машинний і шар
   worktree ігноруються з повідомленням. Команди — argv без оболонки.
6. **`cleanup` не видаляє головний checkout** і шлях, що не є зареєстрованим worktree (новий тест — сьогодні
   непокритий). `worktree remove` без `--force`; `--force` — лише для `scratch rm` після перевірки `path_safety`.

### 6.2 Інші пишучі команди

- `track` пише в GitHub лише після перевірки всіх рядків і віх; `-DryRun` — жодного пишучого виклику (тест журналу
  фальшивого `gh`).
- `kit-setup` не пише `.claude/settings.json`; `-SetVersion` пише одне поле одного файлу (§5.6).
- `sdd` пише лише в теці журналу головного checkout; журнал лише дописується.
- `codex-audit`: `codex` у пісочниці `read-only` (типово); тека прогону — `<private>` профілю, гітігнорована;
  промпт, звіт і журнал можуть містити код репозиторію — нічого з них не йде поза теку прогону.
- `kit run-tests` виконує argv з профілю; проєктний шар профілю — у git і проходить рев'ю, локальний і машинний —
  налаштування людини. Без оболонки — без ін'єкції через значення. Дозволи без запиту — OQ-2.

### 6.3 Секрети й вивід

`gh` і `codex` отримують облікові дані зі свого оточення; kit їх не читає й не друкує. Текст помилки `gh` чи `git`
kit передає першим рядком stderr дослівно — як у PowerShell-версіях. URL origin у виводі — через маску userinfo
(ADR-0021 п. 5). Паніка — сталий текст без даних.

### 6.4 Часткові збої

- `land` ідемпотентний: повтор після збою на будь-якому кроці продовжує з першого незробленого; маркер
  `land-<pr>.json` не дає двічі виконати `pr.afterMerge`.
- `track spec` перевіряє все до першого запису; збій посеред запису — повтор знаходить створені issue за маркерами.
- `kit-setup` пише кожен файл атомарно; перевірка звіту — до будь-якого запису.

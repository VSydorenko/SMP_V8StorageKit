# Перейменування регістром і незалежність від налаштувань git машини — дизайн

Статус: **узгоджено власником 2026-10-04 (розділи 1–5 дизайну в розмові)**, гілка `fix/case-renames`,
реліз 1.4.0. Ішузи: #31 (sync: регістр-дублікати в `storage/*`, злиття падає), #32 (verify не бачить
регістр-дублікатів і дає `equal`).

## 1. Проблема

Пілоти `tehnokrat_unf` і `interoptica_unf` (kit 1.3.1, Windows Server 2022, git 2.53.0.windows.1,
`core.ignorecase=true`). Вендор у оновленні змінює регістр кириличної літери в імені об'єкта чи
макета (`Записатькод` → `ЗаписатьКод`, `ОбразецABCанализ…` → `ОбразецABCАнализ…`,
`…Персучета` → `…ПерсУчета`). Наслідки:

1. У дзеркалі `storage/*` з'являються **фантомні дублікати**: файл під старим регістром лишається
   в дереві поруч із новим (tehnokrat — 10 груп з v107; interoptica — 17 груп з v183/v319).
   Дзеркало ≠ сховище.
2. Злиття дзеркала в робочу гілку (`sync -MergeMain`, на місці) падає з
   `untracked working tree files would be overwritten by merge`; далі `merge --abort` падає з
   `MERGE_HEAD missing`, і kit хибно повідомляє про «незавершений стан злиття».
3. `verify` на вершині з 17 фантомами дає `equal` (у дереві 56061 файл, у дампі 56044 + службовий).

Обидва дзеркала вже виправлені вручну переписуванням історії (interoptica `feadd8f`, tehnokrat
`785c7cf`); tehnokrat вручну злив дзеркало в гілку онбордингу (`ed06bfe`). **Ремонт дзеркал не є
частиною цієї роботи** — kit не переписує їх удруге й не отримує команди ремонту (рішення власника).

## 2. Факти (виміряно 2026-10-04)

Умови: git 2.53.0.windows.1, NTFS, `core.ignorecase=true`; проби в scratchpad на синтетичних репо,
незалежний тест сесії tehnokrat на живому репо, тимчасовий клон `SMB_ukr_vendor` (репо від
ГітКонвертера, EDT).

**Корінь.** Регістронечутливість git (`core.ignorecase`) складає регістр **лише ASCII**: `memihash()`
у `hashmap.c` перетворює тільки `a`–`z`; у розсилці git з 2011 визнано, що регістронечутливе
порівняння не працює для не-ASCII імен. NTFS складає регістр усього Юнікоду. Налаштування git, що
змінює це, не знайдено.

| Що перейменовано лише регістром | `add -A` (як у kit ≤1.3.1) | `rm -r --cached` + `add -A` | перехід робочої копії (`merge`/`checkout`/`pull --ff-only`/`reset --keep`/`read-tree -m -u`/`cherry-pick`/`rebase`) |
|---|---|---|---|
| ASCII (`abc→aBc`) | новий регістр **губиться** (індекс лишає старий) | ✔ | ✔ |
| кирилиця (`а→А`) | **фантом** поруч із новим шляхом | ✔ | ✘ `would be overwritten` |

- Перехід ламається **й без фантома**: на чистому коміті з `R100` (tehnokrat після ремонту; клон
  `SMB_ukr_vendor`, `checkout` коміту перейменувань `c85e32a18` з попереднього `74c022c2e`).
- Не допомагають: `-c core.ignorecase=false`, `switch --discard-changes`, явний `git mv`
  (тека — `Permission denied`, файл — `destination exists`).
- Проходять: `git merge-tree --write-tree` (без робочої копії; з `--allow-unrelated-histories` для
  першого злиття) і примусові `read-tree --reset -u`, `reset --hard`, `checkout -f`.
- `read-tree --reset -u HEAD` на клоні `SMB_ukr_vendor` (16 812 файлів, 6 543 зміни): 13 с,
  незмінені файли не переписуються (mtime той самий), `git status` після — чистий.
- `adopt` через `merge -s ours --no-commit` робочу копію не змінює й проходить; з `rm --cached`
  дерево після нього правильне.
- У теці з чутливістю до регістру NTFS (`fsutil file setCaseSensitiveInfo`) git поводиться як на
  Linux (усе проходить), але вплив на платформу 1С не виміряно — напрям відхилено (§3).

**Як роблять інші.**
- gitsync (код прочитано): вивантаження в тимчасову теку → повне очищення теки робочої копії →
  перенесення → `git add -A .` → коміт. Алгоритм ідентичний kit; обробки регістру немає.
- ГітКонвертер (вікі «Как это работает», «Коммит в Git»): фіксує не через `add -A`, а явними
  командами, згенерованими з `DumpFilesIndex.txt` (UUID ↔ файли), до трьох комітів на версію
  (видалення / перейменування / решта). У `SMB_ukr_vendor` версія №27 — коміт лише з 510
  перейменуваннями (серед них кириличні регістрові, без фантомів) + коміт решти.
- Ні gitsync, ні ГітКонвертер не зливають гілку дзеркала в робочу копію: комітять туди, де нове
  дерево вже лежить на диску, а `clone` бере вершину. Тому перехід копії через перейменування в них
  не трапляється — у kit він трапляється на кожному `sync -MergeMain`.

**Налаштування EOL за порадою ГітКонвертера** (вікі «Символы окончания строк»: Windows
`autocrlf=true` + `safecrlf=true`; сам ГітКонвертер ставить `safecrlf=warn`). Платформа пише CRLF у
структурі XML і LF усередині текстових значень:
- `autocrlf=true` + `safecrlf=true` → `git add` відмовляє: `fatal: LF would be replaced by CRLF`;
- `autocrlf=true` + `safecrlf=warn` → blob мовчки нормалізується до LF (незворотно);
- під атрибутом `-text` — байти зберігаються як є за обох налаштувань.

На машині пілотів: системний `gitconfig` — `core.autocrlf=true`, глобальний користувача — `input`;
`safecrlf` не задано. Зараз захищені коміт дзеркала (явні `-c`) і `Export-KitTree` (`cat-file`);
`adopt` покладається лише на `-text`, наявність якого перевіряє тільки `kit check`.

## 4. Дизайн

### 4.1 Фіксація дерева в індексі — коміт дзеркала й `adopt`

**Інваріант:** після кроку, що замінює піддерево джерела, індекс цього піддерева дорівнює вмісту
диска побайтово й з точним регістром шляхів — незалежно від `core.ignorecase`, `core.autocrlf`,
`core.safecrlf` машини.

- **`Write-KitStorageVersion`** (`tools/lib/StorageBranch.psm1`): перед `add -A` —
  `git rm -r -q --cached --ignore-unmatch -- <RepoPath>`; індекс піддерева збирається наново з
  того, що вивантажила платформа. Наявні `-c core.autocrlf=false -c core.safecrlf=false`
  лишаються на `add` і `commit`.
- **`adopt`** (`tools/commands/adopt.psm1`):
  - до першого руйнівного кроку (`Clear-KitTreeExceptSupply`) — `Test-GitTextPolicy` на шляху
    джерела; без `-text` — зупинка, нічого не змінено;
  - перед `add -A` — `rm -r --cached` піддерева;
  - `add` з явними `-c core.autocrlf=false -c core.safecrlf=false`;
  - `:(exclude)` поставки й `Remove-KitSupplyFromIndex` — без змін;
  - коміт гілки без злиття — **без `--only`**, як уже комітить гілка зі злиттям (див. факт нижче).
    Межу «точковий коміт у спільній робочій копії» тримає наявний guard «немає незакомічених змін
    поза шляхом джерела», що стоїть до першого руйнівного кроку.
- **Факт (2026-10-04, доповнення при плануванні):** `git commit --only -- <шлях>` після
  `rm --cached` + `add -A` **воскрешає** фантом: git накладає на тимчасовий індекс записи `HEAD` під
  pathspec і перечитує їх із диска, а старий регістр на NTFS «існує» (у коміті й індексі опиняються
  обидва регістри — і файл, і тека). Тому `--only` непридатний для коміту дерева з кириличним
  перейменуванням регістром — і в kit, і в ручному коміті людини (хук §4.4 це ловить: він бачить
  тимчасовий індекс `--only` через `GIT_INDEX_FILE`).
- **Перевірка після `add`** (спільна функція, обидва місця): перелік індексу піддерева
  (`ls-files -z` через `Invoke-KitGitProcess`, UTF-8) ≡ перелік файлів на диску (`Ordinal`), без
  поставки й службових файлів платформи (`ConfigDumpInfo.xml`, `DumpFilesIndex.txt`). Розбіжність —
  виняток **до** коміту з переліком шляхів (до 5 + рахунок). Ловить фантом, загублений ASCII-регістр
  і будь-яку іншу евристику git.
- `canon` і `dump` індексу не чіпають — без змін; їхній шлях захищають хук (§4.4) і форма коміту в
  скілах (§4.5).

### 4.2 Злиття без робочої копії — `Merge-KitBranchInto`

Зовнішній контракт (параметри, `Outcome = merged|already`, `Sha`) не змінюється; змінюється
механізм. Через функцію йдуть `sync -MergeMain` і `verify -Apply`.

1. Передумови як зараз (`<Into>` існує; уже злито — `already`). Нове: `<Into>` не `storage/*` —
   заміна хука `pre-merge-commit`, який при `commit-tree` не спрацьовує.
2. Де вибрана `<Into>` (`git worktree list --porcelain`): у цій робочій копії — вона мусить бути
   чистою (`status --porcelain` порожній, як зараз, той самий текст зупинки з переліком); в іншому
   worktree — зупинка (інакше `update-ref` пересунув би гілку під чужою копією).
3. `git merge-tree --write-tree [--allow-unrelated-histories] <Into> <storage/X>`: код 0 — дерево;
   код 1 — конфлікт: зупинка з переліком конфліктних шляхів, **нічого не змінено**; текст прямо
   каже, що ручний `git merge` на Windows при кириличному перейменуванні регістром теж упаде.
   Нерозпізнаний `--write-tree` (старий git) — зупинка «потрібен git ≥ 2.38».
   `<storage/X>` фіксується в SHA один раз до цього кроку: `merge-tree` і `commit-tree -p` мусять
   бачити той самий коміт, навіть якщо паралельний `sync` допише версію між ними.
3а. **Лише якщо `<Into>` вибрана тут — ігноровані файли, які злиття перезапише** (рішення архітектора
   2026-10-05, задача 4, на знахідку рев'ю). `read-tree --reset -u` мовчки перезаписує невідстежуваний
   **ігнорований** файл, якщо дзеркало приносить закомічений файл за тим самим шляхом (`git add -f` у
   дзеркалі, або дзеркало kit ≤1.2.0 з поставкою); `status --porcelain` такого файлу не показує, тож
   крок 2 його не ловить. Перевірка до `update-ref`: шляхи, які злиття **додає** відносно `<Into>`
   (`git diff-tree -r -z --name-only --no-renames --diff-filter=A <старий> <дерево>`), ∩ ігноровані
   невідстежувані файли (`git ls-files -z --others --ignored --exclude-standard -- <верхні теки доданих
   шляхів>`; pathspec звужено до верхніх тек доданих шляхів, бо повний перелік ігнорованого охоплює
   `build/` з дампами `verify` на десятки тисяч файлів). Перетин — **`OrdinalIgnoreCase`** (уточнення
   2026-10-05 на спостереження рев'ю задачі 4; спершу тут стояв `Ordinal`): ігнорований `x.BIN` і
   доданий `x.bin` на NTFS — один файл, і `read-tree -u` його перезапише. Хибної зупинки на кириличному
   перейменуванні регістром це не дає: старий файл там **відстежуваний**, у переліку ігнорованих його
   немає. Не годиться лише `Test-Path` на доданому шляху — він знайшов би саме той відстежуваний старий
   файл. Вміст для порівняння береться з фактичного (ігнорованого) шляху на диску. Файл з перетину, вміст якого (`git hash-object --no-filters`) дорівнює blob у дереві злиття,
   не втрачається — його пропустити; решта — зупинка «брудна копія» з переліком (до 5 + рахунок) і
   порадою перенести файли, **нічого не змінено**. Розбіжність зі звичайним `git merge`, який ігноровані
   файли вважає витратними, — свідома: kit зливає без участі людини.
4. `git commit-tree <дерево> -p <Into> -p <storage/X> -F <файл повідомлення>` — повідомлення як
   зараз; автор і комітер — із налаштувань git.
5. `git update-ref -m "kit: <повідомлення>" refs/heads/<Into> <новий> <старий>` — з перевіркою
   старого значення; гілку тим часом пересунули — зупинка, нічого не змінено.
6. Лише якщо `<Into>` вибрана тут: `git read-tree --reset -u HEAD`. Збій тут — повідомлення, що
   коміт злиття вже є, гілка пересунута, а робоча копія відстає; одна команда відновлення
   (`git read-tree --reset -u HEAD`).

Зникають: тимчасовий worktree `build/sync/_main/wt` (залишок від старих версій прибирається, якщо
є) і `merge --abort` разом із хибною діагностикою «незавершений стан злиття» (#31 п.4).

Свідомі відмінності від `git merge`: хуки `pre-merge-commit`/`post-merge` не викликаються; коміт
злиття не підписується за `commit.gpgSign` (коміти дзеркала kit не підписує й зараз); захист
невідстежуваних файлів від перезапису замінює вимога чистої копії з кроку 2, а ігнорованих — крок 3а
(тут kit суворіший за `git merge`). Для злиттів без перейменувань дерево ідентичне: `merge-tree`
працює на тому самому `ort`.

`adopt` (`merge -s ours --no-commit`) — без змін механізму злиття.

### 4.3 `verify` бачить розбіжності регістру (#32)

- **Виявлення з переліку git:** `Export-KitTree` групує відносні шляхи з `ls-tree -r -z` за
  `OrdinalIgnoreCase` (юнікодне складання, як NTFS) до запису на диск і повертає групи > 1 разом із
  лічильником записаних blob-ів.
- **Запобіжник лічильника:** кількість файлів у теці дерева (без службових і поставки) мусить
  дорівнювати кількості шляхів переліку мінус Σ(розмір групи − 1) за виявленими групами; інша
  розбіжність — **виняток** (`verify` не ручається за звірку), не вердикт.
- **Нові класи в `Compare-KitTrees`:**
  - *регістр-дублікати в дереві* — кожна група; член, що точно (`Ordinal`) збігається з дампом,
    позначено як справжній, решту — як фантоми;
  - *лише регістр шляху* — пара «шлях у дампі / шлях у дереві», що різняться тільки регістром
    (загублений ASCII-регістр kit ≤1.3.1); вміст порівнюється як для звичайної пари.
- **Вердикт:** обидва класи — розбіжність, `equal` неможливий; логіка `ref-ahead`/`mixed` не
  змінюється; кожен клас має власний рядок «Увага»: дефект дерева git, не робота для сховища;
  злиття такого дерева на Windows впаде; джерело — запис дзеркала kit ≤1.3.1. Код виходу — 3.
- `Diff` отримує властивості `CaseCollisions`, `CaseOnly`; наявні поля не змінюються.

### 4.4 Запобіжники

- **Спільна функція** пошуку пар шляхів, що різняться лише регістром (умовно
  `Find-KitCaseCollisions -RepoRoot -Ref [-Path]`): `ls-tree -r -z` через `Invoke-KitGitProcess`,
  групування `OrdinalIgnoreCase`. Користувачі: `verify` (§4.3), `check`; перевірка після `add`
  (§4.1) використовує те саме групування для переліку індексу. Не `tr`/ASCII і не голий конвеєр —
  обидва дають хибні 0 на кирилиці (виміряно interoptica).
- **`kit check`:**
  - `Test-KitStorageBranchInvariants`: вершина `storage/*` без пар — рівень `error`, до 5 груп і
    посилання на розбір у `docs/storage-and-git.md`;
  - та сама перевірка для `HEAD` під шляхом кожного джерела;
  - наявна перевірка «файли поза шляхом джерела» переходить із голого конвеєра на
    `Invoke-KitGitProcess` (`-z`).
- **Хук `templates/githooks/pre-commit`:** якщо в індексі є пари шляхів, що різняться лише
  регістром, — коміт відхиляється з переліком і порадою (`git rm --cached <фантом>`). Перевірку
  виконує `perl` (входить до Git for Windows; `lc` на декодованому UTF-8 — повний Юнікод); без
  `perl` — попередження й пропуск, не блокування. Вартість (прототип, 2026-10-04): групування 60 000
  синтетичних кириличних шляхів у `perl` — 0,16 с; прототип відхилив фантом, воскреслий через
  `commit --only`, і пропустив чистий коміт.
  Наявний блок захисту `storage/*` — без змін.
- **Версія git:** `check-environment` — git ≥ 2.38 в обов'язковій категорії; власний запобіжник у
  `Merge-KitBranchInto` (§4.2 крок 3). Мінімум підтверджено документацією тегів git:
  `Documentation/git-merge-tree.txt` у `v2.38.0` описує `--write-tree`, `--name-only`, `-z` і
  `--allow-unrelated-histories`, у `v2.37.0` — жодного з них (перевірено 2026-10-04).
- `sync` не відмовляється реплеїти на дзеркалі з дублями: наступна версія з `rm --cached` прибере їх
  з вершини; історію покажуть `check` і `verify`.

### 4.5 Люди, скіли, документація

- **Робочі копії:** стару Windows-копію через версію з кириличним перейменуванням регістром веде
  лише примусовий перехід на **чистій** копії (`git fetch` → `git reset --hard origin/<гілка>`) або
  свіжий клон; `pull`/`checkout`/`rebase` упадуть з `would be overwritten`, і це не пошкодження.
  Підказка — у скілах `v8storagekit:sync`, `v8storagekit:reconcile`, `v8storagekit:finish`.
- **Коміт після `dump`/`canon`:** скіли `v8storagekit:dump`, `v8storagekit:finish` дають форму
  `git rm -r -q --cached -- <шлях>` + `git add -- <шлях>` замість голого `git add -A`, і коміт
  **без `--only`** (`git commit -F <файл>` після перевірки `git diff --cached --name-only`, що
  застейджено лише цей шлях) — `--only` воскрешає фантом (§4.1, факт).
- **`docs/storage-and-git.md`** — розділ «Перейменування регістром»: корінь (ASCII у git проти
  Юнікоду в NTFS), інваріант «індекс піддерева ≡ диск», чому злиття без робочої копії, що бачать
  люди, як роблять gitsync і ГітКонвертер. Без номерів рядків і лічильників.
- **`docs/text-policy.md`** — розділ про налаштування ГітКонвертера як основний сценарій машини:
  kit дає той самий результат за `autocrlf=true`/`safecrlf`; чому схему «у репо LF» не переймаємо;
  репо від ГітКонвертера вже має нормалізовані blob-и (межа відновлення).
- **`docs/follow-ups.md`** — ідея явних комітів перейменувань за `DumpFilesIndex.txt` з
  обґрунтуванням, чому не зараз.

спеку, план і розмову, з якої цей бриф з'явився, ти не досліджуєш і не знаєш: код kit не читаєш,
виводів з нього не робиш. Єдине місце поза споживачем, куди ти пишеш, — один файл журналу
(розділ 8); єдиний файл плагіна, який ти читаєш, — `upgrades.md` для пункту 0 (розділ 5). Усе, що
потрібно для роботи, написано тут. Чого тут немає — того ти не знаєш, і домислювати не треба:
зупини пункт і запиши питання для архітектора (розділ 3, правило «розбіжність»); якщо без відповіді

## 1. Мета

Перевірити плагін kit версії 1.5.0 разом з плагіном Unica 0.13 на живому репозиторії-споживачі й
записати, що підтвердилось, а що ні. **Нічого не виправляти — лише фіксувати.**

Контур, який ти перевіряєш, у чотирьох реченнях. Конфігурації 1С лежать у сховищах конфігурацій;
плагін kit переносить їхні версії в git як дзеркальні гілки `storage/<ключ>` і зводить їх із
робочою гілкою. Для кожного воркспейсу (тека з `v8project.yaml`) існує **база агента** —
окрема інформаційна база, у якій працює Уніка (вона завантажує в неї вихідники з git і вивантажує
назад); база людини з нею не плутається, і kit це перевіряє. Раннер Уніки (v8-runner 0.14) тримає
про базу агента власну пам'ять — «покоління» бази й хеші каталогів, — і коли kit сам зрушує базу
(переносить версію зі сховища, звіряє тощо), ця пам'ять застаріває. Тому після таких команд kit
друкує **крок вирівнювання** — точний виклик Уніки (`pull` або `push` з `force`), який
повертає пам'ять у відповідність; чи правильний цей крок і чи справді після нього все збігається —
головне, що ти міряєш.

## 2. Як знайти kit і що означають слова

**Корінь плагіна kit.** Виконай `claude plugin list --json` і знайди елемент з
`"id": "v8storagekit@smp-v8storagekit"`. Для плагіна з локального маркетплейсу корінь — поле
`readFromFolder` (так має бути в пілоті); якщо його немає — поле `installPath`. Це `<корінь>`.
(У звичайному виводі `claude plugin list` шлях може не показуватись.) У плагіні kit і в файлах, які
ти читаєш (зокрема `upgrades.md`), позначка кореня плагіна — слово `CLAUDE_PLUGIN_ROOT` у фігурних дужках після знака долара —
означає те саме, що `<корінь>`: у файлі, прочитаному напряму, її ніхто не підставляє, тож підстав сам
(шлях до `templates/…` у тому ж файлі — теж `<корінь>/templates/…`). Усі команди kit мають одну форму (тут і далі `<корінь>` —
цей шлях, а `<ws>` і `<ключ>` — з маніфесту й воркспейсів споживача):

    pwsh -NoProfile -File "<корінь>/tools/kit.ps1" <команда> -RepoRoot . [-Workspace <ws>] [-Source <ключ>] [-Apply] [власні параметри]

Без `-Apply` команди лише показують прев'ю, але навіть воно може піднімати тимчасову базу й
запускати платформу 1С. Код виходу 0 — виконано; 1 — зупинка або помилки; 2 — лише для `sync`:
дзеркало оновлено, злиття не виконано; 3 — `verify`: є що робити. Коди 2 і 3 — штатні відповіді
команди, не «команда не запустилась».

**Глосарій.**

- **Воркспейс** — тека з `v8project.yaml` (конфіг Уніки). Його гітігнорований напарник
  `v8project.local.yaml` тримає базу агента й секрети.
- **Набір** (`sourceSet`) — елемент списку `source-set:` у `v8project.yaml`, його `name`. Має тип:
  `CONFIGURATION` (основна конфігурація), `EXTENSION` (розширення, ім'я набору = ім'я розширення) або
  зовнішні обробки/звіти.
- **`<шлях набору>`** — шлях теки набору від кореня репозиторію: тека воркспейсу + ключ `path`
  цього набору в `v8project.yaml`. Найнадійніше — взяти
  з рядка, який друкує kit у кроці вирівнювання: «Після pull: git status --porcelain -- <шлях>».
  Для виводу до першого кроку — склади сам і перевір `git ls-files -- <шлях> | Select-Object -First 3`.
- **Ключ** — те саме ім'я набору в маніфесті `v8storagekit.yaml` (корінь репозиторію). Параметр
  `-Source <ключ>` вибирає джерело.
- **Накладка** — гітігнорований файл `v8storagekit.local.yaml`: особисті налаштування машини
  (шляхи сховищ, паролі сховищ, бази людини). Читати його можна, **значення секретів не друкувати**.
- **База агента** — `infobases.origin` у `v8project.local.yaml` (поля `connection`, `user`,
  `password`; для нової серверної ще `dbms` і `cluster`). Інших баз Уніка не обслуговує.
- **Пам'ять раннера** — тека `<workPath>/infobases/origin/` (`<workPath>` — ключ `workPath` у
  `v8project.yaml` воркспейсу, типово `build`): `generation.json` (токен покоління на набір),
  `hashes/<набір>.redb` (пара «каталог ↔ база»), `dump-info/`. Пишуть успішний `push`, `pull` і
  `infobase.create` (останній лише хеші, без покоління).
- **Крок вирівнювання** — блок у виводі `kit sync`/`verify`/`provision`, що починається словами
  «Далі — вирівняти пам'ять раннера для '<набір>' …» і містить нумеровані виклики `unica.run {…}` та
  інколи команди kit. Виконується дослівно, без питання людині, але з межами розділу 3. Замість
  нього може бути рядок «ЗУПИНКА: …» з рецептом — це **зупинка**, не робота для тебе.
- **`unica.run`** — інструмент Уніки (MCP); в Claude Code його повне ім'я
  `mcp__plugin_unica_unica__unica_run` (точні імена перевіряє пункт 7). Аргументи в кроці мають
  форму `{"op":"<операція>","args":{…},"dryRun":true}`: спершу `dryRun:true` (прев'ю, показує
  попередження на кшталт `infobase_overwritten`), потім той самий виклик з `"dryRun":false`.
  Виклик `unica_run` з `{}` повертає словник операцій. Операції, які тобі трапляться: `push`
  (вихідники → база), `pull` (база → вихідники; лише з `force:true`), `infobase.create`,
  `infobase.restore`, `make` (збірка `.cf`/`.cfe`).
- **`push force` / `pull force`** — `force:true` вимикає звірку пам'яті раннера: `push force` — повне
  завантаження набору з git у базу, `pull force` — повне вивантаження бази з **заміною всієї теки
  набору** (разом з ігнорованими git файлами).
- **Попередження `infobase_state_unverified`** — відповідь `push` для набору, чиє дерево не
  змінилось проти хеш-пам'яті: набір пропущено без звірки покоління. `non_fast_forward` і
  `no_memory` — відмови `push` (покоління бази не збігається із записаним / пам'яті немає).
- **Дзеркало** — гілка `storage/<ключ>` у git: те, що kit переніс зі сховища. kit читає її як
  **локальну** гілку `refs/heads/storage/<ключ>`, а не `origin/storage/…`.
- **Пілотна гілка** — гілка споживача, яку назвав власник і на якій закомічено перехід на 1.5.0.
  Міграції 1.5.0 немає ні в головній гілці споживача (злиття туди заборонене), ні в гілках, не
  відгалужених від пілотної, а без неї `kit check` зупиняє кожну команду. Тому **в пілоті «головна
  гілка» з усіх рецептів і з текстів kit означає пілотну гілку**: клони роби з пілотної, гілки
  задачі відгалужуй від неї, а де kit порівнює з головною гілкою (`verify` без `-Ref`) — передавай
  `-Ref HEAD`. **Гілка задачі** — робоча гілка агента, відгалужена від пілотної.
- **Поставка вендора** — конфігурація клієнта на підтримці в постачальника. У git лежить
  `<набір>/Ext/ParentConfigurations.bin` (опис поставки); гітігнорований бінарний
  `<набір>/Ext/ParentConfigurations/*.cf` платформа вивантажує сама при повному вивантаженні. Поруч
  із `.cf` kit тримає позначку `.kit-bin-sha1` (SHA-1 того `.bin`, з якого вивантажено `.cf`). Стан
  поставки (рівно ці чотири значення друкує kit): `none` — `.bin` поставки не описує; `current` —
  `.cf` є, позначка дорівнює SHA-1 поточного `.bin`; `stale` — позначка не дорівнює SHA-1 `.bin`
  («застаріла»); `missing` — `.cf` або позначки немає («відсутня»). Повне завантаження набору з
  поставкою без `.cf` падає — тому стани `missing`/`stale` лікуються лише за рецептом (відновити
  `.cf` вивантаженням з бази, `pull`, і записати позначку, `kit canon … -MarkerOnly -Apply`). У
  онбордингу kit це рецепти: **(ii)** — свіжий клон, у якому поставка `missing`, і **(iii)** —
  поставка `stale`; обидва виконуються лише на пілотній гілці з чистим деревом: `provision` (за
  потреби) → `verify -Ref HEAD` → надрукований ним крок.
- **Критерій вирівнювання** — умова, за якої kit друкує `pull`: дерево набору в `HEAD` дорівнює
  дереву, яке він щойно вивантажив зі сховища (`git rev-parse HEAD:<шлях набору>` ==
  `git rev-parse storage/<ключ>:<шлях набору>`), і `git status --porcelain -- <шлях набору>` порожній.
  Інакше друкується `push` з `force:true`. Для **серверної** бази агента — завжди `push force`.
- **Одноразова база агента** — база агента, яку власник у повідомленні запуску **прямо назвав**
  такою, що її можна знищити й перестворити. Без цього — див. межі.

## 3. Межі

Дослівно:

- сховища конфігурацій — лише читання (жодних `ConfigurationRepositoryCommit`/`Lock`/`UnlockObjects`);
- база людини — лише читання; `push`/`push force` і `-ServerBase Existing` — **лише на базі, яку
  власник явно назвав одноразовою базою агента**;
- `-Apply` — у межах кроків цього брифу, інакше не робити;
- `git push`, PR, злиття в головну гілку споживача — ніколи;
- підрядки `лиценз`/`ліценз`/`license`/`HASP` у виводі платформи — зупинка й доповідь, а не привід
  чіпати служби, реєстр чи `nethasp.ini`;
- будь-яка розбіжність із «Очікувано» — зупинка пункту, сирий вивід у журнал, перехід до наступного
  незалежного пункту;
- **без обходів і без пояснень собі**;
- **секрети**: перед записом виводу в журнал вичитати його на пароль бази агента, пароль сховища,
  `dbms`/`cluster`-реквізити й рядки підключення з ними; збіг — замінити на `<приховано>` і записати
  в журнал рядок «витік у виводі, див. п. N» (це сам по собі дефект для архітектора). Журнал власник
  комітить лише після власної вичитки.

Доповнення, що випливають із цього і з інструментів, якими ти користуєшся:

- **Розбіжність пілоту з «Очікувано» — це зупинка пункту, а не привід щось полагодити.** Запиши
  сирий вивід у журнал, у «Підсумку для архітектора» сформулюй питання архітекторові (до нього
  звертається власник; напряму ти з ним не спілкуєшся), і йди до наступного пункту, який від
  зупиненого не залежить (залежності — у кінці розділу 6). Не знаходь обхід, не підбирай інший
  синтаксис тієї самої дії, не пояснюй собі, чому «виглядає нормально».
- **Незрозумілий стан робочого дерева** (чужі зміни, брудне дерево після `pull`, невідомі файли) —
  зупинка пункту. **Ніколи** не виконуй `git checkout -- <шлях>`, `git restore`, `git stash`,
  `git clean`, `git reset --hard`: вони безповоротно знищують чужу незакомічену роботу. Своє
  незакомічене не відкочуй — фіксуй і питай.
- **Коміти:** лише на пілотній гілці та гілках з префіксом `pilot/` (`pilot/eol-<дата>`,
  `pilot/task-<дата>-<номер>`), які ти сам створив, і лише якщо власник у повідомленні запуску
  дозволив коміти; точково: `git add <явний перелік>` і
  `git commit --only -m "<повідомлення>" -- <ті самі шляхи>` (`-m` йде **до** `--`); без `-a`/`-A`/`.`.
  Дозволу немає — зупинка там, де без коміту не продовжити. Якщо коміт відхиляє хук `pre-commit` —
  зупинка пункту, сирий вивід хука в журнал і доповідь; не вимикай хук, не став змінних оточення,
  не міняй гілку чи шлях, щоб його минути.
- Журнал не містить пояснень «чому, мабуть, так вийшло»: лише команда, сирий вивід і висновок, який
  прямо випливає з виміру.
- Якщо вивід містить секрет (пароль бази агента чи сховища, рядок підключення з `Pwd=`/`SPwd=`,
  `dbms`/`cluster` з паролями) — це знахідка «витік у виводі», зафіксуй її за правилом вище. Значення
  паролів, щоб шукати їх у виводі, читай із `v8project.local.yaml`/накладки в змінну оболонки, не
  друкуючи, і шукай через `Select-String -SimpleMatch`.

## 4. Власник: перемикання і відкіт

Цей розділ — для власника машини, не для тебе. Ти починаєш роботу, коли власник виконав
перемикання й відкрив **нову сесію**; ти його не повторюєш. Тут він потрібен, щоб ти знав, що має бути
встановлено до початку, і що робити, якщо пілот доведеться відкотити.

**Перемикання (kit 1.5.0 з локального маркетплейсу).**

1. Знімок kit на названому коміті (не жива робоча копія: плагін з локального маркетплейсу
   вантажиться на місці з теки, тож правки в теці діють з наступної сесії):

       mkdir %USERPROFILE%\.claude\local-marketplaces\smp-v8storagekit\v8storagekit
       git -C R:\github\SMP_V8StorageKit archive <коміт> | tar -x -C %USERPROFILE%\.claude\local-marketplaces\smp-v8storagekit\v8storagekit

   (або detached `git worktree add` на цьому коміті).
2. У `%USERPROFILE%\.claude\local-marketplaces\smp-v8storagekit\.claude-plugin\marketplace.json`:
   `name: smp-v8storagekit`, плагін `v8storagekit` з `"source": "./v8storagekit"` (ім'я маркетплейсу
   лишається тим самим — ідентифікатор `v8storagekit@smp-v8storagekit` у шаблонах споживачів не
   змінюється). Файл писати редактором, не heredoc (зворотні слеші). Перевірка:
   `claude plugin validate <тека>` → `✔ Validation passed`.
3. `claude plugin uninstall v8storagekit@smp-v8storagekit`, потім
   `claude plugin marketplace remove smp-v8storagekit` (маркетплейс із тим самим ім'ям з GitHub мусить
   бути прибраний перед `add`; `remove` стирає дані плагіна), потім
   `claude plugin marketplace add <тека>`, потім `claude plugin install v8storagekit@smp-v8storagekit`.
4. Ознака успіху — поля, а не текст відповіді: `claude plugin list --json` → `"id":
   "v8storagekit@smp-v8storagekit"`, `"version": "1.5.0"`, `"readFromFolder": "<тека>\\v8storagekit"`,
   `"folderVersion": "1.5.0"`. Нова сесія.
5. Уніка 0.13: `claude plugin marketplace update unica`, потім `claude plugin update unica@unica`.
   Ознака — версія 0.13.x у `claude plugin list`, а скіла `unica:v8-runner` немає. Нова сесія; перший
   старт MCP Уніки качає рантайм.
6. `pwsh -NoProfile -File "<корінь>/tools/check-environment.ps1"` — рядок `Плагін unica` з версією
   0.13.x без зауважень, платформа 1С 8.3.27.x знайдена.

**Відкіт.**

- **Уніка 0.12.3.** Тег `#v0.12.3` НЕ годиться: на цьому тегу маркетплейсу лежить каталог `version
  0.12.2`. Хеш через `#<повний sha>` команда `marketplace add` не приймає. Робочий маршрут:

      git clone https://github.com/IngvarConsulting/unica-marketplace.git <тека>
      git -C <тека> checkout --detach 1a89beac10efbf5e04a35bd4a3cccc7487bbb658
      claude plugin uninstall unica@unica
      claude plugin marketplace remove unica
      claude plugin marketplace add <тека>
      claude plugin install unica@unica

  Ознака успіху: `claude plugin list --json` → `"version": "0.12.3"`, `installPath` закінчується на
  `cache\unica\unica\0.12.3`, у кеші є `skills\v8-runner`. Нова сесія. Після цього
  `claude plugin marketplace update unica` тягнутиме теку-клон, а не `main`; повернення на 0.13:
  `claude plugin marketplace remove unica`, потім
  `claude plugin marketplace add IngvarConsulting/unica-marketplace`.
- **kit 1.4.0.** `claude plugin uninstall v8storagekit@smp-v8storagekit`, потім
  `claude plugin marketplace remove smp-v8storagekit`, потім
  `claude plugin marketplace add VSydorenko/SMP_V8StorageKit`, потім
  `claude plugin install v8storagekit@smp-v8storagekit`. Ознака: `version 1.4.0`, `installPath` у
  `cache\smp-v8storagekit\v8storagekit\1.4.0`, поля `readFromFolder` немає.

Ознака оновлення плагіна — завжди поля `claude plugin list --json`, а не текст відповіді команди

### Пункт 2. `sync` → вирівнювання `pull force` → дерево набору чисте [гіп]

Теза: після `UpdateCfg` дерево дзеркала дорівнює тому, що віддасть база, а `pull force` Уніки
вивантажує **побайтово те саме**, що вивантажив kit, тож після нього `git status` набору порожній.
Кодом доведено, на живій платформі не виміряно.

- **Команда.** Файлова база агента, набір без поставки або з нею (вибери той, де є нові версії у
  сховищі; для розширення — окремий прохід). Як дізнатись про нові версії: спершу прев'ю
  `kit sync -RepoRoot . -Workspace <ws> -Source <ключ>` (без `-Apply`) — воно називає версії, які
  прийшли б зі сховища; їх кількість запиши в журнал (шапка «Середовище»). На пілотній гілці з
  чистим деревом (перед `-Apply` перевір `git branch --show-current` — це не головна гілка споживача):

      pwsh -NoProfile -File "<корінь>/tools/kit.ps1" sync -RepoRoot . -Workspace <ws> -Source <ключ> -Apply

  Не передавай `-MergeMain` і `-DumpPlatform`. Умова: нових версій у сховищі ≥ 1 (для 0 версій крок не
  друкується за дизайном — тоді запиши «умову не виконано» і використай запасну форму нижче).
  Для набору `CONFIGURATION` з поставкою **до** `pull` зніми
  `Get-ChildItem -Force -Recurse "<шлях набору>/Ext/ParentConfigurations" | Select-Object FullName,Length`.
  Виконай надрукований крок: `unica_run` з `dryRun:true`, потім `false`. Потім:

      git status --porcelain -- <шлях набору>

  Запасна форма за відсутності нових версій: `kit verify … -Source <ключ> -Ref HEAD` на чистому
  дереві (`-Ref HEAD`, бо за замовчуванням `verify` порівнює з головною гілкою); кроком має стати той
  самий `pull`. **Перед нею базу агента треба завантажити з `HEAD`**: звичайним `push` по набору
  (`dryRun:true`, потім `false`; на базі без пам'яті — `push` з `"force":true`), на одноразовій базі;
  інакше `pull force` перепише дерево набору станом бази, а не станом `HEAD`. У журналі явно
  запиши «використано запасну форму `verify -Ref HEAD`» і що саме було завантажено перед нею.
- **Очікувано.** `sync` друкує блок «Далі — вирівняти пам'ять раннера для '<ключ>' … pull: дерево
  набору дорівнює вивантаженому kit» з викликом `unica.run {"op":"pull","args":{"sourceSet":"<ключ>"[,
  "extension":"<ключ>"],"force":true},"dryRun":true}` (для набору `EXTENSION` аргумент `extension`
  присутній). Після виконання `pull` `git status --porcelain -- <шлях набору>` **порожній**. Якщо ж
  непорожній — kit пише, що вивантаження раннера дало інші байти, ніж kit: це **зупинка** з доповіддю,
  не робота для тебе.
- **Записати.** Який крок надруковано (pull чи push) і чому (рядок «критерій не обчислено», якщо є);
  вивід `git status --porcelain` (при непорожньому — ще `git diff --stat -- <шлях набору>` і перші
  20 рядків `git diff` за умови, що в них немає секретів); стан `Ext/ParentConfigurations/` до і після
  `pull` (перелік файлів з розмірами); код виходу `sync`.
- **Запасна гілка (для архітектора, не для тебе).** Якщо дерево брудне — архітектор зведе
  вирівнювання для всіх випадків до `push force`. Ти цього не робиш і дерево не чистиш.

    прибирає `<workPath>/infobases/origin/`; `push force` проходить.
  - Записати: що надруковано, відповідь `push`, стан теки `origin` до і після.

### Пункт 4. `make` кладе `.cfe` у `build/artifacts` воркспейсу [док]

- **Команда.** Набір `EXTENSION`. `unica_run` з `{}` — прочитай словник і форму аргументів `make`.
  Потім `kit build -RepoRoot . -Workspace <ws>` без `-Apply` — прев'ю друкує точний виклик `make`.
  Його форма: `unica_run` з `{"op":"make","args":{"sourceSet":"<розширення>","extension":"<розширення>",
  "output":"build/artifacts/<розширення>.cfe"},"dryRun":true}` — `output` **відносний до
  воркспейсу** (платформа Уніки відмовляє, якщо шлях виходить за воркспейс), тож файл ляже в
  `<ws>/build/artifacts/<розширення>.cfe`; виконай його (`dryRun:true`, потім `false`). Якщо
  надрукований kit виклик відрізняється від цього — виконуй надрукований і запиши розбіжність. Потім
  `Get-ChildItem -Recurse "<ws>/build/artifacts"`, далі:

      pwsh -NoProfile -File "<корінь>/tools/kit.ps1" build -RepoRoot . -Workspace <ws> -Apply

  і `Get-ChildItem -Recurse "build/artifacts"` у корені репозиторію.
- **Очікувано.** `make` лишає `.cfe` у `<ws>/build/artifacts`; `kit build -Apply` забирає його в
  кореневу теку `build/artifacts/` репозиторію (`.cf`/`.cfe` kit сам не будує — лише забирає).
- **Записати.** Точний виклик `make`, що відповіла Уніка (шлях, розмір файлу), перелік обох тек до й
  після `kit build`.

### Пункт 5. Рядок підключення `Srvr="…";Ref="…"` у лапках [гіп]

Потрібна серверна база агента, названа одноразовою. Немає — «не відтворено».

- **Команда.** Збережи поточний текст `connection` для `infobases.origin` у `v8project.local.yaml`

  значень, тими самими `Srvr`/`Ref` — у YAML це `connection: 'Srvr="<сервер>";Ref="<база>";'`.

- **Очікувано.** `kit check` лапок не відхиляє (парні приймаються; непарні відхиляються); `push`

- **Записати.** Вивід `kit check` (рядок підключення в журналі — як `Srvr=<приховано>`), відповідь

### Пункт 8. Серверна база агента: створення і `push force`; `sync` на серверній [гіп]

Потрібні серверна одноразова база і реквізити від власника (СУБД: `kind`, `server`, `name`,
`locale`, `user`, `password`; адміністратор кластера: `user`, `password`). Немає кластера —
«не відтворено». Секрети лише в `v8project.local.yaml`; у журнал не потрапляють. Допустимі значення
`kind` kit не перевіряє (лише що значення не порожнє) — їх визначає раннер Уніки, тож `kind`
бери дослівно від власника; відмову раннера через `kind` фіксуй як результат пункту, не підбирай
інше значення. Перед пунктом збережи копію `v8project.local.yaml` (див. вище про стан бази).

- **Команда.** У `infobases.origin` `v8project.local.yaml` виставити `connection: 'Srvr=<сервер>;Ref=<база>;'`,
  блок `dbms {kind, server, name, locale, user, password}` і блок `cluster {user, password}`. Прев'ю:
  `kit provision -RepoRoot . -Workspace <ws> -ServerBase New` (без `-Apply`) — воно друкує
  застереження про `CrSQLDB=Y`: **ім'я бази даних СУБД підтверджує власник**, ще до `-Apply`
  (`CrSQLDB=Y` мовчки бере наявну БД з тим самим іменем). Механізм: зупинись, процитуй власникові в
  сесії рядок застереження (з іменем БД і сервера з прев'ю) і чекай його прямої відповіді в сесії
  «ім'я БД `<ім'я>` підтверджую»; слова з повідомлення запуску про «база одноразова» підтвердженням
  імені не є. Підтвердження (дослівно) запиши в журнал. Без нього `-Apply` не виконуй — пункт
  «не відтворено». Лише після підтвердження:
  `kit provision … -ServerBase New -Apply`, виконати надрукований `infobase.create`, потім
  `push` з `force:true`. Окремо, після цього, на серверній базі:
  `kit sync -RepoRoot . -Workspace <ws> -Source <ключ> -Apply` (потрібна ≥ 1 нова версія сховища;
  нема — «умову не виконано»).
- **Очікувано.** Уніка передає раннеру блоки `dbms` і `cluster` (`infobase.create` вдалий; база в
  кластері створена порожньою із забороною регламентних завдань); після неї `push force` проходить; після
  `sync` на серверній базі kit друкує `push` з `force:true`, **а не `pull`** (на серверній `pull`
  немає за побудовою).
- **Записати.** Прев'ю `provision`, відповіді `infobase.create` і `push` (параметри підключення в
  журналі — лише у прихованому вигляді), крок після `sync`.

### Пункт 9. Користувач і пароль бази агента [док; вивід платформи — не виміряно]

База агента вимагає вхід: у `infobases.origin` є `user` і `password` (тестові, одноразова база).
Значення пароля прочитай у змінну оболонки без друку.

- **Команда.** (а) Виконай `push` Уніки (`dryRun:true`) на цій базі; (б) `kit sync … -Source <ключ>`
  (без `-Apply`); (в) `kit canon … -Source <ключ>` (без `-Apply`). Кожен вивід (і відповідь MCP-інструмента
  Уніки — перепиши її текст у файл власноруч) збережи у файл у системній тимчасовій теці й перевір, що значення пароля в ньому немає:
  `Select-String -Path <файл> -SimpleMatch -Pattern $kitSecret` (змінна `$kitSecret` не друкується;
  не називай її `$pwd` — це системна змінна PowerShell; результат пошуку має бути порожній). (г) Один вивід **з тексту зупинки, що містить вивід платформи** (рядок із
  `/Out`-логом): якщо він трапився в пунктах 1–8, використай його; якщо ні — домовся з власником про
  безпечний спосіб викликати зупинку на одноразовій базі (наприклад, ненаявне джерело чи пошкоджена
  база) і виконай його лише за дозволом; якщо способу нема — «не відтворено».
- **Очікувано.** (а)–(в) заходять у базу без запиту пароля; пароль бази агента не з'являється ні у
  виводі kit, ні (г) у логу платформи `/Out`, який kit прокидає в тексти зупинок.
- **Записати.** Для кожного з (а)–(г): команда, чи був запит пароля, результат пошуку пароля у
  виводі (збіг/нема — без самого пароля).

### Пункт 10. `unica.apply` і кінці рядків CRLF [гіп щодо профілю]

Робиться на окремій гілці, відгалуженій від пілотної, щоб не лишити брудне дерево:
`git switch <пілотна гілка>`, потім `git switch -c pilot/eol-$(Get-Date -Format yyyyMMdd)` (коміт на
ній — за розділом 3; після фіксації результату `git switch <пілотна гілка>`).

- **Команда.** Знайди в наборі файл `.bsl` (і `.xml`) з CRLF: `git ls-files --eol -- <шлях набору>`
  (ознака `i/crlf w/crlf`), і впевнись, що політика репозиторію — `-text`/без перетворення кінців
  (`git check-attr text eol`). Через `unica_apply` (він працює планом: спершу виклик повертає план та
  `executionToken`, потім виклик із токеном застосовує; форму аргументів бери з опису інструмента й
  з `unica_docs`) (а) змінь наявний `.bsl`, (б) додай новий `.bsl`, (в) змінь наявний `.xml`
  (наприклад, синонім чи коментар у модулі). Після кожного застосування порахуй байти в зміненому й
  новому файлах:

      $b=[IO.File]::ReadAllBytes("<файл>"); $crlf=0;$lf=0
      for($i=0;$i -lt $b.Length;$i++){ if($b[$i] -eq 10){ if($i -gt 0 -and $b[$i-1] -eq 13){$crlf++}else{$lf++} } }
      "CRLF=$crlf LF=$lf"

  і `git ls-files --eol -- <файл>`, `git diff --stat`.
- **Очікувано.** Спека допускає два результати: Уніка тримає профіль кінців рядків файлу
  (змінений файл з CRLF лишається CRLF, новий — за профілем репозиторію/сусідніх файлів) **або**
  пише LF. Розбіжності між «CRLF/LF» — це відповідь на питання пілоту, не помилка; помилка — змішані
  кінці в одному файлі.
- **Записати.** Для кожного файла: кількість CRLF і LF до й після, `git ls-files --eol`, чи змінились
  сусідні рядки (весь файл у `git diff` — ознака перетворення кінців). Приклад точного виклику
  `unica_apply`.

### Пункт 11. `pull force` на `CONFIGURATION` з поставкою вендора [гіп]

Потрібен набір `CONFIGURATION` з поставкою вендора (у git є `Ext/ParentConfigurations.bin`). Немає —
«не застосовно», запиши це.

- **Команда.** Якщо знімки з пункту 2 для такого набору є — використай їх, інакше: стан поставки
  (`kit check -RepoRoot .` показує поставку; попередження «поставка вендора відсутня/застаріла»),
  перелік `Ext/ParentConfigurations` (файли, розміри), потім надрукований кроком `pull` (див. пункт 2).
  Після `pull`: той самий перелік; `git status --porcelain -- <шлях набору>`; наявність позначки
  `.kit-bin-sha1`. Якщо `.cf` є, а позначки нема —
  `kit canon -RepoRoot . -Workspace <ws> -Source <ключ> -MarkerOnly -Apply`, потім перевір позначку
  й `kit check`. Окремо: `infobase.create` (через `provision -Force`, як у пункті 3а) на придатному
  дереві з поставкою `current`.
- **Очікувано.** `pull force` кладе `.cf` у `Ext/ParentConfigurations/` (платформа виводить його
  при повному вивантаженні), але знищує позначку `.kit-bin-sha1` (бо стирає теку набору цілком);
  режим `canon -MarkerOnly -Apply` лише пише позначку (передумови: набір `CONFIGURATION`, поставка ≠
  `none`, `.cf` на місці, дерево набору чисте; наявна позначка при `-MarkerOnly` — відмова з рецептом
  «спершу надрукований pull»). `infobase.create` на придатному дереві з поставкою проходить.
- **Записати.** Перелік `Ext/ParentConfigurations/` до й після `pull`; що сталося з іншими
  ігнорованими файлами теки набору (`git status --ignored --porcelain -- <шлях набору>` до й після);
  стан поставки до й після (`kit check`); результат `canon -MarkerOnly -Apply`; результат
  `infobase.create`.

### Пункт 12. Рецепт (ii) наскрізно: свіжий клон, поставка без `.cf` [гіп]

Потрібен набір `CONFIGURATION` з поставкою (інакше — «не застосовно»). Усе — у **окремому клоні**
поза робочою копією, не торкаючись основної. «Головна гілка» рецепта (ii) у пілоті — **пілотна
гілка** (див. глосарій): на головній гілці споживача міграції 1.5.0 немає, і `kit check` зупиняв би
кожну команду.

- **Підготовка клона.** (а) Якщо пілотну гілку запушено: `git clone <origin споживача> -b <пілотна гілка>
  <тека клона>`; якщо ні — локальний клон з робочої копії тестера: `git clone <шлях робочої копії> -b
  <пілотна гілка> <тека клона>` (тут `origin` клона — робоча копія). (б) kit читає дзеркало як
  **локальну** гілку `refs/heads/storage/<ключ>`, а клон створює лише `origin/storage/*` і не локальні.
  Створи їх у клоні: `git fetch origin 'refs/heads/storage/*:refs/heads/storage/*'` (або по одній:
  `git branch storage/<ключ> origin/storage/<ключ>`) і перевір
  `git branch --list 'storage/*'`. Якщо в `origin` дзеркал немає (`git ls-remote --heads origin
  'storage/*'` порожній) — пункт «не відтворено» з цією причиною. (в) Чисте дерево:
  `git status --porcelain` порожній, `git branch --show-current` — пілотна гілка.
- **Команда.** У клоні немає гітігнорованих файлів: ні `v8project.local.yaml`, ні `.cf`. Скопіюй
  накладку `v8storagekit.local.yaml` з основної копії (вона містить секрети, не друкуй). Кроки:
  1. `kit provision -RepoRoot . -Workspace <ws>` — очікувана зупинка: бази агента не налаштовано,
     рецепт `v8storagekit:provision`. Створи в клоні `v8project.local.yaml` з
     `infobases.origin.connection: 'File=build/ib'` (файловий шлях усередині клона, одноразова база).
  2. `kit provision -RepoRoot . -Workspace <ws> -Apply` — kit сам створює порожню базу (дерево з
     поставкою `missing` до завантаження не придатне).
  3. `kit verify -RepoRoot . -Workspace <ws> -Source <ключ> -Ref HEAD` → виконай надрукований крок
     (`pull`) як у пункті 2.
  4. `kit canon -RepoRoot . -Workspace <ws> -Source <ключ> -MarkerOnly -Apply`.
  5. Звичайний `push` Уніки (`dryRun:true`, потім `false`) по цьому набору.
  6. `kit check -RepoRoot .`.
- **Очікувано.** Крок 2 створює порожню файлову базу; крок 3 друкує `pull` для набору (дерево рівне
  дзеркалу, поставка `missing` → друкується `pull` і другий рядок `kit canon … -MarkerOnly -Apply`);
  після кроку 4 позначка є; `push` у кроці 5 проходить без `no_memory`/`non_fast_forward`;
  `kit check` не має знахідок щодо поставки вендора.
- **Записати.** Вивід кожного кроку; стан поставки (`kit check`) після кроків 2, 3, 4, 6.

### Пункт 13. Приймальний критерій: робота гілки задачі не губиться [гіп щодо кроку]

Закриває проблему «після `sync -Apply` прев'ю `adopt` хибно порожнє». Потрібні одноразова база
агента й **участь власника**: лише він, у Конфігураторі, кладе зміну в сховище — ти в сховище не
пишеш. Тестер на цьому місці зупиняється й чекає (див. крок 2).

- **Команда.** Усі гілки цього пункту називай `pilot/task-<дата>-<номер>` (коміти дозволено лише на
  `pilot/…` і пілотній гілці). «Головної гілки» в пілоті немає (глосарій): гілку задачі
  відгалужуй від **пілотної**: `git switch <пілотна гілка>`, `git switch -c pilot/task-<дата>-1`.
  Якщо коміт відхиляє `pre-commit`-хук (гілки `storage/*` пише лише `kit sync`; хук може відхилити
  й інше) — це зупинка пункту й доповідь із сирим виводом хука, **без обходу** (не вимикай хук, не
  став змінних оточення, не змінюй гілку, щоб його минути).
  1. На гілці задачі внеси в набір `CONFIGURATION` зміну, **яку власник не переноситиме в
     сховище** (наприклад, новий коментар у модулі); закоміть; завантаж у базу агента `push`
     (`dryRun:true`, потім `false`; на базі без пам'яті — з `"force":true`).
  2. **Участь власника, названо явно.** Запиши в журнал «очікує власника: покласти в сховище
     `<ключ>` частину роботи, відмінну від зміни з кроку 1» і скажи про це власникові в сесії. Далі
     нічого не роби, доки власник у сесії не підтвердить, що поклав версію в сховище.
  3. Після підтвердження, на гілці задачі: прев'ю `kit sync -RepoRoot . -Workspace <ws> -Source
     <ключ>`, потім `kit sync -RepoRoot . -Workspace <ws> -Source <ключ> -Apply`. Виконай надрукований
     крок (очікується `push` з `"force":true` для гілки задачі).
  4. `kit canon -RepoRoot . -Workspace <ws> -Source <ключ> -Apply`. Якщо `canon` змінив файли —
     закомітити на гілці задачі **до** `adopt`, точково (скіл reconcile kit):
     `git rm -r -q --cached -- <шлях набору>`, `git add -- <шлях набору>`,
     `git diff --cached --name-only` (має показати лише шлях набору),
     `git commit -m "canon: дерево у форматі платформи"` (без `-a`). Не змінив — коміту нема.
  5. Прев'ю: `kit adopt -RepoRoot . -Workspace <ws> -Source <ключ>` (без `-Apply`; `-Apply` не
     виконуй — заміна дерева виходить за пілот).
  6. **Окремо (сітка)** — на новій гілці `pilot/task-<дата>-2` від пілотної повтори кроки 1–3
     (крок 2 — знову участь власника: потрібна ще одна нова версія в сховищі), але після
     `sync -Apply` замість надрукованого кроку виконай звичайний `push` без `force` по цьому
     набору (`dryRun:false`).
- **Очікувано.** (3) `sync -Apply` на гілці задачі друкує `push` з `"force":true`, не `pull`; (5)
  прев'ю `adopt` у переліку «зникне» називає саме ту роботу, яку власник не переносив (твоя зміна з
  кроку 1), а не порожній список; (6) звичайний `push` на незміненому дереві гілки відповідає
  попередженням `infobase_state_unverified` **з назвою набору** (а не мовчить) — тоді виконай
  `push` з `"force":true` для названого набору (так вимагає правило контуру для баз агента:
  `infobase_state_unverified`/`non_fast_forward` не ігнорувати).
- **Записати.** Вивід кожного кроку; точний текст «зникне» з прев'ю `adopt`; відповідь звичайного
  `push` (чи є попередження і яка назва набору); що саме виконано після нього.

## 7. Формат журналу

Для кожного пункту (0, 1 … 13) у журналі:

- **Команда** — повна, як виконана;
- **Сирий вивід** — без обрізання (жодних `head`/`tail`), але з приховуванням секретів за правилом
  розділу 3;
- **Висновок:** одне з трьох — **підтверджено** (збіг з «Очікувано»), **спростовано** (розбіжність),
  **не відтворено** (умову пункту не виконано: нема потрібної бази, версії у сховищі, `.dt`,
  кластера, допуску) — **з умовою виміру**: на якій базі (файлова/серверна), наборі, гілці, які
  були нові версії сховища, версії плагінів.

Для «спростовано» додатково: сирий вивід розбіжності, що ти зробив після неї (нічого, окрім
фіксації) і питання до архітектора. У «Підсумку для архітектора» окремо: список спростованих
пунктів, список «не відтворено» з причинами, знахідки про `upgrades.md`, витоки секретів.

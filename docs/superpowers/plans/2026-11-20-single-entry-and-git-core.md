# План: одна точка входу, один контракт кодів виходу, одне ядро запуску git (#51)

## 1. Шапка

- **Статус:** чернетка автора плану. Зафіксовано виміри §5 спеки й контракт блоку — мовно-нейтрально. Задачі реалізації — лише каркас: власник вирішує, чи лишається реалізація на PowerShell, чи переходить на іншу мову (кандидат — Go; архітектор пропонує спершу спайк). Після рішення автор розписує задачі під обрану мову, потім аудит за ризиком і `codex-audit`. Приймає план архітектор блоку (сесія `smp-v8storagekit-1a`).
- **Спека:** `docs/superpowers/specs/2026-11-20-single-entry-and-git-core-design.md` на коміті `c557203` (D1–D5 і поправка D4а). Посилання — `doc <спека> §N`.
- **Якорі після X:** немає; план спирається на `main` після злиття #49 (1.6.3).
- **Робоча копія:** `workspace.mode = worktree`, дерево блоку `.worktrees/51-single-entry`, гілка `issue-51-single-entry`. Бази агента тут немає (ADR-0005); спільний ресурс — локальний маркетплейс `smp-v8storagekit`, блок його не чіпає.
- **Заборони:** повний прогін без `-ExcludeTag Integration` не запускати; дозволи (`.claude/settings.json`, `templates/settings.json`) не змінювати без рішення власника (§9).

## 2. Мета / Архітектура / Спека

**Мета.** Прибрати три наслідки склейки двох інструментів (спека §1): два входи з різною прив'язкою аргументів, два контракти кодів виходу, десять місць запуску git з трьома контрактами збою.

**Архітектура.** Один вхід маршрутизує обидві родини команд одним розбором аргументів. Один контракт кодів `0–4` і рядки `<команда>: ERROR …` / `next: …`. Одне ядро запуску git з двома входами (зібраний вивід і потоковий обмін). Запобіжник — структурна перевірка, що не пускає запуск git поза ядро. Мова реалізації — рішення власника; контракт нижче від неї не залежить.

**Спека:** §1 (навіщо, інвентар), §2 D1–D5 і D4а, §3 інваріанти, §4 поза обсягом, §5 (виміряно в §3 плану), §6 ризик, §7 процес.

## 4. Контракт блоку (мовно-нейтральний)

**К1. Вхід і аргументи (D1, D2).**
1. Один вхід `kit <команда> [аргументи]` для команд сховища й процесу. Обгортки `bin/` (Bash і PowerShell) кличуть цей вхід; короткі імена процесу (`sdd`, `pr-gate`, `doc`, …) лишаються. `tools/kit-process.ps1` зникає.
2. Розбір — один для обох родин, форма нинішнього `ConvertFrom-KitArguments`: позиційні токени; `-Ім'я значення`, `-Ім'я:значення`, `-Прапорець`, `-Прапорець:true|false`; імена нечутливі до регістру; `-Help`/`--help` завжди; `--ім'я` — помилка виклику з підказкою. Значенням стає наступний токен, якщо він не є відомим іменем.
3. Команди сховища: `-RepoRoot` (умовчання — поточна тека), `-Workspace`, `-Source`, `-Apply` — лише в тих командах, що їх оголошують; позиційний токен — помилка виклику. Команди процесу: корінь — поточна тека, `-RepoRoot` не приймають.
4. Невідома команда чи параметр, параметр без значення, спільний параметр, якого команда не оголошує — код `2`, а команда не запускається.
5. Команда процесу не платить за ініціалізацію сховища (зараз — вибірковий імпорт модулів); префлайт сховища — лише для команд сховища.
6. Хук старту сесії кличе вхід абсолютним шляхом плагіна, не `kit` з `PATH`.

**К2. Коди й рядки (D3).** `0` виконано/так; `1` зупинка/ні/відмова; `2` помилка виклику; `3` не перевірено, ніколи не зелений; `4` виконано, є наступний крок (`sync`: дзеркало оновлено, злиття ні; `verify`/`session-check`: є що робити). Помилка — перший рядок stderr `<команда>: ERROR <причина>`. `next: <команда>` — останній рядок успіху там, де є детермінований наступний крок (на затвердження — §6, Р3). Хук: `0` — друк як є (порожньо — тиша); `1` і `4` — друк виводу, порожній — «стан НЕВІДОМИЙ»; будь-який інший код — «неочікуваний код». Сумісності зі старими кодами немає.

**К3. Ядро git (D4, D4а).**
1. Кожен запуск git: `-c core.quotepath=false`; stdout і stderr як UTF-8; `GIT_TERMINAL_PROMPT=0`; оточення успадковане від поточного процесу (зокрема `V8KIT_SYNC`, `GIT_AUTHOR_DATE` на час коміту дзеркала); stdout і stderr читаються одночасно й до запису stdin (інакше дедлок на великому виводі — коментар `Invoke-KitGitProcess`).
2. Вхід «зібраний вивід» (`Invoke-KitGit`): stdin — текст або записи через NUL; результат — код, stdout, stderr. Контракт збою обирає викликач явно: без дозволу на збій — виняток з дослівним stderr git; з дозволом — об'єкт з кодом. Режиму «тихий `$null`/порожній рядок» немає.
3. Вхід «потоковий обмін» (`Start-KitGitProcess`): запуск з налаштуваннями п.1, повертає запущений процес; байтовий обмін веде викликач; кличе лише `Export-KitTree`.
4. Усі обгортки з інвентарю спеки §1 і прямі запуски з §3 (5.2+) переходять на ядро або зникають. Штатні ненульові коди git (`check-ignore` 1, `merge-base --is-ancestor` 1, `diff --quiet` 1, `check-ignore --stdin`) — лише через явний дозвіл на збій з перевіркою коду.
5. Байти, які kit порівнює чи хешує (`-z`-вивід, `ls-tree`, `cat-file`, діфи `verify`/`adopt`/`TreeCompare`), після переходу ті самі. Зокрема: якщо реалізація не знімає BOM, як знімає нинішнє декодування .NET, жоден викликач не сміє від цього залежати — перевірити місця, де вивід git порівнюється з рядком.

**К4. Запобіжники (D5).** (1) Структурна перевірка: запуск git у коді kit (`tools/` без тестів, `hooks/`, `bin/`) — лише в модулі ядра; перевірка має контроль сліпоти (влучення в ядрі є, викликів ядра — понад 10) і набір мутацій, які мусить ловити. Для PowerShell форму виміряно (§3, 5.5, детектор B). (2) Тест ядра на справжньому git: кириличний шлях без вісімкових кодів, з `-z` і без; NUL-записи з кирилицею на stdin; бінарний блоб байт у байт через потоковий вхід; збій без дозволу — виняток з текстом stderr. Контроль: тест на вісімкові коди червоніє, якщо прибрати `quotepath=false` з ядра. (3) Тест контракту К2: кожен код `0–4` хоча б однією справжньою командою підпроцесом; контроль — команда, що свідомо віддає інший код, червонить твердження.

## 9. Задачі власника

Виконуються лише після схвалення.

1. Рішення про мову реалізації (PowerShell чи інша) — від нього залежить §7.
2. Пілот на локальному маркетплейсі перед злиттям: `kit sync`/`kit verify`/`kit session-check` у Bash і PowerShell на справжньому репозиторії-споживачі, хук старту сесії, одна команда процесу.
3. Чи додавати в `templates/settings.json` дозвіл без запиту для діагностики `kit check` і `kit session-check` (зараз дозволів на команди сховища там немає). Умовчання плану — не додавати.
4. Тег, `gh release`, `ref` у `marketplace.json` — після злиття, за порядком релізу з `CLAUDE.md`.

## 10. Підсумок аудиту

Аудит не запускався: за вказівкою архітектора — до рішення власника про мову, щоб не витратити його на план, який може змінитись. Після рішення: класифікація ризику (`skills/plan/references/audit-risk.md`), аудитор `v8storagekit:auditor` на лінзу, потім `codex-audit`.

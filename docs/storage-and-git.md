# Контур «сховище ↔ git»

Документ описує архітектуру конвеєра, яким плагін Claude Code `v8storagekit` синхронізує
сховища конфігурацій 1С із git у репозиторії-споживачі. Це модель **1.0**: сховище
лишається істиною в останній інстанції, але git тепер — робоче середовище **агента**, а не
лише дзеркало для «хто змінив рядок». Агент працює у власній базі, на власній гілці задачі,
і повертає людині зібрані артефакти; людина застосовує їх у своїй базі сама.

Модель 1.0 замінює модель 0.6.0 повністю, не частково: там був один закомічений файл стану
`storage.json` на продукт, реплей ішов у поточну робочу гілку, і жодного розділення на
гілку задачі агента й головну гілку не було. У 1.0 немає файлу стану — стан виводиться з
git (трейлери комітів), сховище кожного джерела дзеркалиться в окрему orphan-гілку
`storage/<ключ>`, а структуру репозиторію описує маніфест `v8storagekit.yaml` разом із
`v8project.yaml` Уніки, а не жорстко зашита конвенція «тека продукту = ім'я розширення».

Архітектурне обґрунтування цієї моделі, з переліком блоків реалізації, —
`docs/superpowers/specs/2026-09-03-agent-contour-design.md`; цей документ — карта того, що
з неї реально збудовано, для читача, який працює з репозиторієм, а не проєктує його.

## Команди kit

Один диспетчер `tools/kit.ps1 <команда>` зі спільним префлайтом (`Invoke-KitPreflight`,
`tools/lib/Preflight.psm1`): читає й валідує маніфест, накладку, перевіряє, що кожен
`workspaces[].path` існує і містить `v8project.yaml`, і що кожен ключ `sources` відповідає
`name:` source-set у ньому. Команд рівно десять — окремі модулі `tools/commands/*.psm1`:

| Команда | Що робить | Платформа | Мутує |
|---|---|---|---|
| `check` | аудит: маніфест ↔ `v8project.yaml` ↔ `.gitignore`/`.gitattributes` ↔ `Configuration.xml` ↔ інваріанти `storage/*` ↔ хуки | ні | ні |
| `session-check` | дешевий сигнал старту сесії: чи є нові версії у сховищах, чи `storage/*` розійшлися з `main` | ні | ні |
| `sync` | реплей нових версій кожного джерела `truth: storage` у `storage/<ключ>`; перше злиття в головну гілку | так | git, робочі теки під `build/` |
| `dump` | дамп джерела `truth: dump`/`vendor` з живої бази за накладкою | так | файли дерева |
| `verify` | звірка дерева `ref` із канонічним дампом зі сховища на версії з трейлера | так | ні (звірочний коміт — лише з `-Apply`) |
| `canon` | `/DumpConfigToFiles` з бази агента назад у дерево кожного джерела воркспейсу | так | файли дерева |
| `provision` | база агента: порожня (`operation=init`-подібне через платформу) або з `.dt` | так | база агента |
| `build` | `.epf` через платформу в `build/artifacts/`; забирає туди `.cf`/`.cfe`, які там лишила `operation=make` Уніки | так | файли |
| `install-hooks` | кладе `.githooks/` + `core.hooksPath`, шим `.claude/hooks/session-start.ps1` і `.claude/settings.json` (якщо його ще немає) | ні | git-конфіг, файли, індекс |
| `rename-edt` | переносить EDT-дерево gitsync-вивантаження в точні шляхи Designer (перехід наявних репозиторіїв, `docs/migration/legacy-gitsync-repo.md`) | ні | файли, `git mv` |

Спільні параметри — `-RepoRoot`, `-Workspace`, `-Source`, `-Apply`. `-Source` без
`-Workspace` дозволений, якщо ключ джерела унікальний у маніфесті (для `truth: storage` —
завжди, гілка `storage/<ключ>` одна на репозиторій); інакше диспетчер зупиняється з
переліком воркспейсів, де ключ повторюється (`Select-KitSources`,
`tools/lib/Preflight.psm1`). Без `-Apply` кожна команда, що щось міняє, лише друкує план.

**Код виходу** визначає зміст, не назва команди:

| Код | Зміст | Хто повертає |
|---|---|---|
| `0` | виконано; нічого не вимагає уваги (`check` лише з `warn` — теж `0`) | усі |
| `1` | зупинка: `throw` у команді, провал префлайту, невідома команда, нерозпізнаний аргумент, `check` з `error` | усі |
| `2` | стан частково змінено: зроблене лишається, решта — рішення людини | лише `sync` — дзеркало `storage/*` оновлено, злиття в головну гілку не виконано |
| `3` | нічого не змінено, репозиторій несуперечливий, але є що робити | `verify` (`ref-ahead`/`storage-ahead`/`mixed`), `session-check` (є сигнал) |

## Модель git

### Три ролі гілок

```
storage/X    S1 ──── S2 ──── S3 ──── S4          дзеркало сховища X: лише sync, лише дописується
              \        \              \
main    ──────M1───────M2────[PR F]───R──►       злиття PR-ів + звірочні коміти
                         \          /
F (задача)                A1──A2──A3              гілка задачі; живе до PR
                               ↑
                          merge storage/X
```

**`storage/<ключ джерела>`** — по одній гілці на кожне джерело з `truth: storage`. Це
**orphan**-гілка (`git worktree add --orphan -b storage/<ключ>` для першого коміту): дерево
несе рівно шлях цього джерела, більше нічого. Пише в неї лише `sync`
(`Write-KitStorageVersion`, `tools/lib/StorageBranch.psm1`) — один коміт на версію сховища,
дата автора й комітера = дата версії, повідомлення = перший рядок коментаря версії плюс
трейлери. Історія `storage/*` не переписується.

**Головна гілка** (типово `main`; будь-яку іншу задає `mainBranch:` у `v8storagekit.yaml`,
перевірка на кшталт імені гілки — `Read-KitManifest`) — історія проєкту: злиття PR-ів
плюс **звірочні коміти** для того, що прийшло у сховище повз агента (`verify -Apply`,
розділ нижче). Реплей сховища напряму в головну гілку не йде — лише через `storage/*`.

**Гілка задачі** (`F` у діаграмі) — звичайна гілка від головної. Коли частину роботи
переносять у сховище — `merge storage/X` у `F` (скіл `reconcile`). Це не rebase й не
перебудова історії: історія `F` лишається цілою, конфлікти — семантичні (після
канонізації, розділ нижче) і розв'язуються тим, хто працює в `F`.

### Чотири трейлери коміту

Кожен коміт `sync` на `storage/<ключ>` (`New-KitStorageCommitMessage`,
`tools/lib/StorageBranch.psm1`) несе в кінці повідомлення:

```
Storage-Source: SMP_BankExchange_SMB
Storage-Version: 47
Extension-Version: 1.2.3        (для конфігурації — Config-Version:)
Storage-User: Абдулов
```

- **`Storage-Source`** — ключ джерела з маніфесту; `check` звіряє його з ключем самої гілки
  (`storage/<ключ>` мусить нести трейлер із тим самим ключем — `Test-KitStorageBranchInvariants`).
- **`Storage-Version`** — номер версії в самому сховищі. Це єдине джерело істини про те, що
  вже перенесено (розділ «Стан синхронізації» нижче) — не число з окремого файлу.
- **`Config-Version`**/**`Extension-Version`** — версія конфігурації чи розширення зі звіту
  сховища («Версия конфигурации:»), якщо вона зафіксована для цієї версії; трейлер відсутній,
  якщо поле порожнє.
- **`Storage-User`** — **сирий** рядок «Пользователь:» зі звіту сховища, без перетворення
  через `AUTHORS`. Це свідомо не те саме, що `git author` коміту: `git author` — уже
  результат `Resolve-Author` (рішення, кому належить це ім'я), а `Storage-User` — факт,
  який можна перевірити незалежно (`git log --grep`), у тому числі коли зіставлення
  виявиться неточним (розділ «AUTHORS» нижче).

### Стан синхронізації виводиться з git

«Остання залита версія джерела X» = значення трейлера `Storage-Version:` **вершини**
`storage/X` (`Get-KitStorageBranchLastVersion`, `tools/lib/StorageBranch.psm1`). Окремого
файлу стану немає — `storage.json` вилучено разом із модулем `SyncState.psm1`, який його
читав і писав у 0.6.0.

- Гілки ще немає → `$null` → перший реплей бере версії зі звіту від `-FromVersion N` або
  лише максимальну (`-FromLatest`), без жодного з них — усі версії зі звіту
  (`Get-KitPendingVersions`). На непорожній гілці обидва прапорці — зупинка: «звідки
  почати» вже вирішено трейлером вершини.
- Вершина `storage/X` без числового трейлера `Storage-Version:` — це ознака, що гілку
  писав не `sync`, і `Get-KitStorageBranchLastVersion` кидає виняток із текстом «розбір:
  kit check» — вгадувати стан заборонено.
- Нумерація сховища може починатись із будь-якого числа й мати пропуски: `Get-KitPendingVersions`
  бере **перелік версій зі звіту, більших за останню**, а не діапазон номерів. Якщо
  найменша з нових версій більша за `остання + 1`, `Get-KitVersionGapNote` друкує
  інформаційний рядок «проміжних версій у сховищі вже немає (оптимізовано)» — це не помилка.
- `check` (`Test-KitStorageBranchInvariants`, `tools/lib/StorageBranch.psm1`) вимагає: кожен
  коміт `storage/*` має трейлери `Storage-Source:` і числовий `Storage-Version:`; значення
  `Storage-Version:` строго зростають від кореня до вершини; батьків не більше одного —
  кореневий коміт orphan-гілки їх не має взагалі, а merge-коміт (два батьки) заборонений
  на дзеркалі повністю. Окремо перевіряється, що дерево гілки не містить файлів поза
  шляхом джерела (`git ls-tree`, з `-c core.quotepath=false`, щоб кириличні шляхи не
  прочитались екранованими і не дали хибної знахідки).

### Захист гілок `storage/*`

Три шари, кожен ловить своє, і жоден не суцільний сам по собі:

1. **Запис лише через worktree.** Гілки ще немає (перший `sync` джерела) —
   `git worktree add --orphan -b storage/<ключ> build/sync/<ключ>/wt`; гілка вже є —
   `git worktree add build/sync/<ключ>/wt storage/<ключ>` (`New-KitStorageWorktree`,
   `tools/lib/StorageBranch.psm1`). `sync` вивантажує версію, комітить і прибирає worktree
   там; робоча копія людини й поточна гілка при цьому не торкаються взагалі —
   вимоги «чиста робоча копія перед `-Apply`», яку мав старий `storage-sync.ps1`, більше
   немає.
2. **Локальний хук, що відмовляє.** Версійована тека `.githooks/` із `pre-commit` і
   `pre-merge-commit` (`templates/githooks/`); `install-hooks`/`onboarding` вмикають
   `git config core.hooksPath .githooks` (`Install-KitGitHooks`, `tools/lib/Hooks.psm1`).
   Обидва скрипти хука — POSIX `sh`: якщо `HEAD` (`git symbolic-ref -q HEAD`) указує на
   `refs/heads/storage/*` і не виставлено `V8KIT_SYNC=1` — відмова з кодом `1` і поясненням
   на `stderr`. `pre-commit` (`templates/githooks/pre-commit`) друкує «гілка '…' — дзеркало
   сховища, її пише лише 'kit sync'. Коміт відхилено (pre-commit). Працюйте у гілці задачі
   від головної гілки.»; `pre-merge-commit` — «у гілку '…' нічого не зливають — це дзеркало
   сховища. Злиття відхилено (pre-merge-commit). Скасуйте його: `git merge --abort`».

   **Цей шар не суцільний.** `core.hooksPath`, коли він відносний (а `.githooks` — саме
   такий), git розв'язує від кореня **того worktree, у якому виконується коміт** — не від
   кореня репозиторію взагалі. В orphan-worktree дзеркала (`build/sync/<ключ>/wt`) дерево
   несе лише шлях джерела, теки `.githooks/` там немає, і хук у цьому worktree **не
   спрацьовує**. Отже шар 2 накриває головну робочу копію і будь-який worktree, чиє
   дерево містить `.githooks/`, — але не сам worktree дзеркала, під яким `sync` реально
   комітить. `V8KIT_SYNC=1`, який `sync` виставляє на кожен коміт версії
   (`Write-KitStorageVersion`), — **контракт для хука, не механізм захисту**: змінна
   виставляється завжди, щоб коміт пройшов там, де хук є; сама вона нічого не захищає.
   Дірка вузька — worktree дзеркала існує лише на час `sync` під `build/` — і закривається
   шаром 3.
3. **`check` як аудит повноти.** Ловить те, що просочилось повз хук: клон без
   `core.hooksPath`, коміт у worktree дзеркала, де хука немає, чужий коміт після
   `git config core.hooksPath` знято руками. Саме на цьому шарі лежить повнота захисту, не
   на другому — `Test-KitStorageBranchInvariants` перевіряє результат (merge-коміт,
   немонотонні версії, відсутність трейлерів), незалежно від того, чи хук узагалі стояв.

   `Test-KitGitHooks` (`tools/lib/Hooks.psm1`) додатково звіряє встановлене з шаблоном
   плагіна побайтово (після нормалізації CRLF→LF) і перевіряє, що обидва файли закомічені
   з бітом виконання (`git ls-files -s` → режим `100755`) — інакше клон на Linux/macOS
   отримає хуки без права виконання, і git їх мовчки проігнорує.

Варіант `refs/storage/*` (не гілки) розглядався й відхилений: сильніший захист, але GitHub
не показав би такі посилання як гілки, і «хто змінив рядок» лишилося б консольним.

### Як `storage/X` зливається у головну гілку і в гілку задачі

Git зливає **зміни від спільного предка**, а не дерева цілком; `storage/X` ніколи не
торкалась файлів поза своїм шляхом, тому решта дерева головної гілки не зачіпається, хоч
вона й у сто разів більша (`Merge-KitBranchInto`, `tools/lib/GitMerge.psm1`).

- **Перше злиття** — з прапорцем `--allow-unrelated-histories` (orphan-гілка без спільної
  історії з головною): об'єднання, файли головної гілки лишаються, файли сховища
  додаються. Робить `sync` одразу після першого реплею (`Invoke-KitMainMerge`,
  `tools/commands/sync.psm1`).
- **Наступні** — звичайні тристоронні злиття: спільний предок — вершина `storage/X` на
  момент попереднього злиття; приходять лише нові версії, видалені у сховищі об'єкти
  видаляються. Завжди `--no-ff`: головна гілка не є предком `storage/X`, і fast-forward
  перетворив би її на дзеркало — краще, щоб git це навіть не розглядав.
- У гілку задачі — так само, командою `merge storage/X` під час `reconcile`.
- Кілька джерел одного воркспейсу — незалежні orphan-гілки з неперетинними шляхами,
  зливаються незалежно.

**Куди фізично йде злиття в головну гілку** (`Merge-KitBranchInto` розрізняє три випадки):
якщо `HEAD` уже стоїть на головній гілці й робоча копія чиста — злиття на місці; якщо
`HEAD` на головній, а копія брудна — зупинка з переліком незакомічених шляхів (до п'яти,
решта — рахунком) — у брудну головну гілку не зливаємо; якщо `HEAD` на іншій гілці
(звичайний випадок: людина чи агент працює в `F`) — тимчасовий worktree
`build/sync/_main/wt` на головній гілці, злиття там, worktree прибирається. Git не дає
другого worktree на вже вибрану гілку, а `update-ref` під нею лишив би індекс застарілим —
звідси саме така розвилка. Конфлікт злиття — `git merge --abort` і зупинка з готовою
командою для ручного розбору; якщо сам `--abort` не спрацював, повідомлення каже про це
прямо, а не стверджує відкіт, якого не було.

## Запаковане сховище і дешевий сигнал `session-check`

`Get-KitStorageActivity` (`tools/lib/StorageBranch.psm1`) розпізнає «це взагалі сховище
1С» без платформи й без ліцензії — одним обходом каталогу: наявність `1cv8ddb.1CD` плюс
хоча б один файл в одній із двох тек, `data/objects` або `data/pack`. `mtime` самого
`1cv8ddb.1CD` індикатором **часу** не є — він переписується при кожному інтерактивному
підключенні Конфігуратора; лише як ознака «це сховище» він годиться.

Пакування сховища — норма, не аномалія: живий прогін B3 на `СМП_BankExchange_SMBru` (16
версій) показав `data/objects` цілком порожньою, усе — у 60+ pack-файлах `data/pack`.
Пакування зсуває `mtime` цих файлів, не додаючи версій, тому:

- файли в `data/objects` новіші за дзеркало → «ймовірно нові версії», код `3` — pack при
  цьому не важить;
- pack не новіший за дзеркало → рахує звичайна логіка по `data/objects`;
- pack новіший, а `data/objects` сигналу не дає (порожня чи не змінювалась) →
  **«дешево не визначається»**: рядок «усі об'єкти запаковані після останнього дзеркала —
  чи є нові версії, дешева перевірка сказати не може; точну відповідь дає
  `kit sync -Source X` без `-Apply`», код `3`. Не `1` — команда дійшла до задуманого
  результату, дія відома; не `0` — тиша тут читалась би як «змін немає», хибний all-clear.

Щоб це «не знаю» не залишалось назавжди для неактивного запакованого сховища (дзеркало не
рухається, `sync` не має чого комітити, pack лишається новішим постійно), `sync` пише
**відбиток** після кожного читання звіту сховища — і в прев'ю, і з `-Apply`
(`Write-KitStorageImprint`, `tools/lib/StorageImprint.psm1`) у
`build/session-check/<ключ>.json`: версію сховища зі звіту, момент читання, максимальний
`mtime` під `data/objects`, перелік pack-файлів (ім'я, розмір, `mtime`). `session-check`
лише **читає** його (`Read-KitStorageImprint`, `Test-KitStorageImprintCurrent`) і ніколи не
пише — детальніше про різницю кешу й стану нижче.

`Invoke-KitSessionCheck` (`tools/commands/session-check.psm1`) спершу проганяє повний
`check` тим самим контекстом (`Invoke-KitCheck -Quiet`): якщо є хоч одна `error`-знахідка —
сигнали не обчислюються взагалі, код `1`, бо на суперечливому репозиторії (наприклад, чужий
коміт на `storage/*`) дата дзеркала нічого не означає. Лише `warn`-знахідки друкуються
рядками `[!]` над сигналами й коду не міняють. Допуск порівняння `mtime` сховища з датою
коміту дзеркала — 5 секунд (`$script:StorageMirrorTolerance`,
`tools/commands/session-check.psm1`): `sync` штампує дату автора цілими секундами, а
`mtime` файлу несе частку секунди, і без допуску власний щойно зроблений коміт завжди
виглядав би «новішим» за самого себе.

Пріоритет коду для команди з кількома джерелами: `1`, якщо хоч одне джерело не прочитало
стан git (гілка є, а `git log`/`git rev-list` не відповіли); інакше `3`, якщо хоч один
сигнал дії (нові версії, дзеркала немає при доступному сховищі, шлях не схожий на сховище,
є незлиті в головну гілку коміти); інакше `0`. Недоступне сховище саме по собі — стан
машини, код не піднімає (лише рядок-порада перевизначити шлях у накладці); дзеркало є, а
головної гілки з маніфесту немає — не «не знаю» (незлиті коміти — всі коміти дзеркала,
дія відома), а `3`, з текстом «зробіть перший коміт» на ненародженій гілці й «перевірте
`mainBranch:`» — на описці.

## `verify` — інваріант «`ref` ≡ сховище»

`Invoke-KitVerify` (`tools/commands/verify.psm1`) звіряє дерево заданого `ref` (типово —
головна гілка маніфесту; `storage/X` — перевірка канонічності самого дзеркала) за шляхом
джерела з **канонічним дампом зі сховища на версії з трейлера**. Джерело порівняння
навмисно незалежне — сховище, а не власна робоча копія: класичний round-trip годував би
платформі те, що сам і перевіряє (знахідка BankExchange). Це не лише архітектурний вибір —
дев-база людини, підключена до сховища, `/LoadConfigFromFiles` не приймає взагалі
(«Соединение с хранилищем конфигурации не установлено»): узяти канонічний зразок із бази,
де людина вже працює в Конфігураторі, платформа не дає технічно. Тому `verify` (як і `sync`,
і `canon` через базу агента) завжди піднімає власну тимчасову ІБ і бере зразок зі сховища
напряму — межа «база людини лише читання» тут не лише принцип 3, а й властивість платформи.

**Яка саме версія.** `Get-KitVerifyVersion` (`tools/lib/StorageBranch.psm1`) бере трейлер
`Storage-Version:` коміту `git merge-base <ref> storage/X` — не вершину `storage/X` і не
максимум у звіті сховища. Для `verify storage/X` це вершина самої гілки; для `verify main`
чи `verify F` — остання версія, яку `<ref>` уже реально злив. Версії на `storage/X` після
цього merge-base `verify` називає окремим інформаційним рядком «сховище попереду»; якщо
merge-base порожній (`<ref>` ніколи не зливав `storage/X`) — зупинка: спершу `kit sync`.

**Порівняння — на сирих блобах, не на checkout.** `Export-KitTree`
(`tools/lib/TreeCompare.psm1`) читає дерево `<ref>:<шлях>` напряму з `git cat-file --batch`,
байт-у-байт із блобів. `git archive` і `git checkout` застосовують eol-конверсію з
`.gitattributes`, і якщо порівнювати те, що вони віддають, «лише CR» діагностувала б
налаштування машини (`core.autocrlf`), а не стан самого репозиторію.

`Compare-KitTrees` (`tools/lib/TreeCompare.psm1`) класифікує кожен файл на п'ять категорій:

| Категорія | Означає |
|---|---|
| побайтово рівні | усе застосовано, дерево канонічне |
| лише CR (`CrOnly`) | зіпсована політика тексту — див. `docs/text-policy.md` |
| змістовна (`Content`) | git розійшовся зі сховищем реальним вмістом |
| тільки в дампі (`OnlyInDump`) | файл є у сховищі, але зник із дерева `<ref>` |
| тільки в дереві (`OnlyInTree`) | файл є в дереві `<ref>`, але немає у сховищі |

Файли, позначені `binary` в `.gitattributes` (`Get-KitBinaryPaths`, той самий
`git check-attr`, що й у checkout), звіряються **лише побайтово** — без CR-нормалізації;
`ConfigDumpInfo.xml` і `DumpFilesIndex.txt` виключаються з порівняння завжди
(`$script:PlatformJunk`, `tools/lib/TreeCompare.psm1` — обидва службові файли платформи, не
частина конфігурації).

Вердикт складається з двох незалежних осей — чи є розбіжності дерева, чи є нові версії на
`storage/X` після merge-base:

| Вердикт | Розбіжності дерева | Нові версії на дзеркалі | Дія |
|---|---|---|---|
| `equal` | немає | немає | нічого |
| `ref-ahead` | є | немає | у сховище ще не потрапила частина роботи (зберіть артефакт і застосуйте залишок) |
| `storage-ahead` | немає | є | у сховищі є щось повз агента — звірочний коміт: `kit verify -Apply` |
| `mixed` | є | є | спершу звірочний коміт, потім розбір залишку |

`OnlyInDump` (файл, який `<ref>` **втратив** порівняно зі сховищем) окремо позначається
попередженням: це не «робота, яку треба застосувати у сховищі», а прогалина в самому `ref`
— привід перевірити злиття `storage/X` і `canon`.

## База агента

`provision` розгортає базу агента (`Invoke-KitProvision`, `tools/commands/provision.psm1`) —
порожню або з `.dt` — а `operation=build` Уніки далі наповнює її з джерел воркспейсу.
«Порожня» означає рівно це: порожня інформаційна база, яку `build` наповнює спершу з
`CONFIGURATION` source-set — **власника** (шлях типово `cf/src`) — і лише потім із джерел
розширень. Для джерела `truth: vendor` `cf/src` гітігнорований, і на щойно клонованій
машині він порожній: `build` не має чим наповнити власника, і «порожня база» тихо веде в
глухий кут — розширення не піднімається саме тому, що конфігурація, до якої воно
прив'язане, порожня.

Тому `provision`, **до** питання «порожня / `.dt` / серверна», перевіряє наявність
власника на диску.

- **Перевірка безумовна**, а не лише для розширень із запозиченими об'єктами: складання
  `.cfe` і сам `operation=build` без власника не працюють і для «чистого» розширення без
  жодного запозичення — заглушка (`tools/assets/empty-extension`, розділ «Особливості
  платформи» нижче) не тримає типи конкретної конфігурації (УНФ, БАС тощо), і збірка падає
  незалежно від того, скільки саме об'єктів розширення запозичено.
- **Лічильник запозичених (`Adopted`) об'єктів нічого не вмикає** — він лише пояснює
  людині, чому відсутність власника не питання смаку чи майбутньої зручності, а зупинка вже
  зараз. Дешева перевірка без платформи: `git grep -c "ObjectBelonging>Adopted"` по дереву
  розширення. Вимір, що поставив цю задачу: у `SMP_BankExchange` **45 із 53** об'єктів
  розширення — запозичені.
- **Кожен варіант називається людині з ціною**: дамп власника з дев-бази (`kit dump`,
  **20–40 хвилин і 1–2 ГБ** на повній конфігурації), `.dt` із конфігурацією, серверна база,
  або `kit sync` — якщо сам власник під `truth: storage` (клієнтський репозиторій, де
  базова конфігурація змінена й веде власну історію в сховищі).

## Канонізація дерева агента

Агент, що редагує через Unica, ніколи не має байт-канонічного дерева: Unica пише свій
формат XML, а git має містити рівно те, що вивантажує сама платформа 1С. `canon`
(`Invoke-KitCanon`, `tools/commands/canon.psm1`) переписує дерево кожного джерела воркспейсу
тим, що `/DumpConfigToFiles` справді віддає з **бази агента**. Передумова — `operation=build`
Уніки вже наповнив цю базу з джерел; `canon` цього не робить і не перевіряє інакше, ніж за
самою наявністю бази.

Канонізуються джерела типу `CONFIGURATION`/`EXTENSION` з `truth ∈ {storage, dump, git}` —
усе, крім `truth: vendor` (його канон дав би дамп бази **людини**, а це вже задача
`kit dump`, не `canon`) і `EXTERNAL_DATA_PROCESSORS` (платформа не вивантажує зовнішні
обробки через `/DumpConfigToFiles`; обидва випадки друкуються з поясненням і пропускаються).

Без `-Apply` — лише перелік цілей і причин пропуску. З `-Apply` дерево кожної цілі
**стирається** (`Remove-Item -Recurse -Force`) перед тим, як платформа запише туди свій
дамп — інакше лишились би файли, яких платформа вже не віддає. Перед самим видаленням —
страховка: `Backup-KitCanonDirtyFiles` копіює все незакомічене й невідстежуване з дерева
джерела (`git status --porcelain -z -uall`, розібраний `Get-KitCanonStatusRecords`) у
`<воркспейс>/<workPath>/canon-backup/<ключ>-<yyyyMMdd-HHmmss>/` — гітігноровану теку поруч
із базою агента. Це не заборона канонізувати брудне дерево (дерево на момент `canon`
**завжди** потенційно брудне за задумом циклу: Unica щойно писала в нього, коміт іде
**після** `canon`, не до) — це лікування безслідності: якщо агент забув `operation=build`
перед `canon`, його ще не закомічена робота не зникає, а лишається копією поруч.

## Три теки `build`

Три теки з однаковою на вигляд назвою `build` мають трьох різних власників, і жодна не
знає про дві інші:

| Тека | Власник | Що там |
|---|---|---|
| `<корінь репозиторію>/build/` | kit | `build/sync/<ключ>/wt` — worktree дзеркала на час `sync`; `build/sync/_main/wt` — тимчасовий worktree головної гілки для злиття; `build/verify/<ключ>/` — тимчасова ІБ і дампи `verify`; `build/session-check/<ключ>.json` — відбиток сховища; `build/build-ib/` — тимчасова ІБ команди `build` для `.epf`; `build/artifacts/` — зібрані `.epf`/`.cf`/`.cfe` для людини |
| `<воркспейс>/<workPath>/` (типово `<воркспейс>/build/`, конфігуровано `workPath:` у `v8project.yaml`) | Unica | база агента (`infobase.connection: 'File=build/ib'`, шлях відносний від теки воркспейсу); `<workPath>/artifacts/` — запасний шлях, куди `operation=make` кладе `.cf`/`.cfe`, якщо Unica відмовляє в шляху виводу поза воркспейсом (`kit build` забирає звідти, `Copy-KitWorkspaceArtifacts`, `tools/commands/build.psm1`); `<workPath>/canon-backup/` — страховка `canon` (розділ вище) |
| `<воркспейс>/.build/unica` | Unica | власний кеш платформи, створюється автоматично при кожному використанні кореня воркспейсу — **поведінка Уніки, а не kit**: цей репозиторій не містить коду, що створює чи перевіряє цю теку (`grep -rn "\.build.unica" tools/` порожній); факт відомий лише з дослідження контракту Уніки (спека §2.1), звірити його `grep`-ом по цьому дереву неможливо |

`.gitignore` репозиторія-споживача (шаблон `templates/gitignore`) ігнорує і `build/`, і
`.build/` цілком — жодна з трьох тек не потрапляє в git.

**Артефакти збірки в git не лежать.** `*.epf`/`*.erf`/`*.cfe`/`*.cf` — похідні файли;
єдине їх законне місце — `<корінь>/build/artifacts/`. Причина не в зручності: бінарний блоб,
раз закомічений, лишається в історії репозиторію назавжди, а закомічений артефакт поруч зі
свіжим зібраним не відрізнити — хто читає дерево, не бачить, який із них зібрано з поточних
вихідників. `check` (перевірка `build-artifacts`, `tools/commands/check.psm1`) шукає
закомічені файли з розширеннями `.epf`, `.erf`, `.cfe`, `.cf` під кожним воркспейсом, за
межами його `workPath`, і видає **`WARN`, не `error`**: у формі 0.6.0 такі артефакти в git
були законною нормою (`epf/dist/*.epf` у `SMP_BankExchange`), і `error` тут завалив би
перехід репозиторіїв парку саме за той стан, який щойно був легальним. Прибрати з індексу
(`git rm --cached`, історія лишається) пропонує скіл `onboarding`, лише з підтвердженням
людини — `check` сам нічого не змінює.

## Маніфест і накладка

**`v8storagekit.yaml`** — один файл у корені репозиторію-споживача, закомічений. Не дублює
структуру: шляхи й типи джерел описує `v8project.yaml` кожного воркспейсу, маніфест
посилається на source-set-и за іменем і додає те, чого Unica не знає. Читає й валідує
`Read-KitManifest` (`tools/lib/Manifest.psm1`): рівно один із ключів `product:`/`client:`,
необов'язковий `mainBranch:` (типово `main`), список `workspaces:`, кожен — `path:` (тека
безпосередньо в корені) і `sources:` (мапа «ключ = `name:` source-set → `{ truth, storage,
dump }»`). Словник `truth` — рівно чотири значення: `storage` (сховище конфігурацій,
дзеркалиться в `storage/<ключ>`), `dump` (жива база, лише поточний стан, без гілки),
`vendor` (чужа конфігурація, у git не потрапляє), `git` (зовнішнього джерела немає). Зразок
— `templates/v8storagekit.yaml.example`.

**`v8storagekit.local.yaml`** — гітігнорована накладка тієї самої машини: дев-бази, з яких
kit лише читає (`infobases:`), перевизначення шляхів і облікових даних сховищ
(`storages:`), шаблон `.dt` бази агента (`workspaces.<шлях>.agentBase.template`). Читає й
валідує `Read-KitLocalOverlay` (`tools/lib/Manifest.psm1`); дублікат ключа накладка
відхиляє сама. Kit не ділить файлів з Unica: `v8project.local.yaml` — файл Уніки, і kit бере
з нього рівно одне значення — підключення бази **агента**, якщо воно там перекриває
закомічене (`Resolve-V8AgentInfobase`, `tools/lib/V8Project.psm1`), тим самим шляхом, яким
іде сама Unica. Зразок — `templates/v8storagekit.local.yaml.example`.

Кожне підключення до бази людини з `infobases:` накладки звіряється з базою агента через
`Test-KitSameInfobase` (`tools/lib/AgentBase.psm1`) — за **розібраними** полями, не за
текстом рядка: `File="D:\X\"` і `File=D:\X` — та сама тека, `Srvr="A";Ref="B";` і
`Ref="B";Srvr="A";` — та сама база, порядок ключів не важить. Підключення, яке не
розбирається однозначно (невідомий вид, `Srvr=` без `Ref=`, порожній рядок), fail-closed
кидає виняток, а не мовчки повертає «не збігається» — за помилковим «не збігається» тут
стояв би `provision -Force`, тобто `Remove-Item -Recurse -Force` над чужою базою.

## Відбиток сховища — кеш, не стан

`build/session-check/<ключ>.json` (`Write-KitStorageImprint`/`Read-KitStorageImprint`,
`tools/lib/StorageImprint.psm1`) легко сплутати зі старим `storage.json` — обидва JSON, обидва
про стан сховища. Різниця не в розташуванні файлу, а в **ролі**.

Джерело істини про те, що вже перенесено в git, лишається одне й те саме завжди: трейлер
`Storage-Version:` на вершині `storage/<ключ>` (розділ «Стан синхронізації» вище). Відбиток
цю роль не займає й не дублює — це прискорювач: `sync` після кожного читання звіту сховища
(і в прев'ю, і з `-Apply`) записує туди версію зі звіту, момент читання й знімок
`data/objects`/`data/pack` (`Get-KitStorageActivity`). Коли `session-check` бачить, що диск
сховища з того моменту не змінювався (`Test-KitStorageImprintCurrent` — порівняння без
допуску: обидва боки зняті одним годинником, файловою системою сервера сховища), він
відповідає **точно** — «на такий-то момент сховище було на версії N» — замість здогадки за
`mtime`. Пише відбиток **лише** `sync`; `session-check` його лише читає й ніколи не мутує —
на цьому інваріанті тримається законність примусового завершення процесу `session-check` за
стелею часу в шимі старту сесії (розділ «Особливості платформи» нижче не про це, а сам шим
— `templates/hooks/session-start.ps1`).

Файл гітігнорований, локальний для машини. Якщо його видалити чи він пошкодиться —
`Read-KitStorageImprint` мовчки повертає `$null` (битий JSON, чужа версія схеми — усі три
випадки рівнозначні «відбитка немає», жоден не кидає винятку), і `session-check` просто
повертається до евристик `mtime` (розділ «Запаковане сховище» вище) — синхронізація цього
не помічає. Саме тому, що втрата відбитка нічого не ламає, а втрата `storage.json` в 0.6.0
ламала синхронізацію повністю, ці два файли — не той самий механізм під іншим іменем: один
був єдиним джерелом стану, другий — лише прискорювач дешевого читання.

## Порядок «`.gitignore` → накладка» — властивість безпеки

`v8storagekit.local.yaml` несе логіни й паролі до сховищ і дев-баз, а репозиторії-споживачі
парку бувають публічними. Тому скіл `onboarding` пише цю накладку **лише після** того, як
у репозиторії з'явився закомічений `.gitignore` з рядком `v8storagekit.local.yaml` — і
підтверджує це `git check-ignore` на конкретний шлях, а не припущенням. Порядок навпаки —
не незручність, а вразливість: до появи `.gitignore` накладка лишається звичайним
невідстеженим файлом, і перший же `git add -A` застейджить її разом із рештою робочого
дерева.

Знахідка пілоту B6 на `SMP_SimplyCatalog` (2026-09-10): у самому тексті скіла нумерація
розділів підказувала зворотний, небезпечний порядок, і безпечний виходив лише випадково —
через те, що виконавець тримав у голові більше, ніж було написано. `check` таки ловить
наслідок постфактум (`overlay-ignored`: «`v8storagekit.local.yaml` не гітігноровано…» —
`error`, а не `warn`, бо це суперечність, видима з будь-якої машини), а комітяться перший
коміт каркаса — явним списком файлів, не `-A` — але обидва запобіжники другого ешелону, не
заміна порядку кроків. Зупинка потрібна **до** запису файла, не попередження **після**.

## AUTHORS — межа інструмента

`AUTHORS` — файл у корені репозиторію-споживача, один на весь репозиторій. `sync` читає
його ще до будь-якого звернення до сховища (`Read-AuthorMap`, `tools/lib/Authors.psm1`) і
зупиняється негайно, якщо файлу немає. Формат рядка: `<логін сховища>=<Git Name> <email>`;
рядки з `#` і порожні рядки ігноруються. Логін сховища, якого немає в мапі, `sync` **не
вгадує й не підставляє** (`Get-UnknownAuthors` перед циклом реплею, до першого звернення
до сховища за оновленням) — друкує список невідомих і зупиняється; той самий логін двічі з
різними іменами в самому файлі — `Read-AuthorMap` зупиняється вже при читанні. Зразок для
першого створення — `templates/AUTHORS.example`.

**Межа моделі, названа свідомо, щоб її не «лагодили».** `AUTHORS` — статична мапа «логін →
одна особа» **за побудовою**. На живому парку технічні логіни сховищ звуться за клієнтами
(`Decoratorskyi_UNF_work` — за клієнтом «Декораторський»), а комітять під ними в спільне
сховище нашого продукту різні люди — це робоча практика, не аномалія. У сховищі
`SMP_SimplyCatalog` межа виміряна точно: логін `Decoratorskyi_UNF_work` у версії 28 — одна
людина, у версії 29 — вже інша. Статична мапа цього виразити не може.

**Рішення користувача (2026-09-10): kit цього не автоматизує** — ні `-AuthorOverride`, ні
мап із діапазонами версій. Штатний спосіб — нарізка реплею порціями (`sync -MaxVersions N`)
з ручною правкою `AUTHORS` між скибками; людина в контурі **і є** механізмом, що розрізняє
авторів. Після кожної скибки — `git log -1`, щоб бачити, що саме записалось, а не пам'ятати
про це абстрактно.

Наслідок стосується не лише переходу парку, а **щоденного** `sync`: нова версія під
спільним логіном отримує автора, якого `AUTHORS` називає **на момент реплею** — kit про
можливу неточність не попереджає, актуальність мапи тримає людина. Це не дефект, який варто
полагодити, а межа, яку обрали свідомо.

## Kit не покладається на git-конфіг машини

Кожна залежність від локального налаштування git — `core.autocrlf`, `core.quotepath`,
`core.hooksPath`, `core.eol` — або виставляється явно на кожному виклику, або перевіряється
й повідомляється; порада в документації репозиторія-споживача не заміна цьому.

- **`-c core.quotepath=false`** — на кожному git-виклику, що читає чи друкує шляхи
  (`git ls-tree`, `git status`, `git check-ignore`, `git check-attr`, `git ls-files`).
  Типове `core.quotepath=true` екранує неASCII-імена вісімково (`"\320\221...".xml` замість
  `Банки.xml`), і без цього прапорця перевірка меж джерела (`Test-KitStorageBranchInvariants`)
  давала 240+ хибних «файл поза шляхом джерела» на першому ж репозиторії з кириличними
  об'єктами 1С — норма для цієї предметної області, не виняток. Дефект був колись
  замаскований локальним `core.quotepath=false` у `.git/config` одного репозиторію
  (`SMP_BankExchange`, порада зі старого переходу) і сплив аж на другому — той самий клас
  проблеми, що й фільтр eol-попереджень у 0.6.0: поведінка, яка залежить від того, на чиїй
  машині запускають.
- **`-z`** — там, де запис читається *і* ділиться на записи роздільником, а створити його
  міг не kit (довільний ref, довільна робоча копія): без `-z` кирилиця приходить
  екранованою в лапках навіть при виставленому `core.quotepath=false` за виклик, бо `"`,
  `\` і перевід рядка git C-квотує завжди — `quotepath` керує лише байтами ≥ `0x80`.
- **`git worktree add`/`remove`/`prune`** обгортаються перевіркою коду виходу й `Test-Path`
  на випадок, коли `--force` не спрацював (заблокований файл, антивірус чи індексатор на
  Windows) — тоді лишається попередження, а не мовчазний «успіх».
- **`core.autocrlf=false`** форсується на `git add`/`git commit` у worktree дзеркала
  (`Write-KitStorageVersion`, `tools/lib/StorageBranch.psm1`): у цьому worktree немає
  `.gitattributes` (дерево несе лише шлях джерела), тож без явного вимкнення git застосував
  би `core.autocrlf` машини й зіпсував побайтову відповідність тому, що записав
  `/DumpConfigToFiles`.

## Особливості платформи, на яких легко втратити час

- **`-Extension <Ім'я>` належить команді-дії**, а не самому підключенню до сховища:
  `/ConfigurationRepositoryReport`, `/ConfigurationRepositoryUpdateCfg`, `/DumpConfigToFiles`,
  `/LoadConfigFromFiles` (`Get-KitExtensionArgument`, `tools/lib/StoragePlatform.psm1`).
  Переплутати легко, бо `-Extension` виглядає як загальний прапорець з'єднання — платформа
  на помилку відповідає «Соединение основной конфигурации с хранилищем расширений
  конфигураций невозможно».
- **Розширення має існувати в ІБ до звернення до сховища розширень.** У порожній
  тимчасовій базі спершу `/LoadConfigFromFiles tools/assets/empty-extension -Extension
  <Ім'я>` (`New-ExtensionInfobase`, `tools/lib/V8.psm1`) — внутрішнє ім'я стаба ролі не
  грає, розширення створюється під тим іменем, що в ключі `-Extension` цього виклику. Без
  цього — «расширение конфигурации с указанным именем не найдено».
- **Запускати платформу лише через `Start-Process` з готовим рядком аргументів**
  (`Invoke-V8Designer`, `tools/lib/V8.psm1`): нативний виклик PowerShell псує лапки.
  `/IBConnectionString` вимагає подвоєних лапок усередині, тому використовується `/F
  "<шлях>"` для файлових ІБ і `/S "<сервер>\<база>"` для серверних — вкладених лапок немає
  взагалі.
- **Кириличні шляхи не вшивати в `.cmd`-обгортки** — вони читаються в OEM-кодуванні, і
  шлях ламається («хранилище не обнаружено»). У поточному коді таких обгорток немає — kit
  запускає платформу напряму через PowerShell, — але застереження лишається чинним для
  будь-якого майбутнього консольного шару поверх `1cv8.exe`.
- **Звіт сховища — це MXL**, не текст: бінарна сигнатура, далі BOM і рядки
  `{"#","значення"}`. Мітки й величини йдуть парами (`Версия:`, `Пользователь:`, `Дата
  создания:`, `Время создания:`, `Версия конфигурации:`, `Комментарий:`); коментар буває
  багаторядковим, подвоєні лапки всередині розгортаються в одинарні. Розбирає
  `tools/lib/StorageReport.psm1`: `ConvertFrom-MxlText` відкидає бінарний заголовок до BOM,
  `Get-MxlStringCells` склеює багаторядкові комірки, `Read-StorageReport` групує комірки по
  версіях і будує `[datetime]` з окремих полів дати й часу одинарними специфікаторами
  (`d.M.yyyy H:m:s`) — платформа не доповнює нулем односимвольні компоненти («1:27:39»), і
  подвоєні специфікатори (`dd.MM.yyyy HH:mm:ss`) падають на першій же такій величині. Крім
  шести основних пар, у звіті трапляються титульний рядок друкованої форми перед першою
  міткою (розбір ігнорує все до першого відомого заголовка), пара `Метка:`/`Комментарий
  метки:` і до трьох розділів зі змінною кількістю комірок-імен об'єктів —
  `Добавлены:`/`Изменены:`/`Удалены:`. Будь-яка ще не бачена форма комірки кидає винятком,
  а не губиться мовчки — інструмент, що пише незамінну історію в git, не має права тихо
  втратити вміст комірки лише тому, що її форма не передбачена.
- **`/DumpConfigToFiles` не видаляє зниклих об'єктів** — цільову теку треба чистити перед
  кожним вивантаженням версії. Робить це `Invoke-KitStorageCheckout`
  (`tools/lib/StoragePlatform.psm1`) для `sync`/`verify` і `Clear-KitWorktreeSource`
  (`tools/lib/StorageBranch.psm1`) для робочого дерева worktree дзеркала.
- **`/ConfigurationRepositoryUpdateCfg -v` не валідує аргумент.** Спайк B2 (платформа
  8.3.27.1644) через помилку у власному скрипті спайку відправив `-v 1 2 3 … 65` замість
  одного числа — платформа завершилась кодом `0` і повідомленням «Обновление конфигурации
  из хранилища успешно завершено», без жодної помилки чи попередження; що саме вона при
  цьому підняла, не характеризовано. Тому `Invoke-KitStorageCheckout` типізує параметр
  `-Version` строго як `[int]` (скаляр, масив у нього не пролізе) і формує ключ `-v` рівно
  зі скаляра з циклу по версіях — ніколи зі списку. Інваріант «одна версія — один коміт»
  тримає `verify` (розділ вище), а не сам `sync`.

## Сховище конфігурації без `-Extension`

Рецепт «стаб + `ConfigurationRepositoryUpdateCfg -v N -force`» був перевірений спершу лише
для сховищ **розширень**. Для сховища **основної конфігурації** гіпотеза, з якою заходив
спайк B2, — що порожня ІБ потребує `/ConfigurationRepositoryBindCfg` перед `UpdateCfg`, бо
`Bind` — це запис у сховище (таблиця прив'язок), і межа «сховище лише читання» мала б
лишитись правдивою з точністю до цього документованого винятку.

Результат спайку (2026-09-04, сховище `КормЦентр_DEV`, платформа 8.3.27.1644):
`ConfigurationRepositoryUpdateCfg -v N -force` **без `-Extension` і без прив'язки** працює
на порожній файловій ІБ так само, як для розширень — `/ConfigurationRepositoryReport`,
`UpdateCfg -v 1`, `/DumpConfigToFiles` пройшли чисто. Тому в коді
`$script:ConfigurationStorageNeedsBind = $false`
(`tools/lib/StoragePlatform.psm1`), і `Enter-KitStorageBind`/`Exit-KitStorageBind` для
джерел типу `CONFIGURATION` нічого не роблять — прапорець лишений у коді як задокументована
точка розширення на випадок, якщо майбутня версія платформи цю поведінку змінить, а сам
`BindCfg`/`UnbindCfg` жодного разу не викликається жодною командою kit. `New-KitStorageInfobase`
(`tools/lib/StoragePlatform.psm1`) для `CONFIGURATION` створює звичайну порожню файлову ІБ
(`New-V8FileInfobase`) — без стаба, який потрібен лише розширенням.

Передумова доступу («заведіть у сховищі користувача `gitbot` із порожнім паролем») тим
самим спайком підтверджена і для сховищ конфігурацій, не лише розширень — перший раунд
спайку впав саме на автентифікації, доки такого користувача в сховищі конфігурації не було.

## Обрізання коментарів на `//` у `/ConfigurationRepositoryReport`

`/ConfigurationRepositoryReport` без ключа `-IncludeCommentLinesWithDoubleSlash` сам
трактує `//` усередині тексту коментаря версії як межу рядкового коментаря — усе від `//`
до кінця рядка зникає з MXL ще до того, як звіт узагалі потрапляє в цей інструмент, і межа
самого рядка теж зникає (наступний рядок доклеюється до обрізаного без розриву). Це не
дефект парсера MXL у `tools/lib/StorageReport.psm1` — втрата стається на боці платформи,
усередині самої команди звіту. Підтверджено побайтовим порівнянням звіту з ключем і без
нього для однієї й тієї самої версії сховища: сховище саме по собі нічого не втрачає —
губить саме неозброєний виклик команди звіту.

**Канал відновлення знайдено, а не вигаданий.** Джерело `gitsync`
(`oscript-library/gitsync`, залежність `oscript-library/v8storage`,
`МенеджерХранилищаКонфигурации.ПолучитьОтчетПоВерсиям`) теж викликає
`/ConfigurationRepositoryReport` тими самими ключами `-NBegin`/`-NEnd`/`-Extension`, і
додатково, на платформі ≥ 8.3.17, ключем `-IncludeCommentLinesWithDoubleSlash`. Саме цей
один додатковий ключ — уся різниця.

`Get-StorageReportArguments` (`tools/lib/StorageReport.psm1`) тепер **завжди** додає
`-IncludeCommentLinesWithDoubleSlash` до команди звіту — незалежно від версії платформи
(kit працює лише з гілкою 8.3.27.x, де ключ підтримується завжди), тож прогони `kit sync`
більше не наступають на цю ж втрату.

## Пряме обмеження на локальні шляхи розробників

Політика репозиторія-споживача (типово зафіксована в його `CLAUDE.md`, розділ «Межі» —
приклад у `templates/CLAUDE.md` цього плагіна) забороняє рядки підключення до баз, імена
серверів 1С, логіни й паролі в закомічених файлах — **і водночас** закомічений
`v8storagekit.yaml` цілком свідомо несе `storage.path:` — локальний шлях розробницької
машини до каталогу сховища (`R:\СховищаРозширень_1С\…`). Це не помилка: синхронізація
повинна бути самоналаштовуваною (репозиторій сам знає, звідки себе оновлювати, без
параметрів командного рядка), а шлях до каталогу — не той самий клас секрету, що логін,
пароль чи ім'я сервера бази даних: сам собою він не дає доступу ні до чого. Точне
формулювання обмеження: **рядки підключення до баз, імена серверів 1С, логіни та паролі**
ніколи не потрапляють у закомічені файли; шлях до каталогу сховища — єдиний свідомий
виняток.

Живе цей шлях, однак, не лише в маніфесті. `storage.path:` у `v8storagekit.yaml` — спільне
для команди значення за замовчуванням (працює одразу після клону, поки шляхи збігаються).
Але в іншого розробника з іншим розташуванням дисків цей шлях може не існувати —
редагувати заради цього закомічений файл означало б або чужий diff, або локальний коміт
поверх спільного маніфесту щоразу після `pull`. Тому шлях (а за потреби й користувач та
пароль сховища) можна перевизначити для цієї машини рядком у гітігнорованій
`v8storagekit.local.yaml`, розділ `storages:` — коротка форма (лише шлях) або повна
(`{ path, user, password }`); паролів у самому маніфесті не буває ніколи, лише тут
(`Read-KitLocalOverlay`, `tools/lib/Manifest.psm1`, застосовується в `Invoke-KitPreflight`
одразу після читання маніфесту). Відсутність файлу чи ключа — не помилка: перевизначення
просто немає, і лишається значення з `v8storagekit.yaml`. Це той самий свідомий виняток із
заборони на локальні шляхи — лише з двома можливими місцями, де конкретна машина може

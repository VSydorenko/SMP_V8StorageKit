# Разовий промпт: привести мігровані з EDT репозиторії до конвенції 0.6.0

> **Тимчасовий документ.** Він потрібен рівно для двох репозиторіїв, які підключили до
> конвеєра до версії 0.6.0 — `SMP_SimplyConnect` і `SMP_BankExchange`. Нові репозиторії
> отримують правильну форму одразу з `v8storagekit:product-onboarding` і цього промпту не
> потребують.
>
> **Після використання в обох — видалити цей файл разом із текою `docs/migration/`.**
> Він навмисно не оформлений як скіл: скіл лишився б у роздачі назавжди й плутав би тих,
> кому міграція не потрібна.

## Як користуватись

Відкрийте сесію Claude Code в корені репозиторію-споживача й передайте текст із блоку
нижче. Він самодостатній: агент прочитає деталі з документації плагіна сам.

Порядок між репозиторіями значення не має, але **всередині** одного порядок кроків
важливий — промпт це проговорює.

---

```
Змінилася конвенція роботи з продуктами в конвеєрі v8storagekit (версія 0.6.0). Це
міграція вже наявного репозиторію, а не нова розробка: нічого не проєктуй заново, не
переписуй скрипти й не вигадуй структуру — просто приведи те, що є, до нової форми.

ПЕРШ ЗА ВСЕ онови плагін, інакше працюватимеш за старими інструкціями:

    claude plugin update v8storagekit@smp-v8storagekit

Після оновлення почни нову сесію (скіли фіксуються на межі сесії) і прочитай:
- docs/text-policy.md у корені плагіна — політика тексту й процедура міграції
- skills/product-onboarding/SKILL.md — цільова форма конфігів
Корінь плагіна показує команда /plugin.

Перевір перед початком, що робоча копія чиста: git status має бути порожній.

Виконай чотири кроки В ЦЬОМУ ПОРЯДКУ. Після кожного — окремий коміт.

──────────────────────────────────────────────────────────────────────
КРОК 1. Перейменувати теки продуктів під імена розширень
──────────────────────────────────────────────────────────────────────

Нова конвенція: ім'я теки продукту дорівнює імені розширення в 1С. Один ідентифікатор
у чотирьох місцях — тека, extensionName у storage.json, <Name> у
cfe/src/Configuration.xml, name: EXTENSION-джерела у v8project.yaml.

Для кожної теки продукту (та, де лежить storage.json) звір її ім'я з extensionName.
Якщо збігаються — нічого не роби. Якщо ні — перейменуй теку на extensionName.

Перейменовуй ЗВИЧАЙНИМ переміщенням, не git mv:

    Move-Item -LiteralPath 'СтараНазва' -Destination 'НоваНазва'
    git add -A

Причина: git mv рухає лише відстежувані файли, а в теці продукту лежать ще й
гітігноровані — cf/src (кілька гігабайтів вивантаженої конфігурації), build/ і
v8project.local.yaml із підключенням до дев-бази. Move-Item рухає все разом. Історію це
зберігає так само: git визначає перейменування за схожістю вмісту в момент diff, а не
записує його в коміт, тож результат ідентичний git mv.

Після git add -A перевір, що git status показує саме перейменування (R), а не пари
"видалено + додано". Якщо показує пари — зупинись і розберись, не комить.

Нічого всередині файлів на цьому кроці не міняй.

Коміт: "перейменувати теки продуктів під імена розширень (конвенція 0.6.0)"

──────────────────────────────────────────────────────────────────────
КРОК 2. Політика тексту в .gitattributes
──────────────────────────────────────────────────────────────────────

Це найважчий і найцінніший крок. Він виправляє тихе псування вихідників, якого не видно
ні в git status, ні у валідаторах.

Візьми .gitattributes із templates/gitattributes плагіна. Якщо sourcePath у якомусь
storage.json не типовий (не cfe/src) — додай для нього окремий рядок
"**/<sourcePath>/** -text" поруч із наявними.

Далі виконай процедуру міграції з docs/text-policy.md плагіна ПОВНІСТЮ і в тому порядку,
як вона там написана. Не скорочуй її. Два місця, де скорочення псує репозиторій:

- примусовий перечек-аут дерева вихідників треба зробити ДО round-trip через платформу,
  інакше в базу поїде вже зіпсована робоча копія;
- git add --renormalize не можна робити ДО round-trip, інакше він зафіксує пошкодження
  як канон.

Після процедури прожени round-trip ще раз як приймальну перевірку: розбіжностей має не
лишитись, окрім ConfigDumpInfo.xml (він гітігнорований).

Очікувано і НОРМАЛЬНО: unica.project.status почне видавати error
git.text_resource_marked_binary на кожному файлі вихідників і радити замінити -text на
"text eol=lf". Цю пораду виконувати НЕ МОЖНА — вона повертає проблему, яку ми лікуємо.
Пояснення в docs/text-policy.md.

Коміт: "gitattributes: -text на деревах платформи + перенормалізація вихідників"

──────────────────────────────────────────────────────────────────────
КРОК 3. v8project.yaml кожного продукту
──────────────────────────────────────────────────────────────────────

Дві зміни в кожному файлі.

Перша: додай блок бази воркспейсу, якщо його немає:

    infobase:
      connection: 'File=build/ib'

Це машинна база під build/ — похідна від git, її можна викидати. Дев-база до неї
відношення не має.

Друга: ім'я EXTENSION-джерела має дорівнювати extensionName зі storage.json (після
кроку 1 це те саме, що ім'я теки). Не імені теки "за замовчуванням" — саме
extensionName.

Коміт: "v8project.yaml: база воркспейсу та імʼя EXTENSION-джерела"

──────────────────────────────────────────────────────────────────────
КРОК 4. v8project.local.yaml кожного продукту
──────────────────────────────────────────────────────────────────────

Файл гітігнорований, коміту не буде — але без цього кроку крок 3 не працює взагалі.

Зараз підключення до дев-бази лежить під ключем infobase:. Перейменуй цей ключ на
devInfobase:, більше нічого не чіпай:

    devInfobase:
      connection: 'Srvr="..."; Ref="...";'
      user: '...'

Причина: Unica автоматично підхоплює цей файл і ПЕРЕКРИВАЄ ним блок infobase: із
закоміченого v8project.yaml. Поки дев-база лежить під infobase:, база воркспейсу з
кроку 3 інертна — Unica ходитиме в дев-базу. Ключ devInfobase: Unica не знає, а скрипти
плагіна читають підключення власним регексом і знаходять його там без проблем.

Перевір, що в файлі рівно ОДИН рядок connection:. Якщо два — прибери зайвий: скрипти
беруть перший збіг, і load-ext.ps1 міг би мовчки розкотити розширення не в ту базу.

──────────────────────────────────────────────────────────────────────
ПЕРЕВІРКА
──────────────────────────────────────────────────────────────────────

    pwsh -NoProfile -File "<корінь плагіна>/tools/storage-sync.ps1" -RepoRoot . -Product <Продукт>

Без -Apply — це прев'ю, воно нічого не змінює. Має відпрацювати без винятків і БЕЗ
попередження про конверсію кінців рядків. Якщо попередження є — крок 2 неповний.

Далі доповідай результат людині. Не роби -Apply, не пуш і не створюй PR без окремого
прохання.
```

## Що промпт свідомо НЕ робить

- **Не збирає `.cfe`.** Збірка після міграції — окрема робота, і в `SMP_SimplyConnect`
  вона все одно впреться в несумісність типу реквізиту `НомерЧекаККМ` із поточною УНФ.
- **Не чіпає сховище.** Жодного `-Apply`, жодного запису.
- **Не пушить.** Рішення про PR лишається за людиною.
- **Не мігрує `SMP_OnlineExchange`** — його розширення називається
  `СМП_ОнлайнОбменДанными`, кирилицею, і крок 1 завів би кириличну теку продукту. Це
  неперевірена зона (`docs/follow-ups.md` §10). Для нього потрібне окреме рішення.

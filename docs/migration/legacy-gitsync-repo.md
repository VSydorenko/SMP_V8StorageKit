## 1. Розвідка парку — деталі, на які скіл лише посилається

Знайдіть усі продукти репозиторію за квартетом старого формату — `AUTHORS` + `VERSION` +
`DT-INF/` + `ConfigDumpInfo.xml` разом в одній теці. Квартет може лежати в корені репо або в
підтеках, зокрема у вкладеній само-іменованій (нижче):

```powershell
Get-ChildItem -Recurse -Depth 3 -File -Filter 'ConfigDumpInfo.xml' |
  ForEach-Object { $_.Directory } |
  Where-Object {
    (Test-Path (Join-Path $_.FullName 'AUTHORS')) -and
    (Test-Path (Join-Path $_.FullName 'VERSION')) -and
    (Test-Path (Join-Path $_.FullName 'DT-INF'))
  } |
  Select-Object -ExpandProperty FullName -Unique
```

`-Depth 3` — практичний ліміт, не архітектурне рішення. **Квартет у само-іменованій вкладеній
теці** (наприклад `SMP_OnlineExchange/SMP_OnlineExchange`) сам по собі вже на глибині 2 — одна
додаткова вкладеність над ним виходить за `-Depth 3`, і команда мовчки повертає порожній
список. Якщо результат порожній, а інші ознаки все одно вказують на старий репозиторій — є
`VERSION`, є `DT-INF`, дерево виглядає як EDT-вихідники — не довіряйте порожньому результату
мовчки: підійміть `-Depth` і перезапустіть пошук, перш ніж робити висновок «це не старий
репозиторій».

Квартет однаковий і для розширення, і для повної конфігурації — з самих цих файлів надійно не
визначити, що саме тут відстежується; це закладається в `type:` кожного source-set при
записі `v8project.yaml` (`skills/onboarding/SKILL.md` §3.2) — і, на відміну від 0.6.0,
відповідь «повна конфігурація» вже не зупиняє перехід. З відомих випадків парку
`SMP_SMB_rus_DEV` і `SMP_SMB_ukr_DEV` — це завжди повна конфігурація.

Для кожної знайденої теки:

- `VERSION` — остання синхронізована версія сховища. Файл — **XML з UTF-8 BOM**, не гола
  цифра: `<?xml version="1.0" encoding="UTF-8"?><VERSION>51</VERSION>`. Число живе в елементі
  `<VERSION>` — не беріть перші цифри файлу (`grep -o '[0-9]\+' | head -1` чи подібне): вони
  належать `version="1.0"` з XML-декларації й дадуть `1` мовчки, без помилки. Читайте,
  націлюючись саме на елемент: `([xml](Get-Content -Raw -Path <шлях>/VERSION)).VERSION`.
- `AUTHORS` — мапа «користувач сховища = Ім'я `<email>`»; формат такий самий, як у kit
  (`tools/lib/Authors.psm1`: `#`-коментарі й порожні рядки ігноруються) — gitsync
  використовував той самий формат, тому файл зазвичай можна перенести як є (розділ 5).
- поточна гілка (`git branch --show-current`) — знадобиться і для тегу межі, і для посилання
  в новому `CLAUDE.md` на те, де лишився немігрований код.

## 2. Страхувальний bundle — рецепт, якого скіл не наводить

`skills/onboarding/references/gitsync-migration.md` каже зробити `git bundle --all` як частину
кроку 1 (розвідка й страховка) і — перед відкотом чи переписом гілки — в розділі «Спадок 0.6.0:
якщо `storage.json` трапився поза парком», але сам рецепт — не там; він короткий і завжди однаковий:

```bash
git bundle create ../<repo>-pre-migration-<YYYY-MM-DD>.bundle --all
git bundle verify ../<repo>-pre-migration-<YYYY-MM-DD>.bundle
```

`--all` пакує **всі посилання** (`refs`) репозиторія — усі гілки, усі теги, і через них усю
закомічену історію, яку вони тримають живою. Це рятує будь-що, що дістало коміт. Bundle **не**
несе нічого, чого нема в жодному коміті: незакомічені зміни в робочій копії,
застейджені-але-не-закомічені зміни, невідстежувані файли. Якщо зупинка на брудній робочій
копії (`skills/onboarding/references/gitsync-migration.md`, крок 1 — розвідка й страховка) уже спрацювала — цей bundle однаково не
рятує те, що там знайшлося; рішення для цих змін (закомітити, зберегти окремим diff, чи
свідомо відкинути) приймається там, до цього моменту, а не тут.

Кладіть bundle **поза деревом репозиторія** (на рівень вище, `..`), а не в `build/` усередині
нього: на цьому етапі політики git kit (`.gitattributes`, `.gitignore`) ще не скопійовані — це
теж частина кроку 1 скіла, — тож `build/` тут ще нічим не ігнорується, і файл на сотні
мегабайт міг би випадково потрапити під наступний `git add`. `git bundle verify` повинен
завершитись без помилок, перш ніж рухатись далі — якщо ні, зупиніться і розберіться, а не
продовжуйте.

## 3. Локальний git-конфіг — довгі кириличні шляхи

```bash
git config core.longpaths true
git config core.quotepath false
```

Обидва — **локальні** (без `--global`), не переносяться клоном: виставляйте в кожному клоні,
де відбувається робота з цим репо. Причина: кириличні шляхи `.mdo`-дерева вже сягають 221
символу, а додавання префіксу продуктової теки в новій структурі підштовхує частину з них за
260 — за цією межею Windows-API не бачить файл узагалі, і `rename-edt`/`git mv` мовчки
пропускають частину дерева, а не падають з очевидною помилкою. Це не деталь стилю: без
`core.longpaths` довгі шляхи 1С просто не викачуються. Проблема нікуди не поділась із новою
процедурою — вона ж один з приводів для рішення по `SMP_OnlineExchange` (кирилична тека,
шапка цієї довідки).

## 4. Проба доступу до сховища — навіщо і якою ціною

Найдорожчий провал цього переходу — виявити недоступне сховище, невідомий сервісний
користувач чи неправильне ім'я розширення вже **після** того, як `rename-edt` розібрав
EDT-дерево. Це відновно (стара гілка й `git bundle --all` нікуди не діваються — див.
`skills/onboarding/references/gitsync-migration.md`, крок 1 — розвідка й страховка), але це поганий і — на дев'ять репозиторіїв парку —
багаторазово повторюваний досвід. Тому проба йде **до** будь-якої зміни в дереві.

**Технічно проба не потребує ізольованого сміттєвого репозиторію** (0.6.0-текст цієї довідки
раніше пропонував саме це, зі `storage.json`, — тепер зайве). `kit.ps1 sync` без `-Apply` —
безпечне, суто читальне прев'ю: воно нічого не змінює в git, лише піднімає тимчасову ІБ і
читає звіт сховища (`skills/sync/SKILL.md` §2). Дирту робочої копії воно теж не помічає —
запобіжник брудної копії належить лише `rename-edt` (успадкований від 0.6.0,
`tools/commands/rename-edt.psm1:225`), і на `sync` не поширюється. Тобто пробу можна робити
просто на реальному репозиторії, одразу після того, як маніфест `v8storagekit.yaml`,
воркспейс `v8project.yaml` і `AUTHORS` намальовані в робочій копії (навіть ще не закомічені) —
раніше за `rename-edt`, як і веде скіл. Єдина вимога: `AUTHORS` мусить існувати фізично, бо
`kit.ps1 sync` читає його ще до прев'ю й без нього зупиняється одразу («Файл мапінгу авторів
не знайдено», `tools/lib/Authors.psm1:13`).

Яким саме `AUTHORS` користуватись для проби — залежить від того, що вона має довести:

- **Реальний `AUTHORS` зі старої гілки** (уже перенесений на цьому кроці) — прев'ю доходить до
  кінця: код виходу 0, і скрипт друкує повний список версій сховища з авторами, датами й
  першим рядком коментаря кожної.
- **`templates/AUTHORS.example`** — коли треба перевірити саме сховище, а не конкретний
  `AUTHORS`, або коли реальний з якоїсь причини недоступний. У цьому файлі кожен рядок —
  коментар, мапа авторів порожня, тож прогін **завжди** зупиняється на гейті невідомих
  авторів (`Get-UnknownAuthors`, `tools/lib/Authors.psm1:90`; кидає виняток
  `tools/commands/sync.psm1` рядок із текстом «Синхронізацію зупинено через невідомих
  авторів.»). **Це очікувано, а не провал проби** — до цієї зупинки скрипт уже встиг довести
  все, заради чого проба затівалась: звіт сховища прочитано, і рядок «У сховищі версій: N,
  максимальна: M» (`tools/commands/sync.psm1:171`) уже надрукувався. Бонус запасного шляху:
  сама зупинка друкує логіни сховища у форматі, готовому вставити в `AUTHORS` —
  буквально `  <логін>=Ім'я <пошта>` (`tools/commands/sync.psm1`, блок біля throw) — тобто
  відповідає на питання «кого довести до `AUTHORS`», ще до того, як реальний `AUTHORS`
  розібраний.

Що означає провал (до того, як проба взагалі дійшла до сховища, — не зупинка на гейті
авторів) і на що він вказує:

- «расширение конфигурации с указанным именем не найдено» — ім'я розширення чи сам слот
  розширення, не сховище;
- помилка шляху — `storagePath` (у маніфесті `storages.<ключ>.path` накладки);
- помилка автентифікації чи доступу — сервісний користувач саме в цьому сховищі, не в
  сховищах узагалі.

Ціна проби — чесно: вона запускає платформу 1С, займає хвилину-дві й витрачає одну ліцензію —
так само, як і будь-яке прев'ю `sync` без `-Apply` (`skills/sync/SKILL.md` §2, правило
`-Apply`).

## 5. AUTHORS зі спадку — злиття і одноразові зіставлення

Файл дістають з історії старої гілки (`git show <стара-гілка>:<шлях-до-квартету>/AUTHORS >
AUTHORS`). Якщо продуктів декілька і в кожного був свій `AUTHORS` — обʼєднайте вручну
(унікальні рядки; конфліктні відповідності для одного й того ж ключа вирішує людина, не
підставляйте автоматично).

**Перед тим, як дописувати вміст одного `AUTHORS` за іншим — перевірте, що файл, до якого
дописуєте, закінчується порожнім рядком.** Якщо ні, останній рядок першого файлу зіллється з
першим рядком другого в один спотворений запис із фабрикованою git-особою — так побайтово
влаштовані і `AUTHORS` у `SMP_BankExchange`, і `AUTHORS` у `SimplyConnect_SMB`. Перевірка
одним рядком (порожній вивід — рядок є, дописувати без порожнього рядка попереду не можна):

```bash
tail -c1 AUTHORS | xxd
```

`Read-AuthorMap` (`tools/lib/Authors.psm1`) зупиняє прогін, коли результат такого злиття все ж
трапився — розпізнане ім'я не сміє містити `<`, `>` чи `=`, а зліплений рядок несе їх завжди —
але це страховка на випадок, коли перевірку вище пропустили, а не привід її пропускати: guard
ловить проблему вже після того, як злиття сталося.

**Один технічний логін сховища може стояти за різними людьми в різних версіях** — механізм
(різати реплей `-MaxVersions` по межах, правлячи `AUTHORS` між скибками; трейлер
`Storage-User` лишає сирий логін навіть після заміни рядка на коментар) уже в
`skills/onboarding/SKILL.md` §5.3 — тут лише робочий приклад, якого скіл не наводить.
Технічні логіни звуться за клієнтами (`Clarity_UNF_work`), а комітять у сховище нашого
продукту — за таким логіном у різні періоди могли працювати різні співробітники. Робочий
приклад послідовності — `AUTHORS` у `R:\github\SMP_BankExchange` (форма коментаря там — не
активний рядок мапи, а інертний слід із датою, логіном, людиною й причиною): тимчасовий
активний рядок іде в той самий коміт, що й продукт, для якого він потрібен; реплей
проганяється під цим іменем; окремий подальший коміт прибирає активний рядок і лишає на його
місці інертний коментар — не стирає слід, а вимикає його, бо це знання власника про один
конкретний період, а не стабільний звʼязок логін → людина.

## 6. Виміри трьох живих переходів (2026-09-10)

Це те, чого в скілі бути не може (він інструкція, не літопис), а людині, яка оцінює вартість
свого переходу, потрібне:

| Перехід | Форма | Результат |
|---|---|---|
| `SMP_SimplyCatalog` | gitsync, одне джерело, 121 файл | `verify` equal 121/121; `blame -w` 95,6 % рядків з комітів до 30.04.2024; реплей 4,8 с/версію |
| `SMP_BankExchange` | двошарова (0.6.0 над gitsync), три джерела | `verify` equal 274/274, 82/82, 160/160; `blame -w` 2 657 із 2 661; хеші дерев зійшлися з першого разу на всіх трьох |
| `SMP_SimplyConnect` | 0.6.0 **мержем orphan-гілки**, два джерела, 54 коміти роботи над точкою міграції | `verify` equal 187/187 і 231/231; `--follow` 1 → 19 комітів; 60 комітів перечеплено бітом-у-біт із обома PR-мержами |

`SMP_SimplyCatalog` (121/121) і `SMP_BankExchange` (274/274, 82/82, 160/160; `blame -w`
2 657/2 661) звірені з незалежно закоміченими джерелами (`docs/superpowers/plans/2026-09-03-B7-memory-and-runbook.md`,
`skills/onboarding/SKILL.md`). Решта чисел цього рядка й обидва результати `SMP_SimplyConnect`
(187/187, 231/231) і `blame -w` 95,6 % для `SimplyCatalog` — **як повідомлено із сесії
живого переходу**, без окремого повторного відтворення тут: інша сесія, яка ці переходи
проводила, назвала їх дослівно; довідка їх записує, а не переміряє заново.

**Усі три завершені й опубліковані — жоден не чекає рішення власника.** `SMP_SimplyCatalog`
запушив користувач сам. `SMP_BankExchange` — пуш за його командою, `force-with-lease`;
тринадцять старих тегів уціліли, бо лежать нижче точки відкоту. `SMP_SimplyConnect` — пуш за
прямою командою: `main` force-update, дві гілки `storage/*`, теги; службові гілки видалені,
локальне й віддалене зведені повністю.

Виміри часу: `rename-edt` — **0,073 с/файл — це стеля**, на малих деревах удвічі швидше (195
файлів — 9,7 с; 179 — 7,8 с; повна формула й парк — `skills/onboarding/references/gitsync-migration.md`, крок 3 — коміт перейменування).
`sync` — 4,1–4,8 с/версію на розширенні; друге злиття `-MergeMain` на вже піднятій ІБ — 5,9–6 с
(а «хвилина-дві» — це перший запуск платформи). Наповнення бази агента (`v8project.yaml`
`execution_timeout`): 19 011 файлів — 2,3 хв, 24 687 — 4 хв, 58 994 — 11,5 хв — звідси
`execution_timeout: 3600000` для воркспейсів повної конфігурації (`skills/onboarding/SKILL.md`
§3.2).

## 7. R098 проти R100 — не властивість процедури, а наслідок машини

**R098 vs R100 — наслідок `core.autocrlf` МАШИНИ, на якій виконують перейменування, а не
властивість процедури.** При `autocrlf = input` checkout пише LF, диск і індекс збігаються,
`git commit --only` перечитує ті самі байти — виходить R100. При `autocrlf = true` диск
тримає CRLF при LF в індексі — виходить R098 (або, без додаткової страховки нижче, ширший
розкид R092–R100). Обидва результати вище порогу 50 %, тож `--follow` працює в обох, і
**лагодити тут нічого не треба**.

Це варто написати саме так, а не як «має бути R098»: людина, яка через рік прочитає таку
вимогу й побачить у себе R100, піде шукати неіснуючу поломку.

Детермінованим результат (R100 незалежно від `autocrlf` машини) робить `-text` **з обох
боків** перейменування — не лише на цілі, а й на джерелі, і лише на час переходу
(`skills/onboarding/references/gitsync-migration.md`, крок 1 — розвідка й страховка). Так `SMP_SimplyConnect` дістав 166 × R100.
`SMP_BankExchange` без цієї другої половини рецепта дістав 195/68/126 × R100 (усього 389,
по одному числу на кожне з трьох джерел) — бо на тій машині `autocrlf = input` і так дав
R100 сам, без допомоги `-text` на джерелі. **Обов'язковий, без винятків, лише `-text` на
теці-цілі** — без нього форма дає R066, і `--follow` тихо рветься.

## 8. Чому orphan-гілка й повне `git rm -rf .` більше не використовуються

Це — знахідка з історії `SMP_SimplyConnect`: репозиторій уже ніс orphan-гілку від раннього
(0.6.0) заходу на перехід, який будував безперервну історію саме через `git checkout --orphan
restructure/<YYYY-MM>` і повне `git rm -rf .` кореня — той самий прийом, яким колись була ця
довідка, коли вона ще була чинним скілом `repo-migration`. **Реконструкція, не підтверджена
окремим джерелом:** що саме .gitmodules/.gitignore-знахідку нижче виявили ІМЕННО тоді, коли
цей прийом ще діяв як чинна процедура, — висновок із самої появи orphan-гілки в історії
`SimplyConnect` і зі старої редакції цього ж документа; жоден інший файл дерева цю подію не
називає буквально (`grep -rl 'SimplyConnect_Addin\|gitmodules'` — лише цей файл). Технічний
факт (що саме `git rm -rf .` робить із submodules і вкладеним `.gitignore`) не залежить від
цієї реконструкції й перевіряється поведінкою git незалежно.

**Поточна процедура (`kit.ps1
rename-edt`) цього кроку не має**: вона перейменовує файли лише всередині вказаного
EDT-піддерева (`-SourceRelPath`), а плоский коміт конверсії видаляє лише теку конкретного
джерела (`git rm -r -- <шлях теки джерела>`), не весь корінь репозиторію. Тому саму
небезпеку, описану нижче, під поточну процедуру відтворити нема як — але знання лишається
тут, бо воно реальне, дороге й ніде більше не записане.

`git rm -rf .` на дереві з зареєстрованими git submodules сам переписує `.gitmodules` —
вичищає з нього записи й лишає файл нульового розміру; «прибрати `.gitmodules`» після цього
означає видалити вже порожню оболонку, а не редагувати вміст, якого більше нема.
Попереднє `git submodule deinit -f <шлях>` для кожного зареєстрованого submodule робить
подальше видалення передбачуваним.

Важливіше: **видалення текованого каталогу забирає і його власний `.gitignore`.** У пілоті
`SimplyConnect_Addin/.gitignore` був закомічений і ховав 334 МБ артефактів збірки. `git rm -rf
.` прибрав теку — а разом із нею й цей файл, тож артефакти стали невідстеженими тією самою
операцією, яка щойно видалила теку. Якщо коли-небудь знадобиться повне очищення робочого
дерева (а не точкове видалення теки джерела, яке робить сьогоднішня процедура) — перевіряти
`git status --porcelain` одразу після, а не покладатись на те, що видима різниця вичерпується
самим видаленим деревом.

## 9. Продукт-плейсхолдер — рішення, якого скіл не питає

Порожня тека без реального вихідного коду (продукт заявлений, робота ще не почалась) — рішення
не належить жодному з кроків `skills/onboarding/SKILL.md`: підключати зараз як звичайний
продукт (розділ 3 скіла), чи позначити рядком-приміткою «пізніше» в новому `CLAUDE.md`, без
`v8project.yaml` і без реплею. Різних машин, окрім самого рішення, тут немає — воно ухвалюється
разово для кожної такої теки під час розвідки (розділ 1 вище).

## 10. Опис для нового `CLAUDE.md` — зі старого README, якщо він є

Абзац опису репозиторію (що це за підсистема, для яких конфігурацій) у новому `CLAUDE.md` —
не питання до людини (`skills/onboarding/SKILL.md` §2 і §3.6 просять лише «заповнити
плейсхолдери»), а факт, який складає сам скіл, і специфічно-міграційний прийом для цього — не
в скілі. Джерело — старий `README`, якщо він є: `git show <стара-гілка>:README.md` (лежить
зазвичай поруч із квартетом чи в корені старої гілки).

Якщо `README` немає в жодній гілці — той самий абзац складається без нього: з назв продуктів і
розширень, зі складу об'єктів метаданих, видимого у старих вихідниках, і з коментарів
сховища, вже видимих в історії старої гілки (`git log <стара-гілка>` — вона сама є реплеєм
історії сховища, зробленим свого часу `gitsync`).

В обох випадках — показати нарис людині для звірки перед першим комітом (`skills/onboarding/SKILL.md`
§3.6), а не вставляти мовчки: це нарис для підтвердження, а не запитання, що блокує прогін.

## 11. Форми, яких ця довідка вже не описує

Три форми, на які раніше довелось би шукати відповідь тут, тепер повністю веде скіл — розвилки
немає, переказувати нічого:

- **кілька джерел в одному репозиторії** (розкладка «крок 1–2 один раз на репозиторій, кроки
  3–6 окремим комплектом на кожне джерело, вертикально») — `skills/onboarding/references/gitsync-migration.md`,
  абзац «Джерел у репозиторії буває кілька» (перед нумерованими кроками);
- **двошарова історія, 0.6.0 над gitsync** (коли `storage.json` ховає під собою чисту
  gitsync-точку, а сама 0.6.0-конверсія в історії репозиторію могла лишити orphan-гілку —
  розділ 8 вище пояснює, звідки вона там узялась) — `skills/onboarding/SKILL.md` §5, таблиця
  форм, і `skills/onboarding/references/gitsync-migration.md`, розділ «Спадок 0.6.0: якщо
  `storage.json` трапився поза парком» (два способи, якими цю конверсію робили);
- **переїзд не-EDT шляхів простим `git mv`** (зовнішні обробки старої розкладки) —
  `skills/onboarding/references/gitsync-migration.md`, крок 3 (коміт перейменування).

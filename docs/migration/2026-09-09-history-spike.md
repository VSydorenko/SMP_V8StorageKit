
```
00000000: efbb bf0d 0ad0 9fd1 80d0 bed1 86d0 b5d0  ................
00000010: b4d1 83d1 80d0 b020 d09f d180 d0be d187  ....... ........
```

Точний підрахунок байтів:

| | байтів | CR (`0d`) | LF (`0a`) | BOM |
|---|---|---|---|---|
| EDT | 203 685 | **0** | 2 730 | немає |
| Designer | 206 418 | **2 730** | 2 730 | `efbbbf` |

Різниця рівно **2 733 байти = 3 (BOM) + 2 730 (один CR на рядок)**.

Після нормалізації (зняти BOM, прибрати `\r`) файли **побайтово ідентичні**.

```
git diff --numstat 945dca1:<EDT> f77aaf4:<Designer>   → 2730  2730
git diff -w --numstat 945dca1:<EDT> f77aaf4:<Designer> → 1     1
```

### Висновок (а)

EDT-сторона — **LF без BOM**; Designer-сторона — **CRLF з UTF-8 BOM**. Вміст той самий.
Без `-w` різниця «кожен рядок»; з `-w` різниця **рівно один рядок** — перший, до якого
прилип BOM. Це і визначає поведінку `blame` нижче.

### Знахідка, якої в §9.2 немає: `.gitattributes` мусить бути ДО конверсії

Перша спроба робила конверсію одразу після перейменування, як описує §9.2. Результат:

```
warning: in the working copy of '…/Ext/Module.bsl', CRLF will be replaced by LF the next time Git touches it
```

```
еталон f77aaf4        : 5b34daa077ce5b09c4315f4ab2beb7966642f973 (206418 байтів)
коміт конверсії c60d5ed: 39430804b5f7883f8d2b688f01fe639254a8e1dd (203688 байтів)
→ РОЗБІЖНІСТЬ: дерево НЕ стало рівним дзеркалу
```

Причина: на EDT-вершині `945dca1` файл `.gitattributes` містить лише

```
*.bin binary
*.axdt binary
*.addin binary
```

— ані `* text=auto`, ані `**/cfe/src/** -text`. А `core.autocrlf` у репозиторії — **`input`**.
Тобто `git add` тихо нормалізує CRLF→LF, і §9.2 крок 5 («тека джерела стає побайтово рівною
вершині `storage/<ключ>`») **не виконується**, хоча жодної помилки не видно. Наступний
`verify` показав би розбіжність на кожному файлі.

**Вимога до процедури:** коміт із сучасним `.gitattributes` (`* text=auto` плюс `-text` на
дерева платформи) має йти **між** перейменуванням і конверсією. Після цього всі три блоби
збіглися з еталоном побайтово.

## Step 5. Контроль: конверсія ВСЕРЕДИНІ злиття

Гілка `spike/order-wrong` від того самого `9d928c6`, злиття з `-X theirs` — конверсія
відбувається в самому злитті. Дерево змінилось, вміст рівний еталону, батьків 2.

```
TREESAME за шляхом модуля:
  spike/order-correct    = батько1? ТАК   = батько2 (дзеркало)? ТАК
  spike/order-wrong      = батько1? ні    = батько2 (дзеркало)? ТАК
```

| Показник | правильний порядок | зворотний порядок |
|---|---|---|
| `git log -- <шлях>` (модуль / метадані / форма) | 2 / 2 / 2 | **1 / 1 / 1** |
| `git log --follow` (модуль / метадані / форма) | 12 / 7 / 13 | 11 / 6 / 12 |
| `blame -w` → старим (модуль / метадані / форма) | 2 729 / 0 / 456 | **0 / 0 / 0** |

### Очікування §9.2 підтвердилось лише частково — і не тим механізмом

§9.2 стверджує: «конверсія **всередині** злиття викинула б EDT-історію з `git log`».

- Для **`git log -- <шлях>`** це **правда**: у зворотному порядку лишається **один** коміт —
  `b1483a8 sync: реплей версії сховища`. Спрощення історії йде за батьком-дзеркалом
  (єдиним TREESAME), і вся наша гілка, включно з комітом перейменування, відсікається.
- Для **`git log --follow`** це **неправда** на git 2.53: історія збереглась (11 проти 12
  комітів; менше рівно на відсутній коміт конверсії), і найдавніший коміт той самий,
  2021-05-18. `--follow` проходить обидва батьки.

**Справжня ціна зворотного порядку — не `log`, а `blame`:** `blame -w` атрибутує старим
комітам **нуль** рядків проти 2 729 і 456 у правильному порядку. Тобто порядок §9.2
навмисний і обґрунтований, але формулювання обґрунтування треба виправити: рятується
не `--follow`, а `blame` і plain `log`.

## Висновки

### (а) Кінці рядків і BOM

EDT — LF без BOM, Designer — CRLF з BOM; вміст ідентичний після нормалізації. Наслідок:
`git blame` без `-w` через межу марний (0–1 рядок), `git blame -w` зшиває BSL майже
повністю. Обов'язкова умова — `.gitattributes` із `-text` **до** коміту конверсії, інакше
`core.autocrlf=input` тихо зіпсує побайтову рівність із дзеркалом.

### (б) Поведінка git

Маршрут §9.2 дає безперервний `git log --follow` для всіх трьох видів файлів — до
2021-05-18. `blame -w` зшивається для BSL (99,96 % модуля, 85,9 % форми) і не зшивається
для метаданих (0 з 27) — очікувано, бо `.mdo` і `.xml` це різні формати, а не різні
кінці рядків. Порядок кроків критичний: зворотний порядок обнуляє `blame` і залишає
`git log -- <шлях>` з одним комітом.

### Рядок для `CLAUDE.md` репозиторію-споживача

> Історія до межі міграції (тег `legacy/gitsync-<YYYY-MM>`): `git log --follow -- <шлях>`
> показує її наскрізно. `git blame` через межу працює лише з `-w` (EDT писав LF без BOM,
> Designer пише CRLF з BOM) — і лише для модулів BSL; для метаданих і форм історію рядків
> дивитись як `git blame <коміт-перейменування> -- <той самий шлях>`.

### Що додати до §9.2

1. Крок «оновити `.gitattributes` під `-text`» **між** перейменуванням і конверсією —
   інакше побайтова рівність із дзеркалом не досягається, і збою при цьому не видно.
2. Виправити обґрунтування порядку: зворотний порядок ламає `blame` і plain `git log`,
   а не `git log --follow`.
3. Таблиця відповідності (Task 3) має врахувати **три** епохи шляхів у BankExchange,
   а не дві: між EDT і поточними іменами була проміжна Designer-епоха зі старими іменами тек.

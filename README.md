# SMP_V8StorageKit

Плагін Claude Code: конвеєр «сховище конфігурацій 1С ↔ git» для репозиторіїв SMP_*.
Походження — SMP_BankExchange (перезапуск 2026-08); скрипти й тести перенесені звідти.

## Встановлення

    claude plugin marketplace add VSydorenko/SMP_V8StorageKit
    claude plugin install v8storagekit@smp-v8storagekit

## Що всередині

- `tools/` — скрипти конвеєра (storage-sync, dump-config, load-ext, build) + модулі + Pester-тести
- `skills/` — storage-pipeline (щоденний цикл), product-onboarding (новий продукт), repo-migration (міграція старого репо)
- `templates/` — шаблони файлів репо-споживача (CLAUDE.md, .gitattributes, .gitignore, settings.json, storage.json)
- `docs/` — архітектура контуру «сховище ↔ git»
  - `docs/follow-ups.md` — свідомо припарковані знахідки аудиту й фінального рев'ю (junction/symlink, RepoRoot, MXL-обрив, тести, модульний probe)

Скіли реєструються з префіксом плагіна: викликаються як `v8storagekit:storage-pipeline`,
`v8storagekit:product-onboarding`, `v8storagekit:repo-migration` (не голим іменем зі
`skills/` вище — плагін-реєстр додає префікс сам, і без нього виклик впаде з `Unknown skill`).

## Розробка

Робоча копія — звичайний клон. Живе тестування на реальному проєкті:

    claude --plugin-dir R:\github\SMP_V8StorageKit

`/reload-plugins` підхоплює правки без перезапуску сесії. Тести:

    pwsh -NoProfile -File tools/tests/Run-Tests.ps1 -ExcludeTag Integration

Повний прогін (з тегом Integration) реально запускає 1cv8.exe і створює файлову ІБ.

Дешевий спосіб перевірити скіл так, як його побачить модель, не чекаючи на
`/reload-plugins` від користувача: `claude -p "..."` із шелу піднімає свіжу сесію з новим
реєстром плагінів.

### Як посилатись на файли плагіна зі скіла

У тілі `SKILL.md` токен `${CLAUDE_PLUGIN_ROOT}` замінюється абсолютним шляхом плагіна в
момент завантаження скіла. Це єдиний працездатний спосіб: змінної оточення з таким іменем
у Bash-виклику немає, тож форма з префіксом `env` дає битий шлях.

**Правило: вживати токен ЛИШЕ всередині шляху.** Підстановка сліпа — вона не розрізняє
адресу файлу й речення, яке про змінну розповідає. Пояснення на кшталт «пишіть
`${CLAUDE_PLUGIN_ROOT}` саме в цій формі, з фігурними дужками» після підстановки
перетворюється на робочу вказівку вписати абсолютний шлях конкретної машини — рівно те,
чого токен мав уникнути. Один такий випадок у `storage-pipeline` вже ловили в живій сесії;
теорія механізму тому живе тут, у README, який скілом не є й підстановці не підлягає.

Перевірка, що правило не порушене (має бути порожньо):

    grep -rn 'CLAUDE_PLUGIN_ROOT' skills/ | grep -v '/tools/\|/templates/\|/docs/'

### Кеш встановленої копії

`claude plugin update` перезаписує кеш `~/.claude/plugins/cache/...` **лише коли змінилась
версія** в `.claude-plugin/plugin.json`. За локального маркетплейсу це не заважає: сесії
вантажать саме робочу копію, а кеш лишається побічним артефактом. Але після встановлення з
GitHub авторитетним стає кеш — тому кожна зміна, яку мають побачити споживачі, потребує
підняття версії.

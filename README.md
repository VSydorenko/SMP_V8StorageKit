# SMP_V8StorageKit

Плагін Claude Code `v8storagekit` — контур роботи агента з 1С:Підприємством поруч з
[Unica](https://github.com/IngvarConsulting/unica). Unica редагує метадані, форми, СКД і код,
перевіряє, завантажує вихідники в базу й вивантажує їх з неї, збирає `.cf`/`.cfe`/`.epf`/`.erf`;
kit закриває те, чого Unica не вміє: сховища конфігурацій, дамп із живої бази людини, звірка git
зі сховищем, старт сесії.

Плагін має дві незалежні частини: **контур сховища** (цей вступ і розділи до «Процесу
розробки») і **процес розробки** — обговорення, спека, план, виконання субагентами, рецензія,
PR, закриття блоку; форк agent-kit 0.9.1, переписаний під 1С і PowerShell
([розділ нижче](#процес-розробки), рішення — `docs/adr/`). Кожна працює без іншої: процес не
потребує `v8storagekit.yaml`, контур сховища — профілю процесу.

Три речі, на яких тримається контур:

- **Сховище конфігурації — істина в останній інстанції.** Kit у сховище ніколи не пише,
  лише читає. Git — робоче середовище агента й історія «хто і коли змінив рядок».
- **Агент працює у своїй базі й ніколи не пише в базу людини.** Базу людини kit лише
  читає дампом, і лише на явне прохання.
- **Результат агента — `.cf`, `.cfe`, `.epf`, зібрані `make` Уніки.** Застосовує їх
  людина своїм Конфігуратором і сама кладе у сховище; kit підхоплює нову версію далі.

## Встановлення

    claude plugin marketplace add VSydorenko/SMP_V8StorageKit
    claude plugin install v8storagekit@smp-v8storagekit

Потрібно: PowerShell 7+, git, платформа 1С гілки **8.3.27.x**, модуль powershell-yaml
(`Install-Module powershell-yaml -Scope CurrentUser`), `gh` для PR у `task-finish`, плагін
Unica 0.16 з раннером `v8-runner`, який вона постачає (нижчу версію Уніки й відсутній раннер
`kit check` відхиляє як `error`). Для процесу розробки необов'язкові `gh` (`pr-gate`, `track`)
і Node 22 (сервер скіла `visual-companion`). Перевірити все одразу:

    pwsh -NoProfile -File tools/check-environment.ps1

Категорії у виводі відповідають реальним залежностям. Kit Уніку (MCP) не викликає, але її
раннер — інструмент kit: `sync` і `verify` беруть у нього платформу для бази агента, тож без
Уніки вони не працюють. `dump` з бази людини працює й без неї.

## Як це працює

- **Маніфест `v8storagekit.yaml`** у корені репозиторію описує воркспейси й джерела. Для
  кожного джерела — `truth`: `storage` (сховище, дзеркалиться в git), `vendor` або `dump`
  (дамп із живої бази), `git` (живе лише в git). Локальне для машини — підключення до баз,
  шляхи сховищ, шаблон `.dt` — у гітігнорованій накладці `v8storagekit.local.yaml`, паролі
  лише там. Слів «клієнт» і «продукт» у логіці немає: одна форма описує і продуктовий
  репозиторій з кількома варіаціями розширення, і клієнтську базу з конфігурацією,
  адаптацією та спільними розширеннями.
- **Дзеркала сховищ — orphan-гілки `storage/<джерело>`**, по коміту на версію сховища з
  автором, датою й коментарем поміщення; `AUTHORS` перекладає логін сховища в git-автора.
  Стан живе в трейлерах комітів, файлу стану немає. Глибина першого реплею — питання за
  джерелом: з початку, з версії N або лише поточна. Головна гілка приймає дзеркала
  злиттям; гілки задач агента йдуть від головної й закриваються PR.
- **База агента** — файлова під `build/` воркспейсу або серверна; її підключення — це
  `infobases.origin` у `v8project.local.yaml`. `provision` перевіряє конфігурацію-власника й
  підключення, запам'ятовує вибір `.dt` і друкує кроки Unica (`infobase.create`,
  `infobase.restore` з `.dt`, `push`); серверну базу створює людина в кластері, kit лише
  перевіряє підключення до неї й друкує крок `push force`. Kit базу агента не
  видаляє ніколи; порожню файлову створює сам лише тоді, коли першим її наповнює зі сховища.
  Пам'ять покоління бази веде раннер Unica (v8-runner): команди kit, що зрушують базу,
  друкують крок `push force` — Unica спитає людину про перезапис. Базу можна зламати й
  розгорнути знову.
- **Хук старту сесії** поставляє сам плагін (`hooks/hooks.json`): у репозиторії-споживачі
  показує, чи є у сховищах нові версії, і пропонує оновити; якщо сесію відкрито в підтеці,
  попереджає, що Unica бачитиме лише її. Правила спілкування процесу хук друкує в
  репозиторії з `v8storagekit.yaml` **або** з профілем процесу `.agents/kit.profile.json`;
  стан сховищ — лише з маніфестом. У проєкті без
  `v8storagekit.yaml` і без профілю хук мовчить і виходить з кодом 0, тож чужим проєктам машини
  не заважає.
- **Дозволи на MCP-інструменти Unica** лишаються в `templates/settings.json`, який
  `onboarding` кладе споживачу, а не в плагіні: плагін Claude Code не може постачати
  `permissions` — у його складі немає налаштувань із дозволами. Тому дозволи живуть у
  `.claude/settings.json` репозиторію-споживача.
- **Перед PR** `task-finish` звіряє гілку зі сховищем: версії, що з'явились у сховищі під час
  задачі, переносяться, а перетин зачеплених файлів називається людині до злиття.

Архітектура й знахідки живих прогонів — `docs/storage-and-git.md`.

## Команди `kit.ps1`

Один диспетчер `pwsh tools/kit.ps1 <команда> -RepoRoot <репозиторій-споживач>` зі
спільними параметрами `-RepoRoot`, `-Workspace`, `-Source`, `-Apply`. Команди — окремі
модулі `tools/commands/*.psm1`.

| Команда | Що робить |
|---|---|
| `check` | аудит: маніфест ↔ `v8project.yaml` ↔ `.gitignore`/`.gitattributes` ↔ `Configuration.xml` ↔ інваріанти `storage/*` ↔ хуки ↔ артефакти збірки в git; нічого не мутує |
| `session-check` | дешевий сигнал старту сесії: нові версії у сховищах, розбіжність `storage/*` з головною гілкою; спершу виконує повний `check` |
| `sync` | реплей нових версій кожного джерела `truth: storage` у `storage/<джерело>`; перше злиття в головну гілку; `-FromVersion N` або `-FromLatest` для першого реплею |
| `dump` | дамп джерела `truth: dump` або `vendor` із живої бази людини; розпізнає відкритий Конфігуратор |
| `verify` | звірка дерева гілки з канонічним дампом сховища на версії з трейлера; звірочний коміт — лише з `-Apply` |
| `supply-marker` | позначка поставки вендора `.kit-bin-sha1` після повного `pull` Unica; нічого не вивантажує |
| `provision` | база агента: перевірка власника й підключення, кроки Unica; порожню файлову створює лише для першого наповнення зі сховища; нічого не видаляє |
| `adopt` | прийняти дзеркало `storage/<джерело>` у гілку задачі заміною піддерева джерела |
| `install-hooks` | `.githooks/` + `core.hooksPath`, `.claude/settings.json` (якщо його немає) |

Коди виходу: `0` — виконано; `1` — зупинка; `2` — стан змінено частково, решта за людиною
(лише `sync`); `3` — нічого не змінено, але є що робити (`verify`, `session-check`). Без
`-Apply` жодна команда нічого не змінює в git, сховищі чи базах, але `sync` і `verify` усе
одно піднімають платформу — хвилина-дві й ліцензія.

## Скіли

Усі з префіксом плагіна: `v8storagekit:storage-sync`, а не `storage-sync` — голе ім'я дає `Unknown skill`.

| Скіл | Коли |
|---|---|
| `storage-rules` | правила контуру; хук старту сесії показує стан сховищ і називає цей скіл, агент завантажує його перед першою командою kit |
| `onboarding` | підключити репозиторій, воркспейс або джерело — діалогом: розпізнає форму репозиторію, показує, що бачить, пропонує кроки |
| `storage-sync` | перенести нові версії сховища в git |
| `infobase-dump` | вивантажити стан із живої бази людини в дерево джерела |
| `infobase-agent` | розгорнути або перестворити базу агента |
| `storage-adopt` | звести гілку задачі зі сховищем після того, як людина сама поклала туди частину |
| `storage-verify` | звірити гілку зі сховищем |
| `task-finish` | закрити задачу: sync → вирівнювання й канон Unica (`push force` → `pull force`) → adopt → verify → перевірка коду Unica (`unica.check`) → артефакти `make` Unica → PR; у процесі розробки сюди передає закриття `execute` |

Скіли процесу розробки — у розділі [«Процес розробки»](#процес-розробки).

### Предметні скіли 1С

Знання, виміряне в живих проєктах, яке раніше жило в користувацьких скілах окремої машини; тепер
приходить у кожен проєкт разом із плагіном.

| Скіл | Коли |
|---|---|
| `1c-unica` | розробка для 1С через Уніку: карта інструментів і скілів `unica:*`, пастки платформи, діагностичний виклик MCP поза сесією; Уніка не бачить потрібну теку проєкту (поза теками сесії) — сесія в корені репозиторію, `/add-dir` або, лише за згодою людини, `permissions.additionalDirectories` в `.claude/settings.local.json` |
| `1c-localization` | багатомовна конфігурація чи розширення: `НСтр`, багатомовні рядки метаданих і форм; скрипт перевірки вихідників |
| `1c-bsp-service-user` | службовий користувач ІБ, який створюється сам після встановлення розширення на БСП |
| `1c-websocket-client` | постійне WebSocket-з'єднання бази 1С із зовнішнім сервером і повернення після обриву |
| `codex-companion` | делегувати аудит чи рев'ю локальному Codex CLI як другу думку |

Скіл про 1С чи Уніку, що лежить поза плагіном (користувацький або проєктний), `kit-scan` показує в
розділі `Skills outside the plugin` як кандидата на перенесення сюди.

## Формат вихідників

Kit працює лише з форматом Designer. Вихідники в EDT-форматі (ознака — тека `DT-INF/`)
префлайт відхиляє; перетворіть їх операцією `convert` раннера Уніки або вивантажте сховище
наново.

## Процес розробки

Форк процесу agent-kit 0.9.1 (ADR-0001): ті самі назви скілів, агентів і команд, переписані під
1С і Windows. Відмінності від оригіналу — у `docs/adr/`; спільна мова — `docs/GLOSSARY.md`.
Тексти — українською (ADR-0008); кожен перенесений файл має шапку
`Ported from agent-kit 0.9.1 <шлях>, modified.` Що з оригіналу не перенесено свідомо й чому —
`docs/adr/`.

### Склад

| Вид | Що це | Перелік |
|---|---|---|
| Скіл | Інструкція для головної сесії: що робити й коли. Тіло вантажиться лише при виклику | `ls skills` — скіли процесу поруч зі скілами контуру |
| Агент | Субагент з однією роллю, моделлю за замовчуванням і списком інструментів | `ls agents` |
| Команда процесу | Механічна робота однаково щоразу, короткий результат, рядок `next:` | `tools/commands/process-commands.txt` |
| Хук | Хук старту сесії плагіна; правила спілкування (`hooks/communication-rules.md`) друкує в репозиторії з маніфестом або з профілем процесу | `hooks/` |

Агенти мають у `tools:` читальні MCP-інструменти Уніки (`unica_view`, `unica_search`,
`unica_resolve`, `unica_docs`, `unica_check`, `unica_diff`) — лише точними іменами: ім'я сервера
без інструмента відкрило б агенту й мутуючі `unica_apply`, `unica_run` (вимір у ADR-0006). Мутуючі
має лише `implementer`, і лише в межах брифу задачі.

### Як запускати

| Що | Як | Приклад |
|---|---|---|
| Скіл, що спрацьовує сам | Фраза своїми словами; агент обирає скіл за описом | «давай обговоримо …», «виконай план …», «який статус?» |
| Скіл лише для власника | Слеш-команда | `/v8storagekit:onboarding`, `/v8storagekit:close-block` (ретро — його необов'язковий крок) |
| Команда процесу | Попросіть агента; зазвичай її кличе скіл, бриф чи рядок `next:` попередньої команди | «запусти session-board» |
| Команда напряму, сирий вивід | Префікс `!` у полі вводу | `! sdd status` |

Скіли й агенти адресуються з префіксом плагіна: `v8storagekit:execute`, `v8storagekit:implementer`.

| Етап | Як запустити | Що відбувається | Результат |
|---|---|---|---|

| Дослідження | «проведи дослідження» | `research`: агенти `researcher` по одному питанню; код — через Уніку, поведінка платформи — справка й дамп | Факти з якорями й рекомендація |

| Спека | вихід «спека» з обговорення | `spec`: таблиця блоків і «інтерфейс → блок-власник», глосарій, ADR; аудит агентами `spec-auditor`; `track spec` — issues блоків | Затверджена спека |
| План | «план блоку X» | `plan`: ескіз із задачею 0; аудит агентами `plan-auditor` за ризиком 1С (права й RLS, обміни, проведення й блокування, перехоплення вендора) | Прийнятий план |

| Приймання | фінал `execute`, «зроби рецензію гілки» | `review`: `code-reviewer` на лінзу (зокрема 1С-лінзи `localization`, `vendor-compat`, `metadata`), `code-review-verifier` пробує спростувати кожну знахідку | Лише доведені знахідки |

| Закриття блоку | `/v8storagekit:close-block` | живий борг → issues, готові плани й мертві посилання прибрано, пам'ять переглянуто | Чистий канон |
| Ретро | крок 8 `/v8storagekit:close-block` | патерни → issue чи малий PR у цьому репо; загальні — ще й пропозиція в agent-kit | Правки пам'яті, issue |

Статус проєкту — скіл `track` і GitHub (віхи, issues блоків, PR), не файли.

### Команди процесу

Кличуться коротким ім'ям з Bash і з PowerShell: тека `bin/` плагіна є в `PATH` обох інструментів,
поруч лежать обгортки `<команда>` (bash) і `<команда>.ps1` (ADR-0002). Обидві кличуть
`tools/kit-process.ps1` — окремий вхід без param-блоку, щоб параметри `kit.ps1` і загальні
параметри PowerShell не перехоплювали аргументи команд. Прапорці — у стилі PowerShell
(`-Model sonnet`, не `--model`).

| Команда | Що робить | Головні форми |
|---|---|---|
| `sdd` | Журнал виконання плану: вікна задач, раунди, рішення | `init <план>`, `dispatch <N> -Model … -Weight …`, `watch`, `review`, `fix <N> -Note …`, `done`, `ruling`, `status`, `handoff`, `close` |
| `review-pack` | Пакет для рецензента: лише зміни гілки | `review-pack <base> [<head>]`, `review-pack -Branch` |
| `doc` | Читання документа частинами, пошук, якорі, борг | `doc <файл>`, `doc <файл> §N`, `doc find`, `doc anchors`, `doc refs`, `doc debt`, `doc history` |
| `pr-gate` | Життя PR і worktree | `start <issue> [<slug>]`, `open [-Draft]`, `ready`, `land <pr>`, `cleanup`, `prune`, `scratch add\|rm` |
| `track` | Статус і структура в GitHub | `track status`, `track spec <спека>`, `track milestone <назва>` |
| `session-board` | Дошка сесій для архітектора | `session-board [-Fetch]` |
| `session-cost` | Вартість сесій | `session-cost -By model\|agent\|day` |
| `kit-setup`, `kit-scan` | Підключення процесу до проєкту й відставання версії | `kit-setup -DryRun`, `kit-scan -Json` |

Спільний контракт (`tools/lib/KitCli.psm1`): коди виходу `0` — так, `1` — ні чи провал, `2` —
помилка виклику, `3` — **не перевірено** (перевірка не відбулась; ніколи не зелений). Помилка —
перший рядок stderr `<команда>: ERROR <причина>`; останній рядок успіху — `next: <точна наступна
команда>`. Контракт команд сховища (`kit.ps1`) — інший, див. «Команди `kit.ps1`» вище. Команди
процесу не потребують маніфесту й не проходять префлайт сховища.

### Підключення й оновлення проєкту

Проєкт підключає й оновлює власник командою `/v8storagekit:onboarding`; для процесу скіл веде дві команди:

- **`kit-scan`** — лише читання. Розрив версії проєкту й плагіна з кроками оновлення, дублікати
  частин kit, посилання на superpowers і його файли, журнали `.superpowers/sdd/` і `.agents/sdd/`,
  пам'ять про процедури, які тепер робить kit, скіли поза плагіном (копії скілів плагіна й
  кандидати на перенесення в нього), місця поза репозиторієм. `-Json` — те саме для
  машинного розбору. Рядок скану — кандидат, не вирок: класифікує скіл, читаючи файл.
- **`kit-setup`** — запис, ідемпотентно, нічого не видаляє; `-DryRun` друкує точний diff і нічого
  не пише. Дописує в `.claude/settings.json` проєкту правила дозволів на локальні команди процесу,
  кожне у двох формах — `Bash(…)` і `PowerShell(…)` (зовнішні дії: `pr-gate open|ready|merge|land|prune`,
  `track spec|milestone` і сам `kit-setup` лишаються з питанням); рядки `.gitignore`; каркас профілю
  з `workspace.mode` з фактів і `kit.version` (у репозиторії самого плагіна — без неї). Плагін не може постачати дозволи сам — тому команда.

**Версії.** Версія плагіна — `version` у `.claude-plugin/plugin.json`; версія проєкту — `kit.version`
у профілі (версія плагіна, до якої проєкт востаннє підключено чи оновлено). Що проєкт мусить
зробити після кожної версії — розділ `Чекліст оновлення проєкту` її запису в
[`CHANGELOG.md`](CHANGELOG.md). Проєкт відстав → хук старту сесії каже це одним рядком,
`kit-scan` (розділ `Kit version`) друкує кроки всіх версій після версії проєкту, `onboarding`
проходить їх одним PR і останнім комітом пише нову `kit.version`.

### Профіль і робочі теки

Усе проєктне — у профілі процесу, не в командах (ADR-0003). Шари, від нижчого до вищого:

1. `%USERPROFILE%\.config\v8storagekit\profile.json` — машина (`XDG_CONFIG_HOME`, якщо задана,
   замінює `%USERPROFILE%\.config`);
2. `.agents/kit.profile.json` — проєкт, комітиться;
3. `.agents/kit.profile.local.json` — локальне перекриття, git-ignored.

Об'єкти зливаються, масиви й скаляри замінюються. Поля мають ті самі імена, що в agent-kit, коли
значення те саме. Команда без потрібного поля називає його й виходить з кодом 3 — не вгадує.

**Режим робочої копії** — поле `workspace.mode` (ADR-0005), і лише воно визначає поведінку
`pr-gate start`/`land`:

- `shared` — 1С-репозиторій з базою агента: одна робоча копія й одна база на воркспейс; базу
  збирає чи тестує один виконавець за раз; коміти точкові (`git add <перелік>` +
  `git commit --only`); мутаційних перевірок рецензентів немає;
- `worktree` — репозиторій без бази (як цей): блок отримує worktree через `pr-gate start`.

Робочі теки — у **головному** checkout, навіть коли команда йде з worktree:

| Тека | Що там |
|---|---|
| `.agents/out/` | пакети рецензії, повний вивід команд |
| `.agents/sdd/<план>/` | журнал виконання плану: `progress.md`, брифи й звіти задач |
| `.agents/briefs/` | брифи архітектора сесіям (поле `orchestrate.briefs`) |
| `.agents/private/` | те, що не комітиться ніколи (поле `private.dir`) |

Кожна з цих тек має власний `.gitignore` `*`; комітиться лише `.agents/kit.profile.json`.

## Межі

- Сховища конфігурацій — тільки читання: жодних `ConfigurationRepositoryCommit`, `Lock`,
  `UnlockObjects`. Запис у сховище виконує людина в Конфігураторі.
- `-Apply` — лише коли людина явно попросила. `git push`, PR і релізи — лише за її словом.
- Рядки `лиценз`, `ліценз`, `license`, `HASP` у виводі платформи зупиняють роботу.
- Артефакти збірки в git не лежать; `check` попереджає про закомічені.
- Накладка з паролями пишеться лише після того, як `.gitignore` її ховає.

## Розробка плагіна

Будова репозиторію, тести, правила розробки, механізм `${CLAUDE_PLUGIN_ROOT}` у скілах, кеш
встановленої копії й порядок релізу — `CLAUDE.md` (для того, хто розробляє сам плагін). Що саме
роздається споживачам — `templates/README.md`.

Після релізу споживач на машині оновлює плагін так: `claude plugin marketplace update
smp-v8storagekit`, потім `claude plugin update v8storagekit@smp-v8storagekit` і **нова сесія**.
Якщо `update` мовчки відповів «вже встановлено» — ознака застряглого кеша одна, відсутність нових
скілів, і лікує лише `uninstall` плюс `install`.

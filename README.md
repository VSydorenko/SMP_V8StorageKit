# SMP_V8StorageKit

Плагін Claude Code: конвеєр «сховище конфігурацій 1С ↔ git» для репозиторіїв SMP_*.
Походження — SMP_BankExchange (перезапуск 2026-08); скрипти й тести перенесені звідти.

## Встановлення

    claude plugin marketplace add VSydorenko/SMP_V8StorageKit
    claude plugin install v8storagekit@smp-v8storagekit

## Що всередині

- `tools/` — диспетчер `kit.ps1` (десять команд, `commands/*.psm1`, список нижче), спільні
  модулі `lib/*.psm1`, Pester-тести `tests/`, окремий `check-environment.ps1`, статичний стаб
  `assets/empty-extension/`
- `skills/` — вісім скілів (список нижче)
- `templates/` — файли, які плагін копіює в репозиторій-споживач: `CLAUDE.md`, `README.md`,
  `settings.json`, `gitattributes`/`gitignore` (без провідної крапки — щоб не діяти на сам
  kit), `hooks/session-start.ps1`, `githooks/pre-commit`+`pre-merge-commit`, приклади
  `v8storagekit.yaml.example`, `v8storagekit.local.yaml.example`, `AUTHORS.example`; повна
  відповідність «файл тут → файл у споживачі» — `templates/README.md`
- `docs/` — `storage-and-git.md` (архітектура контуру), `follow-ups.md` (свідомо припаркована
  робота), `text-policy.md` (чому вихідники не конвертуються), `unica-contract.md` (на що
  покладаємось в Unica), `migration/legacy-gitsync-repo.md` (перехід старого gitsync/EDT-репо)

Скіли реєструються з префіксом плагіна: `v8storagekit:sync`, `v8storagekit:onboarding` і так
далі (не голим іменем зі `skills/` вище — плагін-реєстр додає префікс сам, і без нього виклик
впаде з `Unknown skill`).

## Команди kit.ps1

Один диспетчер `pwsh tools/kit.ps1 <команда> -RepoRoot <шлях до репо-споживача>` зі спільними
параметрами `-RepoRoot`, `-Workspace`, `-Source`, `-Apply`. Команд рівно десять — окремі
модулі `tools/commands/*.psm1`; повний опис, коди виходу й контракт «мутує/не мутує» —
`docs/storage-and-git.md` §«Команди kit»:

| Команда | Що робить |
|---|---|
| `check` | аудит: маніфест ↔ `v8project.yaml` ↔ `.gitignore`/`.gitattributes` ↔ `Configuration.xml` ↔ інваріанти `storage/*` ↔ хуки ↔ артефакти збірки в git; нічого не мутує |
| `session-check` | дешевий сигнал старту сесії — чи є нові версії у сховищах, чи `storage/*` розійшлися з головною гілкою; його викликає хук споживача |
| `sync` | реплей нових версій кожного джерела `truth: storage` у `storage/<ключ>`; перше злиття в головну гілку |
| `dump` | дамп джерела `truth: dump`/`vendor` із живої бази людини (лише читання бази, лише на явне прохання) |
| `verify` | звірка дерева `<ref>` із канонічним дампом зі сховища на версії з трейлера; звірочний коміт — лише з `-Apply` |
| `canon` | `/DumpConfigToFiles` з бази агента назад у дерево кожного джерела воркспейсу |
| `provision` | база агента: порожня або з `.dt`; спершу перевіряє, що на диску є непорожнє дерево конфігурації-власника |
| `build` | `.epf` через платформу в `build/artifacts/`; забирає туди `.cf`/`.cfe`, які там лишила `operation=make` Уніки |
| `install-hooks` | кладе `.githooks/` + `core.hooksPath`, шим `.claude/hooks/session-start.ps1` і `.claude/settings.json` (якщо його ще немає) |
| `rename-edt` | переносить EDT-дерево gitsync-вивантаження в точні шляхи Designer — перехід наявних репозиторіїв, `docs/migration/legacy-gitsync-repo.md` |

## Скіли

Усі — з префіксом `v8storagekit:`.

| Скіл | Коли |
|---|---|
| `using-v8storagekit` | вступ до контуру; вантажиться хуком старту сесії в репозиторії-споживачі, вручну не викликається |
| `onboarding` | підключити репозиторій, воркспейс або нове джерело |
| `sync` | перенести нові версії сховища в git |
| `dump` | вивантажити стан із живої бази людини в дерево джерела |
| `reconcile` | звести гілку задачі зі сховищем після того, як людина сама щось туди поклала |
| `provision` | розгорнути або перестворити базу агента |
| `verify` | звірити гілку (типово головну) зі сховищем |
| `finish` | закрити задачу: sync → canon → merge → verify → тести й синтаксис Unica → артефакти → PR |

## Хук старту сесії

**Плагін хуків не оголошує** — `hooks/hooks.json` у kit немає, і не буде: хук у плагіні
спрацьовував би в кожній сесії, де плагін встановлений, і в не-1С проєктах цього оточення
теж. Хук живе в репозиторії-споживачі: `templates/settings.json` реєструє
`SessionStart` → `.claude/hooks/session-start.ps1`, а сам файл — це шим
`templates/hooks/session-start.ps1`: без власної логіки, він лише знаходить корінь плагіна в
реєстрі встановлених плагінів, кличе `kit.ps1 session-check` у поточній теці й друкує
контекст. Плагіна не встановлено — шим мовчить, код виходу 0 завжди. Кладе його скіл
`v8storagekit:onboarding` або команда `kit install-hooks`.

## Залежності

- PowerShell 7+, git, платформа 1С гілки **8.3.27.x** — без цього `tools/` не запуститься
  взагалі.
- Модуль **powershell-yaml** (PSGallery) — читає `v8storagekit.yaml` і `v8project.yaml`:
  `Install-Module powershell-yaml -Scope CurrentUser`.
- Pester 5+ — для розробки самого kit (прогону тестів).

Перевірити все одразу:

    pwsh -NoProfile -File tools/check-environment.ps1

Докладніше про архітектуру, знахідки й межі — `docs/storage-and-git.md`,
`docs/follow-ups.md`, `docs/text-policy.md`, `docs/unica-contract.md`.

## Зв'язок з Unica — доповнення, а не залежність

`v8storagekit` розрахований на роботу в парі з плагіном
[`unica`](https://github.com/IngvarConsulting/unica) (маркетплейс —
`IngvarConsulting/unica-marketplace`), але **не викликає його і не потребує для
запуску**. Різницю варто тримати чіткою: вона визначає, що ламається без Уніки, а що ні.

**Конвеєр самодостатній.** У `tools/` немає жодного виклику Unica (жодного MCP-виклику,
жодного запуску `unica`/`oscript`) — платформу шукає сам `Get-V8Path`
(`tools/lib/V8.psm1`) у `C:\Program Files\1cv8\8.3.27.*`, а всі операції йдуть через
Конфігуратор напряму. `kit.ps1 build` (`tools/commands/build.psm1`) обходить Уніку
свідомо: її `operation=make` для `.epf`/`.erf` на Windows падає на публікації артефакту.
Мінімум для роботи скриптів — PowerShell 7, git і платформа 1С гілки 8.3.27.x.

**Уніка потрібна для роботи з тим, що конвеєр синхронізував.** Kit доставляє вихідники
розширення в git; редагування метаданих, форм, СКД, ролей і BSL, валідація й пошук по коду
— це Уніка. Три місця, де kit це прямо передбачає:

- `v8storagekit:onboarding` створює кожному продукту `v8project.yaml` — воркспейс Уніки;
- `kit.ps1 dump` існує рівно заради операцій Уніки, яким потрібен склад
  конфігурації-власника (`cfe.borrow`, `cfe.diff`, `cfe.validate`);
- `templates/settings.json` дозволяє репозиторію-споживачу 34 MCP-інструменти Уніки.

Тому: без Уніки синхронізація сховища з git працює повністю, а працювати з
синхронізованими вихідниками нема чим — лишається ручне редагування Designer XML.
Формулювання «плагін не працює без Уніки» неточне й веде до хибної діагностики.

## Розробка

Робоча копія — звичайний клон. Живе тестування на реальному проєкті:

    claude --plugin-dir R:\github\SMP_V8StorageKit

`/reload-plugins` підхоплює правки без перезапуску сесії. Тести:

    pwsh -NoProfile -File tools/tests/Run-Tests.ps1 -ExcludeTag Integration

Повний прогін (з тегом Integration) реально запускає `1cv8.exe`, створює файлову ІБ і
вантажить у неї розширення.

Дешевий спосіб перевірити скіл так, як його побачить модель, не чекаючи на
`/reload-plugins` від користувача: `claude -p "..."` із шелу піднімає свіжу сесію з новим
реєстром плагінів.

### Як посилатись на файли плагіна зі скіла

У тілі `SKILL.md` токен `${CLAUDE_PLUGIN_ROOT}` замінюється абсолютним шляхом плагіна в
момент завантаження скіла. Це єдиний працездатний спосіб: змінної оточення з таким іменем
у Bash-виклику немає, тож форма з префіксом `env` дає битий шлях.

**Правило: вживати токен ЛИШЕ всередині шляху.** Підстановка сліпа — вона не розрізняє
адресу файлу й речення, яке про змінну розповідає. Пояснення на кшталт «пишіть
`${CLAUDE_PLUGIN_ROOT}` саме в цій формі, з фігурними дужками» після підстановки
перетворюється на робочу вказівку вписати абсолютний шлях конкретної машини — рівно те,
чого токен мав уникнути. Один такий випадок уже ловили в живій сесії одного зі скілів (до
поділу на восьмеро — тодішньої назви той скіл більше не носить); теорія механізму тому
живе тут, у README, який скілом не є й підстановці не підлягає.

Перевірка, що правило не порушене (має бути порожньо):

    grep -rn 'CLAUDE_PLUGIN_ROOT' skills/ | grep -v '/tools/\|/templates/\|/docs/'

### Кеш встановленої копії

`claude plugin update` перезаписує кеш `~/.claude/plugins/cache/...` **лише коли змінилась
версія** в `.claude-plugin/plugin.json`. Кожна зміна, яку мають побачити споживачі, потребує
підняття версії. Окремо: `claude plugin install`/`update` на встановлений плагін можуть
мовчки відповісти «вже встановлено» й нічого не зробити — оновлює лише `uninstall` →
`install`, і єдина ознака застряглого кешу — **відсутність нових скілів у ньому**.

**За локального маркетплейсу сесії вантажать саме робочу копію, а кеш лишається побічним
артефактом** — і це стосується скілів та команд, тобто того, з чим працює агент.

Це твердження двічі переписували в протилежні боки, тож нижче — як його перевіряти, а не
кому вірити. **Не дивіться в `installed_plugins.json`:** там `installPath` показує на
кеш (`…\cache\smp-v8storagekit\v8storagekit\<версія>`) навіть тоді, коли скіли беруться не
звідти. Це проксі, і 2026-09-09 висновок із нього вже виявився хибним.

**Правильний вимір — рядок `Base directory for this skill:`**, з яким скіл приходить у
сесію. Виміряно 2026-09-09 у сесії споживача (`SMP_SimplyCatalog`, запущеній **без**
`--plugin-dir`): скіл прийшов із `R:\github\SMP_V8StorageKit\skills\onboarding`, у його
тексті були `rename-edt` і `-FromVersion`, а `kit.ps1` показував `rename-edt` серед
доступних команд. У кеші `0.6.0` того ж дня: `skills/onboarding/SKILL.md` — 317 рядків
проти 436 у робочій копії, жодної згадки `rename-edt`, файла
`tools/commands/rename-edt.psm1` немає. Тобто сесія читала теку, а не знімок.

(Збіг чисел, а не зміна висновку: після поділу `onboarding/SKILL.md` 2026-09-10 на
`SKILL.md` + `references/gitsync-migration.md` робоча копія сама має 317 рядків у
`SKILL.md` — це вимір іншого дня й іншого файлу, ніж кеш `0.6.0` вище, збіглося випадково.)

Знахідка B5 («кеш був знімком від 02.09, а `update` відповідав "вже встановлено"») цьому
**не суперечить**: вона про сам кеш і про поведінку `plugin update`, а не про те, з якої
теки резолвляться скіли.

Практичний висновок: **щоб перевірити власну правку, робити не треба нічого** — сесія в
репозиторії-споживачі вже бачить робочу копію. Бамп версії й переустановлення потрібні
рівно для одного: віддати зміни тому, хто ставив плагін **із GitHub**, — там авторитетним
стає кеш.

Прапорець `claude --plugin-dir R:\github\SMP_V8StorageKit` лишається чинним способом
(діє лише на ту сесію, `/reload-plugins` підхоплює правки), але для локального
маркетплейсу він **не обов'язковий**.

Не перевірено й тому не стверджується: чи так само резолвиться `${CLAUDE_PLUGIN_ROOT}`
для **хуків** і **MCP-серверів** плагіна — вимір вище стосується лише скілів і команд.

# Рев'ю влитої роботи

Мета не в тому, щоб знайти якомога більше. Вона в тому, щоб не пропустити те, що коштуватиме окремого виправлення, і не завалити власника шумом. У проєктах власника верифікатор спростовував 19–40 % знахідок першого проходу (agent-kit), тож у кожному рев'ю діють дві речі: поріг упевненості й спроба спростування кожної знахідки.

## 1. Брама й межа

- Пропусти, одним рядком, diff, що є лише перейменуванням із зеленими воротами, файлом блокування залежностей, форматуванням, згенерованими файлами чи документами без коду (документи як результат можуть дістати лише лінзу `drift`).
- Зафіксуй межу: база й голова. Збери вхід один раз: `review-pack <base> [<head>]` — усі рецензенти читають той самий пакет. Без межі рев'ю стає аудитом репозиторію.
- Правила проєкту: поле профілю `review.criteria` називає файл критеріїв проєкту. Передай його шлях кожному рецензентові; плагін правил проєкту не тримає.
- Режим робочої копії (`workspace.mode`): у `shared` (1С) база агента спільна — рецензенти й верифікатори її не збирають і мутуючих інструментів Уніки (`unica_apply`, `unica_run`) не кличуть; мутаційних перевірок у цьому режимі нема.

## 2. Лінзи

Одна лінза = один незалежний рецензент. Обирай за тим, що торкається diff; зазвичай спрацьовують 3–4. Перевірки кожної лінзи: [references/lenses.md](references/lenses.md).

| Лінза | Коли |
| --- | --- |
| `correctness` | завжди |
| `test-honesty` | лише коли зачеплено тести (YaXUnit, фікстури, налаштування перевірок) |
| `drift` | у грі план, спека, скіл чи документ |
| `architecture` | зачеплено кілька модулів чи підсистем, спільний модуль, межу клієнт/сервер, межу «розширення ↔ конфігурація» |
| `data-layer` | запити, регістри, проведення, права й RLS, блокування, транзакції, шляхи запису |
| `localization` | зачеплено тексти для людини, `НСтр`, кілька мов |
| `vendor-compat` | розширення з перехопленнями (`&Перед`/`&После`/`&Вместо`/`&ИзменениеИКонтроль`) чи запозиченими формами |
| `metadata` | зачеплено XML метаданих чи форм |
| `history` | змінено старий чи гарячий код |

На прийманні додай лінзу, якої не мав виконавець (`v8storagekit:code-reviewer` із приймальною лінзою з `references/lenses.md`, `model: opus` у виклику — свідомо, бо приймальна лінза мусить бачити те, що пропустили задачні рецензенти на Sonnet).

## 3. Названі ризики

Дай кожному рецензентові 3–6 конкретних сценаріїв збою з diff **і** плану: «вхід чи стан → що ламається». Рецензент дає вердикт на кожен окремо від власних знахідок. Без названих ризиків рев'ю звіряє diff із планом і пропускає дефект, закладений у самому плані.

## 4. Розгалуження

| Що рецензують | Лінзи | Верифікатор |
| --- | --- | --- |
| мала правка, 1–2 файли | `correctness` | знахідки blocker і major |
| блок чи фаза плану | 3–4 | кожна знахідка |
| перед злиттям гілки; чутливий код (запити, права й RLS, блокування, проведення, транзакції, публічні контракти) | усі доречні + `history` | кожна знахідка; два верифікатори на blocker |

- Запускай `v8storagekit:code-reviewer` по разу на лінзу, усіх в одному повідомленні, щоб жоден рецензент не бачив результатів іншого.
- Модель за ризиком, у виклику Agent: типово `sonnet`; `opus` для `data-layer` і для будь-якої лінзи на правах, RLS, транзакціях, блокуваннях, проведенні, бо дефекти прав і меж довіри Sonnet пропускає частіше (вимір agent-kit, його ADR-0005).
- Потім по одному `v8storagekit:code-review-verifier` на кожну знахідку, лише з текстом знахідки — без міркувань рецензента. Модель — `sonnet`; `opus` для знахідки blocker і для знахідки на правах, RLS, транзакціях, блокуваннях, проведенні, бо там хибне «спростовано» коштує дефекту в злитому коді.
- Необов'язкова незалежна перевірка чутливого коду: скіл `codex-companion`, якщо він є на машині (рев'ю проти бази `<branch>`, лише читання); його знахідки верифікуй так само. Скіла немає — нічого не вигадуй і не імітуй.
- Помічники Уніки (`unica:code-review`, `unica:code-diagnostics`) — джерело сигналу для рецензентів, не заміна лінзам.
- Інструмент Workflow — лише коли власник просив; розгалуження read-only агентів в одному повідомленні робить те саме.

## 5. Зведення

- Прибери дублі, відсортуй за серйозністю, відкинь спростоване верифікатором.
- Усе, що додаєш під час зведення, перевір сам: більше ніхто цього не перевіряв.
- Згода між рецензентами — не доказ: це та сама модель.
- Порахуй частку спростованого й внеси її в звіт.
- Знахідка, яку аудит плану міг зловити дешевше, має позначку `plan-class`: передай її архітектору, він додасть цей клас до аудиту плану.

## 6. Звіт

Формат, шкала й перелік «не знахідка»: [references/report.md](references/report.md). Завжди додавай «Not checked»: рев'ю, що не називає своїх меж, читається як гарантія, якої воно не давало. У режимі `shared` назви там відсутність мутаційних перевірок і, якщо Уніки не було, пошук лише `git grep`.

Протокол верифікатора: [references/verifier.md](references/verifier.md).

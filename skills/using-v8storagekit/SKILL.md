# using-v8storagekit — як тут працює агент

Цей репозиторій підключено до плагіна `v8storagekit`: сховища конфігурацій 1С — істина,
git — робоче середовище агента, Unica — основний інструмент. Kit закриває рівно те, чого
Unica не вміє: сховища, дамп із живої бази, база агента, звірка git зі сховищем.

## Принципи

1. **Сховище — істина.** Коли git попереду сховища — це видимий борг «застосувати залишок», не помилка. У сховище kit не пише.
2. **Unica — основний інструмент; kit доповнює.** Редагування, перевірка, завантаження в базу агента, збірка `.cf`/`.cfe`/`.epf`/`.erf` — Unica 0.16.
3. **Агент працює у своїй базі й ніколи не пише в базу людини.** Базу людини kit лише читає (`dump`), і лише на явне прохання.
4. **Результат агента — зібрані файли** у `build/artifacts/` воркспейсу (`make` Уніки). Застосовує людина, у своїй базі, своїм Конфігуратором.
5. **Структура репозиторію — у `v8storagekit.yaml` і `v8project.yaml`.** Слів «клієнт» і «продукт» у логіці немає.
6. **Байти в git — байти платформи.** Перед порівнянням дерево набору вивантажує з бази агента сама платформа — повний `pull` з `"force":true` Уніки (окремої команди kit для цього немає).

## Куди йти за яким наміром

| Намір | Скіл | Команда kit |
|---|---|---|
| «є нові версії у сховищі», «перенеси зі сховища» | `v8storagekit:sync` | `kit.ps1 sync [-Apply]` |
| «вивантаж конфігурацію з бази» | `v8storagekit:dump` | `kit.ps1 dump [-Apply]` |
| «я поклав частину в сховище» | `v8storagekit:reconcile` | `sync` → `push force` → `pull force` → `adopt storage/*` у гілку задачі (заміна, з прев'ю всіх списків) |
| «закриваємо задачу», «готуй PR» | `v8storagekit:finish` | `sync` → `push force` → `pull force` → `adopt storage/*` → `verify` → артефакти → PR |
| «розгорни / перезбери базу агента» | `v8storagekit:provision` | `kit.ps1 provision [-Apply]` |
| «звір git зі сховищем» | `v8storagekit:verify` | `kit.ps1 verify [-Ref X] [-Apply]` |
| «підключи репозиторій / воркспейс / джерело», «переведи репозиторій на маніфест» | `v8storagekit:onboarding` | `kit.ps1 check`, `kit.ps1 install-hooks [-Apply]` |
| Уніка не бачить потрібної теки (немає в `unica.view {}`, тека поза сесією) | `v8storagekit:unica-folders` | — |

### Процес розробки (обговорення → спека → план → виконання → приймання)

Окрема від контуру сховища частина плагіна: працює й без `v8storagekit.yaml`, проєктне бере з
профілю `.agents/kit.profile.json`. Команди процесу (`sdd`, `review-pack`, `doc`, `pr-gate`, …)
кличуться коротким ім'ям.

| Намір | Скіл |
|---|---|
| «давай обговоримо», ідея без форми | `v8storagekit:discuss` |
| питання ширше за один факт, «досліди» | `v8storagekit:research` |
| спека, глосарій, ADR | `v8storagekit:spec` |
| план блоку, аудит плану | `v8storagekit:plan` |
| «виконай план», бриф виконавця | `v8storagekit:execute` — закриття блоку в репозиторії з маніфестом передає `v8storagekit:finish` |
| рецензія готової роботи | `v8storagekit:landed-review` |
| роль архітектора частини | `v8storagekit:architect` |
| статус, віхи, issues у GitHub | `v8storagekit:track` |
| лише власник: закрити блок, ретро, підключити процес | `/v8storagekit:close-block`, `/v8storagekit:retro`, `/v8storagekit:kit-onboard` |

`v8storagekit:onboarding` підключає контур сховища, `v8storagekit:kit-onboard` — процес; це
різні підключення, і одне не потребує іншого.

Вихідники в EDT-форматі (`DT-INF/`) kit не підтримує: зупиніться й скажіть людині про `convert`
раннера Уніки чи повторне вивантаження сховища.

Команди kit: `check`, `session-check`, `sync`, `dump`, `verify`, `supply-marker`, `adopt`,
`provision`, `install-hooks`. Запускаються з кореня репозиторію:
`pwsh -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/tools/kit.ps1" <команда> -RepoRoot .`
Без `-Apply` жодна команда нічого не змінює в git, сховищі чи базах — але `sync` і `verify`
без `-Apply` усе одно піднімають платформу (хвилина-дві, ліцензія). `dump` — ні: без `-Apply`
він лише друкує базу, користувача й ціль (`dump.psm1`, гілка без `-Apply`, `continue` до
запуску Конфігуратора). `-Apply` — лише на явне прохання людини.

## Unica поруч із kit

Код, метадані, перевірку, збірку й базу агента веде Уніка: вхід — `unica.view {}` і скіл
`unica:unica-dev`; словник операцій `unica.run` зі схемою аргументів (`push`, `pull`, `make`, …)
віддає сам виклик без `op`. Kit аргументів Уніки не повторює — нижче лише конвенції kit поверх неї.

**Канонізація дерева** — `pull` набору з `"force":true` із бази агента: лише на гілці з закоміченою
роботою й базою, вирівняною `push force`. Збірка `.cf`/`.cfe`/`.epf`/`.erf` — `make` Уніки; kit
файлів не копіює й не перейменовує.

Уніка вимагає явний `"dryRun"` у кожному `unica.run`; kit **за власною конвенцією** друкує
спершу `"dryRun":true` (превью показує попередження на кшталт `infobase_overwritten` до виконання),
потім той самий виклик з `"dryRun":false`.

**Крок, надрукований командою kit, — виконати дослівно.** `sync`, `verify` і `provision` зрушують
чи створюють базу агента й друкують блок «Далі …» — `sync` і `verify` після кожного свого набору
(наприкінці виводу лишаються підсумок і, за потреби, рядки `ЗУПИНКА`), `provision` — у кінці дій над
воркспейсом. У блоці — точний `unica.run …` і, для поставки
вендора — зупинка з рецептом (повний `pull` набору з `"force":true`, далі `kit supply-marker … -Apply`; текст друкує kit). Їх не
переказують і не замінюють своїм. **Крок, надрукований командою kit, виконуй у воркспейсі, названому
в її виводі** (заголовок `Воркспейс: …` або «воркспейс …» у заголовку блоку «Далі …»); як обрати цей
воркспейс в Уніці — знання Уніки та її скілів. Після `pull` — `git status --porcelain -- <шлях набору>`:
непорожній вивід означає, що вивантаження раннера дало інші байти, ніж kit, — зупинка й доповідь,
не робота для агента. **Рядок `ЗУПИНКА: …` наприкінці виводу команди — зупинка з доповіддю людині,
без обходу і без наступних кроків скіла**; поле `AlignSteps` з `Op = 'blocked'` означає те саме.

**Після `sync` і `verify` — `push` з `"force":true` на кожен зрушений набір.** Команда друкує його
сама: `unica.run {"op":"push","args":{"sourceSet":"<набір>","force":true},"dryRun":true}` — повне
завантаження набору з git. Обов'язковий, а не страховий: після оновлення бази версією сховища
звичайний `push` не відмовляє й мовчки лишив би в базі суміш версії сховища з git.
- **Уніка спитає людину** «Перезаписать базу «origin» исходниками набора …?» — це очікувано. Не
  обходити, не повторювати без відповіді: модель згоди за людину не дає, і Уніка це перевіряє.
- **Лише в інтерактивній сесії** — основній чи в її субагенті (питання доходить до людини, виклик
  чекає відповіді). У `claude -p` цей крок миттєво закінчується `cancelled`: `sync`/`verify` без людини
  можливі, крок після них — ні.
- **Відповідь `cancelled`** — зупинка з доповіддю людині: «база агента не вирівняна; наступний `push`
  відмовить». Без повтору.
- **`os error 5` («Отказано в доступе») на `pull`** — найчастіше редактор чи його
  розширення-аналізатори (git, Pylance) тримають файли набору в мить підміни теки. Закрити редактор
  чи вимкнути розширення для робочої області й повторити один раз; повторилось — зупинка й доповідь.

Сам `"force":true` агент додає лише в надрукований kit крок і в сітку нижче, на базі агента
(`infobases.origin`, перевірена kit як не база людини). Для будь-якої іншої бази правило Уніки діє без винятків.

**Сітка на пропущений крок.** Від пропущеного кроку захищає лише сам надрукований крок, а не раннер:
набір з **незміненим** деревом звичайний `push` пропускає без звірки покоління. Тому в контурі kit
`infobase_state_unverified` або `non_fast_forward` (чи `no_memory`) у відповіді `push` бази агента —
**не ігнорувати**, а виконати
`unica.run {"op":"push","args":{"sourceSet":"<набір>","force":true},"dryRun":true}` для кожного
названого набору — з тим самим питанням людині й тими самими правилами, що вище.

**Порада Уніки замінити `-text` — не виконувати.** `unica.check {}` на політиці kit дає
`git.text_resource_marked_binary` і радить `text eol=lf`. Це рівень «репозиторій»: на `ready` і на
допуск операцій не впливає. `-text` — політика kit для вихідників 1С (`v8storagekit:onboarding`);
змінює її лише людина.

Набір основи `truth: vendor` — лише для читання Унікою: ні `push`, ні `pull` його не виконувати
(процедура оновлення вендора — `v8storagekit:dump`, розділ про дерево vendor).

`push` без `sourceSet` вантажить **усі оголошені набори** воркспейсу: на серверній базі агента —
лише з явного підтвердження людини (кроки, які надрукував `provision -ServerBase Existing`, підтверджено
тим `-Apply`, на яке людина погодилась; питання Уніки про перезапис бази людина однаково отримає); для
правок розширення — `sourceSet` цього розширення.
`.cf` основної конфігурації людина в сховищі «порівнює й об'єднує з конфігурацією з файлу», а не
завантажує цілком. Застосовні операції Уніки поза кроками kit (`unica.apply` з `executionToken`,
`unica.run` з `"dryRun":false`) — лише на явне прохання, з названим ризиком.

## Як читати «Стан сховищ» нижче

Рядки `- <джерело>: …` — результат `kit session-check` (без платформи, нічого не змінює):
- «ймовірно нові версії … kit sync» — у сховищі писали після останнього дзеркала; спитайте людину, чи оновити;
- «коміти, не злиті в main … kit verify -Apply» — дзеркало попереду головної гілки;
- «дзеркала ще немає» — перший `sync` ще не робили;
- «недоступне» — шлях сховища не існує на цій машині. **Причини дві, протилежні, і вибір за людиною:**
  або шлях у маніфесті правильний, а машина інша — тоді перевизначити в накладці
  `v8storagekit.local.yaml`, `storages:`; або в маніфесті записане **не те сховище** — тоді правити
  `v8storagekit.yaml`. Другий випадок не теоретичний: у живому репозиторії маніфест указував на
  `…_ACC`, а джерелом було `…_BP` (`check.psm1`, знахідка `storage-path`). Не радьте накладку, не
  спитавши: накладка, що маскує помилку маніфесту, розводить репозиторій по машинах — на кожній
  він синхронізується зі свого сховища.

Хук лише повідомляє. Рішення — людині, дія — скіл `v8storagekit:sync`.

## Межі

Сховища — тільки читання. `-Apply` — лише на явне прохання. У базу людини kit не пише.
Підрядки `лиценз`, `ліценз`, `license`, `HASP` у виводі платформи — зупинка й доповідь.

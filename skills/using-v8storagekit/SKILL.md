# using-v8storagekit — як тут працює агент

Цей репозиторій підключено до плагіна `v8storagekit`: сховища конфігурацій 1С — істина,
git — робоче середовище агента, Unica — основний інструмент. Kit закриває рівно те, чого
Unica не вміє: сховища, дамп із живої бази, база агента, звірка git зі сховищем.

## Принципи

1. **Сховище — істина.** Коли git попереду сховища — це видимий борг «застосувати залишок», не помилка. У сховище kit не пише.
2. **Unica — основний інструмент; kit доповнює.** Редагування, перевірка, завантаження в базу агента, збірка `.cf`/`.cfe` — Unica 0.13.
3. **Агент працює у своїй базі й ніколи не пише в базу людини.** Базу людини kit лише читає (`dump`), і лише на явне прохання.
4. **Результат агента — зібрані файли** у `build/artifacts/`. Застосовує людина, у своїй базі, своїм Конфігуратором.
5. **Структура репозиторію — у `v8storagekit.yaml` і `v8project.yaml`.** Слів «клієнт» і «продукт» у логіці немає.
6. **Байти в git — байти платформи.** Перед порівнянням дерево канонізується (`canon`).

## Куди йти за яким наміром

| Намір | Скіл | Команда kit |
|---|---|---|
| «є нові версії у сховищі», «перенеси зі сховища» | `v8storagekit:sync` | `kit.ps1 sync [-Apply]` |
| «вивантаж конфігурацію з бази» | `v8storagekit:dump` | `kit.ps1 dump [-Apply]` |
| «я поклав частину в сховище» | `v8storagekit:reconcile` | `sync` → `canon` → `adopt storage/*` у гілку задачі (заміна, з прев'ю всіх списків) |
| «закриваємо задачу», «готуй PR» | `v8storagekit:finish` | `sync` → `canon` → `adopt storage/*` → `verify` → артефакти → PR |
| «розгорни / перезбери базу агента» | `v8storagekit:provision` | `kit.ps1 provision [-Apply] [-Force]` |
| «звір git зі сховищем» | `v8storagekit:verify` | `kit.ps1 verify [-Ref X] [-Apply]` |
| «підключи репозиторій / воркспейс / джерело», «переведи репозиторій на маніфест» | `v8storagekit:onboarding` | `kit.ps1 check`, `kit.ps1 install-hooks [-Apply]` |

Окремої команди чи скіла для переходу зі старої схеми немає навмисно: обидві вхідні форми —
порожній репозиторій і gitsync-вивантаження сховища — веде `onboarding`; `storage.json` —
реліквія форми 0.6.0, яка зникла з парку: побачивши його, зупиніться й спитайте людину.

Команди kit: `check`, `session-check`, `sync`, `dump`, `verify`, `canon`, `adopt`,
`provision`, `build`, `install-hooks`, `rename-edt` (лише крок переходу, його кличе `onboarding`). Запускаються з кореня репозиторію:
`pwsh -NoProfile -File "<корінь плагіна>/tools/kit.ps1" <команда> -RepoRoot .`
Без `-Apply` жодна команда нічого не змінює в git, сховищі чи базах — але `sync` і `verify`
без `-Apply` усе одно піднімають платформу (хвилина-дві, ліцензія). `dump` — ні: без `-Apply`
він лише друкує базу, користувача й ціль (`dump.psm1`, гілка без `-Apply`, `continue` до
запуску Конфігуратора). `-Apply` — лише на явне прохання людини.

## Маршрутизація до Unica (0.13)

Kit говорить лише мовою Уніки 0.13. Стара поверхня 0.12 знята без аліасів; її перелік — у
запобіжнику kit `<корінь плагіна>/tools/tests/Vocabulary.Tests.ps1` (тут не повторюється).

| Що | Виклик |
|---|---|
| огляд воркспейсу | `unica.view {}` |
| готовність воркспейсу, політика git | `unica.check {}` |
| перевірка коду й метаданих | `unica.check {at: <шлях або логічна адреса>}` |
| пошук, адреса, документація, різниця | `unica.search`, `unica.resolve`, `unica.docs`, `unica.diff` |
| правка вихідників (зокрема запозичення в розширення — операція `object.borrow`) | `unica.apply`: план → `executionToken` → застосування |
| завантажити дерево в базу агента | `unica.run {"op":"push","args":{"sourceSet":"<набір>"},"dryRun":true}` |
| перезібрати лише одне розширення, не всю базу | `unica.run {"op":"push","args":{"sourceSet":"<розширення>","full":true},"dryRun":true}` — `full` теж звіряє покоління: без пам'яті раннера відповідь `no_memory`, і тоді — той самий виклик з `"force":true` (лише база агента, див. нижче) |
| зібрати `.cf`/`.cfe` | `unica.run {"op":"make","args":{"sourceSet":"<набір>","extension":"<ім'я>","output":"build/artifacts/<ім'я>.cfe"},"dryRun":true}` — `output` відносний до воркспейсу (поза свій корінь Уніка не пише), `extension` обов'язковий для `.cfe` |
| довга операція | `unica.task.get`, `unica.task.result` |

Уніка вимагає явний `"dryRun"` у кожному `unica.run`; kit **за власною конвенцією** друкує
спершу `"dryRun":true` (превью показує попередження на кшталт `infobase_overwritten` до виконання),
потім той самий виклик з `"dryRun":false`.

**Крок, надрукований командою kit, — виконати дослівно.** `sync`, `verify` і `provision` зрушують
чи створюють базу агента й завершуються рядками «Далі …» — точний `unica.run …` і, для поставки
вендора, `kit canon … -MarkerOnly -Apply` (файлова база) чи `kit canon … -Apply` (серверна). Їх не
переказують і не замінюють своїм. Після `pull` — `git status --porcelain -- <шлях набору>`:
непорожній вивід означає, що вивантаження раннера дало інші байти, ніж kit, — зупинка й доповідь,
не робота для агента. **Рядок `ЗУПИНКА: …` наприкінці виводу команди — зупинка з доповіддю людині,
без обходу і без наступних кроків скіла**; поле `AlignSteps` з `Op = 'blocked'` означає те саме.

**`force:true` на базі агента — виняток із правила Уніки** («never add force:true on your own after
a non_fast_forward or no_memory refusal … belongs to the user»). Правило Уніки захищає базу, в яку
могли писати поза цією робочою копією. База агента в контурі kit (`infobases.origin`, перевірена kit
як не база людини) за побудовою похідна від git: людина в ній не працює, сховище — істина. Тому для
неї рішення про `force:true` власник прийняв заздалегідь, і агент виконує надрукований kit крок без
питання. Для будь-якої іншої бази правило Уніки діє без винятків.

**Сітка на пропущений крок.** Від пропущеного кроку захищає лише сам надрукований крок, а не раннер:
набір з **незміненим** деревом звичайний `push` пропускає без звірки покоління, а на серверній базі
звірки немає взагалі. Тому в контурі kit `infobase_state_unverified` або `non_fast_forward` (чи
`no_memory`) у відповіді `push` бази агента — **не ігнорувати**, а виконати
`unica.run {"op":"push","args":{"sourceSet":"<набір>","force":true},"dryRun":true}` для кожного
названого набору — повне завантаження з git, безпечне для бази агента за побудовою.

`push` без `sourceSet` вантажить **усі оголошені набори** воркспейсу: на серверній базі агента —
лише з явного підтвердження людини (кроки, які надрукував `provision -ServerBase …`, підтверджено
тим `-Apply`, на яке людина погодилась); для правок розширення — `sourceSet` цього розширення.
`.cf` основної конфігурації людина в сховищі «порівнює й об'єднує з конфігурацією з файлу», а не
завантажує цілком. Застосовні операції Уніки поза кроками kit (`unica.apply` з `executionToken`,
`unica.run` з `"dryRun":false`) — лише на явне прохання, з названим ризиком.

## Як читати «Стан сховищ» нижче

Рядки `- <джерело>: …` — результат `kit session-check` (без платформи, нічого не змінює):
- «ймовірно нові версії … kit sync» — у сховищі писали після останнього дзеркала; спитайте людину, чи оновити;
- «коміти, не злиті в main … kit verify -Apply» — дзеркало попереду головної гілки;
- «дзеркала ще немає» — перший `sync` ще не робили;
- «недоступне» — шлях сховища не існує на цій машині. **Причини дві, протилежні, і вибір за людиною:**
  або шлях у маніфесті правильний, а машина інша — тоді перевизначити в накладці
  `v8storagekit.local.yaml`, `storages:`; або в маніфесті записане **не те сховище** — тоді правити
  `v8storagekit.yaml`. Другий випадок не теоретичний: у живому репозиторії маніфест указував на
  `…_ACC`, а джерелом було `…_BP` (`check.psm1`, знахідка `storage-path`). Не радьте накладку, не
  спитавши: накладка, що маскує помилку маніфесту, розводить репозиторій по машинах — на кожній
  він синхронізується зі свого сховища.

Хук лише повідомляє. Рішення — людині, дія — скіл `v8storagekit:sync`.

## Межі

Сховища — тільки читання. `-Apply` — лише на явне прохання. У базу людини kit не пише.
Підрядки `лиценз`, `ліценз`, `license`, `HASP` у виводі платформи — зупинка й доповідь.

# task-finish — закриття задачі: PR завжди повний

Головна гілка не отримувала роботи агента через реплей, тому PR `F → main` завжди несе всю
роботу. Артефакти в `build/artifacts/` застосовує людина у своїй базі; повідомити їх у PR.

Ланцюжок: onboarding → storage-sync → infobase-agent → (робота в Unica) → storage-adopt → **task-finish** → storage-verify.

**Виклик із `v8storagekit:execute`.** У репозиторії з `v8storagekit.yaml` контролер плану не
закриває блок сам: після фінального рев'ю й `sdd close` він передає закриття сюди. Шлях закриття
один — цей скіл. Від `execute` приходять три речі, і кожна має своє місце:

- розділ `## Rulings` з `sdd close` — у тіло PR, розділ «Рішення» (крок 8);
- рядок `Push:` брифу архітектора — це та вказівка, яку крок 8 називає явним проханням про push
  і PR; рядка немає — PR не готувати, доповісти архітектору;
- рядок `report:` з `sdd close` — доповідь архітектору наприкінці, з PR і результатом кроку 6.

Гейт «повідомити користувача» (крок 4) і всі зупинки нижче діють так само. Кроки Уніки цього
скіла (`push force`, `pull force`, `make`) виконує сама сесія контролера, не субагент: Уніка питає
людину про перезапис бази, тож у процесі `execute` закриття йде в інтерактивній сесії. Push і PR
у процесі — через `pr-gate open` (крок 8), як і без маніфесту, щоб механізм push був один.

## 1. Передумови

Поточна гілка — `F`; копія чиста; база агента є й наповнена (`push` Уніки після останніх правок). Людина поруч: процедура інтерактивна — питання Уніки (`push force`, а за незбереженого чи поза git — `pull force`) адресоване їй, і на `cancelled` агент зупиняється з доповіддю.

## 2. Кроки

1. **Сховище → дзеркало**: `kit sync -RepoRoot . -Apply`
   (`-Apply` — після прев'ю й згоди; прохання «готуй PR» це включає, якщо людина не сказала інакше).
2. **База з `F` і канонізація — один список з двох кроків, у цьому порядку** (обидва по `unica.run`, спершу
   `"dryRun":true`, тоді той самий виклик з `"dryRun":false`; `sourceSet` називається явно):
   1. **`push force:true`** — крок, надрукований `sync` у кроці 1 (`{"op":"push","args":{"sourceSet":"<ключ>","force":true}}`;
      якщо `sync` нових версій не приніс — звичайний `push`). `push` не приймає `extension`. Відповідь
      `cancelled` — **зупинка до `pull`**: база не вирівняна, і `pull` вивантажив би з неї не те, що в `F`.
   2. **`pull force:true`** — `{"op":"pull","args":{"sourceSet":"<ключ>","force":true}}`; для розширення ще
      `"extension":"<ключ>"` (ім'я набору). Платформа вивантажує набір з бази в дерево, у git лягають її
      байти. **Передумова: дерево цього набору закомічено в `F`** (процедура інтерактивна, людина поруч). На
      чистому закоміченому наборі Уніка людину не питає; незбережене чи поза git захищає її питання, на
      `cancelled` — зупинка.

   Зміни від `pull` — комітом у `F` у формі з `v8storagekit:storage-adopt` (крок 3 розділу 2): `git rm -r -q --cached --
   <шлях джерела>`, `git add -- <шлях джерела>`, перевірка `git diff --cached --name-only`
   (очікувано лише шлях джерела; сторонні шляхи — зупинка й питання людині: коміт без `--only` забирає весь індекс),
   `git commit` без `-a` і без `--only` (`--only` воскрешає фантом при перейменуванні регістром). Крок не марний, хоч крок 3 і замінить дерево: канон і дамп дзеркала —
   один формат платформи, тож саме `pull force` лишає у прев'ю `adopt` роботу людини замість різниці
   форматів (`v8storagekit:storage-adopt`, кроки 2–3 розділу 2).
3. **Прийняти дзеркала в `F`**: для кожного `truth: storage`
   `kit adopt -RepoRoot . -Source <ключ>`
   — прев'ю, показ людині всіх списків, і за її згодою `-Apply` (як у `v8storagekit:storage-adopt`,
   кроки 4–5 розділу 2).
4. **Звірка `F` зі сховищем**: `kit verify -RepoRoot . -Ref <F>`.
   Очікувано `ref-ahead` (робота задачі — це й є залишок для сховища) або `equal`; `storage-ahead`/`mixed`
   означає, що крок 3 не завершено.

   **Гейт «повідомити користувача» — зупинка перед кроком 6, якщо сталося суттєве** (вимога власника №13:
   звірити сховища, подивитись, що помінялось, при суттєвому — повідомити, далі за його рішенням).
   Суттєве — хоч одне з: (а) нові версії, які крок 1 приніс у дзеркало, **торкаються файлів, що їх змінила
   `F`** (перетин на рівні файлів; версії без перетину лише називаються одним рядком, і task-finish іде далі —
   інакше кожен коміт колеги в іншому кутку конфігурації зупиняв би кожен PR); (б) прев'ю `adopt` на кроці 3
   показало непорожній список «ЗНИКНЕ з гілки» — людина не взяла частину роботи агента; (в) `verify` дав
   `storage-ahead` або `mixed`.

   Критерії (а) і (б) доповнюють один одного і навмисно не зводяться до одного: (а) відповідає на питання
   «чи хтось працював у тому самому місці», (б) — «чи частина роботи агента не ввійшла у сховище». Жоден не
   покриває іншого. Агент **додав** файл, якого у сховищі немає: при `adopt` він зникне, хоча нові версії
   його не торкались — ловить лише (б). Агент змінив файл, і людина цю зміну у своїй версії **врахувала**:
   з гілки нічого не зникає, хоча чужа робота лягла рівно туди, де агент працював — ловить лише (а).

   Перетин рахується двома командами git, без нового модуля: перед кроком 1 запам'ятати вершину дзеркала
   `$before = git rev-parse storage/<ключ>` (гілки немає → усе нове вважати перетином); файли `F` — `git -c
   core.quotepath=false diff --name-only <mainBranch>...HEAD -- <ws>/<path>` (до `adopt`); файли нових
   версій — `git -c core.quotepath=false diff --name-only $before storage/<ключ>` (без `-c` кириличні імена
   прийшли б екранованими, і перетин був би хибно порожнім); спільні шляхи = перетин.
   Тоді **зупинитись** і доповісти: які версії й чиї (з виводу `sync`), перетин файлів, два списки прев'ю
   `adopt` (що прийде зі сховища, що зникне з гілки), вердикт `verify`. Продовжувати до перевірки коду й PR — лише
   за рішенням людини. Нічого суттєвого — йти далі без питання. Критерій «суттєвого» живе тут
   і більше ніде; якщо власник розуміє його ширше — міняти тут.
5. **Відновити базу агента**: крок, надрукований `verify` у кроці 4 (`push` з `"force":true`
   для зрушеного набору; виконується те, що надруковано). `verify` лишив базу у стані версії сховища (контракт) — без
   цього кроку перевірка коду побіжить не на тому стані, який іде в PR. Уніка спитає людину про
   перезапис бази; відповідь `cancelled` — зупинка з доповіддю «база агента не вирівняна; наступний
   `push` відмовить», без повтору. Рядок `ЗУПИНКА: …`
   наприкінці виводу `verify` — зупинка: далі не йти, доповісти людині.
6. **Перевірка коду** (Unica, `cwd` = воркспейс): `unica.check {}` по воркспейсу і `unica.check {at: <модуль або корінь набору>}`
   по модулях і коренях наборів, змінених у гілці (`git -c core.quotepath=false diff --name-only <mainBranch>...HEAD`).
   Помилки — PR не готувати; повернутись до роботи. Запуску тестів (YaXUnit/VA) цей крок не передбачає.
7. **Артефакти** `.cfe`/`.cf`/`.epf`/`.erf` — операція `make` Уніки (аргументи — з `argsSchema`, яку
   віддає `unica.run` без `op`) з `output` у `build/artifacts/` воркспейсу. Kit нічого не копіює;
   `build/` гітігнорований: артефакти не комітяться, їхній перелік іде в PR. Відмова `make` через
   передумову набору (напр. немає оголошеної основної конфігурації) — сказати людині, конфігурацію
   самому не створювати.
   **`.cf` основної конфігурації** людина не завантажує цілком — це замінило б усю конфігурацію
   разом із поставкою й вимагало б захоплення всього сховища; вона робить «Порівняти, об'єднати з
   конфігурацією з файлу», і сам діалог показує, що відрізняється.
8. **PR `F → <mainBranch>`** — **лише за явним проханням** (людини або, у процесі `execute`, рядка
   `Push:` брифу архітектора). У процесі `execute` — `pr-gate open -Title … -BodyFile <тіло>`: він пушить
   і відкриває PR без запиту дозволу (ADR-0017; ніколи в одному виклику Bash із `git push`: класифікатор
   відхиляє весь виклик). Поза процесом — `git push` і `gh pr create`, і harness питає дозволу (`ask`).
   Тіло PR (у процесі `execute` — ще й розділ `## Рішення` з Rulings від `sdd close`):
   ```
   ## Що зроблено
   <з коментарів комітів F>
   ## Сховище
   Дзеркала прийняті (adopt): storage/<ключ> до версії <N> (verify -Ref <F>: <вердикт>)
   ## Артефакти для застосування (build/artifacts/)
   - <Ім'я>.cfe  — застосувати в базі <…> Конфігуратором
   - <Ім'я>.cf   — порівняти й об'єднати з конфігурацією з файлу, НЕ завантажувати цілком
   ## Перевірка
   unica.check: <результат>
   ```
9. **Після злиття PR** (наступна сесія або на прохання): `v8storagekit:storage-verify` на головній гілці —
   `equal` / `ref-ahead` (застосуйте залишок) / `storage-ahead` (звірочний коміт).

## 3. Штатні зупинки

`sync`, `verify` — зупинки їхніх скілів; `cancelled` у відповідь на `push force` чи `pull force` Уніки — зупинка з доповіддю (після відхиленого `push` `pull` не виконувати). Рядок `ЗУПИНКА: …` наприкінці виводу
`sync`/`verify` — зупинка з доповіддю. Помилки `unica.check` — зупинка: PR не готувати, доповісти. `gh pr create` відхилено класифікатором дозволів — сказати людині, не
шукати обхід. Якщо в Windows-копії `pull`/`checkout` падає з «would be overwritten» — це перейменування
регістром, а не пошкодження: та сама підказка й умови, що в `v8storagekit:storage-sync` (`git status` чистий **і**
`git log origin/<гілка>..HEAD` порожній; агент `reset` сам не виконує, а показує людині перевірки).

## 4. Межі

Артефакти застосовує людина. PR — лише за явним проханням (через `pr-gate open` — без запиту дозволу, голі
`git push`/`gh pr create` — з запитом). Сховище — тільки читання.

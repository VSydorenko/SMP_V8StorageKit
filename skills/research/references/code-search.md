# Пошук коду 1С через Уніку

**Завантаж, коли** досліджуєш код чи документи в репозиторії (ADR-0006).

Карта (де, хто викликає, який документ) і істина (сигнатури, типи, поведінка) — різні речі. Карту дає Уніка, істину — прочитаний вузол чи файл. Читай лише те, на що вказала карта.

| Питання | Інструмент |
| --- | --- |
| Які воркспейси й логічні адреси є | `unica.view {}` (порожній об'єкт) |
| Тема словами, імена ще невідомі | `unica.search` |
| Де визначено й що саме там | `unica.resolve`, потім `unica.view` за логічною адресою |
| Чи читається вузол чи джерело | `unica.check` |
| Чим два вузли різняться | `unica.diff` |
| Що робить код | прочитай вузол чи файл |
| Код вендора | дамп конфігурації-власника воркспейсу (`truth: vendor\|dump`) — читай його, а не пам'ять про типову конфігурацію |
| Поведінка платформи й об'єктної моделі | скіл `unica:platform-help`, `unica_docs` — для версії воркспейсу |
| Типові рішення (БСП, транзакції, блокування) | предметні скіли Уніки: `unica:bsp-patterns`, `unica:transactions-locks`, … |
| Пошук по документах проєкту (спеки, плани, ADR) | `doc find` |

Адреси бери з відповіді `unica.view`, а не вгадуй. Логічна адреса має вигляд `<sourceSet>:<Kind>[.<Name>...]`.

## Межі субагента

Дослідник, рецензент, аудитор і верифікатор користуються лише читальними інструментами Уніки (`unica_view`, `unica_search`, `unica_resolve`, `unica_docs`, `unica_check`, `unica_diff`). Мутуючі (`unica_apply`, `unica_run`) і збирання бази агента — серед субагентів лише виконавець, і лише в межах брифу. Поза субагентами їх кличе основна сесія в присутності людини, коли так каже скіл (`v8storagekit:finish`, кроки, надруковані командою kit): Уніка питає людину про перезапис бази. База людини — лише читання й лише на явне прохання власника (`kit dump`); база агента не є джерелом фактів про базу людини.

## «Нічого не знайдено» — не доказ

Порожній результат може означати регістр, синонім, іншу форму імені чи неповний індекс. Перш ніж писати «нема» чи «ніхто не викликає»:

- шукай без урахування регістру й кількома словоформами, зокрема рос/укр формами імен 1С (`Проведение`/`Проведення`, `Организация`/`Організація`, `ПриЗаписи`/`ПриЗаписе`) і синонімами з метаданих;
- перевір покриття: чи воркспейс і джерело (`sourceSet`) входять до того, що проіндексовано (`unica.view {}`, `unica.check`);
- виклик може бути не прямим: через `Выполнить`/`Вычислить`, рядок з іменем процедури, підписку на подію, перехоплення `&Перед/&После/&Вместо` в розширенні, обробник форми за іменем;
- для питання «хто викликає» доповни результат `git grep` по вихідниках і скажи, що саме було пошуком за рядком.

## Деградація

- Уніка не відповідає чи її нема на машині: `git grep`/Grep по вихідниках і дампу. Скажи в звіті, що саме не перевірено (логічні адреси, індекс, виклики) — не вигадуй результат.
- `git grep` по імені дає збіги в коментарях і рядках: прочитай місце, перш ніж називати збіг викликом.
- Розширення бачить лише свої й запозичені об'єкти; щоб знати, що перехоплюється, читай код вендора в дампі.

## Як формулювати пошук за темою

Речення краще за мішок ключових слів. Імена в 1С бувають рос. чи укр.; став обидві форми, коли знаєш: `проведение проведення регистр`.

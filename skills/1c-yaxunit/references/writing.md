# Авторство тестів YAxUnit

Шляхи `references/…` і `templates/…` нижче — від теки скілу `v8storagekit:1c-yaxunit`; політика тестів, маршрутизація, протокол червоного й правила спільної бази агента — у `SKILL.md` цього скілу.

- Пишеш на BSL тести фреймворка YAxUnit для конфігурації 1С:Підприємство. Вихідники проєкту — вивантаження Конфігуратора (Designer XML), платформа гілки 8.3.27.
- Тести лежать у розширенні конфігурації; його назву, платформу runtime, розташування вихідників основної конфігурації та інших розширень бери з розділу `## Тести YaXUnit` у `CLAUDE.md` проєкту та з `v8project.yaml` воркспейсу. Людину про середовище не питай. Нижче це розширення називається тестовим розширенням `Тести`.
- **Обсяг тестів.** Перелік тестів задає план (або бриф); цей текст — лише форма тесту: він не підстава додавати тести понад перелік.
- Ідентифікатор задачі: у задачі може бути ідентифікатор (задача, проєкт, SRS тощо) — за ним ставиться проєктний тег (`references/tags.md`). Бери його з плану чи брифу задачі; якщо ідентифікатора там немає — тест пишеться без проєктного тега, людину про це не питай.
- Метадані тестового розширення (модулі, запозичення, перехоплювачі) створює Уніка: `unica.apply`, скіли `unica:meta-add`, `unica:cfe-borrow`, `unica:cfe-patch-method`. Шаблони й правила розкладки з `references/project-format.md` — довідка для звірки результату. Файли метаданих пишуться під платформу runtime — шаблони лежать у `templates/8.3.27/`.
- База агента спільна: тест не покладається на наявні в базі дані, а дані, які пише, — лише в транзакції на рівні тесту (`ВТранзакции()`); подробиці — розділ «Спільна база агента» в `SKILL.md`.
- Код основної конфігурації й інших розширень шукай і читай через Уніку (`unica.search`, `unica.view`), а не grep по XML.

Читай потрібний файл у міру роботи над тестом:

| Коли потрібен                                                               | Що робити                                                                                   |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Потрібно визначити ім'я нового тестового модуля                             | Читай `references/module-naming.md`                                                         |
| Шукаєш файли проєкту, створюєш тестовий модуль чи перехоплювач              | Читай `references/project-format.md`                                                        |
| Розставляєш теги або визначаєш рівень тегування                             | Читай `references/tags.md`                                                                  |

## Процес написання тесту

### 1. Підготовка модуля

Підготуй тестовий модуль за розділом «Структура файлів тесту». Якщо модуль уже існує — прочитай його код, щоб знати, які тести вже написано.

### 2. Аналіз і проєктування

1. **Прочитай метод, що тестується, повністю** — обов'язково перед проєктуванням тестів; код основної конфігурації шукай і читай через Уніку (`unica.search`, `unica.view`).
   - Перевір, чи не перехоплено метод, що тестується, і методи, які збираєшся мокати, в інших розширеннях проєкту (крім тестового): знайди в модулі того ж об'єкта анотації `&Вместо`, `&Перед`, `&После`, `&ИзменениеИКонтроль` з іменем методу (через Уніку). Які ще розширення є в проєкті й де лежать їхні вихідники — у `CLAUDE.md` проєкту (розділ `## Тести YaXUnit`) та `v8project.yaml`. Якщо перехоплення є, у базі виконується код з його урахуванням — читай і проєктуй тести за ним: виклику, який збирався мокати, може не бути.
2. Визнач тип кожного тесту за розділом «Типи тестів»
   - Гілка залежить від того, що метод, який мокається, записує в переданий йому параметр — моком її не покрити: тест цієї гілки інтеграційний, без мока цього методу (розділ «Гілка, що залежить від зміни параметра методом, який мокається»)
3. Сформуй імена тестових методів за розділом «Іменування тестів»
4. Якщо ім'я виходить неочевидним — додай `// TODO: пояснення` в заготовку

### 3. Фіксація заготовок

Запиши у файл **до початку реалізації**:
- Реєстрацію в `ИсполняемыеСценарии` (див. «Способи оголошення тестів»)
- Порожні експортні процедури з коментарями `// given`, `// when`, `// then` (див. «Структура тестового модуля»)

### 4. Реалізація

Пиши тіла тестових методів. Які references читати — за таблицею на початку. Метод, що тестується, викликай так само, як його викликає код основної конфігурації: метод глобального загального модуля — без імені модуля.

### 5. Організація

Приведи структуру реєстрації й модуля до ладу з урахуванням **усіх** тестів (старих + нових):

1. Усі тести інтеграційні → `.ВТранзакции()` на рівні модуля або єдиного набору
2. Є і інтеграційні, і юніти → розбий на набори; інтеграційному набору — тег `"Интеграционный"` і `.ВТранзакции()`
3. Тестів понад 5 → групуй за логічними групами в набори для читабельності
4. Реалізації тестів із набору обгортай у `#Область` з іменем аспекту набору — усередині області `СлужебныйПрограммныйИнтерфейс`, після `ИсполняемыеСценарии` (див. «Структура тестового модуля»). Якщо в наявному модулі області наборів розташовано інакше — дотримуйся прийнятого в модулі.
5. Проставь теги (див. `references/tags.md`)
6. Перевір за розділом «Чекліст при створенні нового тесту» наприкінці

## Структура файлів тесту

- Тести — це загальні модулі тестового розширення `Тести`. Де лежать вихідники розширення, залежить від проєкту — розділ «Розташування проєктів» у `references/project-format.md`.
- Кожен тестовий модуль має бути названий за шаблоном `[Префікс типу об'єкта_][Ім'я об'єкта, що перевіряється][_Суфікс типу модуля]`.

Як назвати модуль — `references/module-naming.md`.

Де лежать файли модуля, як перевірити його існування, створити метадані й зареєструвати модуль — розділ «Новий тестовий модуль» у `references/project-format.md`; самі метадані створює Уніка. Якщо модуль уже існує, його метадані й реєстрацію не чіпай, працюй лише з кодом модуля.

### Контексти компіляції тестового модуля

Контексти компіляції (доступність у клієнті керованого й звичайного застосунку) залежать від типу об'єкта, що тестується. Тут — правило; точний набір прапорів модуля й звідки брати значення — у `references/project-format.md`:

- **ОМ_ (загальний модуль)** — той самий тип модуля, що в загального модуля, який тестується (клієнт-серверний або серверний): тест має бути доступний у тих самих контекстах, що й код, який тестується. Прапори «Виклик сервера» і «Глобальний» не переносяться — YAxUnit не вважає такі модулі тестовими.
- **Інші типи (Док_, РС_, Спр_ тощо)** — серверний модуль (за можливості лише сервер).

### Генерація UUID

Кожен об'єкт метаданих отримує свій UUID; скільки UUID потрібно й куди вони підставляються — у `references/project-format.md`. Якщо об'єкти створює Уніка, UUID вона проставляє сама; для звірки чи ручної генерації на Windows використовуй PowerShell:

```bash
# Один UUID
powershell -Command "[guid]::NewGuid().ToString()"
# Одразу кілька (наприклад 15)
powershell -Command "1..15 | % { [guid]::NewGuid().ToString() }"
```

## Типи тестів

Перед написанням визнач тип кожного тесту — це впливає на ізоляцію залежностей, потребу в `.ВТранзакции()` і підсумкову структуру реєстрації.

### Бізнес-шар — загальні модулі (префікс `ОМ_`)

Містять бізнес-правила й оркестрацію. За грамотного проєктування не звертаються до БД напряму — делегують це менеджерам об'єктів. Тести для ОМ_ — класичні **юніт-тести**:
- Шар даних (регістри, довідники) **мокається** через Мокито
- Бібліотечні методи й методи інших компонентів **мокаються** через Мокито
- Без звернень до БД → **без `.ВТранзакции()`**
- Швидкі, детерміновані

```bsl
// ОМ_ тест: мокируем регистр, тестируем бизнес-логику
Мокито.Обучение(РегистрыСведений.ЦеныНоменклатуры)
    .Когда("ПолучитьЦеныНоменклатур")
        .Вернуть(МоковыеДанные)
    .Прогон();

Результат = Ценообразование.РассчитатьЦену(Параметры);
```

### Шар об'єктів метаданих — модулі менеджерів і об'єктів (`_ММ`, `_МО`, `Док_`, `Спр_`, `РС_`)

Містять логіку роботи з даними: запити, запис, обробку подій об'єкта (`ПередЗаписью`, `ОбработкаПроверкиЗаполнения`). Тип тесту визначається тим, чи звертається конкретний метод до БД:

- **Інтеграційний** (метод звертається до БД: запити, запис, читання регістрів) — працює з реальними даними, потребує `.ВТранзакции()` для відкату
- **Компонентний** (метод звертається до бібліотечних методів, методів інших бізнес-правил) — якщо замоканий, то без транзакції; якщо мокання неможливе і метод, що викликається, звертається до БД — у транзакції
- **Юніт** (метод не звертається до БД) — наприклад, `ОбработкаПроверкиЗаполнения`, що перевіряє лише стан об'єкта в пам'яті — без транзакції

### Гілка, що залежить від зміни параметра методом, який мокається

Мокито не змінює параметри методу: мок уміє повернути значення, викинути виняток або пропустити виклик, але не записати значення в переданий параметр. Якщо гілка методу, що тестується, залежить від того, що метод, який викликається, записав у параметр, мок у цю гілку не приведе:

```bsl
Процедура ОтправитьЗаказ(Заказ) Экспорт

    Отказ = Ложь;
    ПроверкиЗаказов.ПроверитьЗаказ(Заказ, Отказ);  // при ошибке ставит Отказ = Истина

    Если Отказ Тогда
        Возврат;                                   // ветка 1: заказ с ошибкой не отправляется
    КонецЕсли;

    ОбменСВнешнейСистемой.Отправить(Заказ);        // ветка 2: отправка

КонецПроцедуры
```

- **Гілка 2** — юніт-тест: `ПроверитьЗаказ` мокається з `Пропустить()`, `Отказ` лишається `Ложь`, перевіряється виклик `Отправить`.
- **Гілка 1** — моком не покрити: мок не запише `Истина` в `Отказ`. Тест інтеграційний, без мока `ПроверитьЗаказ`: створи замовлення, яке реально не проходить перевірку (наприклад, без контрагента), виклич метод і перевір, що `Отправить` не викликався. Дані в БД — `.ВТранзакции()` і тег `"Интеграционный"`.

Якщо інтеграційний тест неможливий — не підганяй тест: залиш у заготовці `// TODO: ветка <...> не покрыта: <причина>` і повідом користувача.

## Структура тестового модуля

```bsl
#Область СлужебныйПрограммныйИнтерфейс

Процедура ИсполняемыеСценарии() Экспорт
    ЮТТесты
        .Тег("srs-NNN")  // если у задачи есть идентификатор
        .ДобавитьТестовыйНабор("ОМ_Модуль: аспект поведения", "ТипТеста")  // набор обязателен; тег типа теста — если применимо
            .ДобавитьТест("ИмяТеста1")
            .ДобавитьТест("ИмяТеста2")
            .ДобавитьТест("ИмяТеста3")
                .СПараметрами(Вход1, Ожидание1)
                .СПараметрами(Вход2, Ожидание2);
КонецПроцедуры

#Область АспектПоведения // реализации тестов набора — в области с именем аспекта набора

Процедура ИмяТеста1() Экспорт
    // given
    // when
    // then
КонецПроцедуры

Процедура ИмяТеста2() Экспорт
    // ...
КонецПроцедуры

Процедура ИмяТеста3(Вход, Ожидание) Экспорт
    // ...
КонецПроцедуры

#КонецОбласти

#КонецОбласти

#Область СлужебныеПроцедурыИФункции

Функция СоздатьТовар(Наименование, Родитель = Неопределено)
    // вспомогательный код для подготовки тестовых данных
КонецФункции

#КонецОбласти
```

### Правила

- `ИсполняемыеСценарии` — лише реєстрація тестів, жодних даних усередині
- Усі тестові процедури — **експортні**
- Допоміжні методи (helper-методи) розміщуються в області `СлужебныеПроцедурыИФункции` — вони **не експортні**. Типові helper-методи: створення тестових об'єктів (`СоздатьГруппу`, `СоздатьТовар`), побудова колекцій (`КолеровочнаяКарта`, `Товары`), додавання рядків (`ДобавитьВКарту`)

## Реєстрація тестів

### Іменування тестів

Ім'я тесту будується за схемою **[Метод][Результат][Умова]** злито, у CamelCase:

```
МетодРезультатУсловие
```

- **Метод** — ім'я методу, що тестується, або дії. Ім'я методу, що тестується, береться повністю, зі службовим префіксом (`ДМ_ЗаполнитьТовары` → `ДМ_ЗаполнитьТоварыЗаполняетТабличнуюЧасть...`): за іменем тесту знаходиться метод, що тестується. Якщо в наявному модулі префікс послідовно опускають — дотримуйся модуля.
- **Результат** — що робить або повертає (`Возвращает`, `НеВыполняет`, `Выбрасывает`, `Сортирует`)
- **Умова** — за яких обставин (`ПриОтсутствииДанных`, `ЕслиЭтоУслуга`, `ПриДублировании`)

Приклади:

```
ПолучитьЦенуВозвращаетПустоеЗначениеПриОтсутствииДанных
ЗаписатьНеВыполняетЗаписьПриОшибкеПроверкиУникальности
ЭтоКолеровкаВозвращаетИстинуЕслиЭтоУслугаКолеровки
ПередЗаписьюСортируетДиапазоныПоВерхнейГранице
```


### Способи оголошення тестів

```bsl
ЮТТесты
    .Тег("srs-123")
    .ДобавитьТестовыйНабор("ОМ_Модуль: аспект поведения", "Теги")  // группа тестов по критерию
        .ДобавитьТест("ИмяМетода")                       // тест на всех контекстах
        .ДобавитьСерверныйТест("ИмяМетода")              // только сервер
        .ДобавитьКлиентскийТест("ИмяМетода")             // только клиент
        .ДобавитьТест("ИмяМетода", "Читаемое описание")  // с читаемым именем
        .ДобавитьТест("ИмяМетода", , "Интеграционный")   // интеграционный (тег, 3-й параметр)
        .ДобавитьТест("ИмяМетода")                       // параметризованный тест
            .СПараметрами(Арг1, Арг2)
            .СПараметрами(Арг3, Арг4);
```

### Іменування тестових наборів

YAxUnit піднімає кожен тестовий набір у корінь дерева прогону як самостійний вузол (незалежно від модуля). Через це верхній рівень дерева перетворюється на кашу: у модулів без наборів у корені видно ім'я модуля (`Док_X_МО`), а в модулів з наборами — голу назву набору («Ветвление»), без прив'язки до об'єкта.

**Правило: ім'я набору = `<ИмяМодуля>: <аспект поведінки>`. Набори обов'язкові — обгортай тести хоча б в один набір.**

```bsl
.ДобавитьТестовыйНабор("Док_ПеремещениеТоваров_МО: Условия запуска формирования планов")
.ДобавитьТестовыйНабор("Док_ПеремещениеТоваров_МО: Формирование планов")
```

Чому так:
- префікс = ім'я модуля → обидва випадки (модуль без наборів і набори) у корені починаються однаково, дерево однорідне, за іменем модуля все кластеризується й шукається;
- префікс виводиться механічно з імені модуля — не потрібно вигадувати «людську» назву;
- з вузла дерева одразу зрозуміло, у якому файлі тест; імена наборів не зіллються між модулями.

Аспект після `:` пиши як звичайну фразу (регістр першого символу не змінюй заради префікса). Імена `#Область` для групування коду всередині файлу — за аспектом, **без** префікса. Ім'я області — аспект, записаний ідентифікатором: слова злито, кожне з великої літери, розділові знаки й тире відкидаються (`удвоение числа` → `УдвоениеЧисла`, `Согласование — процесс` → `СогласованиеПроцесс`).

Правила формулювання аспекту:

**Аспект — коротка російська фраза про поведінку** (мова імен наборів — як у проєкті), не ім'я методу, що тестується, не ім'я функціональної опції, не технічний ярлик:

```bsl
// ❌ Плохо — имена методов, ФО и ярлыки: узлы неинформативны и совпадают между
// модулями (реальная коллизия: два неотличимых узла «ФункциональныеОпции»)
.ДобавитьТестовыйНабор("ФункциональныеОпции")
.ДобавитьТестовыйНабор("CRUD")
.ДобавитьТестовыйНабор("ИспользоватьПодразделенияПунктаВыдачиЗаказа")

// ✅ Хорошо — фраза о поведении
.ДобавитьТестовыйНабор("РС_ПоставщикиНекондиции_ММ: операции с записями")
.ДобавитьТестовыйНабор("ОМ_УправлениеЗаказами: влияние функциональной опции ИспользоватьПодразделенияПунктаВыдачиЗаказа")
```

**Жодних наборів-заголовків без тестів.** Вкладених наборів у YAxUnit не існує: «вкладений» набір — просто наступний елемент плоского списку, а набір без тестів відкидається під час фільтрації, і його «діти» лишаються в корені дерева без контексту. Псевдорівень виражай усередині аспекту через тире:

```bsl
// ❌ Плохо — «Согласование» без своих тестов исчезнет из дерева,
// остальные наборы повиснут в корне сами по себе
.ДобавитьТестовыйНабор("Согласование")
    .ДобавитьТестовыйНабор("Процесс согласования")
        .ДобавитьТест("...")
    .ДобавитьТестовыйНабор("Поиск записей")
        .ДобавитьТест("...")

// ✅ Хорошо — уровень влит в аспект
.ДобавитьТестовыйНабор("РС_ДокументыКСогласованию_ММ: Согласование — процесс")
    .ДобавитьТест("...")
.ДобавитьТестовыйНабор("РС_ДокументыКСогласованию_ММ: Согласование — поиск записей")
    .ДобавитьТест("...")
```

**Теги й режими не кодувати в імені набору** — для них є колонки «Теги» й «Контекст» у формі запуску та мітки в Allure-звіті:

```bsl
// ❌ Плохо — тег продублирован в имени
.ДобавитьТестовыйНабор("Процесс согласования (интеграционные)")

// ✅ Хорошо — тег передан отдельным параметром
.ДобавитьТестовыйНабор("РС_ДокументыКСогласованию_ММ: Согласование — процесс", "Интеграционный")
```

### Транзакція

`.ВТранзакции()` відкочує всі зміни в БД після тесту. Використовуй для тестів, що записують дані.

#### Транзакція на весь модуль

Коли всі тести в модулі інтеграційні (пишуть у БД, файлові операції тощо):

```bsl
ЮТТесты
    .ВТранзакции()          // все тесты модуля выполняются в транзакции, наборы наследуют настройку
    .ДобавитьТестовыйНабор("РС_Пример_ММ: запись")
        .ДобавитьТест("ЗаписатьВыполняетЗаписьБезОшибок")
        .ДобавитьТест("ЗаписатьНеВыполняетЗаписьПриОшибке")
    ;
```

#### Транзакція на окремий тест

Коли частина тестів працює з БД, частина — ні:

```bsl
ЮТТесты
    .ДобавитьТестовыйНабор("Спр_Пример_ММ: поиск и проверка заполнения")
        .ДобавитьТест("ПоискВозвращаетПустойРезультат")        // без транзакции: не пишет в БД
        .ДобавитьТест("ПоискНаходитСозданныйЭлемент")
            .ВТранзакции()                                      // пишет в БД → нужна транзакция
        .ДобавитьТест("ПроверкаЗаполнения")                    // без транзакции: объект не сохраняется
    ;
```

#### Транзакція в групі тестів

`.ВТранзакции()` після `.ДобавитьТестовыйНабор()` застосовується до всіх тестів набору:

```bsl
ЮТТесты
    .Тег("srs-123")
    .ДобавитьТестовыйНабор("РС_Пример_ММ: запись данных")
        .ВТранзакции()
            .ДобавитьТест("Тест1")
            .ДобавитьТест("Тест2")
    .ДобавитьТестовыйНабор("РС_Пример_ММ: чтение данных")  // без транзакции
        .ДобавитьТест("Тест3")
    ;
```

### Коли ставити `.ВТранзакции()`

| Ситуація                                                                | Транзакція |
| ----------------------------------------------------------------------- | ---------- |
| Тест створює/змінює записи через `КонструкторОбъекта(...).Записать()`   | **так**    |
| Тест викликає метод, що пише в БД, файлові операції тощо                | **так**    |
| Тест лише читає дані або працює з незбереженим об'єктом                 | ні         |
| Тест із мокуванням (без реальної БД, файлових операцій тощо)            | ні         |
| Тест встановлює константу й перевіряє результат через `ПолучитьФункциональнуюОпцию()` | **ні** — значення ФО читається з позатранзакційного кешу, запис константи всередині транзакції невидимий для ФО |

### Маркування інтеграційних тестів

Тест, що працює з реальною БД, позначається тегом `"Интеграционный"`. Рівень проставлення тега — модуль, набір чи окремий тест — визначай за правилами в `references/tags.md` (розділ «Рівні тегування»).

## Практики написання тестів

### Дані в тесті — без залежності від коду, що тестується

**Ніколи не використовуй методи модуля, що тестується, для підготовки вхідних даних тесту.** Це крихко: якщо реалізація допоміжного методу зміниться, тест зламається незалежно від того, чи правильно працює метод, що тестується.

Усі структури, контракти й колекції, які тест передає як вхідні дані, будуй напряму — через `Новый Структура`, `Новый Массив`, `Новый Соответствие` і конструктори об'єктів:

```bsl
// ❌ Плохо — зависимость от реализации ВнешняяСистемаИнтеграция.Ошибки_Инициализация
Ошибки = ВнешняяСистемаИнтеграция.Ошибки_Инициализация();
ВнешняяСистемаИнтеграция.Ошибки_Добавить(Ошибки, "Ошибка");

// ✅ Хорошо — контракт выражен явно, без зависимостей
Ошибки = Новый Структура("Отказ, Описания", Истина, Новый Массив);
```

```bsl
// ❌ Плохо — зависимость от фабричного метода другого модуля
ПараметрыПреобразования = ВнешняяСистемаИнтеграция.ПараметрыПреобразования_Инициализация("date");

// ✅ Хорошо — структура видна, намерение очевидно
МассивИмен = Новый Массив;
МассивИмен.Добавить("date");
ПараметрыПреобразования = Новый Структура("ИменаСвойствСоЗначениямиДата", МассивИмен);
```

Якщо та сама структура даних потрібна в кількох тестах — виноси побудову в приватний helper тестового модуля (`СлужебныеПроцедурыИФункции`), не копіюй код.

Роби helper **параметричним конструктором**: приймає лише значущі для сценарію дані, повертає повністю ініціалізований об'єкт. Шаблонний «нудний» код (створення структури, заглушки для необов'язкових полів) лишається всередині helper — тест бачить лише те, що важливе для конкретної перевірки. Необов'язкові частини — через параметри за замовчуванням:

```bsl
// Конструктор структуры с переменными полями
Функция СоздатьДвижение(Период, ТипЦен, Номенклатура, Организация, Цена)
    Результат = Новый Структура();
    Результат.Вставить("Период", Период);
    Результат.Вставить("ТипЦен", ТипЦен);
    Результат.Вставить("Номенклатура", Номенклатура);
    Результат.Вставить("Организация", Организация);
    Результат.Вставить("Цена", Цена);
    Возврат Результат;
КонецФункции

// Конструктор с опциональными параметрами
Функция СоздатьГруппу(Наименование, Родитель = Неопределено, ПометкаУдаления = Ложь)
    Возврат ЮТест.Данные().КонструкторОбъекта("Справочник.Номенклатура")
        .Установить("Наименование", Наименование)
        .Установить("Родитель", Родитель)
        .Установить("ЭтоГруппа", Истина)
        .Установить("ПометкаУдаления", ПометкаУдаления)
        .Записать( , Истина);
КонецФункции

// Конструктор мок-ответа внешнего сервиса — удобно при мокировании HTTP
Функция ОтветВнешнегоСервиса(Знач Код, Знач Метод, Знач Тело, Знач Ошибки = Неопределено)
    Если Ошибки = Неопределено Тогда
        Ошибки = Новый Массив();
    КонецЕсли;
    Возврат Новый Структура(
        "КодСостояния, URL, Метод, Тело, Ошибки",
        Код, "", Метод, Тело, Ошибки);
КонецФункции
```

**Будівник колекції** (створення + додавання рядків):

```bsl
Функция ОписаниеТоваров()
    Результат = Новый ТаблицаЗначений();
    Результат.Колонки.Добавить("Код");
    Результат.Колонки.Добавить("Ссылка");
    Возврат Результат;
КонецФункции

Процедура ДобавитьОписаниеТовара(ОписаниеТоваров, Код, Ссылка)
    Строка = ОписаниеТоваров.Добавить();
    Строка.Код = Код;
    Строка.Ссылка = Ссылка;
КонецПроцедуры
```

**Масив-перелік значень — через `ЮТКоллекции.ЗначениеВМассиве`.** Коли колекція — це просто фіксований перелік значень, явну збірку (`Новый Массив()` + серія `.Добавить()`) заміняй на однорядковий helper фреймворка. Принцип «будуй дані напряму» не порушується — `ЮТКоллекции` є частиною YAxUnit, а не коду, що тестується, — але код коротший і читабельніший:

```bsl
// ❌ Многословно — три строки на список из одного значения
Объекты = Новый Массив();
Объекты.Добавить(Контрагент1);

// ✅ Одна строка; метод принимает до 10 значений
Объекты = ЮТКоллекции.ЗначениеВМассиве(Контрагент1);
Объекты = ЮТКоллекции.ЗначениеВМассиве(Контрагент1, Контрагент2);
```

**Дані «для запиту» — генеруй inline, не виноси в методи, якщо вони не є предметом тесту.** В інтеграційних тестах частина даних потрібна лише для того, щоб відпрацював запит методу, що тестується (наприклад, обов'язкове `ВНУТРЕННЕЕ СОЕДИНЕНИЕ` з курсом валюти), але на логіку методу й на перевірки не впливає. Для такої обв'язки:

- **не заводь окремі helper-методи** (`СоздатьВалюту`, `СоздатьКурс`) — це шум; будуй об'єкт прямо в `// given`;
- **не задавай конкретні значення через `Установить`** там, де значення не важливе — використовуй генератори `ФикцияОбязательныхПолей()`, `Фикция("Реквизит")`. `Установить` лишай лише для полів-зв'язок, від яких залежить потрапляння рядка в результат (ключі з'єднання, виміри з відбору, період зрізу).

```bsl
// given
// Валюта и курс нужны только чтобы прайс прошел ВНУТРЕННЕЕ СОЕДИНЕНИЕ с КурсыВалют
Валюта = ЮТест.Данные().КонструкторОбъекта("Справочник.Валюты").ФикцияОбязательныхПолей().Записать();
ЮТест.Данные().КонструкторОбъекта("РегистрСведений.КурсыВалют")
    .Установить("Период", НачалоДня(ТекущаяДатаСеанса()))   // важно: попасть в срез
    .Установить("Валюта", Валюта)                           // важно: ключ соединения
    .Фикция("Курс")                                         // не важно
    .Фикция("Кратность")                                    // не важно
.ДобавитьЗапись();
```

Іменований helper виправданий для даних, які **є предметом тесту** (їхні поля осмислені для сценарію) — не для чистої запитової обв'язки.

### Атомарність і незалежність тестів

Кожен тест має бути самодостатнім: він сам створює все потрібне й не залежить ні від інших тестів, ні від порядку їхнього виконання. База агента спільна, тож тест також не покладається на наявні в базі дані (розділ «Спільна база агента» в `SKILL.md`).

**Дані — у самому тесті (або в його хуку `ПередКаждымТестом`):**

```bsl
Процедура ПоискНаходитСозданныйЭлемент() Экспорт
    // given — каждый тест создаёт свои данные
    Номенклатура = СоздатьНоменклатуру("Тестовый товар");

    // when
    Результат = МойМодуль.НайтиПоНаименованию("Тестовый товар");

    // then
    ЮТест.ОжидаетЧто(Результат).Равно(Номенклатура);
КонецПроцедуры
```

**Спільні дані допустимі лише для незмінюваних об'єктів.** Якщо дані, створені в `ПередВсемиТестами` або `ПередТестовымНабором`, може змінити хоча б один тест — це крихка конструкція: тест, запущений після модифікуючого, отримає інший стан і дасть хибний результат. Спільні дані — лише для довідкових/статичних об'єктів, які тести читають, але не змінюють.

| Ситуація                                     | Де створювати дані                                      |
| -------------------------------------------- | ------------------------------------------------------- |
| Дані унікальні для тесту                     | у тілі тесту або `ПередКаждымТестом` + `.ВТранзакции()` |
| Важкий незмінюваний об'єкт для всього набору | `ПередТестовымНабором` + `.УдалениеТестовыхДанных()`    |

Ізоляція даних через `.ВТранзакции()` — основний інструмент: кожен тест отримує чистий стан БД без ручного прибирання.

### Що перевіряти

**Граничні умови** — порожні колекції, нульові значення, мінімум/максимум діапазону, порожній рядок замість заповненого.

**Обробку помилок** — якщо метод викидає виняток за порушення передумов, це теж поведінка, яку перевіряє тест (за умови, що її передбачає перелік тестів плану):

```bsl
ЮТест.ОжидаетЧто(МойМодуль)
    .Метод("МойМетод", ЮТКоллекции.ЗначениеВМассиве(НедопустимыйПараметр))
    .ВыбрасываетИсключение("Устойчивый фрагмент текста ошибки");   // аргумент обязателен, совпадение по подстроке
```

Якщо разом з винятком потрібно перевірити виклики мока — спершу твердження про виняток (воно ж викликає метод), потім перевірка Мокито. `Попытка ... Исключение` у тесті не використовуй: порожній обробник приховує відсутність винятку.

```bsl
// when / then
ЮТест.ОжидаетЧто(МойМодуль)
    .Метод("МойМетод", ЮТКоллекции.ЗначениеВМассиве(Параметр))
    .ВыбрасываетИсключение("Ожидаемый текст");

// then
Мокито.Проверить(РегистрыСведений.МойРегистр)
    .КоличествоВызовов("Записать").Равно(0);   // до записи не дошли
```

**Коректність даних** — не лише «повернув щось», а й що саме: перевіряй конкретні поля результату, а не лише факт його наявності. Віддавай перевагу перевіркам через Предикати (`references/framework/predicates.md`).

**Продуктивність** — як правило, поза зоною відповідальності юніт-тесту; не додавай перевірок продуктивності без явної задачі.

---

### Перевірка ранніх виходів через spy, а не через стан

У методу з ранніми виходами (guard-умови: вимкнена функціональна опція, порожній вхід, немає пов'язаних даних) сенс гілки один — **побічний ефект не настав**. Таку гілку можна перевіряти двома способами:

- **State-based** — попередньо записати дані, викликати метод, переконатися, що дані не змінилися;
- **Interaction-based (spy)** — спостерігати за методом-колаборатором, що мутує, і переконатися, що він **не викликався**.

Для ранніх виходів spy зазвичай точніший і дешевший. Він прямо виражає контракт гілки («до мутації не дійшли»), а не виводить його опосередковано з незмінності даних. Плюс прибирає фікстури й читання БД: setup-записи і блок `СодержитЗаписи` не потрібні, а отже такому тесту не потрібна й `.ВТранзакции()`.

**Окремий сильний аргумент — відсутність дублювання покриття.** Якщо `СодержитЗаписи` перевіряє те, що саме метод, який мутує, робить із записами, а цей метод уже покрито власним тестом (напр. тест модуля менеджера регістра), то state-перевірка в тесті-оркестраторі дублює чуже покриття. Завдання тесту-оркестратора — розгалуження, а не дані колаборатора.

**Як:** `Мокито.Наблюдать(...)` у фазі навчання + `Мокито.Проверить(...).КоличествоВызовов(...).Равно(0)` у `// then`. Спостереження, як і мок, працює через `&Вместо` — для методу, за яким спостерігають, потрібен перехоплювач (`references/interceptors.md`). За відсутності навчання перехоплювач іде в `ПродолжитьВызов` — реальний метод, тому додавання перехоплювача не ламає інтеграційні тести того самого методу.

**Кожен тест має доводити свою гілку.** Якщо кілька ранніх виходів перевіряти лише за «мутація не відбулася», їхні перевірки стануть невідмінні. Щоб тест доводив саме свій guard, додай спостереження за колаборатором наступного кроку:

```bsl
// Ветка 1: функциональная опция выключена -> выход на первом же условии,
// заказы даже не запрашивались
Мокито.Обучение(МодульВызова)
    .Когда("ОбрабатыватьГрузовыеМеста").Вернуть(Ложь)
.Обучение(МодульСервер)
    .Наблюдать("ЗаказПоставщику")
.Обучение(РегистрыСведений.ГрузовыеМеста)
    .Наблюдать("УстановитьПризнакСканирования")
.Прогон();

// when
МодульВызова.СброситьПризнакНеполногоСканирования(Неопределено, ТестОтказ);

// then
Мокито.Проверить(МодульСервер)
    .КоличествоВызовов("ЗаказПоставщику").Равно(0);            // выход ДО запроса заказов
Мокито.Проверить(РегистрыСведений.ГрузовыеМеста)
    .КоличествоВызовов("УстановитьПризнакСканирования").Равно(0); // мутации не было
```

```bsl
// Ветка 2: заказы запрошены, но пусты -> выход на втором условии
Мокито.Обучение(МодульВызова)
    .Когда("ОбрабатыватьГрузовыеМеста").Вернуть(Истина)
.Обучение(МодульСервер)
    .Когда("ЗаказПоставщику").Вернуть(Новый Массив)
.Обучение(РегистрыСведений.ГрузовыеМеста)
    .Наблюдать("УстановитьПризнакСканирования")
.Прогон();
// ... then: КоличествоВызовов("УстановитьПризнакСканирования").Равно(0)
```

**Компроміс — назви його.** Spy жорсткіше прив'язаний до реалізації: тест фіксує, що мутація йде саме через конкретний метод-колаборатор. Якщо скидання перепишуть на інший механізм (напр. прямий запис набору), spy-тест доведеться виправити, хоча поведінка лишилася коректною. Для гілок «метод нічого не робить» така прив'язаність прийнятна й навіть доречна. Але якщо гілка виробляє **осмислений** стан (щось записала, порахувала, змінила поля) — перевіряй стан (state-based) і предикати за даними, а не факт виклику.

### Тестування методів з `ПолучитьФункциональнуюОпцию()`

Якщо метод, що тестується, всередині викликає `ПолучитьФункциональнуюОпцию()`, **не можна** використовувати `.ВТранзакции()` для ізоляції даних. Причина: платформа 1С читає значення функціональної опції з позатранзакційного кешу — зміна константи всередині відкритої транзакції невидима для `ПолучитьФункциональнуюОпцию()`, і тест завжди отримає старе значення.

**Правила:**

1. **Без транзакції** — тест встановлює константу напряму, без `.ВТранзакции()`.
2. **Останнє значення — `Ложь`** — якщо тест параметричний (булева константа), останнім став параметр `Ложь`. Це булеве значення за замовчуванням у 1С, і після прогону тестів константа опиниться у «вимкненому» стані, що знизить ризик впливу на інші тести, які використовують ту саму функціональну опцію.

```bsl
// ИсполняемыеСценарии — без .ВТранзакции()
.ДобавитьТест("МетодВозвращаетЗначениеФункциональнойОпции")
    .СПараметрами(Истина)
    .СПараметрами(Ложь)   // ← последний: константа остаётся Ложь после теста

// Реализация
Процедура МетодВозвращаетЗначениеФункциональнойОпции(ЗначениеОпции) Экспорт
    // given
    Константы.МояКонстанта.Установить(ЗначениеОпции);

    // when
    Результат = МойМодуль.МойМетод();

    // then
    ЮТест.ОжидаетЧто(Результат).Равно(ЗначениеОпции);
КонецПроцедуры
```

**Виняток — ФО читається через метод-обгортку.** Якщо код, що тестується, дізнається значення ФО не напряму, а через метод конфігурації-обгортку (напр. `Модуль.ОбрабатыватьХ()` = `ПолучитьФункциональнуюОпцию("...")`), правило вище можна обійти: замокати саму обгортку (`Мокито.Обучение(Модуль).Когда("ОбрабатыватьХ").Вернуть(Истина/Ложь)`). Тоді `ПолучитьФункциональнуюОпцию()` не викликається, позатранзакційного кешу ФО в грі немає — і тест можна тримати в `.ВТранзакции()` (чистий відкат замість ручного прибирання даних). Мок ловить і внутрішньомодульний виклик обгортки з методу, що тестується, того ж модуля.

Обмеження: працює **лише** через метод-обгортку. Прямий виклик `ПолучитьФункциональнуюОпцию()` усередині методу, що тестується, замокати не можна — це платформний метод (див. обмеження Мокито в `references/framework/mocking.md`). Потребує перехоплювача `&Вместо` — див. `references/interceptors.md`.

Тест без транзакції пише константу в спільну базу агента — правила для такого тесту (повернення значення, що було) — розділ «Спільна база агента» в `SKILL.md`.

### Документуй намір, а не механіку

Коментарі `// given / // when / // then` самі по собі структурують тест. Додатковий коментар потрібен лише якщо неочевидно **навіщо** — чому саме ці дані, чому саме цей результат очікується:

```bsl
// given
// Цена = 0 — граничный кейс: при нулевой цене расчёт должен вернуть Неопределено, а не 0
Товар = СоздатьТовар();
ЮТест.Данные().УстановитьЗначениеРеквизита(Товар, "Цена", 0);

// when
Результат = Ценообразование.РассчитатьЦену(Товар);

// then
ЮТест.ОжидаетЧто(Результат).НеЗаполнено();
```

Не описуй те, що читається з коду, — описуй **причину** вибору конкретного сценарію.

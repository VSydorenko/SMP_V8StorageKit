# Редагування вихідників 1С агентом: кінці рядків і BOM

Політика git для вихідників (`-text`, `--renormalize`, round-trip через платформу) — у
`docs/text-policy.md` репозиторію плагіна; тут лише пастки **інструмента**, яким правиш файл.
Канон: структура XML платформи — CRLF, переводи рядків усередині текстових значень — LF, BOM
на місці, завершального переводу рядка в XML немає (файл закінчується на `>`); BSL — CRLF.

## Потокові утиліти руйнують канон

`grep -v … > tmp`, `sed`, `sed -i`, `awk`, `tr` у Git Bash знімають CR і/або дописують
завершальний `\n`. Симптом оманливий: `git diff --stat` показує, що переписано весь файл
(стільки вставок, скільки й видалень, скільки було рядків), а `diff` після `tr -d '\r'` бачить
один рядок різниці. Зіпсовано кінці рядків, не текст.

Правило: до вихідників платформи — лише точкове редагування на місці інструментом `Edit`: він
зберігає CRLF, BOM і відсутність завершального переводу рядка. Потокові утиліти — щоб
*дивитись*, не щоб *писати*. Після правки звіряй розмір: видалення рядка зменшує файл рівно на
його довжину разом із `\r\n`.

## Новий файл через `Write`

`Write` дає LF без BOM, а вихідник Designer XML/BSL мусить бути як сусідні файли того ж дерева
(зазвичай CRLF, XML — з BOM). Нормалізуй кінці рядків і BOM одразу після створення, не
відкладаючи до round-trip. Генератор XML без завершального переводу рядка: інакше побайтова
звірка дає хибне спрацювання на кожному згенерованому файлі.

## Перевірка кінців рядків

```bash
grep -c $'\r$' <файл>
```

Лише ANSI-C цитування. `$(printf '\r')` не працює: command substitution зрізає завершальний
`\r`, і перевірка дає нуль на справному файлі (це не раз видавали за «Edit зіпсував файл»).
Запускай окремою командою, не в ланцюжку `&&`: `grep` без збігів повертає код 1 й рве ланцюг.
Не закладайся на `python3` та `iconv` у Git Bash: їх там може не бути.

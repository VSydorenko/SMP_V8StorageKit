# Хроніка й мітки — що йде, що лишається

Документи описують стан у теперішньому часі. Історія живе в git; статус — у GitHub.

## Замінити

| Прибрати | Замінити на |
| --- | --- |
| «фазу 3 злито (PR #N) — модель змінилась» | опис самої моделі в теперішньому часі |
| «після блоку B3 ми…», «у фазі 2 було…» | чинне правило без блоку чи фази |
| «скасовано розворотом від <дата>», «перша чернетка читала це навпаки» | «обернене до цього — типове хибне прочитання» |
| «видалено у vN: `tokenA`, `propB`…» | «утиліти для X немає й бути не повинно — ось чому» (якщо власник лишає такі списки) |
| журнал змін версій документа | нічого (його тримає git) — спершу прочитай, див. steps.md |
| рядки «Версія / Дата / Оновлено» в шапці | нічого |
| рядки прогресу чи статусу, чекбокси | GitHub (`track`), потім видалити |
| `Модуль.bsl:148-149` | опис місця |

## Лишається (законний шум у `doc history`)

- Вказівник `§` у **живий** документ (специфікація платформи, затверджена спека наступного блоку) та id його рішень.
- Предметний зміст слів «фаза», «етап», «хвиля» (наприклад, фази expand/contract схеми).
- UUID, хеші й суфікси ключів кешу, схожі на мітки.
- Цитати й приклади всередині скіла, який вчить саме цього правила.

## Як правити

- Точкові правки (Edit), одне твердження за раз. Масова заміна regex по прозі дає покалічений текст.
- Прибери навігаційну мітку, лиши причину, чому код такий.
- Ніколи не додавай нового твердження, коли скорочуєш: агенти, що переписують документи, впевненим тоном вигадують API. Кожен символ, параметр чи число, яке ти пишеш, мусить існувати в коді (знайди його пошуком).

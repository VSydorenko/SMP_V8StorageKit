# storage-adopt — людина перенесла частину роботи в сховище

Історія гілки задачі `F` лишається цілою: не rebase, не re-derive. Дерево джерела сховище
**заміняє**, а не зливає з ним, — людина кладе у сховище свою версію, можливо взявши лише
частину роботи агента, і merge лишив би в гілці те, чого вона свідомо не взяла. Прев'ю `adopt` показує ціну заміни заздалегідь: що прийде зі сховища і що
зникне з гілки. Скільки завгодно раундів.

Ланцюжок: onboarding → storage-sync → infobase-agent → (робота в Unica) → **storage-adopt** → task-finish → storage-verify.

## 1. Передумови

- Поточна гілка — гілка задачі `F` (не головна, не `storage/*`): `git branch --show-current`.
- Робоча копія чиста або зміни закомічені в `F` (`git status --porcelain`).
- Людина сказала, які джерела торкнула (або всі `truth: storage` воркспейсу).
- Людина поруч: процедура інтерактивна. Питання Уніки (`push force`, а за незбереженого чи поза git — `pull force`) адресоване їй; kit-команди кодів виходу від цього питання не мають, тож на `cancelled` агент зупиняється з доповіддю.

## 2. Кроки

1. **Нові версії зі сховища → дзеркало.** Спершу прев'ю; `-Apply` — **лише на явне прохання**.
   Те, що людина щойно комітила у сховище, — це контекст, а не дозвіл: вона сказала, що зробила,
   а не що робити далі. Показати прев'ю і спитати:
   ```
   kit sync -RepoRoot . -Source <ключ> -Apply
   ```
   Якщо після цього в Windows-копії `pull`/`checkout` падає з «would be overwritten» — це
   перейменування регістром кириличного імені у версії вендора, не пошкодження. Вихід —
   `git fetch` і `git reset --hard origin/<гілка>` (`<гілка>` — поточна, на якій упала команда)
   або свіжий клон, але лише коли `git status` чистий **і** `git log origin/<гілка>..HEAD` порожній
   (інакше reset відкине непушені коміти). **Агент reset не виконує:** показує людині `git status`
   і ці дві перевірки та чекає її рішення (`docs/storage-and-git.md`, «Перейменування регістром»).
2. **База агента і дерево — з `F`**: один список з двох кроків, у цьому порядку. Обидва виконує агент
   по `unica.run`; `sourceSet` називається явно (для розширення `pull` несе ще `extension` = ім'я
   набору; `push` `extension` не приймає). Спершу прев'ю з `"dryRun":true`, тоді той самий виклик
   з `"dryRun":false`.
   1. **`push force:true`** — крок, який `sync` надрукував у кроці 1 для цього набору («Далі —
      вирівняти пам'ять раннера …»): `unica.run {"op":"push","args":{"sourceSet":"<ключ>","force":true},"dryRun":true}`.
      Повне завантаження гілки задачі в базу, кеш Уніки участі не бере. Звичайний `push` тут не
      годиться: набір з незміненим деревом гілки він пропускає без звірки покоління (відповідь
      `infobase_state_unverified`) — це й був дефект #25 (у 1.4.0 крок мовчки відповідав `skipped`, і
      прев'ю `adopt` виходило хибно порожнім). Від #25 захищає саме надрукований крок; якщо його таки
      пропущено, діє сітка з `v8storagekit:storage-rules` (`infobase_state_unverified` → `push` з
      `"force":true`). Якщо `sync` нових версій не приніс, кроку він не друкує — база не зрушена, і
      досить звичайного `push`, коли дерево `F` змінювалось. Відповідь `cancelled` на `push force` —
      **зупинка до `pull`**: людина відхилила завантаження, база не вирівняна, і `pull` вивантажив би
      з неї не те, що в `F`; доповісти людині. Рядок `ЗУПИНКА: …` наприкінці виводу `sync` — теж
      зупинка: далі не йти.
   2. **`pull force:true`** — канонізація дерева: `unica.run {"op":"pull","args":{"sourceSet":"<ключ>","force":true},"dryRun":true}`
      (розширення: ще `"extension":"<ключ>"`). Платформа вивантажує набір з бази назад у дерево, і в git
      лягають її байти. На чистому закоміченому наборі Уніка людину не питає; незбережене чи поза git
      захищає вже її питання; відповідь `cancelled` — зупинка з доповіддю, не обхід.
      Тому передумова розділу 1 (зміни закомічено в `F`) — не формальність.

   Причини порядку (не одна): (а) `pull` переписує дерево з бази, тож без попереднього `push force`
   база тримала б стан сховища, а не `F`, і він замінив би закомічену роботу версією сховища; (б) крок
   1 (`sync`) щойно лишив базу у стані версії сховища — це контракт, а не збій;
   (в) канонізація робить прев'ю кроку 4 **семантичним** — див. нижче.
3. **Закомітити зміни від `pull`** в `F`, якщо вони є (`git status --porcelain -- <шлях джерела>`), не
   `git commit -am`:
   ```
   git rm -r -q --cached -- <шлях джерела>
   git add -- <шлях джерела>
   git diff --cached --name-only
   git commit -m "pull: дерево у форматі платформи"
   ```
   `git diff --cached --name-only` мусить показати лише шлях джерела. Без `-a` — він не додає нових
   файлів; без `--only` — той воскрешає фантом, коли `pull` змінив лише регістр імені
   (`docs/storage-and-git.md`, «Перейменування регістром»).

   **Крок не марний, хоч крок 4 і замінить це дерево.** Канон і дамп дзеркала — один формат платформи
   (на одній платформі `pull force` і `DumpConfigToFiles` дають однакові
   байти), тож саме `pull force` робить прев'ю `adopt` семантичним: у списку «прийде зі сховища»
   лишається робота людини, а не різниця форматів. Без нього туди потрапив би формат Unica — той самий
   шум, який прибирали зі `verify`, лише перенесений у `adopt`. Умова — kit і раннер працюють на одній
   платформі. Причина кроку лишилась тією самою, хоч його виконує вже Уніка, а не kit; змінилось
   одне: окремої копії незбереженого kit тут не робить — його захищає питання Уніки перед `pull`.
4. **Прийняти версію сховища в `F`** — прев'ю, потім заміна:
   ```
   kit adopt -RepoRoot . -Source <ключ>
   ```
   Прев'ю називає **три** списки: що **прийде зі сховища**, що **зникне з гілки** — робота
   агента, якої людина у сховище не взяла; показати його людині **до** заміни, бо саме вона
   вирішує долю цієї роботи, — і окремо **лише CR** (зіпсована політика тексту,
   `docs/text-policy.md`). З її згодою — той самий виклик із `-Apply`.

5. **Звіт людині**: що поглинуло сховище (перший список прев'ю) і що лишилось поза ним (другий).
   Порожні всі три — вміст уже дорівнює сховищу: коли дзеркало вже предок гілки й нічого
   не незакомічено, `adopt -Apply` не зробить коміту; інакше (прев'ю каже «вміст уже дорівнює
   дзеркалу — буде лише злиття ancestry») `-Apply` лише допише ancestry й закомітить рівне
   дзеркалу незакомічене — файли не чіпає й резервної копії не робить;
   непорожній лише список «лише CR» усе одно означає, що заміна відбудеться — вона виправить
   і зіпсовану політику тексту. Після `adopt -Apply` база вже вирівняна кроком 2 — звичайний
   `push` Уніки довантажить прийняте дерево.

## 3. Штатні зупинки

- `sync`: див. `v8storagekit:storage-sync` (невідомі автори, недоступне сховище).
- рядок `ЗУПИНКА: …` наприкінці виводу `sync` — зупинка з доповіддю людині, далі не йти.
- `sync`: `База агента воркспейсу '…' не налаштована` — `v8storagekit:infobase-agent`; `збігається з
  дев-базою людини` — kit не пише в базу людини.
- `push force` чи `pull force` Уніки відповіли `cancelled` — зупинка з доповіддю людині (`pull` не виконувати після відхиленого `push`).
- `adopt`: `Гілки '<ключ>' немає` — дзеркало ще не створено, спершу `kit sync -Source <ключ> -Apply`.

## 4. Межі

Сховище — тільки читання; реплей — лише через `sync`. Kit не пише в базу людини. `-Apply`
(і `sync`, і `adopt`; `push`/`pull` Уніки — за її запитами) — лише на явне прохання: те, що людина розповіла про свій коміт
у сховище, проханням не є. У головну гілку тут не зливаємо (звірочні коміти —
`v8storagekit:storage-verify`). Нічого не пушити.

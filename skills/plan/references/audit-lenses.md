# Лінзи

| Лінза | Модель | Питання |
| --- | --- | --- |
| план проти спеки й коду | sonnet (opus для ризикового блоку) | Чи кожне твердження й якір правдиві? Чи кожну задачу можна виконати в поточному коді? Чи не втрачено щось із рядка блоку спеки? Для кожного механізму, який називає задача (об'єкт метаданих, генератор, етап, точка розширення), чи план цитує код, що його підтримує (процедура, сигнатура, об'єкт)? Без цитати — знахідка. |
| безпека й старе покоління | opus | Чи дані, записи чи підписки переживають закриття, втрату доступу, старе покоління запиту чи даних? Права ролей, гості й анонімні сеанси, RLS? Чи не витікає секрет чи дані через відповідь, журнал, обмін? Межі обміну й інтеграцій. |
| цілісність даних | opus | Проведення: чи рухи регістрів повні на всіх шляхах, зокрема відміни й перепроведення? Транзакція: чи відкрита на шляху помилки й чи не охоплює зайвого? Управляемые блокировки: чи є порядок і чи вистачає їх до читання перед записом? Чи не ламає зміна дані, створені попередньою версією? |
| сумісність із вендором | sonnet | Чи план спирається на код вендора, який зміниться з оновленням конфігурації-власника (перехоплення `&Перед`/`&После`/`&Вместо`/`&ИзменениеИКонтроль`, запозичені форми)? Чи цей код справді такий у дампі конфігурації-власника? Чи названо, що робити при оновленні? |
| бюджети | sonnet | Чи кожен бюджет — вимірна умова done-when? Чи дизайн вкладається в нього на заявленому обсязі даних (запит у циклі, віртуальні таблиці без параметрів, виклики сервера)? |
| гейт без хибного зеленого | opus | Чи може перевірка стати зеленою без прогону, на порожній множині чи при помилці відбору? Чи гейт ділить код із тим, що перевіряє? |
| виконуваність | sonnet (opus для ризикового блоку) | Чи названа перевірка справді червоніє? Чи працюють команди? Порядок задач, цикли залежностей. Лише коли раунд 1 знайшов blockers виконуваності. |

Codex — не лінза: він працює лише як необов'язковий скіл `codex-companion`, якщо є на машині, і за тригером зі скіла `plan`, «Аудит за ризиком», крок 5.

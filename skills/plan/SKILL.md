# План

**План фіксує те, що дорого змінювати в коді. Він не фіксує те, що виконавець однаково вирішить із коду.** Якість ловиться на прийманні коду (рев'ю Opus з новою лінзою чи моделлю), а не довшим планом. Автор пише й аудитує план; архітектор його приймає.

## Що є планом

| У плані | Не в плані — це пише виконавець |
| --- | --- |
| мета й межі блоку | покрокові випадки перевірок і їхні назви |
| рішення з впливом на спеку (§ або «немає») | імена змінних, помічників, дрібних файлів |
| інтерфейси між блоками: типи, контракти, хто що дає | порядок дрібних кроків усередині задачі |
| інваріанти безпеки, кожен із перевіркою, що ловить дефект | повні команди, очевидні з репозиторію |
| задачі з вимірним done-when і залежностями «після X» | переказ спеки |
| задача 0: звірка якорів із кодом + поправки до спеки, яких вимагають рішення плану | блоки коду |
| задачі власника, окремо | |

Розділи, по порядку: [references/template.md](references/template.md).

Розмір: ціль ≤ 25–30 КБ, міряй `doc <план>` (КБ на розділ) — один рядок таблиці може нести сотні символів, тож рядки вводять в оману. Понад ~40 КБ план переказує спеку чи пише сценарій для виконавця: скороти найбільший розділ, а не слова всюди.

## Вхід

Рядок блоку в таблиці блоків спеки (обсяг, done-when, залежності) і таблиця спеки «інтерфейс → блок-власник», прочитані `doc <спека> §N`. Якщо якоїсь таблиці нема — спитай архітектора до письма: без них близько половини питань автора — «хто дає цей інтерфейс».

## Що робить план виконуваним

- **Репозиторій 1С** (є `v8storagekit.yaml` чи `v8project.yaml`) — також [references/1c.md](references/1c.md): драбина перевірок і поле `Сходинка:` у задачі, розділ «Зміни метаданих», джерела 1С, база агента, лінзи аудиту 1С.
- Поведінка платформи й чужого коду: сам цей код і документація для версії проєкту; цитуй файл і символ (модуль, процедуру).
- Права й ролі: «право ролі X на Y» план не доводить — його перевіряє виконавець у своїй задачі на рантаймі проєкту; у плані лише названо, що перевірити. Гостьові й анонімні сеанси — окремо.
- Кожен інваріант безпеки названо з перевіркою, що його ловить; дефект, на якому перевірка червоніє, — словами. Форму й обсяг перевірок називає бриф задачі: тести — мінімум, лише на логіку й механізми, які справді треба перевіряти.
- Ліміти пам'яті й бюджети — вимірні умови done-when, не коментарі.
- Шапка плану називає режим робочої копії (`workspace.mode`), спільний рантайм (база, стенд) і хто та коли його займає (збирає, тестує); виконавець тоді знає, що в `shared` рантайм тримає один за раз.
- Задача, що додає до спільного рантайму об'єкти чи налаштування, називає свій шлях перевірки й коли рантайм їх отримує.
- Переніс перевірок між проєктами: порівняй переліки імен до й після.
- Якорі: `doc anchors <план>` до аудиту; зламані виправ сам. Якорі на незлите — позначай «після X».
- План торкається блоку, який виконує інша сесія → скажи архітектору, а не виправляй там.

## Аудит за ризиком

Мета — 0 blocker і 0 security major, без раундів заради раундів.

1. **Класифікуй ризик** за [references/audit-risk.md](references/audit-risk.md). Відповіді обирають раунд 1, паралельно в одному повідомленні:

   | Блок | Раунд 1 | codex-audit |
   | --- | --- | --- |
   | без поверхні безпеки (індекси, рефакторинг, перенос перевірок, форма без прав) | Sonnet «план проти спеки й коду» (Opus, якщо блок ризиковий) | ні |
   | права, ролі, ідентичність, секрети, межі обміну й інтеграцій | + Opus «безпека й старе покоління» | лише якщо Opus знайшов security major |
   | облікові записи даних, транзакції, блокування | + Opus «цілісність даних» | ні |
   | перехоплення чи розширення чужого коду (вендор, бібліотека) | + Sonnet «сумісність із вендором» | ні |
   | бюджети (запити, фонові завдання, обсяг даних) | + Sonnet «бюджети» | ні |
   | сам план — гейт: перевірка, на чий зелений вердикт покладаються | + Opus «гейт без хибного зеленого» | ні |

2. **Запусти** по одному `v8storagekit:auditor` на лінзу, `model` із таблиці в виклику Agent. Питання лінз: [references/audit-lenses.md](references/audit-lenses.md); бриф: [references/audit-brief.md](references/audit-brief.md). Аудитори нічого не збирають і в спільному рантаймі нічого не запускають.
3. **Обробляй** кожну знахідку проти тексту плану й коду спершу:

   | Знахідка | Дія |
   | --- | --- |
   | спростована текстом чи кодом | запиши як спростовану, з причиною |
   | blocker, або major про виконуваність | виправ план |
   | security major | виправ план; запускає раунд 2 |
   | minor | не в план; щонайбільше один рядок «нотатка виконавцю» |
   | формулювання, назви, порядок дрібних кроків | план задетальний: скороти цю частину |

4. **Раунд 2 — лише за тригером** (blocker чи security major у раунді 1). Бачить лише diff виправлень (`git diff <коміт раунду 1>..HEAD -- <план>`), один аудитор: Opus для виправлення безпеки (та сама причина, що в лінзі «безпека й старе покоління», `references/audit-lenses.md`), інакше лінза, що знайшла blocker, на її моделі.
5. **`v8storagekit:codex-audit`** — лише коли Opus знайшов security major і на машині налаштовано Codex CLI: аудит плану й розділу спеки, лише читання. Код 3 — не результат; перевір кожну знахідку; сирий звіт далі не пересилай. Codex не налаштовано — раунд 2 з Opus, нічого не вигадуй.
6. **Та сама зона щораунду** → причина в дизайні: правило доводиться повторювати в кількох місцях (друге сховище, паралельний шлях запису). Зупини раунди й запропонуй архітектору зміну моделі, щоб правило діяло на одному шляху, та інваріант «другого авторитетного сховища немає»; після перепроєктування — один вузький раунд.

## Звіт

Підсумок аудиту — один абзац наприкінці плану: раунди й лінзи, знайдено, спростовано, лишилось і чому. Потім доповідь архітектору одним повідомленням:

- гілка, HEAD, файл плану; частини й залежності;
- рішення на затвердження, кожне з причиною; розвилки, що зачіпають інші блоки чи сесії;
- підсумок аудиту; якщо 0 blocker / 0 security major не досягнуто — скажи це й запропонуй наступний крок (вузький раунд чи зміна моделі).

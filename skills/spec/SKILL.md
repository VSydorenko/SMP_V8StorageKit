# Спека

Мета: автор плану читає лише той блок, який будує, і знаходить там обсяг, «готово, коли», залежності й власника кожного інтерфейсу. Пиши мовою документації проєкту.

## Три документи, одне місце для факту

| Документ | Що тримає | Шлях (профіль → типово) |
| --- | --- | --- |
| **Глосарій** | один термін — одне значення на весь проєкт | `docs.glossary` → `docs/GLOSSARY.md` |
| **ADR** | одне вагоме рішення: контекст, рішення, чому, відкинуте, наслідки, статус | `docs.adr` → `docs/adr/` |
| **Спека** | «що» як стан; для «чому» — посилання `ADR-N` | `docs.specs` |

Профіль: `.agents/kit.profile.json`. Теку чи файл, яких бракує, створюють, коли з'являється перший запис. Проєкт зі старими спеками отримує стартовий глосарій і ADR під час підключення (`v8storagekit:kit-onboard`), а не тут.

## 1. Глосарій — поки говорите, а не наприкінці

- У обговоренні з'явився новий термін → додай його зараз. Формат: [references/glossary.md](references/glossary.md).
- Власник чи документ вживає термін глосарію в іншому значенні → скажи про це й улагодь, перш ніж писати далі.
- Два слова на одну річ → вибери одне, друге внеси в *Уникати*. Спеки, плани й код вживають обране слово.

## 2. Розсортуй кожне рішення

| Рішення | Куди йде |
| --- | --- |
| **Вагоме**: важко відкотити, АБО здивує майбутнього читача, АБО справжній компроміс між реальними варіантами; також кожне рішення, яке ставили власнику | новий ADR — [references/adr.md](references/adr.md) |
| **Дрібне технічне** | текст спеки як стан; причина — в повідомлення коміту |
| **Чекає на власника** | відкрите питання в §7 спеки з твоєю рекомендацією; ADR пишуть після відповіді |
| **Зміна прийнятого ADR** | новий ADR з `Supersedes: ADR-N`; старий дістає `Status: superseded by ADR-M`. Прийняте рішення мовчки не правлять |

Хто вирішує: три класи питань, правило 3 скіла `v8storagekit:discuss`.

## 3. Напиши спеку

Шаблон: [references/spec-template.md](references/spec-template.md). Дві таблиці обов'язкові, бо автор плану читає лише їх:

- **Блоки** — рядок на блок: обсяг, «готово, коли», залежить від. Цей рядок — вхід автора плану.
- **Інтерфейс → блок-власник** — кожен інтерфейс між блоками (API, таблиця, подія, тип, формат файла) і єдиний блок, що його визначає. Споживачі вказують його в «залежить від».

Правила:
- Лише стан. Жодних «ми обговорювали», жодних переліків варіантів — відкинуте живе в ADR.
- Кожне твердження про наявний код чи бібліотеку перевіряють до запису: Уніка (`unica_search` за темою, `unica_resolve`/`unica_view` за логічною адресою), код вендора — у дампі конфігурації-власника воркспейсу, поведінка платформи — скіл `unica:platform-help` чи `unica_docs` для версії воркспейсу, предметні скіли Уніки (`unica:bsp-patterns`, `unica:transactions-locks`, …). Неперевірене познач `(unverified)`. Уніки нема на машині — `git grep`, і скажи про це.
- Розмір: перевір `doc <файл>`. Понад ≈ 50 КБ → оглядова спека (мета, таблиця блоків, таблиця інтерфейсів, посилання) і по одній частковій спеці на групу блоків. Автори планів читають `doc <файл> §N`, а не весь файл.
- Правка наявної спеки: перепиши старе правило на місці; старе й нове поруч не лишай.
- Коміт на логічний крок (глосарій, ADR, чернетка спеки, виправлення аудиту) — виправлення аудиту окремим комітом.

## 4. Аудит — три лінзи, доки не чисто

Лінзи й шкала знахідок: [references/audit.md](references/audit.md).

1. Запусти трьох `v8storagekit:spec-auditor` в одному повідомленні, по лінзі кожному: **integrity**, **truth**, **security**. Модель у виклику: `sonnet` для integrity і truth; `opus` для security, бо дефекти прав і меж довіри Sonnet пропускає частіше (вимір agent-kit, його ADR-0005). Бриф: шлях(и) спеки, шляхи глосарію й ADR, лінза, а для раунду 2+ лише diff виправлень (`git diff <перевірений-коміт>..HEAD -- <спека>`).
2. Кожну знахідку перевір сам за спекою й кодом, перш ніж виправляти. Хибну знахідку відхили одним рядком причини.
3. Виправ, закоміть, запусти наступний раунд на diff.
4. Стоп, коли 0 блокерів і 0 security major (зазвичай 2–3 раунди). Решта major/minor іде в план як відомі проблеми.
5. Codex — необов'язковий і за твоїм рішенням (права, дані, гроші): скіл `codex-companion`, якщо він є на машині; знахідки перевіряй так само. Нема скіла — аудит лишається на трьох лінзах.

Далі `doc anchors <спека>` і віддай спеку власнику на прийняття: шлях, таблиця блоків, ADR, що потребують його уваги.

## 5. Зміна спеки під час виконання

- Зміна приходить як **задача 0** плану, якому вона потрібна, в тій самій гілці, що й план.
- Один рядок таблиці блоків чи інтерфейсів — одна гілка за раз. Друга гілка, якій потрібен той самий рядок, чекає на злиття першої.

## Типові помилки

| Помилка | Виправлення |
| --- | --- |
| Власник інтерфейсу лише в прозі або ніде | рядок таблиці інтерфейсів; автори планів питають про це найчастіше |
| Одна спека на сотні КБ | оглядова + часткові на ≈ 50 КБ |
| Таблиця рішень усередині спеки або причина повторена у 2–3 місцях | ADR для вагомого, повідомлення коміту для дрібного |
| Факт про вендора чи платформу взято зі статті чи документації | код дампу конфігурації-власника й справка платформи для версії воркспейсу |
| «У спеці нема» після одного пошуку | шукай без урахування регістру й у кількох словоформах, зокрема рос/укр формах імен 1С (`doc find`) |

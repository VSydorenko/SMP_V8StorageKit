# onboarding — підключення репозиторію, воркспейсу або джерела

Скіл робить репозиторій видимим для kit: маніфест, воркспейси Уніки, політики git, хуки.
Він **питає** там, де kit не вгадує: `truth` кожного джерела, шлях і користувача сховища,
дев-базу для дампу, глибину першого реплею. Мовчазних дефолтів для цих рішень немає. Скіл не
реплеїть сховище сам — це `v8storagekit:sync`; не розгортає базу агента — це
`v8storagekit:provision`. **Усі вхідні форми веде він** (§9): порожній репозиторій,
gitsync-вивантаження сховища, напівмігрований 0.6.0 — розділ 5. Окремої команди чи скіла для
переходу немає навмисно.

Ланцюжок задачі: **onboarding** → sync → provision → (робота в Unica) → reconcile → finish → verify.
Усе — з кореня репозиторію-споживача.

## 1. Розвідка (лише читання)

1. Корінь: `git rev-parse --show-toplevel` збігається з поточною текою; інакше перейти в корінь.
2. Середовище: `pwsh -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/tools/check-environment.ps1"` — усі
   рядки категорії «Конвеєр» мають бути `[+]` (PowerShell 7, git, платформа 8.3.27.x, модуль `powershell-yaml`).
3. Стан: `pwsh -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/tools/kit.ps1" check -RepoRoot .`
   **Читати цей список до кінця, а не до першого збігу.** «Маніфеста немає» — не форма, а
   відсутність ознаки: воно вірне і для порожнього репозиторію, і для обох форм спадку.
   Спершу шукати ознаки спадку, і лише не знайшовши жодної — вважати репозиторій новим.
   - маніфест є → **додати воркспейс або джерело** (розділ 3); перший `[i]`-рядок показує, що вже підключено.
   - `storage.json` поруч із `v8project.yaml` — **напівмігрований 0.6.0** (розділ 5.2). Шукати в
     **усіх** підтеках: у парку є репозиторій із трьома такими воркспейсами.
   - `DT-INF/` поруч із текою вихідників, **без** `storage.json` — дерево у EDT-форматі, і
     **найімовірніше вивантаження сховища** (розділ 5.1): це головна форма переходу, а не «чуже
     дерево». Але `DT-INF/` доводить **формат** дерева, не його **походження** — тому не
     стверджувати, а показати людині, що знайдено, і **спитати, яке сховище за цим стоїть**.
     Підтверджує відповідь проба доступу до сховища й перший звіт, а не вигляд дерева. (Ту саму
     помилку вже робили в інший бік: із `*.mdo` виводили «це EDT-розробка, kit не для неї».)
     **Шукати всі такі теки, не першу**: у парку є
     репозиторій із двома (`SMP_SMB_rus_DEV` — конфігурація плюс розширення), і це два джерела з
     різними `truth` і різною глибиною, а не одне. `AUTHORS`, `VERSION`, `ConfigDumpInfo.xml`
     поруч — **уточнюють, але не обов'язкові**: у парку є дерево без `VERSION` і без `AUTHORS`, де
     `ConfigDumpInfo.xml` лежить усередині `src/`. Вимагати всі чотири маркери разом означає не
     розпізнати форму взагалі. Чого бракує — те й не дає підказки: без `VERSION` питання про
     глибину ставиться без неї;
   - жодної з ознак вище — **порожній репозиторій**: новий проєкт або клієнтська база (розділ 2,
     форми — розділ 5).

## 2. Новий репозиторій

Спитати:
- **`product:` чи `client:`** і назву. `product` — рішення, що живе в кількох конфігураціях
  (кілька воркспейсів по одному розширенню); `client` — одна база клієнта з кількома розширеннями.
  Це метадані для назв артефактів і звітів; у логіці kit слів «клієнт»/«продукт» немає.
- **головна гілка**, якщо не `main` → `mainBranch:`.

Каркас із `${CLAUDE_PLUGIN_ROOT}/templates/` (відповідності — `${CLAUDE_PLUGIN_ROOT}/templates/README.md`):
`gitattributes` → `.gitattributes`, `gitignore` → `.gitignore`, `settings.json` → `.claude/settings.json`,
`CLAUDE.md` → `CLAUDE.md` (заповнити плейсхолдери), `AUTHORS.example` → `AUTHORS`,
`v8storagekit.yaml.example` → `v8storagekit.yaml` (переписати за відповідями нижче),
`v8storagekit.local.yaml.example` → `v8storagekit.local.yaml` (гітігнорований, лише локальне).
Далі — розділ 3 для кожного воркспейсу.

## 3. Воркспейс і його джерела

### 3.1 Тека воркспейсу

Ім'я теки = ім'я воркспейсу. Для воркспейсу з одним розширенням — ім'я розширення в 1С; для
клієнтської бази — ім'я бази/клієнта. Тека — безпосередньо в корені репозиторію. Якщо ім'я не
ASCII — сказати вголос: кириличні теки й імена розширень — прийнятий ризик, не пройдений
конвеєром до кінця (`${CLAUDE_PLUGIN_ROOT}/docs/follow-ups.md` §10).

### 3.2 `v8project.yaml`

Якщо файлу немає — створити (розкладка `<тип>/src`; для кількох розширень — `cfe/<Імʼя>/src`):

```yaml
format: DESIGNER
builder: DESIGNER
workPath: 'build'
execution_timeout: 600000
infobase:
  connection: 'File=build/ib'          # база АГЕНТА: машинна, похідна від git; kit сюди не пише, наповнює operation=build
source-set:
  - name: base
    type: CONFIGURATION
    path: 'cf/src'
  - name: <ІмʼяРозширення>
    type: EXTENSION
    path: 'cfe/src'
```

`name:` тут = `<Name>` у `cfe/…/Configuration.xml` = ключ у `sources:` маніфесту. Воркспейс
зовнішніх обробок — один source-set `type: EXTERNAL_DATA_PROCESSORS`, `path: 'src'`, без
`infobase:`. `name:` EXTENSION мусить дорівнювати імені розширення: v8-runner виводить ім'я з
source-set (`${CLAUDE_PLUGIN_ROOT}/docs/unica-contract.md`, B5–B6).

### 3.3 Питання `truth` — для кожного source-set, завжди

Мовчазного дефолту немає: відрізнити «наша конфігурація під сховищем» від «чужа, беремо
дампом» може лише людина. Варіанти й наслідки — дослівно:

- **storage** — істина у сховищі конфігурацій. У git з історією, гілка `storage/<ключ>`, наповнює
  `sync`. Наше розширення, або конфігурація клієнта, яку ведуть під сховищем.
- **dump** — істина в живій базі, лише поточний стан. У git без історії, наповнює `dump`; гілки немає.
- **vendor** — чужа конфігурація. У git **не потрапляє** (гітігноровано), локально — дамп для
  операцій Unica; гілки немає.
- **git** — зовнішнього джерела немає; пишуть люди й агент (зовнішні обробки).

Далі за відповіддю:
- `storage` → шлях сховища (`R:\СховищаРозширень_1С\…` або `R:\СховищаКонфігурацій_1С\…`) і
  користувач сховища (типово `gitbot`, пароль порожній; для спільного сховища в клієнтському репо —
  користувач за іменем бази). Ключ джерела = `name:`; для `truth: storage` ключі **унікальні в
  репозиторії** — при збігу перейменувати source-set (гілка `storage/<ключ>` одна).
- `dump` / `vendor` → ключ дев-бази для `dump: { from: <ключ> }` і для накладки: рядок підключення
  (`Srvr="…";Ref="…";` або `File="…"`) та користувач → `v8storagekit.local.yaml`, розділ
  `infobases:`. Kit із цієї бази лише читає.

Записати у `v8storagekit.yaml` (форма — `${CLAUDE_PLUGIN_ROOT}/templates/v8storagekit.yaml.example`).

### 3.4 Політики git під фактичні шляхи

Не покладатись на шаблонні `**/cfe/src/**`: дописати рядки з шляхів `v8project.yaml`:
- `.gitattributes`, після `* text=auto`: для **кожного** source-set — `<ws>/<path>/** -text`;
- `.gitignore`: для кожного `truth: vendor` — `<ws>/<path>/**`; поруч створити `<ws>/cf/README.md`
  з одним рядком «Базова конфігурація вивантажується локально (kit dump), у git не потрапляє».
Перевіряє `check` через `git check-attr` / `git check-ignore`.

### 3.5 Хуки й перевірка

```
pwsh -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/tools/kit.ps1" install-hooks -RepoRoot . -Apply
pwsh -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/tools/kit.ps1" check -RepoRoot .
```

`install-hooks` кладе `.githooks/` + `core.hooksPath`, шим `hooks/session-start.ps1` → `.claude/hooks/session-start.ps1` і `.claude/settings.json` (якщо ще немає), і **стейджить хуки з режимом 100755** — інакше клон на
Linux/macOS дістав би їх без біта виконання, і git мовчки їх ігнорував би. `check` має завершитись
без `[-]`; `[!]` про недоступне сховище чи відсутню накладку — прийнятно, але назвати людині.
Приймальна перевірка: `git ls-files -s .githooks/` → `100755` для обох файлів.

### 3.6 Перший коміт — окремо, до будь-якого `-Apply`

**Спершу назвати гілку вголос.** `git branch --show-current`: онбординг комітить у **головну гілку
маніфесту**, і мовчазне «комічу, де стою» — помилка. Репозиторій спадку цілком може стояти на
робочій гілці попереднього переходу; на будь-якій іншій гілці спитати людину, чи перейти на
головну, і не переходити самому — робоча копія може бути не порожня.

```bash
git add v8storagekit.yaml <ws>/v8project.yaml .gitattributes .gitignore .claude/settings.json .claude/hooks/session-start.ps1 AUTHORS CLAUDE.md
# <ws>/cf/README.md — ОКРЕМОЮ командою і лише якщо крок 3.4 його створив (у воркспейсі є
# джерело truth: vendor). Одним списком його додавати не можна: git add з неіснуючим шляхом
# падає атомарно — не стейджить НІЧОГО, включно з файлами, які існують. У воркспейсі
# зовнішніх обробок теки cf немає взагалі, і перший коміт просто не відбувся б.
git add <ws>/cf/README.md
git commit -m "onboarding: <ws> — маніфест, воркспейс Уніки, політики git, хуки"
# .githooks уже застейджено install-hooks з режимом 100755 — не перестейджувати через `git add -A` без потреби:
# сам `git add` режим не змінює, але `git ls-files -s .githooks/` після коміту має показати 100755.
```

Накладку `v8storagekit.local.yaml` не комітити — вона гітігнорована навмисно.

Приймальна перевірка одразу після коміту (вікно «хуки є на диску, але не в git» має закритись тут, і саме тому
коміт іде **до** будь-якого `-Apply`): `git ls-files -s .githooks/` → два рядки `100755`;
`kit check` — без `[-]` і без `[!]` про хуки.

## 4. Далі

- `v8storagekit:sync` — перший реплей джерел `truth: storage` (прев'ю, потім `-Apply` лише на
  прохання). Перше злиття в головну гілку робить сам `sync`. Зупинка на невідомих авторах — штатна:
  людина доповнює `AUTHORS`.
- `v8storagekit:provision` — база агента (питає тип: порожня / з `.dt` / серверна).
- Хук старту сесії почне показувати «Стан сховищ» з наступної сесії.

## 5. Вхідні форми — розпізнати, показати, спитати

Форма визначається **походженням вихідників**, не їхнім форматом (§9.1). Ознаки нижче кажуть лише
про формат: `*.mdo` каже «файли в EDT-форматі», `DT-INF/` — те саме. Висновок про походження з них
**не випливає** — ні «це EDT-розробка, kit не для неї» (цю помилку вже робили), ні зворотний «це
вивантаження сховища». Тому таблиця дає **найімовірнішу** форму, яку скіл показує людині й
підтверджує питанням, а не вироком; остаточно її доводить проба доступу до сховища і його звіт.

| Форма | Ознака | Що робити |
|---|---|---|
| **gitsync-вивантаження** (найімовірніше) | `DT-INF/` поруч із текою вихідників, **без** `storage.json`; `AUTHORS`, `VERSION`, `ConfigDumpInfo.xml` поруч уточнюють, але **не обов'язкові** — у парку є дерево без двох перших, де `ConfigDumpInfo.xml` лежить усередині `src/` | розділ 5.1: показати знайдене й спитати, яке сховище за цим стоїть |
| **Напівмігрований 0.6.0** | `storage.json` поруч із `v8project.yaml` | розділ 5.2 (тимчасовий) |
| **Порожній** — залишковий випадок, коли **жодної** ознаки вище немає | немає ні `v8storagekit.yaml`, ні `storage.json`, ні `DT-INF/` | новий проєкт: структура зі слів людини; сховища сканувати в `R:\СховищаРозширень_1С` і `R:\СховищаКонфігурацій_1С` і пропонувати варіантами. Клієнтська база (конфігурація + адаптація + наші розширення) — ця ж форма |
| **Уже на маніфесті** | `v8storagekit.yaml` | не сюди: `check`, а «додай воркспейс / джерело» — той самий діалог за одне джерело |

### 5.1 gitsync-вивантаження — головна форма переходу

Це вивантаження сховища старим інструментом (gitsync/OneScript, більше не встановлені). Дерево
**не конвертується**, а **заміщується реплеєм зі сховища**; EDT-історія зберігається
перейменуванням файлів у Designer-шляхи. Процедура — §9.2; основа й деталі розвідки — довідка
`${CLAUDE_PLUGIN_ROOT}/docs/migration/legacy-gitsync-repo.md` (колишній скіл `repo-migration`).

Порядок кроків **навмисний і не переставляється**:

1. **Розвідка й страховка до будь-яких змін.** Знайти всі квартети; зупинитись на брудній робочій
   копії; **проба доступу до кожного сховища** — до першої зміни, а не після перейменування;
   `git bundle --all`; перенести `AUTHORS`, зупинитись на невідомому авторі.
2. **Тег межі:** останній gitsync-коміт → `legacy/gitsync-<YYYY-MM>`. Нових гілок для історії
   немає — усе лишається на `main` (рішення користувача 2026-09-09).
3. **Коміт перейменування:** кожен файл EDT-дерева → його точний Designer-шлях за таблицею
   відповідності видів метаданих; вміст поки EDT-ний. Файли без відповідника (`DT-INF/`,
   `.project`, `.settings`, сам квартет) — **показати переліком і видалити лише після
   підтвердження**. Два EDT-файли в один Designer-шлях — зупинка.
4. **`sync`** реплеїть сховище в `storage/<ключ>`; глибина — розділ 5.3.
5. **Коміт конверсії на `main` — плоский, не злиття:** тека джерела стає побайтово рівною вершині
   `storage/<ключ>`, включно з видаленням об'єктів, яких у сховищі вже немає.
6. **І лише тоді** перше злиття `storage/<ключ>` у `main` — без змін дерева.

**Чому саме такий порядок.** При злитті git спрощує історію за батьком, з яким дерево збігається;
конверсія **всередині** злиття викинула б EDT-історію з `git log`. Результат правильного порядку:
`git log --follow` безперервний для всіх файлів; `git blame` через межу — для модулів BSL, якщо
рядки збігаються побайтово. Метадані й форми змінюються кожним рядком, їхня історія до межі —
`git blame <коміт-перейменування> -- <той самий шлях>`.

Після цього: коміт конверсії → у `.git-blame-ignore-revs`; в `CLAUDE.md` репозиторію — абзац із
тегом, датою межі й відповідністю «шлях в EDT → шлях у Designer», і обидві форми запиту історії.
Далі — як у будь-якого онбордингу: маніфест із `truth` на кожне джерело, накладка, політики git під
фактичні шляхи, хуки, шим, `check`, `verify`.

### 5.2 Напівмігрований 0.6.0 — підказки зі спадку

**Тимчасовий розділ:** потрібен рівно двом репозиторіям (`SMP_SimplyConnect`, `SMP_BankExchange`)
і вилучається після їх переходу (B6 Task 6).

| Звідки | Що | Куди |
|---|---|---|
| `<Продукт>/storage.json` | `storagePath` | `storages.<ключ>.path` у **накладці** |
| `<Продукт>/storage.json` | `extensionName` | ключ джерела й `name:` source-set (§3.2) |
| `<Продукт>/storage.json` | `sourcePath` | `path` source-set у `v8project.yaml` |
| `<ws>/v8project.local.yaml` | `devInfobase.connection` | `infobases.<ключ>.connection` накладки kit |
| `<ws>/v8project.local.yaml` | `devInfobase.user` | `infobases.<ключ>.user` накладки kit |

`devInfobase:` має **два** підключі, і переносити треба обидва: перенісши лише `connection`,
загубите користувача, і `dump` спитає його заново. **Самого `<ключ>` у спадку немає** — імені
дев-бази 0.6.0 не зберігав ніде. Його треба **спитати** (пропозиція за іменем воркспейсу — не
мовчазний дефолт, а варіант на підтвердження), бо на нього посилатиметься `dump: { from: <ключ> }`
у маніфесті.

**Ключ у локальному файлі називається по-різному, і одна з назв небезпечна.** У парку є обидві:
`devInfobase:` (конвенція kit) і **`infobase:`**. Друга — це рівно той ключ, яким Уніка визначає
**базу агента**: `v8project.local.yaml` перекриває закомічений `v8project.yaml`, тож поки він там
лежить, базою агента вважається дев-база людини. Якщо в закоміченому `v8project.yaml` воркспейсу
`infobase:` немає взагалі — база агента не оголошена, і `provision` зупиниться (kit відмовляється
цілитись у базу людини). Тому: перенести значення в накладку kit, **прибрати `infobase:` з
`v8project.local.yaml`** і оголосити базу агента в `v8project.yaml` (§3.2). Сказати це людині
вголос — вона могла роками працювати з таким файлом і не знати, що база агента підмінена.

**Ключ джерела мусить дорівнювати `name:` source-set, а не `extensionName`.** Маніфест kit
звіряється саме з `name:` у `v8project.yaml`; `extensionName` зі спадку — це те, як розширення
зветься **в 1С**. У парку вони розходяться, і навіть по-різному у двох воркспейсах одного
репозиторію. Порядок дій: якщо `name:` ≠ `extensionName` — виправляти **`v8project.yaml`**
(перейменувати source-set на ім'я розширення, §3.2), а не брати ключ зі спадку. Скопіювавши
`extensionName` у маніфест при старому `name:`, дістанете `Джерело '…' не відповідає жодному
name: source-set` — і це найдешевший з можливих наслідків; гірший — мовчазна відмова
`operation=make`, який виводить ім'я розширення саме з `name:`.

**Ім'я теки сховища не зобов'язане збігатися з іменем розширення.** У парку є джерело, де
`storagePath` закінчується на `…_BP`, а `extensionName` — `…_ACC`: ключ і `name:` беруться з
імені розширення, шлях — зі `storagePath`, і це не помилка. Показуючи людині відповідність на
підтвердження, назвати обидва значення й сказати, що розбіжність очікувана, — інакше вона
відхилить правильне перенесення. (Зворотний випадок — коли в маніфесті справді записане не те
сховище — описано в `v8storagekit:using-v8storagekit`; там ознакою є недоступність шляху.)

**`storage.json` знає лише про джерела `truth: storage`, але маніфест без решти не збереться.**
Джерело `truth: vendor` обов'язково потребує блоку `dump: { from: <ключ у infobases:> }` — без
нього `check` зупиняється, і зібрати маніфест «з самої таблиці» неможливо. Тобто спадок дає
частину значень, а не готовий маніфест: решту питаємо за §3.3, і серед першого — той самий
`<ключ>` дев-бази.

Решта source-set-ів воркспейсу в таблицю не входить і спадку не має:
`CONFIGURATION` на `cf/src` (базова конфігурація, звичайно
`truth: vendor`) і воркспейси зовнішніх обробок (`EXTERNAL_DATA_PROCESSORS`, без `storage.json`,
без `infobase:` — `truth: git`). Для них `truth` питається як завжди, розділ 3.3; жодного спадку
для них не шукати. У живому репозиторії з чотирьох воркспейсів і семи джерел таблиця покриває
три — це норма, а не ознака того, що чогось не знайшли.

Кожну відповідність людина підтверджує — мовчазного перенесення немає (§2.5: питаємо, не виводимо).
`lastSyncedVersion` **не переноситься як стан**: стан 1.0 живе в трейлері вершини гілки, і
перенесений лічильник був би файлом стану під іншим ім'ям. Він — лише **підказка** до питання про
глибину (розділ 5.3), як `VERSION` у gitsync-формі.

Після запису маніфесту й накладки спадок видаляється: `storage.json`, файли стану `SyncState`,
ключ `devInfobase:` (файл `v8project.local.yaml` лишається, якщо в ньому є серверна база агента).
Історія реплею 0.6.0 на `main` лишається як архів.

### 5.3 Глибина першого реплею — питати за кожним джерелом

Питати за кожним джерелом — **з початку** чи **порціями**. Рішення різне за типом:

- **розширення — «з початку»**: близько хвилини на версію, і повна історія в новому форматі робить
  старе дерево непотрібним для історії;
- **конфігурації** — версія повної конфігурації це 20–40 хвилин оновлення й дампу, а версій сотні;
  історія лишається у сховищі й у старому дереві під тегом.

Керує глибиною лише `-MaxVersions N` — **скільки версій узяти, а не з якої почати**. У порожню
гілку він бере N **найраніших** непере­несених версій, тобто рахує від початку сховища. Перевірено
запуском: `sync -MaxVersions 1` у порожню гілку дає версію 1, а не вершину.

**Наслідок, який треба сказати людині до початку, а не після:** «взяти лише поточну версію»
конвеєр **зараз не вміє** — параметра «почати з версії N» немає (`Invoke-KitSync` приймає
`-Workspace`, `-Source`, `-Apply`, `-MaxVersions`, `-MergeMain`). Для конфігурації з сотнями
версій це означає або повний реплей, або перенос порціями через повторні `-MaxVersions`, або
рішення взагалі не заводити для неї `truth: storage` зараз. Вибір за людиною — не вирішувати
мовчки й не обіцяти швидкого шляху, якого немає.

`VERSION` із квартета (gitsync-форма) і `lastSyncedVersion` зі `storage.json` (форма 0.6.0) —
довідкові: вони кажуть, докуди дійшов старий інструмент. Обидва **можуть бути відсутні** — у
парку є дерево без `VERSION` і без `AUTHORS`; тоді підказки немає, а мовчазного дефолту — тим
паче.

## 6. Штатні зупинки

- `Маніфест … — невідомий ключ '…'. Дозволені: …` — помилка у YAML; звірити з прикладом у `templates/`.
- `Джерело '…' … не відповідає жодному name: source-set` — ключ у `sources:` ≠ `name:` у `v8project.yaml`.
- `check`: `[-] … -text` або `[-] … .gitignore` — розділ 3.4 не завершено.
- `Ключ '…' з truth: storage повторюється у воркспейсах …` — перейменувати source-set в одному з них.
- `core.hooksPath не вказує на .githooks` — `install-hooks -Apply` не виконано.

## 7. Межі

Сховище й база людини — тільки читання. `-Apply` — лише на явне прохання. Нічого не пушити.
`truth` і тип бази агента не вгадувати — питати.

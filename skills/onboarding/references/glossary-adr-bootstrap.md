# Стартові глосарій і ADR для проєкту зі старішими спеками

**Завантаж, коли** в проєкті є спеки, реєстри рішень чи нотатки про дизайн, але немає
глосарію (`docs.glossary`, типово `docs/GLOSSARY.md`) і теки ADR (`docs.adr`, типово
`docs/adr/`). Рішення власника 2026-11-15: наявні проєкти отримують обидва при підключенні, а не
ліниво з наступною спекою. Формати — як у скілі `v8storagekit:spec` (його формати глосарію й ADR;
заходь через `spec`).

Чому: без глосарію старі синоніми живуть у спеках, планах і відповідях власнику; без ADR причини
старих рішень лишаються розсипаними по великих спеках і пам'яті, і агенти знову відкривають
закриті питання.

## 1. Збери (лише читання)

- Джерела: кожна спека й часткова спека (`docs.specs`), реєстри рішень чи таблиці рішень усередині
  спек, нотатки, схожі на ADR, файли дизайну в `docs/`, файли пам'яті проєкту, що фіксують
  рішення власника. Виміряй кожен через `doc <файл>`.
- До 5 агентів `v8storagekit:researcher` в одному повідомленні, кожен на окремому наборі файлів
  (≈ 100–150 КБ на агента). Бриф кожному: поверни два переліки.
  - **Терміни**: поняття проєкту, його значення одним-двома реченнями, кожне інше слово для
    нього (з `файл:рядок`), суперечливі значення (з `файл:рядок`). Лише поняття проєкту;
    загальні програмістські слова не беруться.
  - **Рішення**: одним рядком що вирішено, чому (факт чи цитата з `файл:рядок`), відкинуті
    варіанти, якщо записані, хто вирішив (власник / архітектор / невідомо) і чи рішення досі
    чинне (код чи пізніша спека кажуть інакше → замінене, з доказом).
- Об'єднай переліки сам; один запис на поняття й на рішення.

## 2. Відсортуй

| Елемент | Куди |
| --- | --- |
| Термін з одним значенням | запис глосарію; інші слова під *Avoid* |
| Термін з двома значеннями | питання власнику: яке слово зберігає яке значення |
| Вагоме рішення, що досі чинне (важко відкотити, АБО несподіване без контексту, АБО справжній компроміс, АБО ухвалене власником) | ADR, `Status: accepted <початкова дата>`, `Decided by:` з джерела |
| Вагоме рішення, пізніше змінене | два ADR: старе `superseded by ADR-M`, нове `Supersedes: ADR-N` — лише коли сама зміна ще важлива читачеві |
| Мале рішення | нічого: воно лишається станом у спеці |
| Рішення з невідомою причиною | ADR лише якщо власник пам'ятає причину; інакше питання власнику |

Нумеруй ADR у порядку ухвалення рішень, найстаріші першими.

## 3. Звіт (частина звіту підключення)

- Чернетка глосарію, згрупована за областями.
- Перелік ADR: номер, рішення одним рядком, хто вирішив, джерело `файл:рядок`.
- Питання власнику: суперечливі значення, невідомі причини.
- Збіги синонімів по спеках: скільки рядків змінилось би, якби спеки вживали слова глосарію.

Власник схвалює переліки; великий перелік можна схвалювати по областях.

## 4. Пиши (після схвалення, у PR підключення чи в окремому PR)

1. `GLOSSARY.md` і один файл на ADR, точно як схвалено.
2. У кожній вихідній спеці заміни довге обґрунтування рішення з ADR на `ADR-N` і лиши стан;
   перепиши синоніми на слово глосарію. Один коміт на спеку, щоб рецензент читав один diff за раз.
3. Файли пам'яті, що тримали лише рішення власника, яке тепер в ADR → pointer `→ ADR-N`.
4. `doc anchors` і `doc lint` зелені перед PR.

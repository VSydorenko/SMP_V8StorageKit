# Сесії, статус, нічний режим

**Завантаж, коли** даєш сесії роль, звітуєш власнику про статус, вмикаєш нічний режим чи паузу, або звіряєш рішення з минулими помилками.

## Ролі

| Роль | Робить | Не робить |
| --- | --- | --- |
| **Спайк** | доводить чи спростовує гіпотезу кодом і замірами проти критеріїв так/ні | не зливає код; його звіт іде в main окремим PR |
| **Автор спеки чи плану** | пише документ, веде його аудит, звітує; після того як ти прийняв план, може його виконати | не комітить код, поки документ на аудиті |
| **Виконавець** | виконує план у власній робочій копії, рецензія на задачу, ворота, PR | не правит `CLAUDE.md` без власника |

Сесія, що завершила, — вільний ресурс: дай їй наступну задачу того самого профілю, бо контекст у неї вже є. Автор прийнятого плану — перший кандидат його виконати, поки його контекст нижче бюджету `v8storagekit:execute` §4: друга сесія відбудує той самий контекст. Незалежність дають аудит плану, Codex (`v8storagekit:codex-audit`, якщо налаштовано), рецензія на кожну задачу й фінальна рецензія, а не друга сесія.

## Статус для власника

`session-board -Sessions <файл>` (ти ведеш файл сесія → гілка) дає таблицю; додай, що блокує і що тобі треба від власника. Оцінки — в агенто-днях, не в календарних.

## Спільна база агента

- `session-board` і `track status` показують, який блок де: виконується, запушений, чекає злиття. Перш ніж ставити рядок `Push:`, подивись, хто ще працює зараз.
- Режим `shared` (`workspace.mode`): базу агента воркспейсу збирає чи тестує **одна сесія за раз**. Блоки, що змагаються за одну базу агента, впорядкуй: задай у брифах чергу («після того, як <блок Y> звільнить базу», або партіями). Паралельні збирання тієї самої бази ламають одне одному результат і проходять мовчки.
- Режим `worktree`: кожна сесія має свою робочу копію й свою базу; черги потрібні лише для спільних ресурсів поза репозиторієм.
- Прогін, що тримає базу довго, — лише з причиною в брифі.

## Нічний режим і пауза

- **Нічний режим**: власник дозволив PR і злиття без нього. Спершу запиши межі (що можна зливати, що заборонено) у файл стану; вранці — підсумок.
- **Пауза** (ліміти, власник каже стоп): доведи те, що розпочато (рецензія, аудит, ворота), підготуй наступні брифи, онови файл стану, нового не починай. «Зупини все», що вбиває майже готові блоки, марнує їхню вартість.

## Типові помилки

| Помилка | Правило |
| --- | --- |
| Редактор чи дослідник вигадав поле в хибному контракті | переглянь diff; відкоти вигадки, що б'ються з моделлю, і вирішуй сам |
| Блок виглядав одним планом; код показав п'ять незалежних вузлів | зведи з кодом до брифу автора плану; поділ — твоє рішення |
| Контракт «повна заміна» мовчки губить рядки, яких клієнт не надіслав | для кожного контракту «повна заміна» питай: що, як клієнт надішле лише частину |
| На «докладніше» власнику відповіли переліком механізмів | один наскрізний приклад з іменами |
| Бриф вставлено в повідомлення; звіти довгими повідомленнями | файл брифу + один рядок; звіт у фіксованому форматі |
